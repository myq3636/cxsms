## 2. 测试账户

| 块 | ssid | 说明 |
|---|---|---|

| `[RTV1]`～`[RTV12]` | 9811～9822 | 测试通道：都连到测试工具的 27001 端口，system_id `rtv1`～`rtv12`；`SMSOptionSubmitRetryCode:2300,2500,2600`、`SMSOptionMTRetryPolicy:1M,1M` |
| `[RTVNR]` | 9830 | 同上，但**没有** `SMSOptionSubmitRetryCode`（任何 submit 失败都不改道） |

用例要更多账户（另一个客户、限长度的通道、开了 DR 改道的通道等）时写在用例目录的 `cm.extra.cfg`，运行时接在 base 后面。用例里常用的：`RTCUST2`～`RTCUST7`（9802～9807）、`RTVLEN`（9840）、`RTVD1`～`RTVD8`（9851～9858）、`RTCA*`（9861～9868）。

**测试工具回的 submit_sm_resp 状态和内部状态**（`SMPPRespStatus.getGmmsStatus`，改道看的是内部状态是否在通道的 `SMSOptionSubmitRetryCode` 里）：

| command_status | 内部状态 | 在 base 通道的重试码里 |
|---|---|---|
| `0x45`、`0x65` | 2300 UNDELIVERED | 是 |
| `0x04`、`0x05`、`0x0D`、`0x11`、`0x13`、`0xFE` | 2500 COMMUNICATION_ERROR | 是 |
| `0x14`、`0x58` | 2600 Throttled | 是 |
| `0x0B`、`0x33`、`0x34`、`0x44` | 2120 RECIPIENT_ADDR_ERROR | 否 |
| `0x0A` | SENDER_ADDR_ERROR | 否 |

**重试次数**：`SMSOptionMTRetryPolicy:1M,1M` 有两个点，一条 MT 一共发两轮：第一轮是主路由加逐级的备份，级别用完后 1 分钟重试一次主路由，再失败就回失败 DR（`RetryPolicyManager.isLastRetry`）。

## 3. 测试工具

`rt.RouteCase`（`routetest/src/rt/RouteCase.java`，只用 JDK，`lib/routetest.jar`）在一个进程里：

1. **扮演通道**：在 27001 端口接受 a2p Client 的 bind（每个 system_id 一个通道），等每个通道都有 `vendor.minLinks` 个 bind（两个 Client 各一个）；收到 submit_sm 记下来，按用例配置回 submit_sm_resp（默认成功，消息 id `RTV3-1` 这种），成功的 0.5 秒后回 DR（默认 `DELIVRD`）。
2. **扮演客户**：bind 到 Server，逐条发用例里的 MT（每条的文本是 `{用例}-M{n}-{运行时间}`，用来在通道侧认出它，要求 DR），记下 submit_sm_resp 的状态和 Server 给的 id，收客户的 DR。
3. **逐条核对**：
   - 用 Server 给的 id 在 Server 日志的 `[SUBMIT-IN]` 里找到 msgId，再用 msgId 找出这条 MT 在每个模块日志里的所有行、本次运行期间写的所有 CDR 行；
   - 每条 MT 核对：submit_sm_resp 是 0；**哪个通道收到**和预期一致；Core 的 `[MT-ROUTE]` / `[MT-REROUTE]` 行包含预期的文本（层、前缀、优先级）；客户收到的 DR 状态和预期一致；有 `OUT_SUBMIT` CDR。

### 4.2 case.properties 第 2 版（RC002 起）

RC002～RC022 要检查改道链、重试、DR 改道、CDR MsgID、reload 等，用到下面这些写法。**第 1 版的写法照旧有效**（RC001 不用改）。

**一个目录里的内容**：

| 文件 / 目录 | 作用 |
|---|---|
| `routing/*_routingInfo.cfg` | 用例的路由文件，文件名都以 `RT` 开头（`run_case.sh` 只删、只换 `conf/routing/RT*_routingInfo.cfg`） |
| `cm.extra.cfg` | 追加到 `base/cm.cfg` 的块 |
| `conf/{文件}` | 运行时**替换** a2p `conf/` 下的同名文件（如 `OperatorMode.properties`、`vendorRoutingReplacement.cfg`、`drErrorMapping.cfg`），结束后恢复原文件 |
| `conf.append/{文件}` | 运行时**追加**到 a2p `conf/` 下的同名文件（如 `contentTemplate.cfg`），结束后恢复 |
| `gmms.append/GmmsConfig.properties` | 运行时追加到 a2p 的 `Gmms/GmmsConfig.properties`（同名的后写的生效），结束后恢复 |
| `phase2/routing/`、`phase2/conf/`、`phase2/gmms.append/` | 第 2 阶段换上的路由文件、conf 文件，追加的 GmmsConfig（见下面的 `phase.2.*`） |

**用例级的键**：

| 键 | 例子 | 作用 |
|---|---|---|
| `case.refs` | `J-01 J-02` | 对应《路由重构测试用例清单》的编号 |
| `vendors` | `rtv1,rtv2` | 要等 bind 的通道；空 = 不等（只做用例级检查的用例） |
| `customer.user` | `rtcust2` | 默认用哪个客户发（密码都是 `rtpw`） |
| `customer.{客户}.port` | `16273` | 这个客户 bind 到另一个 Server 的端口（默认 `server.port`，16272 是 MultiSmppServer1，16273 是 MultiSmppServer2） |
| `vendor.{通道}.submitStatus` | `0x45` | 这个通道所有 submit_sm_resp 的 command_status（十六进制或十进制） |
| `vendor.{通道}.submitStatusSeq` | `0x45,0` | 同一条 MT 第几次到这个通道就用第几个，用完后一直用最后一个（测“重试时成功”） |
| `vendor.{通道}.dr` | `UNDELIV` | DR 的 stat；`none` = 不回 DR |
| `vendor.{通道}.drErr` | `005` | DR 文本里的 `err:` |
| `vendor.{通道}.drDelayMs` | `3000` | submit 成功后多久回 DR（默认 env 的 `vendor.drDelayMs`） |
| `vendor.{通道}.respDelayMs` | `300` | 晚这么多毫秒才回 submit_sm_resp（慢供应商），DR 也跟着晚 |
| `vendor.{通道}.slowFirstLink` | `true` | 只让第一个收到 submit_sm 的 bind 按 `respDelayMs` 晚回（一个慢的 bind） |
| `vendor.{通道}.minLinks` | `4` | 这个通道要等几个 bind（默认 env 的 `vendor.minLinks`；`SessionNumber=2` 时两个 Client 共 4 个） |
| `mt.drWaitMs` | `90000` | 每条 MT 最多等多久客户的 DR（默认 60000） |
| `phase.2.afterMs` | `20000` | 第 1 阶段的 MT 都发完（但不等 DR）后多久进第 2 阶段 |
| `phase.2.reload` | `RELOAD_ROUTING` | 进第 2 阶段时，换完 `phase2/` 的文件后发的命令（发到 state Redis 的 `channel:gmms:control`，和 smsui 的 telnet 7000 发的是同一个命令）；不写 = 不发命令（例如 `OperatorMode.properties` 自己 5 秒检查一次） |
| `check.log.{n}` | `CoreEngine1\|文本1\|文本2` | 这次运行期间这个模块（可以逗号分隔写几个，任一个有就行）的日志里有一行同时包含这些文本 |
| `check.redis.{n}` | `key\|field\|文本` | 运行结束时 `HGET key field`（state Redis）包含这个文本 |
| `check.redisAbsent.{n}` | `key` | 运行结束时 state Redis 里没有这个 key |
| `check.metric.{n}` | `metricsname\|client.vendor.submit_rtt.9921\|p95\|250\|700` | 模块（逗号分隔，这里是指标日志 `log/metricsname.log`）在这次运行期间的某一行 `[METRICS-*]` 里有名字以它结尾的指标，耗时取 `count`/`avg`/`p50`/`p95`/`p99`/`max`，计数和瞬时值取 `value`，在 [最小, 最大] 里 |
| `check.redisCmd.{n}` | `ZRANGE metrics:index 0 -1 => metrics:coreengine1:` | state Redis 执行这个命令，输出包含 `=>` 后面的文本（`=文本` 是完全相等） |
| `check.cmd.{n}` | `$RTREDIS TTL key => =ttl ok` | 用 bash 执行，输出包含（或 `=` 完全等于）`=>` 后面的文本；可以用 `$RTREDIS`（state Redis 的 redis-cli，带密码）和 `$A2P_HOME` |

**每条 MT**：`mt.{n}=发送方|号码|预期通道|日志|DR`，第 2 阶段的 MT 写 `mt2.{n}`。

| 位置 | 写法 | 含义 |
|---|---|---|
| 预期通道 | `*` | 不检查通道（例如 reload 时可能重发） |
| 预期通道 | `rtv2` | 只有 rtv2 收到 |
| | `rtv1>rtv3>rtv1` | 按这个顺序依次收到（改道、重试），之后没有别的通道再收到 |
| | `rtv1>(rtv4\|rtv5)>rtv6` | 某一步是其中一个 |
| | `rtv1\|rtv2` | 和 `count` 一起用：每条到其中一个，比例看 `ratio` |
| | `none` | 哪个通道都没收到（路由失败） |
| 日志 | `文本1&&文本2&&!文本3` | 每段都要出现在这条 MT 的某一行 Core 日志里（按 msgId 找）；`!` 开头的那段不能出现；`{MultiSmppClient}文本` 在这类模块的日志里找（按模块名前缀）；`~正则` 按正则找（Java 正则；不能写反斜杠和 `|`，它们会被 properties 或字段分隔吃掉：字面的 `[` 用 `.` 代替或只写后面的 `]`，数字用 `[0-9]`，“后面是空格或行尾”用 `(?![^ ])`）；空 = 不检查 |
| DR | `DELIVRD`、`UNDELIV` | 客户收到的 DR 的 stat |
| | `!DELIVRD` | 收到了 DR，stat 不是 DELIVRD |
| | `none` | 等到 `waitMs` 也没有 DR |

| 键 | 例子 | 作用 |
|---|---|---|
| `text` | `your otp 1234` | 内容：发出去的文本是 `{text} {用例}-M{n}-{运行时间}`（不写时只有后面的标记） |
| `customer` | `rtcust3` | 这条用哪个客户发 |
| `after` | `3000` | 前一条发出后过多久再发（默认 200） |
| `count` | `200` | 同样的发送方、号码发这么多条（每条的标记是 `-M{n}.{k}`），通道和 DR 每条都查 |
| `ratio` | `rtv1:70,rtv2:30,tolerance=10` | 和 `count` 一起：每个通道收到的百分比，误差在 `tolerance` 个百分点内 |
| `waitMs` | `240000` | 这条 MT 最多等多久（重试要 1 分钟以上） |
| `cdr` | `OUT_SUBMIT={id};OUT_SUBMIT={id}-9812;OUT_DELI_REP={id}@10400` | 这条 MT 的 CDR 里有这些行（类型 = MsgID 列，`{id}` 是 msgId，`@10400` = 状态列也要是这个，`~正则` = 这一行还要匹配这个正则）；同样的写几次就要有几行，不看顺序（CDR 的时间只到秒，分在几个文件里），可以有别的行 |

| `bindMax1s`、`bindMax100ms` | `11`、`2` | 和 `count` 一起：这批 MT 在每个 bind 上任意 1 秒 / 100 ms 内最多几条 |
| `spanMs` | `4000,7000` | 和 `count` 一起：这批 MT 的第一条到最后一条 submit_sm 用了多少毫秒 |

| `enc` | `gsm7`、`gsm7packed`、`latin1`、`ucs2`、`ascii` | 客户发送的编码：GSM 7-bit 每字符一字节 / 压缩（data_coding 0）、ISO（3）、UCS2（8）、ASCII（0，默认） |

### 4.3 工具和脚本做了什么（2026-11-17 扩展）

| 地方 | 做法 |
|---|---|
| `RouteCase` 通道侧 | 任何 system_id 都能 bind（只等 `vendors` 里的）；按 MT 的标记记下每次到哪个通道、按时间排序；`submitStatusSeq` 按“这条 MT 第几次到这个通道”取；`drErr`、`drDelayMs` 按通道；长短信按 UDH 收段、拼文本 |
| `RouteCase` 客户侧 | 一次 bind 多个客户（`customer`）；`text`、`after`、`count`、`parts`；按 `waitMs` 等 DR，`none` 表示等满时间也没有 |
| `RouteCase` 核对 | 通道顺序的匹配（`>`、`(a\|b)`、`ratio`）；日志 `&&` 分段在所有 Core 日志里按 msgId 找；`cdr` 按顺序找 CDR 行的类型和 MsgID 列；`db` 在等待期间每 5 秒查一次；`check.*` 用 `redis-cli`；Redis（`Redis_master_*`）和 DB（`DS_gmms_URL`、`DS_gmms_Login`、`DS_gmms_Password`）的连接从 a2p 的 `Gmms/GmmsConfig.properties` 读，命令的位置可以用 env 的 `redis.cli`、`mysql.cli` 改；日志除了 `log/{模块}.log`，还看这次运行期间滚动出去的文件；没有 MT 的用例只做 `check.*` |
| `RouteCase` 第 2 阶段 | 第 1 阶段发完后等 `phase.2.afterMs`：把 `phase2/routing/` 拷到 `conf/routing/`、`phase2/conf/` 拷到 `conf/`，发 `phase.2.reload`，再发 `mt2.*` |
| `run_case.sh` | 运行前备份并替换 `conf/`、追加 `conf.append/`，结束后恢复（`trap EXIT`；被 kill -9 时由下一个用例开始时恢复，备份在 `routetest/.confsave/`）；结果目录的 `config/conf/` 里存这些文件；`RT_SINCE`（重启前的时间）传给工具，`check.log` 从这个时间算起 |
| `base/cm.cfg` | 已经改成 RTV1～RTV12、RTVNR 和新的重试码、重试策略（见第 2 节） |

## 5. 运行

```text
/usr/local/a2p/routetest/bin/run_case.sh /usr/local/a2p/routetest/cases/RC001_prefix_priority_sender               # 换配置、重启模块、测试
/usr/local/a2p/routetest/bin/run_case.sh /usr/local/a2p/routetest/cases/RC001_prefix_priority_sender --no-restart  # 配置没变时不重启
```

`run_case.sh`：写 `conf/cm.cfg`（base + `cm.extra.cfg`）、换 `conf/routing/RT*_routingInfo.cfg`、重启 9 个模块并等 Server 端口、运行工具、把这次用的配置存到结果目录。退出码 0 = 全部通过。

每次运行都在用例的 `result/` 下新建一个目录（旧的保留）；MT 的文本带运行时间，证据按这次的 msgId 重新收集。

**全部用例一起跑**：

```text
/usr/local/a2p/routetest/bin/run_all.sh                      # cases/ 下每个有 case.properties 的目录，按名字顺序
/usr/local/a2p/routetest/bin/run_all.sh RC001_prefix_priority_sender RC002_...   # 只跑这几个
```

每个用例都会换配置并重启模块；汇总在 `runs/{时间}/summary.txt`（每个用例一行：PASS/FAIL、通过的 MT 数、结果目录），每个用例的输出在 `runs/{时间}/{用例}.out`。全部通过时退出码 0。

复制一个用例：复制整个目录，改 `case.properties` 和 `routing/`，删掉 `result/`。

代码更新后，要把新的 `src/`、`jar/`、`regression/` 重新上传到 `routetest/newsms/`（回归跑的是这里的源码），以及把新的 `a2p.jar` 部署到 `/usr/local/a2p/Gmms/WEB-INF/lib/`（消息级用例跑的是部署的系统）。
