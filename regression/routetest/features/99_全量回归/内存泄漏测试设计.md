# 内存泄漏测试（服务器长时间压测）设计

> 日期：2026-11-17。测试服务器 8.219.93.186，a2p 在 `/usr/local/a2p`，用例在 `routetest/cases/MEM001_soak`。和《路由服务器测试说明》用同一个测试工具（`rt.RouteCase`）。

## 1. 要回答的问题

系统在持续流量下运行一段时间后：

1. 各模块（3 个 Core、2 个 Client、2 个 Server、2 个 MQM）的 **Java 堆在 Full GC 之后**是否一直往上涨，流量停下后是否回落；
2. **线程数、文件句柄数、Metaspace** 是否一直涨（线程泄漏、连接泄漏、reload 的类加载泄漏）；
3. **Redis** 里没有过期时间的 key 是否一直增加（Stream 不清理、去重标记不删、合并缓冲不删）。

## 2. 怎么测

### 2.1 流量

测试工具扮演供应商和客户，按固定速率（默认 100 TPS）持续发 MT，混合各条主要路径，让每种处理代码都反复执行：

| 比例 | 路径 | 账户 |
|---|---|---|
| 50% | 普通 MT + DELIVRD DR（Server1） | 客户 RTCS1 → 通道 RTVS1 |
| 15% | 普通 MT + DR，经 MultiSmppServer2 | 客户 RTCS3（bind 到 16273） |
| 10% | 主路由通道 submit 失败（0x45），改道到备份 | RTCS1 → RTVS2 → RTVS1 |
| 10% | 3 段长短信（Redis 合并、按通道重新拆分、每段 DR） | RTCS1 → RTVS1 |
| 5% | 没有路由：路由失败、失败 DR | RTCS1，号码 44… |
| 10% | 通道不回 DR，假 DR 方式 4（5 秒超时）回成功 | 客户 RTCS2 → 通道 RTVS3 |

另外两种周期性的事件（常见的泄漏来源）：

- **客户断开重连**：每 5 分钟轮流断开一个客户的 bind 再连上（会话对象、窗口、待响应表的清理）；
- **reload**：每 10 分钟轮流发 `RELOAD_ROUTING:-f`、`RELOAD_CUSTOMER`、`RELOAD_DRERROR`、`RELOAD_GMMS_CONFIG`（重建对象、缓存、会话）。

号码在前缀后面随机生成，不会都落在同一个分片、同一个 key 上。每条 MT 都要求 DR。

### 2.2 时间

```text
重启模块 ── 预热 5 分钟 ── 测量 50 分钟（流量继续）── 停止流量，等 DR 1 分钟 ── 空闲 10 分钟
            （不计入）     基线 = 预热结束时的值                                   流量停后的值
```

### 2.3 采样（`bin/memwatch.sh`，和流量同时运行）

每 30 秒对每个模块的 JVM 采一次，每隔一次先执行 `jcmd <pid> GC.run`（Full GC）再采，得到“GC 后的堆”：

| 列 | 来源 | 说明 |
|---|---|---|
| `heap` | `jstat -gc` 的 S0U+S1U+EU+OU | 当前使用的堆（MB），随 GC 起伏，只作参考 |
| `afterGc` | GC.run 之后 3 秒的 `heap` | **判断堆泄漏用这个**：Full GC 后还占着的就是活对象 |
| `old` | OU | 老年代 |
| `meta` | MU | Metaspace（类） |
| `rss` | `/proc/pid/status` VmRSS | 进程内存（参考：JVM 申请了就不太还） |
| `threads` | `/proc/pid/status` Threads | 线程数 |
| `fds` | `/proc/pid/fd` 个数 | 文件句柄（含 socket） |

Redis（state 8386、submit 8387、report 8388）：`used_memory`、`dbsize`，以及随机抽 500 个 key 看没有过期时间（TTL = -1）的比例，估算**没有过期时间的 key 数**。

模块中途重启（pid 变了）会记下来，判为失败（可能是 OOM：`-XX:+ExitOnOutOfMemoryError`）。

### 2.4 判断（`rt.MemReport`）

对每个模块，用测量期（预热之后）的 `afterGc` 样本：

| 检查 | 判为可疑的条件 |
|---|---|
| 堆增长趋势 | 线性回归斜率 > 30 MB/小时，并且测量期最后 3 个样本的中位数比最前 3 个多出 max(20 MB, 10%) |
| 流量停后不回落 | 空闲期最后一个 `afterGc` 比基线多出 max(30 MB, 15%) |
| 线程 | 测量期内最大值 - 基线 > 20，并且空闲期没有回落到基线 + 20 以内 |
| 文件句柄 | 同上，阈值 50 |
| Metaspace | 测量期结束比基线多 > 10 MB |
| 模块重启 | pid 变了 |

Redis：空闲期结束时“没有过期时间的 key 数”比基线多出 max(1000, 发送条数的 1%)，判为可疑；有过期时间的 key（DR 查找记录、去重标记等）按设计会在过期后消失，只记录不判断。

流量本身也要正常（否则测不到什么）：实际发送数不少于计划的 95%，submit_sm_resp 成功的比例不少于 99%。

所有检查都通过：`RESULT: PASS`；否则 `RESULT: FAIL`，并列出可疑的模块和指标。阈值都可以在 `case.properties` 里改。

### 2.5 输出

`cases/MEM001_soak/result/{时间}/`：

| 文件 | 内容 |
|---|---|
| `summary.txt` | 流量统计（发送、成功、失败、DR 条数、重连、reload 次数）和最后的结论 |
| `mem/jvm.csv` | 每次采样每个模块一行 |
| `mem/redis.csv` | 每次采样每个 Redis 一行 |
| `mem/phases.txt` | 预热结束、测量结束、空闲结束的时间 |
| `mem_report.txt` | 每个模块的基线、最后值、斜率、各项检查的结果 |

发现可疑时，下一步用 `jcmd <pid> GC.class_histogram` 在两个时间点各取一次，比较哪个类的实例数在涨。

## 3. 局限

- 50 分钟、100 TPS（约 30 万条）只能发现比较明显的泄漏；很慢的泄漏要更长时间（`soak.durationSec` 可以改成几小时）。
- 只覆盖 SMPP，没有 HTTP 通道和 HTTP 客户。
- 测试机上其他东西（回归、消息级用例）不能同时跑：会重启模块。
