# 服务器全量回归失败排查

> 日期：2026-11-17。测试服务器 8.219.93.186 上第一次跑全量回归（`routetest/features/99_全量回归`，`regression/suites.txt` 的 72 个套件）：1945 项通过、10 项失败。本地一直全部通过，这些只在这台机器上出现。改动前的代码（git HEAD）在这台机器上同样失败，和当天的修改无关。下面是每一项的原因和处理。

## 2. 原因

### 2.1 拿到新分片、重启后，Core 不读积压（FT-06、MS-31e）

消费者靠“门铃”（`zset:*:active` 里的 stream 名）知道哪个 stream 有新条目，取走门铃后读这个 stream。门铃被取走后节点死掉，或者门铃在重启前已经被取走，stream 里的积压就没有门铃了：

- Client 的外发、Core 的结果、Server 的 DR、MQM、HTTP 的消费者启动时都调用 `reRingExistingStreams`，给还有条目的 stream 重新按门铃；**Core 的 MT 消费者（`MTStreamConsumer`）和供应商 DR 消费者（`InboundDRStreamConsumer`）没有**；
- `RELOAD_CORE_SHARDS` / `RELOAD_CLIENT_SHARDS` 改了分片后，也没有人给新分片按门铃。

FT-06 的实际过程：Core1 被杀时分片 0 有 293 条在排队、几十条在 Core1 的待确认里；Core2 拿到分片 0 后，自动认领（`RedisStreamAutoClaimRunner`）领走了待确认的 44 条，但排队的 249 条没有门铃，Core2 不去读，直到下一批消息进来按了门铃才处理掉。

**修改**：`MTStreamConsumer`、`InboundDRStreamConsumer` 启动时调用 `reRingExistingStreams`；`RedisControlSubscriber` 处理 `RELOAD_CORE_SHARDS` / `RELOAD_CLIENT_SHARDS` 后调用新的 `StreamQueueManager.reRingAfterShardChange`（Core：mt:pending、inbound-dr、core:results、mqm:submit、mqm:report；Client：mt:routed、http:submit、http:dr）。门铃是共用的，每个节点只取自己分片的门铃，多按不会出错。

### 2.2 bind 后马上断开的会话不清理（D-01）

Server 端会话在 bind 成功时就设成 CONNECT、登记进 bind 注册表，`start()`（`keepRunning = true`）在稍后。客户在 bind 之后 1 ms 内断开时，连接的接收线程调用 `connectionUnavailable()` → `stop()`，而 `stop()` 开头是 `if (keepRunning == false) return;`：会话既不注销也不改状态，一直以 CONNECT 留着。之后这个客户的 DR 都可能派给它，发送失败（`Connection is not open`），DR 按 11005 失败。

ServerFuncIT 里 T-02b 的客户 bind、发一个 enquire_link 就关闭，10 秒后 D-01 的 DR 被派给了它。

**修改**：
- `MultiSmppSession.stop()`：`keepRunning` 还是 false、但这个 Server 会话已经 CONNECT / RECOVER 时，注销 bind 注册并设成 DISCONNECT（日志 `SMSCSession closed before it started, unregistered`）；
- `DRStreamConsumer`：发送失败并且选中的会话已经断开时，重新选一次会话，选到另一个连着的会话就再发一次（日志 `Server DR-to-customer session ... is DISCONNECT, sent again on ...`），再失败才按原来的方式回报失败。

### 2.3 CS-09 的测试时序

测试先 `new MultiSmppClient().startService()`（它已经启动了外发消费者），再放 20 条积压、删掉门铃，再调用 `OutboundStreamConsumer.getInstance().start()` 期望启动时找到积压。消费者已经在运行，`start()` 直接返回，不会再扫。本地 `startService` 启动消费者慢一些，测试的 `start()` 抢在前面，所以能通过。

**修改测试**：放积压之前先 `stop()` 消费者。

### 2.4 断开和重连同时发生时，连接停在 DISCONNECT（S3-03）

Server 上一个客户一个连接对象（如 `SMPPCUST31_c1`），会话挂在它下面（`_2`、`_3`……）。给客户发 DR 时（默认 `random` 策略）先从连接池的**已连接**列表取连接，再从连接里取会话；连接在哪个列表由它的状态（CONNECT / DISCONNECT）决定。

失败那次的日志：

```
10:15:59,941 Receiver2  旧会话 _2 停止 → 状态 DISCONNECT
10:15:59,941 Receiver3  新会话 _3 bind → 登记、加入同一个连接
10:16:00,043 DR 线程     Server DR-to-customer session not found
```

`MultiServerConnectionImpl`（`NodeServerConnection` 一样）：

- 旧会话断开（`handleDisconnect`）：在锁里移出 `_2`，**在锁外**判断“会话数 ≤ 0 就设 DISCONNECT”；
- 新会话加入（`addSession`）：在锁里放入 `_3`，**会话数正好变成 1** 时设 CONNECT。

交错：Receiver2 移出 `_2`、看到会话数 0 → Receiver3 放入 `_3`、设 CONNECT → Receiver2 设 DISCONNECT。连接里有活着的 `_3`，状态却是 DISCONNECT，被移进断开列表，DR 选不到它。而且**不会自己恢复**：之后再加会话，会话数是 2 不是 1，不会设回 CONNECT；要等这个客户的会话全部断开再 bind。在这之前这个客户在这台 Server 上的 DR 都失败，进 RDQ 的重发也一样，客户重连前过期的就过期了。只在断开和重连几乎同时（同一毫秒）时发生，机器忙时才偶尔出现。

**修改**：
- 两个类的 `handleDisconnect`：判断会话数、设 DISCONNECT 挪到移出会话的同一把锁里；`NodeServerConnection.handleConnection` 同样把放入和设 CONNECT 放在一把锁里。`deleteSession`、`addSession` 本来就在锁里调用 `setStatus`，锁的顺序不变；
- `MultiServerConnectionImpl.addSession`：只要状态不是 CONNECT 就设 CONNECT（不再要求会话数正好是 1），已经错过的状态在下一个会话加入时纠正。

**新的单元检查 `ServerConnectionRaceCheck`**（`suites.txt`，`unit`）：把断开的线程卡在“看到会话数 0”和“设 DISCONNECT”之间，让 bind 的线程加入新会话，强制出现上面的交错。改动前的代码 3 项失败（两个类的连接都停在 DISCONNECT、第二个会话也不纠正），改动后全部通过。
