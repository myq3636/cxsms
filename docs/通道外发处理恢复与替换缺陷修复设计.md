# 通道外发处理恢复与替换缺陷修复设计

> 日期：2026-11-27。状态：**已实现（2026-11-27）**。确认的结果见第 7 节，实现见第 8 节。
> 起因：《测试用例说明/替换功能测试（ReplacementIT）》里 13 项失败：5 项是流模式下丢掉的功能，6 项是原有缺陷（另 2 项是同一缺陷的不同检查）。
> 对比的代码：会话模式 `f49bd6d:src/com/king/gmms/connectionpool/session/InternalCoreEngineSession.java`（`d1243cf` 删除），Client 侧 `f49bd6d:…/InternalAgentSession.java`；流模式为当前 `main`。

## 1. 背景：为什么会丢

会话模式下，Core 处理完一条 MT，经内部 TCP 连接交给 Client：`InternalCoreEngineSession.submit()` → `sendNewMessage()`，在**这一步按目标通道（rssid）**做了地址改写和通道检查，再编成内部 PDU 发出。DR 发给 Server（`sendReport()`）、DR 查询发给 Client（`sendReportQuery()`）也一样，在发出前各做了一些处理。

流模式下，`MessageProcessorThread` 路由后直接写 Redis 流（`produceOutboundMessage` / `produceHttpSubmitMessage` / `produceDeliveryReport`），不再调用会话的 `submit()`。从 `f49bd6d` 开始就是这样（那时会话类还在，但只被五个流入口调用：`processSubmitFromStream` 等，见 `d1243cf` 的说明）。于是 `submit()` 下面的这几段从流模式一开始就没人执行，配置照样加载。

Client 侧的 `InternalAgentSession` 收到 Core 的 MT 后只是放进通道的发送队列（`put2OperatorMessageQueue`），没有业务处理，所以 Client 一侧没有缺失。入向（Server → Core）的处理：会话版 `processSuccessSubmit` 和流版 `processSuccessSubmitFromStream` 逐段对比，客户侧的黑白名单、内容黑名单、`HandlePrefix4NewMO`、客户侧 `SenderReplacement`、过期时间都在，没有缺失（会话版里的 `SMSOptionSendFakeDR` 是假 DR 重设计时有意去掉的）。MQM 的处理在 `d1243cf` 里原样搬到 `CoreMessageProcessor`，没有缺失。

旧代码的几个细节，恢复时要按原样或明确地改：

- B、C、D、E 只改“发给通道的地址”（`address[]`），Core 缓存的那份消息不变；A 改的是消息本身。G～J 检查的是消息本身的发送方，也就是 A 之后、B～E 之前的地址。

## 3. 恢复设计

### 3.1 放在哪里

新加一个类 `com.king.gmms.processor.ChannelOutboundPreparer`，在 `MessageProcessorThread.transactNewMessage` 里，**模板替换（路由规则模板、通道模板）之后、内容签名 / 字符集转换 / 拆分之前**调用一次：

```
内容替换（客户）→ 路由规则模板 → 通道模板 → 【ChannelOutboundPreparer：长度控制 A，检查 G～J，改写 D、E】→ 签名、字符集 → 拆分 → 写出向流
```

- 放在拆分之前：拆出的各段自然用同一个发送方，F 不再需要 Redis 的 `senderReplacement_{msgId}`；检查也只做一次（旧代码对每段做一次）。
- SMPP 通道和 HTTP 通道都做（旧代码对两种通道都做）。
- 不做的情况：MO 发给客户（`isMoToCustomer`，写客户 Server 流）、黑洞通道（在这之前就处理掉了）、已经拆过的分段（`splitStatus > 0`，见 3.3）。

K 放在 Core 写客户 DR 的出口：`MessageProcessorThread.transactDR` 恢复原地址之后、写流之前；假 DR（`DirectInDRDispatchService`）走同一个处理。

### 3.2 执行顺序

| 步 | 内容 | 作用于 |
|---|---|---|
| 1 | A 长度控制 | 消息发送方 |
| 2 | G、H、I、J 检查（通道非 VIP 才做 G、H） | 第 1 步后的地址、内容 |
| 3 | D 通道侧 `SenderReplacement`（通道开了 `SMSOptionAdvancedSenderReplacement`） | 发给通道的发送方 |
| 4 | E `Prefix4NewMT` | 发给通道的地址 |

检查失败：状态码同旧代码（2111 / 2112 / 2121 / 2201），走 `handleOutSubmitRes`（OUT_SUBMIT CDR、按客户要求回失败 DR），不发出。

### 3.3 改道、重发时不重复改写

流模式下一条 MT 会多次进入 `transactNewMessage`：改走备份通道（`IOSMSRerouteDispatcher` 把消息交回处理器）、MQM 从 RMQ 重发（`routeSubmitSync`）。进来的那份是上一次发出去的，地址已经按上一个通道改写过。A、E 不一定幂等（例如 `AddPrefix` 会再加一次），而且换了通道要按新通道重新算。

做法：每次进入都先把地址恢复成“**进入通道外发处理前**的地址”（客户侧处理之后、任何通道处理之前），再按**这一次**的通道做第 1～4 步。这个基准地址存在哪：

| 地址 | 基准存在 | 理由 |
|---|---|---|
| 接收号码 | 复用现有的 `originalRecipientAddr` | 单 A2P 的流模式下现在没有地方设置它（只有 peering 的 `CommandSubmit` 和数据库读回会赋值），唯一的使用是回给客户的 DR 恢复接收号码，为空时不恢复，客户看到的就是入向处理后的号码。在**入向处理结束时**（`processSuccessSubmitFromStream` 做完 `HandlePrefix4NewMO` 之后）把它设成当前接收号码，DR 的行为和现在一样，同时可作基准。Redis 流（字段 15）和数据库队列表（`OriginalRecipientAddr` 列）都已经存它 |
| 发送方 | **新加**一个字段 `inSenderAddress` | 不能复用 `originalSenderAddr`：它是客户发来的原始发送方（入向一开始就设置，之后入向还会经过 `HandlePrefix4NewMO`、发送方白名单 `rp`、客户侧 `SenderReplacement`、NMG 借号），并且有三处依赖这个含义：回给客户的 DR 恢复发送方、`OttContentAddOaddr` 把它加在内容前面、NMG 用它判断“已经借过号”（`NMGUtility.alreadyRentAddr`）。改成入向处理后的值，这三处行为都会变；从它出发在外发时重算入向那几步也不可行（白名单 `rp`、借号不能重复做，客户侧替换在入向时还没有 rssid） |

- `inSenderAddress` 第一次进入时（为空）记下当前发送方，之后每次进入先恢复；
- Redis 流：`SerializableHandler` 两种格式在末尾追加一个字段，读旧条目时为空（按第一次进入处理）。

例：客户发送方 123，客户侧 `SenderReplacement` 换成 456（基准 `inSenderAddress` = 456）；主路由通道 b 的规则 456 → abc，备份通道 c 的规则 456 → efg：

| 次序 | 通道 | 从哪个发送方算 | 发出去的 | OUT_SUBMIT CDR |
|---|---|---|---|---|
| 第 1 次 | b | 456 | abc | abc |
| 失败，改走备份 | c | 456 | efg | efg |
| 失败，按重试策略回主路由（MQM 从 RMQ 取回，基准从 `InSenderAddr` 列读出） | b | 456 | abc | abc |

回给客户的 DR：发送方 123（`originalSenderAddr`）。

数据库队列表（RMQ 等）里 `inSenderAddress` 怎么办，两种做法，**2026-11-27 确认用 (a)**：

| 做法 | 内容 | 留下的问题 |
|---|---|---|
| (a) 加一列 `InSenderAddr` | `docs/sql/` 下给出 SQL，沿用 `DB.DrErrorCodeColumns` 的做法加 `DB.InSenderAddrColumn=auto`：所有表都有这列才读写 | 无 |
| (b) 不加列 | RMQ 重发的消息 rssid 不变（`routeSubmitSync` 对 rssid > 0 的不再路由），还是发往原来那个通道，地址已是按这个通道改写过的：基准为空且来自数据库队列（`originalQueue` 是 RMQ 等）时跳过**发送方**改写（接收号码有 `originalRecipientAddr`，照常从基准算） | 先从 RMQ 重发、再改走备份通道时，发送方会以已改写的地址为基准 |

### 3.4 CDR 和 DR 用哪个地址

| 记录 | 地址 | 和旧代码 |
|---|---|---|
| IN_SUBMIT CDR | 客户发来的（入向处理后） | 同 |
| 发给通道、OUT_SUBMIT CDR、WDQ、DR 匹配数据 | 改写后的 | 同（旧代码里通道结果来自 Client 那份） |
| 回给客户的 DR | `OriginalSenderAddr` / `OriginalRecipientAddr`，再按客户做 K | 同 |

### 3.5 上线风险

这些配置在流模式下一直没生效，生产的 cm.cfg、`senderReplacement.cfg`、`senderactiondir` 里如果写了，恢复后**会马上生效**，发出去的发送方、接收号码会变，原来能发的消息可能被通道名单拦下。不加开关（目标就是恢复线上原有的功能），上线前在生产配置里查这些配置项和名单文件（6.2）。

## 4. 6 个原有缺陷：问题和修复

### 4.1 CR-08：替换值里有 `$`，整个客户的替换都失效

- **现象**：`SMSOptionContentReplacementPolicy: (prefix=all,value=price:$5|foo:bar)`，`price foo` 发出去还是 `price foo`，连 `foo:bar` 也没做。
- **原因**：`MessageProcessorThread.transactNewMessage`（第 446、470 行）用 `contentString.replaceAll(key, value)`，`replaceAll` 把替换串里的 `$5` 当成第 5 个分组的引用，抛 `IndexOutOfBoundsException`；异常被外层 try 接住，剩下的规则全部跳过。
- **修复**：
  - 替换串里 `$` 后面**跟数字**时保留分组引用（key 是正则，`(\d{3})\d{4}:$1****` 这种写法可能有人在用），其余的 `$` 和 `\` 转义成字面字符；
  - 每条规则单独 try：出错只跳过这一条，打 WARN（带客户和规则），不影响别的规则。
- **兼容**：写了 `$1` 这类分组引用的配置行为不变。

### 4.2 CR-10b：改走备份通道时内容被再替换一次（MQM 重发同样）

- **现象**：`foo:foofoo`，主通道收到 `foofoo`，失败后备份通道收到 `foofoofoofoo`。
- **原因**：`inTextContent`（“备份路由用的原文”）在内容替换**之后**才保存（第 488 行）。改道时 `IOSMSRerouteDispatcher` 把内容恢复成 `inTextContent`（已经替换过的），再交给处理器，内容替换又做一次。MQM 从 RMQ 重发时也会再进 `transactNewMessage`，同样重复（推断，未测）。另外，重发的是已经拆过的分段时，内容替换和模板也会对这一段再做一次（模板可能因为这段里没有验证码而失败）。
- **修复**：
  - 把保存 `inTextContent` / `inContentType` 挪到内容替换**之前**，并且只在为空时保存（第一次进入时的客户原文）；
  - 每次进入 `transactNewMessage` 时，不是分段（`splitStatus <= 0`）就先把内容恢复成 `inTextContent`，再做内容替换和模板。这样改道、重发每次都从客户原文算一遍，结果一致；
  - 已经拆过的分段（`splitStatus > 0`）跳过内容替换和模板（拆分前已经做过）。
- **兼容**：`inTextContent` 原来的意思就是“备份路由用的原文”；数据库 `InTextContent` 列以后存的是客户原文（以前是内容替换后的）。

### 4.3 TP-05b：模板里的 `Sender` 只在模板池里才生效

- **现象**：`contentTemplate.cfg` 里 `[T2]` 配了 `Sender: TPLSENDER`，规则 `ReplaceContentByTemplate=T2`，内容换了，发送方没换。T2 不存在、走以 T2 开头的模板池时才生效（TP-06）。
- **原因**：`A2PCustomerManager.getTemplateContent`（两个重载，第 6093、6195 行）只在“模板池”分支里读 `sender`；模板 ID 正好存在的分支不读。另外，“没有这种内容类型的文字，取另一种”的循环里，如果 `sender` 排在文字前面会被跳过，排在后面则在 `break` 之前读不到。
- **修复**：取到模板（不论是正好命中还是来自模板池）后，统一用 `content.get("sender")` 读发送方；选文字的循环只看 ASCII、UCS2 两种。
- **兼容**：以前配了 `Sender` 但没生效的模板，修复后会改发送方。和 3.5 一样，上线前要查生产的 `contentTemplate.cfg`、`portalContentTemplate.cfg`。

### 4.4 TP-08：没配模板的规则也套用了模板

- **现象**：同一个客户、同一个通道，规则 `86`（`ReplaceContentByTemplate=T1`）和规则 `8613`（没有模板）。8613 的号码由 8613 规则路由，内容却被换成了 T1。
- **原因**：模板表 `RuleIndex.templates()` 按“客户:通道（:发送方）→ 号码前缀 → 模板”建，只收录配了模板的规则。`isContentReplace` / `getTemplateContent` 用接收号码去匹配这些前缀，不看消息实际是哪条规则路由的。8613 规则没有模板，表里没有它，号码却以 86 开头，就用了 86 规则的模板。另外，`getTemplateContent` 遍历 HashMap，碰到第一个能匹配的前缀就用，不保证是最长的（TP-07 这次碰巧对了）。
- **修复**：
  - 消息上已经有路由时记下的规则（`routingRule`，例如 `main|main:0:86:30`，是层、级别、前缀组、优先级）。`RuleIndex` 另建一张“客户:通道:层:级别:前缀组:优先级 → 模板”的表；
  - 有 `routingRule` 时，只用**这条规则**的模板，规则没配模板就不替换；`IsReplaceTemplateBySender` 照旧（这种规则本来就按发送方命中）；
  - 没有 `routingRule` 时（旧数据），保留现在的查法，但改成**最长前缀**优先。
- **兼容**：只影响“同一个通道下有的规则有模板、有的没有”的配置，修复后按路由那条规则来。

### 4.5 CR-02c：只改大小写的替换不生效

- **现象**：`ab:AB` 不生效。
- **原因**：代码用 `key.equalsIgnoreCase(value)` 判断“这条是号码占位符”（`\{@phone#(\d+)\}:\{@phone#(\d+)\}`，第 467 行），`ab` 和 `AB` 忽略大小写相等，被当成占位符处理，内容里没有占位符，什么都没做。
- **修复**：改成 `key.equals(value) && key.contains("@phone#")` 才按号码占位符处理，其余都按普通替换。
- **兼容**：号码占位符的写法不变。

### 4.6 CR-04b：同一个号码命中几组时，组之间先后不固定

- **现象**：号码 8613… 同时命中 `prefix=86` 和 `prefix=8613` 两组，8613 组的 `one:two` 先执行，把 86 组要找的占位符 `{@phone#4}` 改成了 `{@phtwo#4}`。
- **原因**：前缀组存在 `HashMap`（`smsOptionReplaceContent`），一组里的各条规则也存在 `HashMap`（`contentMap`），遍历顺序由哈希决定，和配置的顺序无关。规则之间有依赖（链式替换、占位符）时结果不确定。
- **修复**：两层都改成 `LinkedHashMap`，并规定执行顺序：
  - 先 `prefix=all`，再按前缀从短到长（86 → 8613）；
  - 同一组里按配置的先后执行。
  写进《配置项说明》。
- **兼容**：现在的结果本来就和顺序有关；规定顺序后，之前碰巧靠哈希顺序得到的结果可能变化，概率很小。
