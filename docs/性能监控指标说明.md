# 性能监控指标说明

> 日期：2026-11-11，对应提交 `b97ae27`。这份文档列出系统输出的全部监控指标，说明每个指标的含义、由哪个模块输出、怎么看，以及怎么配置。设计和取舍见《性能监控埋点评估与设计》，配置项总表见《配置项说明》。

## 1. 总览

每个模块（Server、Core、Client、HTTP Client 等）在进程里自己统计，每个**窗口**（默认 30 秒）汇总输出一次，输出到三个地方：

| 输出 | 位置 | 用途 |
|---|---|---|
| 指标日志 | logger `metrics.logger`，每个窗口几行 `[METRICS-TPS]`、`[METRICS-SSID]`、`[METRICS-GAUGE]`、`[METRICS-TIMER]` | 留历史；给 ELK / Loki 等日志采集 |
| Redis 快照 | `metrics:{模块}:{NodeID}`（Hash，只保留最近一个窗口） | `A2pCtl metrics` 一条命令看所有节点；外部采集脚本读取 |
| 告警日志 | 主日志里的 WARN `[METRICS-ALERT]` | 超过阈值时提醒（不发邮件） |

指标分三种：

| 种类 | 含义 | 输出的值 |
|---|---|---|
| 计数（counter） | 从启动起只增不减的次数 | 本窗口的**每秒次数**（本窗口增量 ÷ 窗口秒数），保留两位小数 |
| 瞬时值（gauge） | 某一时刻的数量（排队数、连接数等） | 汇报时的当前值 |
| 耗时（timer） | 一段时间的长度（毫秒） | 本窗口的次数 `count`、平均 `avg`、`p50`、`p95`、`p99`、最大 `max` |

## 2. 命名规则

所有名字都以**模块名（小写）**开头，例如 `coreengine1.`、`multismppserver1.`、`multismppclient1.`。下面的表里省略这个前缀，写作 `{m}.`。

| 形式 | 例子 | 说明 |
|---|---|---|
| `{m}.business.{环节}.{消息类型}.{动作}` | `coreengine1.business.core.submit.routing_success` | 业务计数。环节：`server`、`core`、`client` |
| `{m}.stream.{in\|out}.{消息类型}.{动作}` | `multismppclient1.stream.in.submit.read` | Redis Stream 读写计数 |
| `{m}.consumer.process.{消息类型}.{动作}` | `coreengine1.consumer.process.submit.fail` | 消费者处理失败、窗口满等计数 |
| `{m}.ssid.{ssid}.{阶段}.{动作}` | `multismppserver1.ssid.8890.insubmit.received` | 按客户 / 通道的计数（`Metrics.Ssid.Enable`） |
| `{m}.{组件}.{名字}` | `coreengine1.redis.stream.server_to_core.xlen` | 瞬时值 |
| `{m}.{耗时名}[.{维度}]` | `multismppclient1.client.vendor.submit_rtt.80` | 耗时，维度是流向、通道 ssid、bind 等 |

**消息类型**：`submit`（MT，包括 deliver 类型的 MO）、`submit_resp`、`dr`、`dr_resp`、`other`。

**按 ssid 的阶段**：

| 阶段 | 按谁统计 | 含义 |
|---|---|---|
| `insubmit` | 客户 ossid | 客户提交 MT |
| `outsubmit` | 通道 rssid | 发给供应商的 MT |
| `indr` | 通道 rssid | 供应商回来的 DR |
| `outdr` | 客户 ossid | 发给客户的 DR |

## 3. 计数（每秒次数，`[METRICS-TPS]`）

### 3.1 业务计数（`{m}.business.*`）

按消息走的顺序：

| 名字（省略 `{m}.business.`） | 模块 | 含义 |
|---|---|---|
| `server.submit.received` | Server（SMPP、HTTP） | 收到客户的 MT |
| `server.submit.accepted_to_redis` | Server | MT 写进 Redis（`stream:mt:pending`），已回客户成功 |
| `server.submit.rejected_before_redis` | Server | MT 没进 Redis 就拒绝了（限流、校验失败、Redis 写失败等） |
| `core.submit.received_from_stream` | Core | Core 从 Stream 读到 MT（含 MQM 重试） |
| `core.submit.routing_success` | Core | 路由成功 |
| `core.submit.routing_failed` | Core | 路由失败 |
| `core.submit.routed_to_redis` | Core | 路由后写给 Client（`stream:mt:routed`） |
| `client.submit.received_from_stream` | Client | Client 读到要发的 MT |
| `client.submit.smpp_sent` | Client（SMPP） | submit_sm 已发给供应商 |
| `client.submit.http_sent` | HTTP Client | HTTP 请求已发给供应商 |
| `client.submit.window_full` | Client | 发送窗口满，这批推迟（之后会重试） |
| `client.submit.failed_before_response` | Client | 没拿到供应商响应就失败了（会话断开、发送异常） |
| `client.submit_resp.response_received` | Client | 收到供应商的 submit_sm_resp / HTTP 响应 |
| `client.submit_resp.result_written` | Client | 发送结果写回 Core（`stream:core:results`） |
| `client.dr.received` | Client（SMPP） | 收到供应商的 DR（deliver_sm） |
| `client.dr.written_to_redis` | Client | 供应商 DR 写给 Core（`stream:core:inbound-dr`） |
| `core.dr.processed` | Core | 供应商 DR 处理完 |
| `core.*.rdq_retry_policy` | Core | DR 按 RDQ 重试策略处理（直接回 DR 的分发） |
| `core.*.registry_fallback_configured_server` | Core | 找 DR 发给哪个 Server 时，注册表里没有，退回到配置的 Server |
| `core.*.registry_no_server_module` | Core | 找不到可以发 DR 的 Server |
| `server.dr.sent_to_customer` | Server | DR 发给客户（deliver_sm 已发出） |
| `server.dr.failed_to_customer` | Server | DR 发给客户失败 |
| `server.dr.window_full` | Server | 客户的窗口满，DR 推迟 |
| `client.dr.received_from_stream` / `client.dr.sent_to_customer` / `client.dr_resp.result_written` | HTTP Client | HTTP 客户的 DR 推送：读到、推送成功、结果写回 |
| `client.{submit\|dr}.failed_before_response` / `failed_to_customer` | HTTP Client | HTTP 发送失败 |

**怎么看**：

- 入口量看 `server.submit.received`，被拒的比例 = `rejected_before_redis` ÷ `received`。
- Core 路由失败率 = `routing_failed` ÷ `received_from_stream`。
- 发给供应商的量看 `client.submit.smpp_sent` + `http_sent`。
- `window_full` 持续很高：供应商响应慢或窗口太小，结合 `client.vendor.submit_rtt`（第 5 节）看。

### 3.2 Stream 计数（`{m}.stream.*`）

| 名字 | 含义 |
|---|---|
| `stream.out.{类型}.write_ok` | 写进 Stream 成功 |
| `stream.out.{类型}.write_fail` | 写失败（Redis 异常、背压拒绝、key 为空） |
| `stream.in.{类型}.read` | 从 Stream 读到（只算新条目，不含重新认领的） |
| `stream.in.{类型}.ack` / `ack_fail` | 处理完确认成功 / 失败 |
| `stream.in.{类型}.dead_letter` | 反序列化失败，放进死信流（`stream:dlq:*`） |
| `stream.process.other.retry_claim` | 推迟的条目重新处理的条数（Client、Server DR） |

`write_fail`、`ack_fail`、`dead_letter` 正常应为 0。

### 3.3 消费者计数（`{m}.consumer.process.*`）

| 名字 | 含义 |
|---|---|
| `consumer.process.{类型}.fail` | 消费者处理一条失败（之后会被重新认领重试） |
| `consumer.process.{类型}.window_full` | Client / Server 因为窗口满推迟 |

### 3.4 SMPP 超时计数

| 名字 | 含义 |
|---|---|
| `smpp.pending.submit.timeout.{类型}.timeout_processed` | 等 submit_sm_resp 超时，按超时处理了 |
| `smpp.pending.submit.timeout.submit.timeout_skipped` | 超时检查时已经有结果了，跳过 |
| `smpp.pending.dr.timeout.{类型}.timeout_processed` / `timeout.dr.timeout_skipped` | 等客户 deliver_sm_resp 超时 |

### 3.5 按 ssid 的计数（`[METRICS-SSID]`）

`Metrics.Ssid.Enable=true` 时，第 3.1 节的主要动作再按客户 / 通道各记一份：`{m}.ssid.{ssid}.{阶段}.{动作}`。动作名和 3.1 一样，另有 `outsubmit.bind_throttled`（bind 限速推迟，见 `SMSOptionOutgoingThrottlingNumPerBind`）和 `processed`（Core 处理完结果 / DR）。

客户多时一个窗口会有几千个键，单独输出成 `[METRICS-SSID]` 行，排查某个客户时再打开。

## 4. 瞬时值（`[METRICS-GAUGE]`，`Metrics.PrintGauge`）

| 名字（省略 `{m}.`） | 模块 | 含义 | 怎么看 |
|---|---|---|---|
| `redis.stream.{流向}.xlen` | 读这个流向的模块 | 本模块负责的分片里，这个流向所有 Stream 的条目总数 | 持续上涨 = 消费跟不上 |
| `redis.stream.{流向}.pending` | 同上 | 已读未确认的条目数 | 持续很高 = 处理卡住或消费者死了 |
| `redis.stream.{流向}.doorbell_missing` | 同上 | 有数据但没有门铃的 Stream 数（会没人读） | 应为 0；不为 0 时看 `[STREAM-BACKLOG]` 日志 |
| `redis.stream.{流向}.streams` | 同上 | 正在监控、还有数据的 Stream 数 | |
| `consumer.{消费者}.pool.active` / `queued` | 各模块 | 消费者线程池的活动线程数、排队任务数 | `queued` 持续不为 0 = 线程不够 |
| `smpp.pending.submit.pending` | Client | 已发 submit_sm、等响应的条数（本进程所有 bind） | 接近窗口总和 = 供应商慢 |
| `smpp.pending.submit.timeout_queue_size` / `timeout_worker_count` | Client | 超时检查队列长度、检查线程数 | |
| `smpp.pending.dr.pending` / `timeout_queue_size` / `timeout_worker_count` | Server | 已发 DR、等客户 deliver_sm_resp 的条数等 | |
| `queue.smpp_server_inbound.global_queued` / `global_inflight` | Server | 收到还没处理的 submit 数、正在处理的数 | |
| `queue.smpp_server_inbound.active_ssids` / `ssid_queues` / `pool_full_retries` | Server | 有排队的客户数、客户队列数、线程池满重试次数 | |
| `queue.multismppserver_customer_sender.*` / `queue.multismppserver_customer_response.*` | Server（长连接客户） | 共享发送 / 响应队列的排队数、处理中、活跃客户数 | |
| `stream.server.dr.window_full.consecutive` | Server | 某个客户连续窗口满的次数 | |
| `db.pool.{数据源}.active` / `idle` / `total` / `waiting` / `max` / `min_idle` | 用 DB 的模块（`DB.PoolStats.Enable`） | 连接池：使用中、空闲、总数、**等连接的线程数**、上限、最小空闲 | `waiting` > 0 = 连接不够或 SQL 慢 |
| `db.async_sql.queued` | 用异步写库的模块 | 等写进 DB 的 SQL 条数 | 持续上涨 = DB 写不过来 |
| `fakedr.timeout.timing` | Core | 假 DR 超时计时中的 MT 数（`SMSOptionFakeDRTimeoutSec`） | |
| `jvm.thread.count` / `daemon_count` / `peak_count` / `total_started` | 各模块 | JVM 线程数 | 一直涨 = 线程泄漏 |

**流向**（Stream 积压和第 5 节的排队延迟都用这个名字）：

| 流向 | Stream | 谁读 |
|---|---|---|
| `server_to_core` | `stream:mt:pending:*` | Core |
| `core_to_client` | `stream:mt:routed:*` | Client |
| `core_to_http_submit` / `core_to_http_dr` | `stream:http:submit:*` / `stream:http:dr:*` | HTTP Client |
| `result_to_core` | `stream:core:results:*` | Core |
| `client_to_core` | `stream:core:inbound-dr:*` | Core |
| `core_to_server` | `stream:dr:pending:*` | Server |
| `mqm_to_core_submit` / `mqm_to_core_report` | `stream:mqm:submit:*` / `stream:mqm:report:*` | Core |
| `outbound_http` | `stream:outbound:http:tasks` | HTTP 外发 |

Stream 积压由 `RedisStreamMonitor` 每 60 秒检查一次，窗口里显示的是最近一次检查的结果。超过 `RedisStreamMonitor.WarnXLEN` / `WarnPending` 或门铃丢失时，主日志另打 WARN `[STREAM-BACKLOG]`，带具体的 Stream 名。

## 5. 耗时（`[METRICS-TIMER]`，毫秒）

| 名字（省略 `{m}.`） | 模块 | 从哪到哪 | 维度 |
|---|---|---|---|
| `stream.lag.{流向}` | 读这个流向的模块 | 条目写进 Stream → 被消费者读到（**排队时间**） | 流向 |
| `client.vendor.submit_rtt.{rssid}` | Client（SMPP） | submit_sm 发出 → 收到 submit_sm_resp（**供应商响应时间**） | 通道 |
| `client.vendor.submit_rtt.{rssid}.{bind}` | Client（SMPP） | 同上，按 bind（会话名） | 通道 + bind（`Metrics.Bind.Enable`） |
| `core.vendor.dr_latency.{rssid}` | Core | 供应商接收 MT（submit_sm_resp 成功）→ Core 匹配到最终 DR（**供应商回 DR 的时间**） | 通道 |
| `e2e.submit` | Client（SMPP） | Server 收到 MT → Client 发出 submit_sm（**网关内 MT 端到端**） | 无 |
| `e2e.dr` | Server（SMPP） | Client 收到供应商 DR（假 DR 从生成时算）→ 客户回 deliver_sm_resp（**网关内 DR 端到端**） | 无 |
| `consumer.{消费者}` | 各模块 | 消费者处理一条消息的时间 | 消费者 |
| `redis.op.xadd` / `redis.op.lua` / `redis.op.read` | 各模块 | 一次 Stream 写（含门铃，Lua）、写结果并确认（Lua）、一次批量读 | 操作 |
| `db.op.insert` / `update` / `delete` / `select` / `batch` / `other` | 用 DB 的模块 | 一次 SQL（含取连接） | 操作 |
| `defer.wait.{消费者}.{原因}` | Client、Server、HTTP Client | 一批消息被推迟到重新处理等了多久 | 消费者 + 原因 |

**消费者名**：

| 名字 | 模块 | 处理什么 |
|---|---|---|
| `mt` | Core | Server 来的 MT（路由） |
| `mqm` | Core | MQM 重试的 MT 和 DR |
| `result` | Core | Client 回来的发送结果、Server 回来的 DR 结果 |
| `inbound_dr` | Core | 供应商 DR |
| `client_out` | Client | 发给供应商的 MT |
| `server_dr` | Server | 发给客户的 DR |
| `http_submit` / `http_dr` | HTTP Client | HTTP 外发 MT / HTTP 推送 DR |

**推迟原因**（`defer.wait`）：`window_full`（窗口满）、`throttled`（通道限速）、`bind_throttled`（bind 限速）、`other`（其他，Server DR 和 HTTP 都记在这里）。

**怎么看**：

- **`stream.lag` 高**：上游写得快、下游读得慢（下游线程不够、下游变慢、或者被限速）。对照同一流向的 `redis.stream.*.xlen`。
- **`client.vendor.submit_rtt` 高**：供应商慢。打开按 bind 可以看出是不是某个 bind 慢（排查连接间发送不平均时用）。
- **`e2e.submit` 高**而供应商响应不高：时间耗在网关里，按 `stream.lag.server_to_core`、`consumer.mt`、`stream.lag.core_to_client`、`defer.wait.client_out.*` 逐段看。
- **`core.vendor.dr_latency`**：供应商回 DR 的速度，按通道比较；它的 `max` 可能是几小时（供应商晚回的 DR）。
- **`db.op.*` 的 p99 高**：DB 慢，对照 `db.pool.*.waiting` 和 `db.async_sql.queued`。

**统计方式**：每次记录落进一个区间（≤1、5、10、25、50、100、250、500、1000、5000 ms，更长）。p50 / p95 / p99 由本窗口的区间次数在区间内线性估算，不超过本窗口的最大值，精度够看趋势。`max` 是本窗口的真实最大值。只在本窗口有记录的耗时才输出。

**不统计的情况**：HTTP 通道的供应商响应和 DR 延迟、HTTP 客户的 `e2e.dr`。从 Redis 恢复的待响应项（Client 重启后）不算 `submit_rtt`。通过 DB 匹配到的 DR（Redis 里的原 MT 已过期）没有 `dr_latency`。

## 6. 输出格式

### 6.1 指标日志

`Metrics.Format=json`（默认）时，每行是标签加一个 JSON 对象：

```
[METRICS-TPS] {"module":"coreengine1","node":"1","ts":1794384130964,"window":30,"tps":{"coreengine1.business.core.submit.received_from_stream":1.50,"coreengine1.business.core.submit.routing_success":1.50}}
[METRICS-GAUGE] {"module":"multismppclient1","node":"1","ts":...,"window":30,"gauge":{"multismppclient1.redis.stream.core_to_client.xlen":0,"multismppclient1.smpp.pending.submit.pending":3}}
[METRICS-TIMER] {"module":"multismppclient1","node":"1","ts":...,"window":30,"timer":{"multismppclient1.client.vendor.submit_rtt.81":{"count":3,"avg":231.67,"p50":212.50,"p95":250.85,"p99":250.97,"max":251.00}}}
```

| 字段 | 含义 |
|---|---|
| `module` / `node` | 模块名（小写）、NodeID |
| `ts` | 汇报时间（毫秒） |
| `window` | 窗口秒数 |
| `part` | 一行超过约 4KB 时分成多行，第几行（只有一行时没有） |
| `tps` / `gauge` / `timer` | 指标 |

没有数据的那一类不输出。TPS 低于 `Metrics.MinTPS` 的计数不输出（`Metrics.PrintZero=true` 时输出全部）。

`Metrics.Format=kv` 时是原来的文本格式：`[METRICS-TPS] module=coreengine1 node=1 window=30s tps="a=1.5/s,b=0.3/s"`。

### 6.2 告警日志

```
WARN ... MetricsReporter [METRICS-ALERT] {"module":"multismppclient1","alert":"vendor_rtt","metric":"multismppclient1.client.vendor.submit_rtt.81","value":250.85,"threshold":100.00,"count":3,"windows":1}
```

| 告警 `alert` | 条件 | `value` |
|---|---|---|
| `stream_lag` | 任一 `stream.lag.*` 的 p95 > `Metrics.Alert.StreamLagMs` | p95（ms） |
| `vendor_rtt` | 任一通道的 `client.vendor.submit_rtt.{rssid}` 的 p95 > `Metrics.Alert.VendorRttMs`（按 bind 的不单独告警） | p95（ms） |
| `db_pool_waiting` | 任一 `db.pool.*.waiting` > `Metrics.Alert.DbPoolWaiting` | 等待线程数 |
| `consumer_fail_ratio` | 本窗口 `consumer.process.{类型}.fail` ÷ `stream.in.{类型}.read` > `Metrics.Alert.ConsumerFailRatio`（读取少于 20 条不判断） | 比例 |

`count` 是本窗口的样本数，`windows` 是距上一条同类告警之间超过阈值的窗口数。同一个告警（同一个指标）在 `Metrics.Alert.RepeatSeconds` 内只打一次。告警打在主日志（logger `MetricsReporter`），外部监控按关键字 `[METRICS-ALERT]` 采集即可。

系统里其他的告警日志（不是指标，也只打日志）：`[ALERT]`（Redis 挂了、DB 从库挂了、SystemManager 挂了、DNS 切换、CDR 文件没切换），`[MGT-ALERT]`（管理命令执行失败），`[STREAM-BACKLOG]`（Stream 积压）。

### 6.3 Redis 快照

`Metrics.Redis.Enable=true`（默认）时，每个窗口写入：

| key | 类型 | 内容 |
|---|---|---|
| `metrics:{模块小写}:{NodeID}` | Hash，TTL 为 3 个窗口（至少 90 秒） | `module`、`node`、`ts`、`window`，以及 `tps`、`gauge`、`timer`（各是一个 JSON 对象，格式同 6.1；不含按 ssid 的） |
| `metrics:index` | ZSET，分数为写入时间 | 所有 `metrics:*` 的 key；模块停了以后它的 Hash 过期，`A2pCtl metrics` 读到空时顺手删掉 |

外部采集（例如推给 Prometheus）可以定时 `ZRANGE metrics:index 0 -1`，再逐个 `HGETALL`。

## 7. 查看

### 7.1 A2pCtl metrics

```
java -Da2p_home=/usr/local/a2p/ -cp "lib/*" com.king.gmms.ha.A2pCtl metrics             # 每个模块一行
java -Da2p_home=/usr/local/a2p/ -cp "lib/*" com.king.gmms.ha.A2pCtl metrics CoreEngine1 # 这个模块的所有指标
java -Da2p_home=/usr/local/a2p/ -cp "lib/*" com.king.gmms.ha.A2pCtl metrics --json      # 原始 JSON，每个节点一行
```

（`-cp` 按现场的安装目录写，和 `A2pCtl status` 一样。）

不带模块名时的输出：

```
module                   node    age      in/s     out/s      dr/s   backlog    lag p95    rtt p95    e2e p95
multismppserver1         1        1s     120.3       0.0     118.0         0          -          -          -
coreengine1              1        0s     118.0       0.0       0.0        12        3.2          -          -
multismppclient1         1        1s     118.5     119.0       0.0         0        2.1      231.0      45.6
```

| 列 | 含义 |
|---|---|
| `age` | 这个窗口是多少秒前写的；远大于窗口秒数说明模块停了或写不进 Redis |
| `in/s` | 所有 `business.*.received` 之和（Server 收到的 MT、Client 收到的供应商 DR） |
| `out/s` | `business.*.smpp_sent` + `http_sent`（发给供应商的 MT） |
| `dr/s` | `business.*.sent_to_customer`（发给客户的 DR） |
| `backlog` | 所有 `redis.stream.*.xlen` 之和 |
| `lag p95` | 各流向 `stream.lag` 的 p95 里最大的 |
| `rtt p95` | 各通道 `client.vendor.submit_rtt` 的 p95 里最大的 |
| `e2e p95` | `e2e.submit` 的 p95 |

`-` 表示本窗口没有这个数据（例如窗口里没有流量）。

## 8. 配置

所有配置都在 `Gmms/GmmsConfig.properties`，都可以热加载（改完执行热加载命令即可，不用重启）。

### 8.1 配置项

| 配置 | 默认 | 作用 |
|---|---|---|
| `Metrics.Enable` | `true` | 总开关。关掉后不统计、不输出 |
| `Metrics.ReportIntervalSeconds` | `30` | 窗口秒数 |
| `Metrics.LogLevel` | `INFO` | 指标日志的级别（`INFO` / `DEBUG` / `TRACE`）。log4j2 里 `metrics.logger` 的级别要不高于它，否则看不到 |
| `Metrics.Format` | `json` | `json` 或 `kv` |
| `Metrics.PrintGauge` | `true` | 是否输出瞬时值 |
| `Metrics.PrintZero` | `false` | 是否输出本窗口为 0 的计数 |
| `Metrics.MinTPS` | `0.01` | 每秒次数低于它的计数不输出 |
| `Metrics.Ssid.Enable` | `false` | 按 ssid 统计（`[METRICS-SSID]`）。客户多时日志量大，排查时再开 |
| `Metrics.Bind.Enable` | `false` | 供应商响应时间再按 bind 统计（只输出本窗口有流量的 bind） |
| `Metrics.Redis.Enable` | `true` | 是否写 Redis 快照（`A2pCtl metrics` 要用） |
| `Metrics.Alert.StreamLagMs` | `0` | Stream 排队 p95 告警阈值（ms），0 不检查 |
| `Metrics.Alert.VendorRttMs` | `0` | 供应商响应 p95 告警阈值（ms），0 不检查 |
| `Metrics.Alert.DbPoolWaiting` | `0` | DB 连接池等待线程数告警阈值，0 不检查 |
| `Metrics.Alert.ConsumerFailRatio` | `0` | 消费者失败比例告警阈值（如 `0.05`），0 不检查 |
| `Metrics.Alert.RepeatSeconds` | `300` | 同一告警的最短间隔（秒） |
| `DB.PoolStats.Enable` | `true` | 是否采集 DB 连接池瞬时值 |
| `DB.PoolStats.IntervalSeconds` | `60` | 连接池采集间隔（秒） |
| `RedisStreamMonitor.Enable` | `true` | 是否检查 Stream 积压 |
| `RedisStreamMonitor.IntervalSeconds` | `60` | 积压检查间隔（秒） |
| `RedisStreamMonitor.FullScanEveryCycles` | `10` | 每多少次检查扫一次整个库（找丢了门铃的 Stream） |
| `RedisStreamMonitor.WarnXLEN` / `RedisStreamMonitor.WarnPending` | `100000` / `10000` | 单个 Stream 积压 / 待确认达到多少打 `[STREAM-BACKLOG]` |

### 8.2 建议的线上配置

```properties
# 默认已是这样，可以不写
Metrics.Enable=true
Metrics.ReportIntervalSeconds=30
Metrics.Format=json
Metrics.Redis.Enable=true

# 告警阈值：按现场的正常值调整（先观察几天的 p95 再定）
Metrics.Alert.StreamLagMs=2000
Metrics.Alert.VendorRttMs=3000
Metrics.Alert.DbPoolWaiting=5
Metrics.Alert.ConsumerFailRatio=0.05
Metrics.Alert.RepeatSeconds=300

# 排查时临时打开，查完关掉
#Metrics.Ssid.Enable=true
#Metrics.Bind.Enable=true
```

### 8.3 log4j2：指标单独一个文件

不配的话 `metrics.logger` 跟随 root 写进主日志。建议在线上的 `conf/log4j2.xml` 里给它单独的文件（按天滚动，保留 7 天）：

```xml
<Appenders>
  ...
  <RollingFile name="M" fileName="${sys:a2p_home}log/metrics.log" filePattern="${sys:a2p_home}log/metrics.%d{yyyy-MM-dd}.log">
    <PatternLayout pattern="%d{yyyy-MM-dd HH:mm:ss} %m%n"/>
    <TimeBasedTriggeringPolicy/><DefaultRolloverStrategy max="7"/>
  </RollingFile>
</Appenders>
<Loggers>
  ...
  <Logger name="metrics.logger" level="info" additivity="false"><AppenderRef ref="M"/></Logger>
</Loggers>
```

`[METRICS-ALERT]` 不在 `metrics.logger` 里，仍然写在主日志，方便和其他告警一起采集。

### 8.4 开销

每条消息约十来次计数和几次计时，每次一两百纳秒；汇总、JSON、告警判断每个窗口只做一次；Stream 积压检查每 60 秒每个 Stream 3 条 Redis 命令（pipeline）。整体对处理性能的影响在 1% 以内。主要的成本是日志量：打开按 ssid、按 bind 后一个窗口可能有几百 KB，所以这两个默认关闭。
