# 配置 reload 防误删与路由表一次性替换设计

## 1. 问题

连续 reload 的测试发现两个问题（单次 reload 也可能碰到，连续执行时概率更高）：

| 问题 | 现象 |
|---|---|
| reload 读到写了一半的 cm.cfg | 文件被截断时，后面的客户被当成删除。实测一次 `changed customers: 36`：所有客户连接断开，下一次 reload 全部新建，结果却是 `ok` |
| `RELOAD_ROUTING` 时路由表逐张替换，并清空旧表 | 正在读旧表的线程可能读到空表。实测 600 条 MT 中有 1 条本来有路由，却按 2120 失败；压测 2100 万次查询有 26 次异常 |

## 2. 方案

### 2.1 确认文件已写完（cm.cfg 和路由文件）

- 文件（路由是目录下所有文件）的修改时间距现在超过 `ConfigFileStableCheckMs`（默认 500 毫秒）时，直接读取，没有额外等待。
- 否则每隔这个时间比较一次大小和修改时间，不变才读取，最多 10 次。一直在变，拒绝这次 reload。
- 读完后再比较一次；读取期间有变化，也拒绝。
- reload 在单线程上排队执行，等待期间到达的 `RELOAD_CUSTOMER` 会被合并。`RELOAD_ROUTING` 不合并，但文件没有刚修改时没有等待，连发不会积压。

这个检查无法发现写入中途暂停超过检查间隔的情况，所以还有下一层保护，推荐的更新方式仍是"临时文件 + `mv`"。

### 2.2 防止误删（cm.cfg）

- 文件为空或读不到：拒绝。
- 文件里没有客户，或者要删除的客户超过当前客户数的 `ReloadCustomerMaxRemovePercent`（默认 20%）：拒绝。100 表示不限制。
- 比较的是块名，所以批量改 shortName 也算删除，要先调大这个配置。

### 2.3 路由文件的保护

没有块或存在空文件时拒绝，路由保持不变。原来的代码先清空 `routingInfoMap` 再解析；现在解析成功才替换。

### 2.4 被拒绝时

所有客户和路由保持原样，连接不受影响。日志 ERROR；`config:files:{模块}:{NodeID}` 里 `{名称}.result=failed`，`{名称}.failReason` 写明原因，下次成功后清空。**被拒绝的 reload 不会自动重试**，修正后要重新发命令。

### 2.5 路由表一次性替换（`A2PCustomerManager.RoutingTables`）

- 36 张路由表（国家、备用、发送方、内容关键字、二次路由、运营商、号码路由和内容模板）移入一个对象，通过一个 volatile 引用发布。
- `loadRoutingInfo` 建好全部新表后，一次替换引用；**不再清空旧表**，还在读旧表的线程读完后由 GC 回收。reload 期间内存里短暂同时有新旧两份。
- 每个查询方法开头取一次引用，一次查询用的是同一版路由表，不会新旧混用。
- 发布后表不再修改。启动时在对象发布前填充。

## 3. 配置项

| 配置项 | 默认 | 生效 | 作用 |
|---|---|---|---|
| `ConfigFileStableCheckMs` | `500` | 热加载 | 见 2.1。0 表示不检查 |
| `ReloadCustomerMaxRemovePercent` | `20` | 热加载 | 见 2.2 |

两项都已加入 `GmmsUtility` 的热加载白名单。

## 4. 不在本次范围

- 其他配置文件（senderReplacement、OperatorMode、模板等）没有加文件稳定性检查。
- `RELOAD_CUSTOMER` 仍会重读路由文件的 `routingInfoMap`（只影响改动过的客户的 ALLOW 策略），文件正在写时跳过。
