# Client 第 1 批：测试用例与执行报告（外发不重复、限流不阻塞、低速通道不影响其他通道）

> 设计见《Client第1批优化设计》。同时对 Core 前 7 批和通道限速做了全量回归。第 1 到 3 节是用例设计，第 4 节是执行结果。

## 1. 测试环境

- 与之前的报告相同：本地 Redis 7.2.5，JDK 17，真实的初始化流程，没有数据库。
- **模拟供应商**：在 `MultiSmppClientFactory` 中替换为测试用的会话。它记录每个 msgId 被发出的次数，可以设为"断开"，也可以让 `submit` 一直不返回（模拟发送时停止的发送者）。
- **测试通道**（cm.cfg）：
  - `VENDOR12`：不限速
  - `VENDOR11`：`SMSOptionOutgoingThrottlingNum: 2`
  - `VENDOR13`：`SMSOptionOutgoingThrottlingNum: 5`
- **为了在几秒内重现原来的重复问题**，把自动重投调得很激进：
  - `RedisStreamAutoClaimEnable=true`
  - `RedisStreamAutoClaimIdleMs=1500`
  - `RedisStreamAutoClaimIntervalMs=500`

  在原来的代码下，每个分片每秒不到 0.67 条的通道就会被重复下发。
- **其他调整**：worker 数设为 4，制造 worker 紧张的情况；`ClientSendLeaseMs=800`。
- **测试套件**：新增 `ClientBatch1IT`。`ConfigReloadIT` 增加了 4 个新配置项的热加载检查。

## 2. 用例

### 2.1 外发去重标记（每种状态各一条消息，按 consumer 的处理方法执行）

| ID | 场景 | 预期 | 级别 |
|---|---|---|---|
| C1-01a | 正常发送 | 发出 1 次；确认消费，同时删除标记 | P0 |
| C1-01b | 已发出、只是确认消费失败，随后重投（标记为 `D`） | 不再发送，只确认消费 | P0 |
| C1-01c | 另一个消费者正在发送（标记为"发送中"，未超过占用期） | 不发送，留在待确认列表 | P0 |
| C1-01d | 同上，但已超过占用期（发送者已停止） | **不重发**，确认消费，**不回失败结果**（由 Core outbox 兜底） | P0 |
| C1-01e/f | 真实场景：第一个发送者卡在 `submit` 里，消息被重投 | 占用期内返回 BUSY，不发送；占用期过后不发送，确认消费 | P0 |
| C1-01g | 会话断开 | 给 Core 回失败结果，确认消费，删除标记 | P0 |
| C1-01h | 会话断开，但被重投的消息之前已经发出 | 不回失败结果（否则会和真实结果冲突），只确认消费 | P0 |
| C1-01i | `ClientSendIdempotency=false` | 正常发送，不写标记 | P1 |

### 2.2 低速通道（真实运行 `OutboundStreamConsumer`）

| ID | 场景 | 预期 | 级别 |
|---|---|---|---|
| C1-02a | 2 TPS 通道积压 20 条 | 全部发出 | P0 |
| C1-02b | 同上，消息排队时间远超自动重投的空闲阈值（1.5 秒） | **没有一条被发两次** | P0 |
| C1-02c | 同上 | 速率不超过限制：20 条在 2 TPS 下用时 ≥ 8.5 秒 | P0 |
| C1-02d | 5 TPS 通道积压 60 条（两个分片） | 每条恰好发出 1 次 | P0 |
| C1-02e | 延后的消息被反复领回 | 不增加投递次数，没有消息进入死信队列 | P0 |
| C1-02f/g | 结束后 | 没有残留的标记，路由 stream 已清空 | P1 |

### 2.3 低速通道不影响其他通道

| ID | 场景 | 预期 | 级别 |
|---|---|---|---|
| C1-03 | 只有 4 个 worker，两个限速通道在所有分片上都有积压，这时给不限速的通道发 20 条 | 不限速通道的 20 条在 1 秒内全部发出，此时 2 TPS 通道仍有积压 | P0 |
| C1-04 | 同上 | 没有任何线程在 `RateLimiter.acquire` 中等待 | P0 |
| C1-05 | 线程池 | 核心线程数 = 最大线程数 = 配置值（4）；池满时拒绝，不再由分发线程执行 | P1 |
| CFG（补充） | 4 个新配置项的热加载 | 新值生效，代码按新值运行 | P1 |

## 3. 不在本地范围的项

| ID | 项 | 建议做法 |
|---|---|---|
| X-C11 | 真实 SMPP 供应商的窗口满 | 本地的模拟会话不是 `MultiSmppSession`，窗口满的分支只做了代码检查（与限流共用同一套延后逻辑，限流部分已测）。测试环境把供应商窗口调小（如 `WindowSize=2`）并压测，确认没有重复下发、`ack_returned_zero` 日志为 0 |
| X-C12 | HTTP 外发的标记 | 本地没有 HTTP 供应商，代码与 SMPP 使用同一个 `ClientSendMarker`。测试环境用一个慢速 HTTP 供应商（响应 5 秒）压测，确认不重复 |
| X-C13 | Client 重启 | 测试环境在发送高峰中 kill -9 Client 再重启，统计供应商侧收到的消息，确认没有重复；不确定是否发出的消息，由 Core 在 180 秒后按 2700 处理 |
| X-C14 | 多个 Client 节点 | 两个节点各自按 `OutgoingThrottlingNum` 限速（按约定不分摊），确认没有重复 |

### 4.2 执行过程中的调整

| 问题 | 原因 | 处理 |
|---|---|---|
| 第一版测试找不到刚写入的消息 | 测试自己计算的分片号与写入时不一致 | 改为按通道扫描路由 stream |
| 测试抛异常后进程没有退出 | 测试中有非守护线程 | 测试主方法改为总是调用 `exit()` |
| 配置了 `WorkerMaxPoolSize=4`，线程池仍是 50 | `workerMaxPoolSize()` 不允许小于核心数（默认 50），而新的线程池不再使用核心数 | **代码修正**：Client 的线程池只读 `WorkerMaxPoolSize`。修正后 C1-03 确实在 4 个 worker 下运行 |
