# MT 路由配置说明

> 日期：2026-11-13。依据《路由重构设计》和当前代码（`com.king.gmms.routing.rule`、`IOSMSChannelRouter`、`IOSMSRerouteDispatcher`、`MessageStoreManager.handleOutSubmitRes`）。这份文档讲**怎么配**：路由分几层、每层怎么选、失败了怎么改道，最后用 8 个例子把常见需求写出来。设计上的取舍见《路由重构设计》，测试见《路由重构测试用例清单》和 `RoutingRuleIT`。

## 1. 文件和格式

### 1.1 文件

| 文件 | 作用 |
|---|---|
| `conf/routing/{名称}_routingInfo.cfg` | 一个客户一个文件，`CCBSSID` 写客户的 ssid |
| `conf/routing/{业务类型}_default_routingInfo.cfg` | 默认路由：客户自己的规则都不命中时用。业务类型是客户的 `CustomerServiceType`（cm.cfg）；这个文件不写 `CCBSSID` |
| `conf/vendorRoutingReplacement.cfg` | 系统路由替换：通道出问题时临时换成另一个通道（第 6 节） |

改完执行 `RELOAD_ROUTING`（只加载有变化的文件），`RELOAD_ROUTING:-f` 全部重新加载。

### 1.2 一行配置

```text
CCBSSID: 8801
A2PMainRouting: (Priority=10,PhonePrefix=86,Sender=BANK,Relay=V1);(Priority=50,PhonePrefix=86,Relay=V2)
A2PBackupRouting: (Priority=10,PhonePrefix=all,Relay=V3)
```

- 一个配置名一行，一行里多条规则用 `;` 连接，每条规则写在 `()` 里，属性之间用 `,`。
- 同一个配置名可以写多行，加载时按顺序用 `;` 接成一行（规则合并，不会覆盖），所以发送方规则、前缀规则分开写几行 `A2PMainRouting:` 也可以。
- 属性名不区分大小写。

### 1.3 配置名：4 层 × 主路由和 10 级备份

| 层 | 主路由 | 备份 1 级 | 备份 2～10 级 |
|---|---|---|---|
| 1 二次路由 | `A2PSecRouting` | `A2PSecBackupRouting` | `A2PSecBackup2Routing` … `A2PSecBackup10Routing` |
| 2 号码路由 | `A2PNumberRouting` | 没有（用普通层的备份） | 没有 |
| 3 运营商路由 | `A2POPRouting` | `A2POPBackupRouting` | `A2POPBackup2Routing` … `A2POPBackup10Routing` |
| 4 普通路由（前缀） | `A2PMainRouting` | `A2PBackupRouting` | `A2PBackup2Routing` … `A2PBackup10Routing` |

注意备份 1 级写作 `A2PBackupRouting`（不是 `A2PBackup1Routing`），2 级起带数字。旧的 `A2P*RoutingRelay*`、`A2PBackup11Routing` 等**不生效**，加载时日志 `WARN [ROUTING] ... not used`。

### 1.4 规则的属性

| 属性 | 用在 | 必填 | 说明 |
|---|---|---|---|
| `Priority` | 全部 | 是 | 1～100，小的先匹配。只在**同一个分组**（同一层、同一级、同一个前缀 / 号码 / 运营商）里比较；同一分组里不能重复 |
| `Relay` | 全部 | 是 | 通道：`V1`；`V1:70,V2:30` 按权重随机；`V1,V2` 轮流。写通道的名称（cm.cfg 的块名，`_` 后缀会去掉）；号码、运营商规则也可以写 ssid 数字 |
| `PhonePrefix` | 二次、普通 | 否 | 接收号码前缀，`;` 分隔；不写或 `all` = 所有号码 |
| `Number` | 号码 | 是 | 完整接收号码，`;` 分隔 |
| `Opid` | 运营商 | 是 | 运营商 id，`;` 分隔：具体运营商（如 `860001`）、国家级 `国家码*10000`（如 `860000`）、`-2` = 所有运营商 |
| `Sender` | 全部 | 否 | 发送方，`;` 分隔，完全相等，不区分大小写 |
| `KeywordId` | 全部 | 否 | 内容关键字（`contentTemplate.cfg` 的模板 id），`;` 分隔，命中任何一个即可 |
| `ExcludeSender` | 全部 | 否 | 排除的发送方：发送方是其中之一时这条规则**不命中** |
| `ExcludeKeywordId` | 全部 | 否 | 排除的关键字：内容命中其中任何一个时不命中 |
| `ExcludePhonePrefix` | 二次、运营商、普通 | 否 | 排除的号段：接收号码以其中任何一个开头时不命中；必须在 `PhonePrefix` 之下（如 `PhonePrefix=86,ExcludePhonePrefix=86170`） |
| `ReplaceContentByTemplate` | 全部 | 否 | 发往这条规则的通道时按内容模板替换内容；`IsReplaceTemplateBySender=true` 时只对 `Sender` 里的发送方替换 |

**条件之间是“并且”**：写了的条件都满足、写了的排除条件都不满足，规则才命中。号码前缀、号码里的 `+` 会去掉再比较。

## 2. 主路由：分层

一条新 MT 按下面的顺序找，**某一层有规则命中，就用这一层**，不再看下面的层：

```text
          ┌─────────────── 客户自己的路由文件 ───────────────┐   ┌──── {业务类型}_default ────┐
新 MT ──> │ 1 二次路由 → 2 号码路由 → 3 运营商路由 → 4 普通路由 │──>│ 同样 4 层                  │──> 都不命中：从备份 1 级找（3.3），备份也没有才路由失败
          └──────────────────────────────────────────────────┘   └────────────────────────────┘
```

| 层 | 什么时候看 | 层内的分组顺序（由具体到宽泛） |
|---|---|---|
| 1 二次路由 | 客户开了 `smsOptionNeedSupportSecondRouting`，号码在 `SMSOptionSecondRoutingRecPrefix` 里，并且这个号码在最近 `smsOptionNeedSupportSecondRoutingExpiredTime` 秒（默认 300）里发过 MT（例如验证码重发换一个通道） | 前缀由长到短，最后 `all` |
| 2 号码路由 | 总是 | 号码完全相等 |
| 3 运营商路由 | MNP / ENUM 查到了接收号码的运营商 | 运营商 id → 国家级 → `-2` |
| 4 普通路由 | 总是 | 前缀由长到短，最后 `all` |

**为什么是这个顺序**：号码是最具体的条件；运营商是 MNP 查出的实际运营商（携号转网后比号段准）；二次路由是对“刚发过的号码”的覆盖，所以最先看。**运营商层总是压过普通层**，哪怕普通层的规则更具体，见例 3。

## 3. 层内怎么选

### 3.1 分组和优先级

```text
for 分组 in 这一层的分组（由具体到宽泛）:
    for 规则 in 分组里的规则（Priority 从小到大）:
        条件不满足 / 被排除 ──> 下一条规则
        命中 ──> 这条规则选通道，结束（命中即定）
    这个分组没有规则命中 ──> 下一个分组（更短的前缀 / 更宽的运营商 / all）
这一层都没命中 ──> 下一层
```

**优先级只在同一个分组里比较**。例如接收号码 `77012345678`，普通层有：

```text
A2PMainRouting: (Priority=1,PhonePrefix=7,Relay=V1);(Priority=2,PhonePrefix=77,Sender=BANK,Relay=V2);(Priority=5,PhonePrefix=77,Relay=V3);(Priority=9,PhonePrefix=all,Relay=V9)
```

分组顺序 `77` → `7` → `all`。先看 77：发送方 BANK 命中 Priority 2 → V2；其他发送方命中 Priority 5 → V3。`7` 的 Priority 1 虽然更小，但 77 已经有规则命中，不会用到它。`70…` 的号码没有 77 分组，用 7 → V1；`44…` 用 all → V9。

### 3.2 选通道

| Relay | 怎么选 |
|---|---|
| `V1` | V1 |
| `V1:70,V2:30` | 按权重随机（70% / 30%） |
| `V1,V2,V3` | 轮流（每条规则自己计数） |

接收号码在路由白名单里（或客户的“不再过滤”缓存里）时，取 Relay 里第一个不是 blackhole 的通道（同以前）。

### 3.3 命中了但通道不能用

| 情况 | 结果 |
|---|---|
| 通道不在 cm.cfg | 算“主路由没有找到路由”：**在选路时从备份 1 级开始找**（第 4 节的逐级规则），不再看主路由的下一条规则、更短的前缀或下一层；日志 WARN 写明规则和原因 |
| 通道的内容长度限制（`SMSSpecialSupportContentLengthByCountry`）不允许这条内容 | 同上，从备份找；例如便宜通道只能发短内容，长内容自动走备份通道（例 8） |
| 主路由一条规则都没命中 | 同上，从备份找（二次层、运营商层、普通层的备份） |
| 备份也找不到 | **路由失败** |
| 通道在 ROP 失败模式 | MT 进 SMQ，等通道恢复后发这个通道 |
| 系统路由替换把通道换成另一个 | 按替换后的通道判断上面几条（第 6 节） |

路由失败的 MT 和以前一样：DB 兜底、按客户配置回失败 DR。从备份选到的 MT 记着它的级别，之后这个通道发送失败，从下一级接着找。

## 4. 备份：失败后逐级改道

备份在两种时候用：**外发失败之后**（这一节），以及**主路由选不出能用的通道时**（3.3，从备份 1 级开始找，选法和这里一样）。

### 4.1 什么时候进下一级

| 失败 | 进下一级的条件 | 不满足时 |
|---|---|---|
| submit 失败（供应商回错误、超时等） | 失败码在**这次发送的通道**的 `SMSOptionSubmitRetryCode` 里（cm.cfg） | 直接回失败 DR，不改道、不重试 |
| DR 失败 | 这次发送的通道 `NeedDRReroute=true`，DR 不是 DELIVERED，在 `RerouteDRDelayTimeInSec`（默认 1800 秒）内，并且状态在 `SMSOptionDRRerouteCode` 里（没配列表 = 任何失败状态都算） | 写 `OUT_DELI_REP` CDR，再按假 DR 的配置决定是否给客户回 IN DR |

成功、`SUBMIT_RESP_ERROR`、`SUBMIT_NOTPAID`、`DELIVERED` 永远不改道。长短信只看第 1 段的结果。

### 4.2 逐级的顺序

```text
主路由（第 0 级）V1 发送失败（码在 V1 的 SMSOptionSubmitRetryCode 里）
  └ 第 1 级：主路由来自哪一层，就先看那一层的备份 1；没命中再看普通层的备份 1；
             客户自己的都没命中，再看默认路由文件的备份 1
             （规则的选法和主路由一样：分组由具体到宽泛，组内按 Priority）
       ├ 命中，选出一个没发过的通道 V4 ──> 发送；失败再到第 2 级 ...
       ├ 没有规则命中，或者 Relay 里的通道都发过了 ──> 直接看第 2 级
       └ 命中但通道不能用（不存在、长度不允许、ROP 失败）──> 跳到第 2 级
  ...一直到第 10 级
```

- **每一级只用一次**：一级选出的通道失败，进下一级，不会在同一级里换另一个通道（例如 `V4:50,V5:50` 选了 V4 失败，进下一级，不再试 V5）。
- **跳过发过的通道**：这条 MT 发过的所有通道（`routingSsIDs`）都不会再选。
- **级别可以不连续**：只配了 1 级和 3 级，就是 1 → 3。
- **改道次数**：客户的 `SMSOptionMaxReroute`（cm.cfg，默认 10）。到了就不再改道，按“级别用完”处理。
- 号码层没有备份：号码路由的通道失败，用普通层的备份。

### 4.3 级别用完之后

| 失败 | 级别用完后 |
|---|---|
| submit | 按重试策略（`RetryPolicy`）等一个间隔，**重试主路由的通道**（这条 MT 第一个发的那个通道）。主路由再失败、码在重试码里：不再走备份，等下一个间隔再重试主路由；码不在里面：回失败 DR。重试次数用完或 MT 过期：回失败 DR |
| DR | 把失败 DR 回给客户（按假 DR 的配置），不重试 |

### 4.4 消息记住到了哪一级

MT 上记着 `routingLevel`（0 = 主路由，1～10 = 备份级别）和 `routingRule`（命中的规则），写在 Stream 里；DB 的 `RoutingLevel` 列（`docs/sql/2026-11-13_routing_level.sql`，`DB.RoutingLevelColumn`）也会存。所以 Core 重启、换 Core、从 DB 重试之后，都从记住的级别接着往下走。DB 没有这一列时，从 DB 重试的 MT 从第 1 级找起，跳过发过的通道，不会重复发到同一个通道。

## 5. 排除条件

“除了某个发送方，其他都走通道 C”：

```text
A2PMainRouting: (Priority=10,PhonePrefix=86,ExcludeSender=BANK;OTP,Relay=C);(Priority=20,PhonePrefix=86,Relay=V1)
```

BANK、OTP 被优先级 10 排除，继续看同一前缀的下一条（优先级 20）→ V1；其他发送方 → C。同一前缀没有下一条时，被排除的 MT 会继续退到更短的前缀、`all`、下一层、默认路由，**就像这条规则不存在一样**，这是排除条件和“先写一条 BANK 的规则”的区别（例 2）。

## 6. 系统路由替换

`conf/vendorRoutingReplacement.cfg`，每行 `前缀:ossid:原通道ssid:替换通道ssid`（ossid `-1` = 所有客户，前缀 `all` = 所有号码），修改后 `RELOAD_SYSTEM_REPLACE`：

```text
86:-1:81:82
86:8801:81:84
```

- 规则选出原通道后，换成替换通道再发；**客户级的优先**（上例客户 8801 的 81 → 84，其他客户 81 → 82）。
- 只换一次（81 → 82 后不再查 82 的替换）。
- 主路由和每一级备份都替换；“通道能不能用”、“这条 MT 发过没有”、改道码，**都按替换后的通道**判断（例 6）。

## 7. 加载和检查

| 情况 | 结果 |
|---|---|
| 缺 `Priority`、`Priority` 不是 1～100、缺 `Relay`、号码规则缺 `Number`、运营商规则缺 `Opid` | **这个文件**加载失败，保留它原来的路由，其他文件照常生效；日志 ERROR 写明文件、配置名和第几条规则；`routing.result=partial` |
| 同一分组里两条规则 `Priority` 相同 | 同上（哪条先不明确） |
| `Sender` 和 `ExcludeSender` 有相同的值；`ExcludePhonePrefix` 不在 `PhonePrefix` 之下 | 同上（写错的规则会悄悄不生效） |
| 旧配置名、未知的 `A2P…Routing` 名、第 11 级以上 | 不生效，WARN `[ROUTING]` |
| `Relay` 的通道不在 cm.cfg | 加载成功，WARN；命中这条规则的 MT 从备份找（主路由），或跳到下一级（备份） |
| `Relay` 里有 `;` | `;` 后面不生效，WARN |

加载后整套规则一次替换，并写进 Redis（7.1）。

### 7.1 在 Redis 里看路由

Redis（state）里有两类路由信息，**以 `Rules` 为准**：

| key | 是什么 | 谁写、什么时候写 |
|---|---|---|
| `routingInfo{Core 模块名}.Rules:{文件名}` | **内存里实际在用的规则**：从加载好的规则直接生成，只有生效的规则，通道是解析后的 ssid | 每个 Core 一套：启动时、每次 `RELOAD_ROUTING` 后 |
| `config:file:routing:{版本}`（及 `:channel`、`:channelRoutes`） | 路由**文件的文本**（每个文件：配置名 → 值，同名多行合并后的样子），以及“通道被哪些客户的哪些规则用”的索引 | 每个模块：启动时、每次 reload 后（《配置项说明》2.4） |

`config:file:routing` 是“文件里写了什么”：旧配置名、第 11 级以上这些不生效的行也在里面，通道是名字；加载失败的文件是它还在用的旧版本。要看“现在实际怎么路由”，看 `Rules`。

**`Rules:{文件名}` 的格式**（Hash），文件名是去掉 `_routingInfo.cfg` 的部分，例如 `CUST8801`、`OTP_default`：

| 字段 | 值 |
|---|---|
| `_file` | `CCBSSID=8801`（客户的文件），或 `default of service type OTP`（默认路由文件） |
| `_warnings` | 加载时被忽略的配置，` \| ` 分隔（例如旧配置名、不支持的级别、Relay 里不在 cm.cfg 的通道）；没有就没有这个字段 |
| `{层}:{级}:{分组}:{优先级}` | 一条规则，值是 JSON（见下）。一条规则写了几个前缀 / 号码 / 运营商，就有几个字段 |

- 层：`second`、`number`、`op`、`main`；级：`0` 主路由，`1`～`10` 备份；分组：前缀（`all` = 所有号码）、号码或运营商 id。
- 规则的 JSON：

  | 键 | 说明 |
  |---|---|
  | `Relay` | 通道 **ssid**：`81`；按权重 `81:70,82:30`；轮流 `81,82`。`-1` = 名字不在 cm.cfg（命中这条规则的 MT 会去找备份，见 3.3） |
  | `Sender`、`ExcludeSender` | 发送方（小写），`;` 分隔 |
  | `KeywordId`、`ExcludeKeywordId`、`ExcludePhonePrefix` | 同规则的属性（号码去掉了 `+`） |
  | `ReplaceContentByTemplate`、`IsReplaceTemplateBySender` | 内容模板 |
  | `Source` | 规则在文件里的位置：`{文件名} {配置名} #{第几条}` |

例：客户 CUST8801（ssid 8801）的文件

```text
CCBSSID: 8801
A2PMainRouting: (Priority=10,PhonePrefix=86;852,Sender=BANK,Relay=V1);(Priority=50,PhonePrefix=86,Relay=V1:70,V2:30)
A2PBackupRouting: (Priority=10,PhonePrefix=all,Relay=V9)
A2PRoutingRelay: (PhonePrefix=86,Relay=V3)
```

在 Core `CoreEngine1` 上是：

```text
HGETALL routingInfoCoreEngine1.Rules:CUST8801
_file           CCBSSID=8801
_warnings       A2PRoutingRelay: the old routing config name is not used any more (docs/路由重构设计.md 第 5 节), convert it
main:0:86:10    {"Relay":"81","Sender":"bank","Source":"CUST8801 A2PMainRouting #1"}
main:0:852:10   {"Relay":"81","Sender":"bank","Source":"CUST8801 A2PMainRouting #1"}
main:0:86:50    {"Relay":"81:70,82:30","Source":"CUST8801 A2PMainRouting #2"}
main:1:all:10   {"Relay":"89","Source":"CUST8801 A2PBackupRouting #1"}
```

常用查法：

```text
SMEMBERS routingkey                                       所有 Core 的所有 Rules key
HGETALL  routingInfoCoreEngine1.Rules:CUST8801           这个客户在 CoreEngine1 上的规则
HSCAN    routingInfoCoreEngine1.Rules:CUST8801 0 MATCH main:1:*   备份 1 级的规则
```

`Rules` 里没有的：系统路由替换（`vendorRoutingReplacement.cfg`，选通道时才做）；客户没有自己的文件时用的是哪个 `_default` 文件（看客户的 `CustomerServiceType`）。

## 8. 日志和 CDR

| 日志 | 例子 |
|---|---|
| 选路 | `[MT-ROUTE] ossid=8801 rssid=81 by main prefix=86 priority=10 file=CUST8801` |
| 选路被替换 | `... by main prefix=86 priority=10 file=CUST8801 rule=81 replaced=82` |
| 没有规则 | `[MT-ROUTE] ossid=8801 no routing rule matched (recipient=..., sender=..., opid=...)` |
| 通道不能用 | `[MT-ROUTE] ossid=8801 rssid=99 by main ... channel 99 not in cm.cfg: routing failed` |
| 改道 | `[MT-REROUTE] level=2 from=83 to=84 code=2500 attempt=2 by main backup2 prefix=86 priority=10 file=CUST8801` |
| 不改道 | `[MT-REROUTE] not rerouted: status 10208 not in SMSOptionSubmitRetryCode of rssid 83` |
| 级别用完 | `[MT-REROUTE] backup levels used up (level 3, rssid 86): retried on the main route rssid 81` |
| 排除（DEBUG） | `[MT-ROUTE] CUST8801 A2PMainRouting #1 not matched by ExcludeSender=bank` |

**CDR 的 MsgID 列**：主路由的 CDR（包括级别用完后重试主路由）是 `msgId`；备份通道的 CDR 是 `msgId-{通道 ssid}`；`IN_DELI_REP` 总是 `msgId`（例 4）。

## 9. 例子

下面的例子里，通道 V1～V9、C、C2 在 cm.cfg 里（ssid 分别是 81～89、90、91），都在同一个 A2P；除非另说，每个通道配了 `SMSOptionSubmitRetryCode: 2500`（2500 = 通讯错误）和重试策略 `SMSOptionMTRetryPolicy: 1M,5M`；客户是 `CUST8801`（ssid 8801）。

### 例 1：按国家、号段和发送方分流

需求：中国走 V1；中国移动号段 135～139 走 V2；发送方 BANK 发往中国的都走 V3；香港走 V4；其他国家走 V9。

```text
CCBSSID: 8801
A2PMainRouting: (Priority=50,PhonePrefix=86,Relay=V1);(Priority=50,PhonePrefix=86135;86136;86137;86138;86139,Relay=V2);(Priority=10,PhonePrefix=86;86135;86136;86137;86138;86139,Sender=BANK,Relay=V3);(Priority=50,PhonePrefix=852,Relay=V4);(Priority=50,PhonePrefix=all,Relay=V9)
```

| MT | 结果 | 为什么 |
|---|---|---|
| 8613800000000，发送方 OTP | V2 | 最长前缀 86138，组内只有 Priority 50 的规则 |
| 8613800000000，发送方 BANK | V3 | 86138 组里 Priority 10 的 BANK 规则先于 50 |
| 8615000000000，发送方 BANK | V3 | 没有 86150 的组，退到 86，组里 BANK 规则 Priority 10 |
| 8615000000000，发送方 bank | V3 | 发送方不区分大小写 |
| 85212345678 | V4 | |
| 447700900000 | V9 | `all` |

要点：BANK 的规则要**同时写在 86 和 86135～86139 下**。只写在 86 下，号段 86138 的组先被看到，组里有规则命中（V2），就到不了 86 的 BANK 规则。如果希望 BANK 不管号段都按 86 的规则走，也可以反过来，在号段组里用排除条件把 BANK 排除掉，让它退到 86（见例 2 的写法）。

### 例 2：除了某几个发送方，其他都走通道 C

需求：中国的验证码通道 C 很便宜但不稳定，除了 BANK、PAY 两个重要发送方，其他都走 C；BANK、PAY 走原来的规则（号段 86138 走 V2，其余中国号码走 V1）。

```text
CCBSSID: 8801
A2PMainRouting: (Priority=10,PhonePrefix=86,ExcludeSender=BANK;PAY,Relay=C);(Priority=50,PhonePrefix=86,Relay=V1);(Priority=10,PhonePrefix=86138,ExcludeSender=BANK;PAY,Relay=C);(Priority=50,PhonePrefix=86138,Relay=V2)
```

| MT | 结果 |
|---|---|
| 8615000000000，OTP | C（86 组 Priority 10） |
| 8615000000000，BANK | V1（Priority 10 排除了 BANK，下一条 Priority 50） |
| 8613800000000，OTP | C（86138 组 Priority 10） |
| 8613800000000，PAY | V2（86138 组 Priority 10 排除了 PAY，下一条 Priority 50） |

同样的需求，**只想让 BANK、PAY 回到“没有这条规则时的路由”**，又不想在每个号段组里都写一遍，可以只在需要的组里加排除规则、不写同组的下一条：

```text
A2PMainRouting: (Priority=10,PhonePrefix=86138,ExcludeSender=BANK;PAY,Relay=C);(Priority=50,PhonePrefix=86,Relay=V1)
```

8613800000000 的 BANK：86138 组没有规则命中 → 退到 86 → V1。这就是排除条件比“先写一条 BANK 的规则”多出来的能力：被排除的 MT 当这条规则不存在。

其他排除条件的写法：

| 需求 | 写法 |
|---|---|
| 营销内容（关键字 5、6）不走 C | `(Priority=10,PhonePrefix=86,ExcludeKeywordId=5;6,Relay=C)` |
| 中国除了 170、171 号段都走 C | `(Priority=10,PhonePrefix=86,ExcludePhonePrefix=86170;86171,Relay=C)` |
| 只有 BANK 走 C，但 BANK 的验证码（关键字 3）不走 C | `(Priority=10,PhonePrefix=86,Sender=BANK,ExcludeKeywordId=3,Relay=C)` |

### 例 3：运营商路由和号码路由

需求：查到是中国移动（860001）的走 V5，中国其他运营商走 V6；测试号码 8613800000000 固定走 V7；查不到运营商的按普通路由走 V1；BANK 发往中国移动的仍走 V3。

```text
CCBSSID: 8801
A2PNumberRouting: (Priority=1,Number=8613800000000,Relay=V7)
A2POPRouting: (Priority=10,Opid=860001,Sender=BANK,Relay=V3);(Priority=50,Opid=860001,Relay=V5);(Priority=50,Opid=860000,Relay=V6)
A2PMainRouting: (Priority=10,PhonePrefix=86,Sender=BANK,Relay=V3);(Priority=50,PhonePrefix=86,Relay=V1)
```

| MT | 查到的运营商 | 结果 | 为什么 |
|---|---|---|---|
| 8613800000000，BANK | 860001 | V7 | 号码层最先 |
| 8613900000000，OTP | 860001 | V5 | 运营商层 |
| 8613900000000，BANK | 860001 | V3 | 运营商层组内 BANK 规则 Priority 10 |
| 8618900000000，OTP | 860003 | V6 | 没有 860003 的组，退到国家级 860000 |
| 8618900000000，OTP | 没查到 | V1 | 不看运营商层 |

要点：普通层里 BANK → V3 的规则**挡不住运营商层**。要“BANK 不管哪个运营商都走 V3”，运营商层里也要写一条带 `Sender=BANK` 的规则（上面的 Priority 10 那条）。

### 例 4：逐级备份和 CDR

需求：中国主路由 V1；V1 失败先换 V2（BANK 换 V3）；再失败在 V4、V5 里按 50/50 选一个；再失败用全球通道 V9；都失败就等一会儿重试 V1。

```text
CCBSSID: 8801
A2PMainRouting:    (Priority=10,PhonePrefix=86,Relay=V1)
A2PBackupRouting:  (Priority=10,PhonePrefix=86,Sender=BANK,Relay=V3);(Priority=20,PhonePrefix=86,Relay=V2)
A2PBackup2Routing: (Priority=10,PhonePrefix=86,Relay=V4:50,V5:50)
A2PBackup3Routing: (Priority=10,PhonePrefix=all,Relay=V9)
```

一条 OTP 发往 8615000000000 的 MT（msgId `M1`），每个通道都回 2500：

| 步骤 | 通道 | 级别 | `OUT_SUBMIT` CDR 的 MsgID | 日志 |
|---|---|---|---|---|
| 1 | V1（81） | 0 | `M1` | `[MT-ROUTE] ... by main prefix=86 priority=10` |
| 2 | V2（82） | 1 | `M1-82` | `[MT-REROUTE] level=1 from=81 to=82 code=2500 attempt=1` |
| 3 | V4（84）或 V5（85），这里是 V4 | 2 | `M1-84` | `level=2 from=82 to=84 ... attempt=2` |
| 4 | V9（89）（不再试 V5） | 3 | `M1-89` | `level=3 from=84 to=89 ... attempt=3` |
| 5 | 1 分钟后重试 V1 | 3（不变） | `M1` | `backup levels used up (level 3, rssid 89): retried on the main route rssid 81` |
| 6 | V1 又失败：不再走备份，5 分钟后再重试 V1 | 3 | `M1` | `not rerouted: no backup level after level 3 (rssid=81, ...)` |
| 7 | 重试次数用完 | | | 失败 DR 回客户 |

同一时刻发送方 BANK 的 MT：第 2 步是 V3（备份 1 里 BANK 规则 Priority 10 先命中）。

如果第 2 步 V2 回的是 `10208`（不在 V2 的 `SMSOptionSubmitRetryCode` 里，例如号码不存在）：不进第 2 级，直接回失败 DR。

如果 V2 **没配** `SMSOptionSubmitRetryCode`：V2 的任何失败都直接回失败 DR。所以要改道的通道一定要配好重试码。

### 例 5：二次路由和默认路由

需求：验证码重发（5 分钟内同一个号码第二次）换到 V8；业务类型 OTP 的客户没有自己的路由文件时，中国统一走 V1、备份 V2。

客户 cm.cfg：

```text
[CUST8801]
CCBSSID: 8801
CustomerServiceType: OTP
smsOptionNeedSupportSecondRouting: true
smsOptionNeedSupportSecondRoutingExpiredTime: 300
SMSOptionSecondRoutingRecPrefix: 86
```

`conf/routing/CUST8801_routingInfo.cfg`：

```text
CCBSSID: 8801
A2PSecRouting: (Priority=10,PhonePrefix=86,Relay=V8)
A2PMainRouting: (Priority=10,PhonePrefix=86,Relay=V1)
```

`conf/routing/OTP_default_routingInfo.cfg`（所有业务类型 OTP 的客户共用，不写 CCBSSID）：

```text
A2PMainRouting: (Priority=10,PhonePrefix=86,Relay=V1)
A2PBackupRouting: (Priority=10,PhonePrefix=86,Relay=V2)
```

| MT | 结果 |
|---|---|
| CUST8801 第一次发 8615000000000 | V1（号码不在二次路由缓存里），之后号码进缓存 300 秒 |
| 2 分钟后同一个号码再发 | V8（二次路由层） |
| 10 分钟后再发 | V1（缓存过期） |
| 另一个 OTP 客户 CUST8802（没有自己的路由文件）发中国 | V1（默认路由） |
| CUST8802 的 V1 失败（2500） | V2（默认路由的备份 1） |
| CUST8801 的 V1 失败（2500） | V2（客户自己没有备份 1，看默认路由的备份 1） |

### 例 6：通道出问题时临时替换

V1（81）出问题，运维要把中国的流量临时切到 V2（82），而备份 1 里也写了 V2：

```text
CUST8801_routingInfo.cfg:
A2PMainRouting:    (Priority=10,PhonePrefix=86,Relay=V1)
A2PBackupRouting:  (Priority=10,PhonePrefix=86,Relay=V2)
A2PBackup2Routing: (Priority=10,PhonePrefix=86,Relay=V3)

vendorRoutingReplacement.cfg:
86:-1:81:82
```

| 步骤 | 结果 |
|---|---|
| 主路由选 V1，替换成 V2 | 发 V2；日志 `rule=81 replaced=82` |
| V2 失败（码在 **V2** 的重试码里） | 第 1 级选 V2：V2 刚发过 → 这一级没有可用通道 → 第 2 级 V3 |
| 备份 1 写的是 V1 时 | V1 也会被替换成 V2，同样算发过，跳到第 2 级 |

替换不会让消息在同一个坏通道上反复发。替换取消（删掉这一行、`RELOAD_SYSTEM_REPLACE`）之后，新的 MT 按规则走 V1。

### 例 7：常见的错误写法

| 写法 | 问题 | 结果 |
|---|---|---|
| `A2PMainRouting: (PhonePrefix=86,Relay=V1)` | 缺 `Priority` | 文件加载失败，保留原来的路由 |
| `(Priority=10,PhonePrefix=86,Relay=V1);(Priority=10,PhonePrefix=86,Sender=BANK,Relay=V2)` | 同一个前缀两条 Priority 10 | 文件加载失败；把 BANK 那条改成 5 |
| `(Priority=10,PhonePrefix=86,Sender=BANK,ExcludeSender=BANK,Relay=V1)` | 发送方既要又排除 | 文件加载失败 |
| `(Priority=10,PhonePrefix=86,ExcludePhonePrefix=852,Relay=V1)` | 排除的号段不在 86 之下，排除不会生效 | 文件加载失败 |
| `A2PBackup1Routing: ...` | 1 级的名字是 `A2PBackupRouting` | WARN，不生效 |
| 只配了 `A2PBackupRouting` 没有 `A2PMainRouting` 的前缀 | 主路由没有这个前缀 | 新 MT 直接从备份 1 级选（日志 `no main routing rule matched`）；能用，但最好补上主路由 |
| `A2PRoutingRelay: (PhonePrefix=86,Relay=V1)` | 旧配置名 | WARN，不生效，要转换（第 10 节） |

### 例 8：长内容走备份通道

需求：V1 便宜但中国只能发 50 字节以内的内容，长内容走 V2。

cm.cfg 里 V1 的配置：

```text
SMSSpecialSupportContentLengthByCountry: (prefix=86,value=50::deny)
```

路由：

```text
CCBSSID: 8801
A2PMainRouting:   (Priority=10,PhonePrefix=86,Relay=V1)
A2PBackupRouting: (Priority=10,PhonePrefix=86,Relay=V2)
```

| MT | 结果 |
|---|---|
| 短内容 | V1（主路由），`routingLevel=0` |
| 60 字节的内容 | V1 不允许 → 选路时从备份 1 级找 → V2，`routingLevel=1`；日志 `[MT-ROUTE] ... content length not allowed by channel 81: by main backup1 prefix=86 priority=10` |
| 长内容发 V2 失败（码在 V2 的重试码里） | 从第 2 级接着找；这里没有第 2 级 → 按重试策略重试 V2（这条 MT 第一个发的通道） |

## 10. 从旧配置转换

旧的配置名不再生效，升级前要转换：

| 旧配置 | 新配置 | 建议的 Priority |
|---|---|---|
| `A2PSenderRoutingRelay` | `A2PMainRouting`，带 `Sender` | 10 |
| `A2PContentKeywordRoutingRelay` | `A2PMainRouting`，带 `KeywordId` | 20 |
| `A2PRoutingRelay` | `A2PMainRouting` | 30 |
| `A2PNumberRoutingRelay` | `A2PNumberRouting` | 原来的 `Priority` |
| `A2POPSenderRoutingRelay` / `A2POPContentKeywordRoutingRelay` / `A2POPRoutingRelay` | `A2POPRouting`，带 `Sender` / `KeywordId` / 不带 | 10 / 20 / 30 |
| `A2PSec*RoutingRelay` | `A2PSecRouting` … 同普通层 | 同普通层 |
| `...Backup...RoutingRelay`（无数字） | 对应层的 `...BackupRouting` | 同上 |
| `...Backup...RoutingRelay1`～`9` | 对应层的 `...Backup2Routing`～`...Backup10Routing` | 同上 |

转换时注意：

1. **同一层的几个旧配置都改成同一个名字**（旧的发送方路由、关键字路由、前缀路由都变成 `A2PMainRouting`，可以分几行写，加载时合并），注意合并后同一前缀里的 `Priority` 不能重复。
2. **旧的发送方 / 关键字路由不看号段长短**（发送方规则总是先于前缀规则）。新规则先按最长前缀分组，所以旧的 `(PhonePrefix=86,Sender=BANK)` 要在 86 下面的每个更长前缀里也写一份，结果才和以前一样（例 1 的写法）。
3. **主路由没有命中、或通道不能用时**：和以前一样会用备份，但不再先看主路由的其他类（以前号码路由的通道不能用会掉到运营商、前缀路由，现在直接从备份找）。
4. Relay 里的通道要都在 cm.cfg 里：写错的通道会让消息一直走备份（日志 WARN）。
5. **改道要配重试码**：以前 submit 几乎所有失败都改道，现在只有失败码在通道的 `SMSOptionSubmitRetryCode` 里才改道。
6. 每级只用一次：以前备份是 `V4,V5` 时会在同一级里换着试，现在试一个就进下一级；需要都试的，把 V5 拆到下一级。
