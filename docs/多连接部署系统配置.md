# 多连接部署：机器系统配置

> 依据：2026-11-20 在测试服务器（16 核 / 61 GB，CentOS 7）上跑 `PF008_multiconn`：2000 个客户、2000 个通道，各 8 个 bind（每个 Server 8000 个客户连接，每个 Client 8000 个通道连接），1000 TPS 稳定。用例和步骤见《性能测试部署与执行手册》、`regression/routetest/cases/PF008_multiconn/README.md`。

## 1. 先算清楚要多少

a2p 的 SMPP 会话是**每个会话固定几个线程**（阻塞 IO），所以连接数直接决定线程数，线程数又决定内存映射数和进程数。实测：

| 模块 | 每个会话的线程 | 本次会话数 | 线程总数 | 内存映射（每线程约 2.06 个） | 文件句柄 |
|---|---|---|---|---|---|
| MultiSmppClient（每个） | 5：2 个 `CustReceiver`、`Sender`、`Receiver`、`ClientSessionThread` | 8000 | 约 40,100 | 约 83,000 | 约 8,300 |
| MultiSmppServer（每个） | 2：`Sender`、`Receiver` | 8000 | 约 16,100 | 约 33,000 | 约 8,300 |
| CoreEngine、MQM | 与连接数无关 | — | 约 100 | 约 600 | 约 300 |

估算公式（N = 该模块的会话数）：

- Client：线程 ≈ 5N + 100，内存映射 ≈ 10.3N + 1000，句柄 ≈ N + 300
- Server：线程 ≈ 2N + 100，内存映射 ≈ 4.2N + 500，句柄 ≈ N + 300
- 整机线程 = 各模块之和；本次 2 个 Client + 2 个 Server ≈ 11.3 万个线程

**通道的会话数**：`OutgoingConnection` 的 `SessionNumber` 是整个通道的会话数，按 Client 模块数平分（有余数时向上取整）。2 个 Client 时 `SessionNumber=8` 是每个 Client 4 个。**客户的会话数**：`IncomingConnection` 的 `SessionNumber` 是每个 Server 上允许的会话数，不平分。

## 2. 要改的系统配置

| 项 | 默认 / 测试机现值 | 本次规模需要 | 建议值 | 不改的后果 |
|---|---|---|---|---|
| `vm.max_map_count`（**每个进程**的内存映射上限） | 65530 / 测试机已临时改为 262144 | Client 约 8.3 万 | **262144**（每个 Client 超过约 2.4 万个会话时再加） | **Client 启动时建不了线程**（`OutOfMemoryError: unable to create native thread`），6000 多个会话就会碰到 |
| `kernel.pid_max` | 32768（多数发行版）/ 测试机 4194304 | 整机约 11.3 万个线程 | **4194304** | 线程号用完，新线程创建失败 |
| `kernel.threads-max` | 按内存算 / 测试机 4194304 | 同上 | 不小于 `pid_max` 的需要 | 同上 |
| 运行用户的 `nproc`（`ulimit -u`，**按用户统计所有线程**） | 4096 或按内存算 / 测试机 252888 | 约 11.3 万 | **≥ 262144** | 同一用户的线程总数超了就建不了线程 |
| 运行用户的 `nofile`（`ulimit -n`，每个进程） | 1024 / 测试机 65535 | 每个 Client、Server 约 8300 | **65535**（每个模块超过约 6 万个会话前够用） | `Too many open files`，新连接失败 |
| systemd 的 `TasksMax`（用 systemd 启动、或登录会话受 logind 限制时） | 视版本而定 | 每个服务 / 会话的线程数 | 服务里 `TasksMax=infinity`，或不小于上面的线程数 | 线程数到上限后新建失败，现象同上 |
| `net.core.somaxconn` | 128 / 测试机 128 | 客户集中重连（Server 重启后 8000 个连接一起来） | **4096** | 只改它不够，见第 3 节 backlog |
| `net.ipv4.tcp_max_syn_backlog` | 1024 / 测试机 1024 | 同上 | **4096** | 握手队列满时丢 SYN，客户重连变慢 |
| `net.ipv4.ip_local_port_range` | 32768–60999 / 测试机同 | 每个"目标 IP:端口"最多约 2.8 万个连接 | 同一 SMSC 地址上的总连接数接近 2 万时改成 `10000 65000` | 连同一个通道地址的连接建不起来 |

其他相关项测试机已够用，不用改：`fs.file-max` 6,419,182、`fs.nr_open` 1,048,576、`net.ipv4.tcp_mem`（3.2 万个连接时 TCP 内存占用很小）。

### 2.1 怎么改（永久生效）

```bash
# /etc/sysctl.d/99-a2p-multiconn.conf
vm.max_map_count = 262144
kernel.pid_max = 4194304
kernel.threads-max = 4194304
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 4096
# 同一 SMSC 地址上的连接很多时再加：
# net.ipv4.ip_local_port_range = 10000 65000
```
`sysctl --system` 生效（`vm.max_map_count` 对已经在运行的进程也立即生效，不用重启 a2p）。

```bash
# /etc/security/limits.d/99-a2p.conf（a2p 的运行用户，测试机是 root）
root soft nofile 65535
root hard nofile 65535
root soft nproc  262144
root hard nproc  262144
```
重新登录后生效，用 `ulimit -n -u` 确认；已经在运行的进程看 `/proc/<pid>/limits`。用 systemd 管理 a2p 时改服务的 `LimitNOFILE`、`LimitNPROC`、`TasksMax`。

**注意**：CentOS 7 的 `sysctl --system` 按文件名顺序加载 `/etc/sysctl.d/`，**最后还会再加载一次 `/etc/sysctl.conf`**。所以 `/etc/sysctl.conf` 里已经写了的项（测试机原来有 `net.ipv4.tcp_max_syn_backlog = 1024`）要直接改那一行，放在 `sysctl.d` 里会被覆盖。

**测试机现状**（2026-11-20 已永久生效）：`/etc/sysctl.d/zz-a2p-multiconn.conf`（`vm.max_map_count`、`kernel.pid_max`、`kernel.threads-max`、`net.core.somaxconn`），`/etc/sysctl.conf` 第 30 行 `net.ipv4.tcp_max_syn_backlog = 4096`（原文件备份为 `/etc/sysctl.conf.bak.20261120_multiconn`），`/etc/security/limits.d/99-a2p.conf`（root 的 `nofile` 65535、`nproc` 262144）。

## 3. 应用侧相关项（不是系统配置，但会受连接数影响）

| 项 | 现状 | 影响 | 建议 |
|---|---|---|---|
| Server 监听 backlog | `AbstractServer` 用 `new ServerSocket(port)`，Java 默认 **50**（`ss -ltn` 看到 16272、16273 的队列上限 50），调大 `somaxconn` 也没用 | 实测同时 4000 个连接：SYN 被丢 12087 个，建连 p99 7.3 秒（《多连接性能分析与优化设计》2.6）。Server 重启后客户一起重连时会出现，客户端连接超时短的会连不上 | 改代码：backlog 做成配置项，默认 4096；`somaxconn` 不小于它 |
| 线程栈 | `a2pStart.sh` 用 `-Xss512k`（`A2P_JVM_XSS`） | 4 万个线程预留约 20 GB 虚拟地址，实际占用很小：Client RSS 约 2.5 GB（堆 2 GB） | 不用改；内存紧时可试 256k，但要先确认没有深递归 |
| 每个会话的线程数 | Client 5 个、Server 2 个 | 线程数和内存映射数随会话数线性增长，是这类部署的主要限制 | 长期看要改成共享线程（NIO 或线程池），本文档只列当前版本需要的系统配置 |
| Client 启动 | 会话按顺序初始化，每个约 10 ms | 8000 个会话约 2～3 分钟才全部建完；这段时间新会话陆续上线 | 规划重启窗口时算上 |
| 连接数限制 | `SmppServerMaxConnections`、`SmppServerMaxConnectionsPerIp` 默认 0（不限） | — | 线上可按客户数设上限，防止异常重连撑爆线程 |

## 4. 测试工具（压测时和 a2p 在同一台机器上）

`rt.RouteCase` 也是每个连接一个线程：本次 1.6 万个客户连接 + 接受 1.6 万个通道连接，约 2.4 万～3.2 万个线程。所以要同样满足上面的 `vm.max_map_count`、`nproc`、`nofile`（这个进程有 3 万多个句柄）。运行时用 `RT_JAVA_OPTS="-Xss256k"`（`bin/run_case.sh`）把线程栈调小。线上没有这一项。

## 5. 检查清单

```bash
sysctl vm.max_map_count kernel.pid_max kernel.threads-max net.core.somaxconn net.ipv4.tcp_max_syn_backlog net.ipv4.ip_local_port_range
ulimit -n -u
for m in MultiSmppClient1 MultiSmppServer1; do p=$(pgrep -f "Dmodule=$m " | head -1)
  echo "$m threads=$(ls /proc/$p/task | wc -l) maps=$(wc -l < /proc/$p/maps) fds=$(ls /proc/$p/fd | wc -l)"
  grep -E "Max open files|Max processes" /proc/$p/limits; done
ss -ltn | grep -E ":(16272|16273) "      # Recv-Q / Send-Q：accept 队列
```
运行中 `maps` 要远小于 `vm.max_map_count`，`fds` 要远小于 `Max open files`，所有 a2p 进程的线程总数要远小于 `nproc` 和 `pid_max`。
