# Core 第 6 批：测试用例与执行报告（供应商 DR 与出向结果的重投去重）

> 设计见《Core第6批优化设计》。同时对前几批和通道限速做全量回归。第 1 到 3 节是用例设计，第 4 节是执行结果。

## 1. 测试环境

与之前的报告相同：本地 Redis 7.2.5，JDK 17，真实的 Core 初始化，没有数据库。

新增测试套件 `Batch6IT`。`ConfigReloadIT` 增加了 `CoreDrResultIdempotency` 的热加载检查。

崩溃和"确认消费失败"的模拟方法：
- 第一次处理在一个单独的线程里执行，处理完后线程直接结束，不确认消费。如果要模拟"确认消费失败"，就在结束前执行 `finish()` 中确认消费之前的那部分步骤（写入 `_done`、执行推迟的清理动作）。
- 重投时用 `XAUTOCLAIM` 重新领取同一条记录，再交给消费者真实的处理方法 `processMessage` / `processResult`。
- 测试里把占用超时缩短为 0.8 秒。

## 2. 用例

### 2.1 供应商 DR 路径

| ID | 场景 | 预期 | 套件：检查 | 级别 |
|---|---|---|---|---|
| B6-01 | DR 处理完、已写入 `_done`，但确认消费失败，随后重投 | 第一次处理：给客户写出 1 条 DR、写 1 条 OUT_DELI_REP CDR，`_done` 写入后删除反查缓存。重投时：只确认消费，没有第二条 DR 或 CDR，**没有**转去 DB/SDQ，删除标记 | Batch6IT：`B6-01a` 到 `B6-01e` | P0 |
| B6-02 | DR 写出后、写入 `_done` 前进程崩溃，随后重投 | 反查缓存仍在（删除被推迟到 `_done` 之后）。重投时能找到原消息、走同样的处理分支，不产生第二条 DR 或 CDR，处理结束后才删除反查缓存 | Batch6IT：`B6-02a` 到 `B6-02d` | P0 |
| B6-03 | 对照：关闭去重开关后重投 | 重投时查不到反查缓存，转去 DB/SDQ（即原来的问题） | Batch6IT：`B6-03` | P1 |
| B6-08 | 两个消费者同时处理同一条 DR | 后来的消费者发现已被占用，不处理，这条记录留在待确认列表 | Batch6IT：`B6-08` | P0 |

### 4.1 性能（B6-09，800 条供应商 DR，预热后比较）

| 运行 | 关闭去重 | 打开去重 | 增加 |
|---|---|---|---|
| 最终全量回归（记录在案） | 6028 ms | 6595 ms | +9.4% |
| 调试期间的几次执行（只记录了范围） | 约 5.6 到 6.3 秒 | 约 6.4 到 6.9 秒 | 约 7% 到 10% |

本地 Redis 的往返时间很短，每条 DR 多出的 2 次 Redis 访问占比不大。线上往返时间更长，这部分开销的比例会更高，预计仍在设计时估算的约 20% 以内（见 X-62，需在压测中确认）。如果某个供应商的 DR 量确实受到影响，可以把 `CoreDrResultIdempotency` 设为 false，或者再把供应商 DR 的 stream 按分片拆开（另行安排）。

### 4.2 执行过程中的调整（都是测试代码的问题，不是产品问题）

| 问题 | 原因 | 处理 |
|---|---|---|
| 性能测试第一版中，"打开去重"反而更快 | 先运行的一轮 JVM 还没预热 | 改为"关、开、关、开"交替，只取后两轮比较 |
| R5-04a 统计到 0 个线程 | 本批之后，结果的确认消费改走 `StreamAttempt.finish`（Lua），不再打印 `STREAM-ACK` 日志 | 改为按每条结果都会打印的 `STREAM-GET` 日志统计 |
| RACE-03 失败 | 用例使用的是 MT 门铃集合，而套件里后台运行的 MT 分发线程也会清理空 stream 的门铃，两者冲突；之前能通过只是凑巧 | 改为使用没有消费者的独立门铃集合 |
| 旧测试编译失败 | `MtAttempt` 改名为 `StreamAttempt` | 测试代码同步改名 |
