# 5000 TPS（Redis 2+2 主）慢在哪里

> 日期：2026-11-18。代码和部署同《Redis多主分片设计》第 10 节。用例 `cases/PF002_cmd`（混合流量 5000 TPS × 60 秒，预热 10 秒）；测试前清空 Redis、MySQL，重启 a2p；脚本不降优先级。每 4 秒记录每段的积压，30 秒、50 秒时对 Core1、Client1、Server1 打线程栈和线程 CPU。结果目录 `/usr/local/a2p/log/hotmm4_*`。

## 1. 结论

1. **最慢的一段是 Client 发给通道**：两个 Client 合计每秒约 2500～2700 段，比 Core 处理 MT 的速度（3700～4650）低，`stream:mt:routed` 从头涨到尾，最多 9 万。
2. **Core 处理 MT 也还没到 5000**：负载期间每秒约 3700 段，发送停止、CPU 空出来后约 4650 段，都低于收进来的约 5140 段，`stream:mt:pending` 最多 12 万。Core 已经不是最慢的，但还不够。
3. **通道 DR 进 Core**（`inbound-dr`）也在积压，最多 4.5 万；结果 stream 在最后集中积压 6.7 万。
4. 没有卡住的消息：发送停止后 30 秒内各段全部清空。
5. 慢的共同原因：**每条消息在处理线程上同步等 Redis，而能同时处理的 stream 少**。整机 CPU 满（空闲 0～7%）时每次 Redis 往返都更慢。

## 2. 每段的积压（条）

| 时间 | `mt:pending`（Server → Core） | `mt:routed`（Core → Client） | `inbound-dr`（Client → Core） | `core:results` | `dr:pending`（Core → Server） |
|---|---|---|---|---|---|
| 18 秒 | 59916 | 6858 | 5925 | 2540 | 164 |
| 35 秒 | 95703 | 22653 | 19331 | 518 | 384 |
| 52 秒 | 111243 | 45028 | 30443 | 698 | 218 |
| 60 秒 | 120496 | 56188 | 36172 | 417 | 505 |
| 69 秒（发送已停） | 88015 | 73858 | 40197 | 307 | 455 |
| 77 秒 | 41515 | 89774 | 44824 | 6511 | 74 |
| 结束后 30 秒 | 0 | 0 | 0 | 67296（之后读完） | 4 |

由积压的变化算出的每秒处理量：

| 段 | 负载期间（18～60 秒） | 发送停止后（60～77 秒） |
|---|---|---|
| Server 收（36 万段 / 70 秒） | 约 5140 | 0 |
| Core 处理 MT | 约 3700 | 约 4650 |
| Client 发给通道 | **约 2500** | **约 2700** |

延时：客户提交 → 通道 p50 24.2 秒（大部分是在 `mt:pending`、`mt:routed` 里排队），通道 DR → 客户 p50 9.7 秒（在 `inbound-dr` 里排队）。

## 3. 线程在等什么

**Client1**（CPU 约 1 个核，没有哪个线程打满，每个都在 6% 左右）：

| 线程 | 30 秒 | 50 秒 |
|---|---|---|
| 发送工作线程等 Redis：发送标记 ACK（`ClientSendMarker.ackSent`） | 7 | 1 |
| 发送工作线程等 Redis：发送标记 CLAIM | 4 | 3 |
| 发送工作线程：`keepPending`（读到但暂时不能发的） | 0 | 3 |
| 收通道回包的线程等 Redis：写结果、写通道 DR（`StreamQueueManager.produce`） | 6 | 6 |

这次没有出现窗口满（日志里的 window full 都是 09:24 第一次测试的）。发送工作线程池最多 200 个，实际只有 8～13 个在干活：一个 stream 同一时刻只有一个任务，每条 MT 发之前同步做一次 CLAIM（Lua），回包后再做一次 ACK（Lua）；`mt:routed` 按 `TotalShards` 16 分片，大通道 rtvs1（约 75% 的流量）只有 16 个 stream，两个 Client 分。

**Core1**：等 Redis 的线程分布在写 `mt:routed`（`produceOnce`）、写给客户的 DR（`produceDrOnce`）、submit 结果认领 outbox（`claimResult`，50 秒时 6 个）、取门铃、**`StreamAttempt.flushNow`（3 个）**、查客户 bind 在哪个 Server（`hasActiveSessionInModule`，50 秒时 3 个，8386）。

其中 `flushNow` 是多主新增的：`mt:pending` 和它写去的 `mt:routed` 分片算法不同，2 个主库时约一半的 MT 两者不在同一个主库，写出后要立即单独记一次标记，每条多一次往返。

## 4. 可以做的（建议，没有改）

| # | 办法 | 针对 | 作用 |
|---|---|---|---|
| 1 | Client 发送标记按批（《Redis消息操作次数统计》第 4 项）：一批读到的 MT 一次 Lua CLAIM，ACK 攒几毫秒一次 Lua | 最慢的一段 | 每条 MT 少 2 次同步往返；同样的线程数每秒能发得更多 |
| 2 | Client 写结果、写通道 DR 按批（第 5 项） | Client 收回包的线程、Core 读结果 | 每条少 2 次 Lua |
| 3 | `TotalShards` 16 → 64（配置，要先清空积压） | Core、Client 能同时处理的 stream 个数 | 并发约 4 倍；CPU 不够时作用有限，要和 1、2 一起做 |
| 4 | 多主时让 `mt:routed` 和它来源的 `mt:pending` 尽量在同一个主库（例如 routed 的分片号取来源 pending 的分片号） | Core 的 `flushNow` | 每条 MT 少一次往返 |
| 5 | Core 缓存客户 bind 在哪个 Server（原来的第 1 项，8386） | Core 处理通道 DR | 每个 DR 少 3 次往返；8386 不是瓶颈，但这 3 次在 DR 的串行路径上 |
| 6 | 压测工具放到另一台机器 | 整机 CPU | 所有 Redis 往返都变快，测出的才是系统自己的能力 |

## 5. 已改：Client 发送标记按批（2026-11-18）

开关 `ClientSendMarkerBatch`（默认 true，热加载）。`OutboundStreamConsumer`：原来 `handleMessageSending` 里"会话、窗口、限速许可、选 bind"抽成 `prepare`，"写到通道"抽成 `submit`，一条一条的路径由这两段组成，行为不变。按批时（`processInBatches`）：

1. 一次读到的 MT 按顺序逐条 `prepare`，能发的放进这一轮；遇到第一条拿不到许可或窗口满就停，它和后面的照原来的方式暂存；
2. 这一轮的 MT 一次 Lua 认领（`ClientSendMarker.claimBatch`，每条的判断和原来的 CLAIM 一样），依次写到通道，再一次 Lua 确认（`ackSentBatch`）；写时窗口满，这条和后面的标记一次删掉（`releaseBatch`），一起暂存；
3. 可能被自动认领拿走的老条目、没有连接的会话、`prepare` 出错的，走一条一条的路径。

只认领马上要发的：标记仍表示"正在发"；限速许可仍是每条一个、在认领之前拿；窗口和每 bind 均匀发送不变。

测试 `ClientMarkerBatchIT`（12 项）：30 条一次读到的 MT 认领加确认共 2 次 Lua（原来 60 次），各发一次；一批里"已发过""别人正在发""发送者已停"三种标记的处理和原来一样；限速 5/s 时 20 条用了 3.9 秒，1.2 秒时还没拿到许可的 14 条都没有标记；关掉开关同样各发一次，Lua 多一倍。

## 6. Client 按批 + `TotalShards` 64 以后的 5000 TPS（2026-11-18）

部署：本节第 5 节的代码；GmmsConfig `TotalShards` 16 → 64，`CoreShard.CoreEngine1/2/3` = 0-21 / 22-42 / 43-63，`ClientShard.MultiSmppClient1/2` = 0-31 / 32-63，`ClientShard.CommonHttpClient1/2` = 0-63（备份 `GmmsConfig.properties.bak.20261118_shards64`，jar 备份 `a2p.jar.20261118b`）。同样的用例和方法（目录 `/usr/local/a2p/log/hotmm5_*`；64 个分片时每次统计积压要十几秒，采样点比上次少）。

| 项 | 上次（第 2 节） | 这次 |
|---|---|---|
| `mt:routed` 最多（Core → Client） | 9.0 万 | **3.2 万** |
| `inbound-dr` 最多（通道 DR 进 Core） | 4.5 万 | **0.2 万** |
| `mt:pending` 最多（Server → Core） | 12.0 万 | 13.4 万 |
| 通道收到的 submit_sm | 24.8 万 | **28.2 万** |
| 客户提交 → 通道 p50 | 24.2 秒 | **9.5 秒** |
| 通道 DR → 客户 p50 | 9.7 秒 | **1.2 秒** |
| 整机 CPU 空闲 | 0～7% | 3～14% |
| CPU：Redis 合计 / 3 个 Core / Server1 / 2 个 Client | — | 400% / 153～176% 各 / 169% / 118%、89% |

结论：

1. **Client 发给通道、通道 DR 进 Core 这两段基本不再积压**：Client 按批和分片加多以后，最慢的已不是 Client；
2. **现在最慢的是 Core 处理 MT**：`mt:pending` 和上次差不多。64 个分片时大客户 rtcs1 有 64 个 `mt:pending` stream（两个主库各 32 个），每个 Core 负责约 22 个，但 30 秒、50 秒的线程栈里每个 Core 只有 9～10 个线程在处理 MT（大多在 `produceOnce` 等 Redis），MT 调度线程两次都在等 Redis。为什么 22 个有积压的 stream 只有一半在处理，还没有查清，要单独测（打开 stream 跟踪日志、按 stream 统计每个任务处理多久、调度线程每秒派出多少任务）；
3. **测试结束时客户收到的 DR 少（10.9 万，上次 18.7 万）、`rmq` 里 8.4 万条 2500（COMMUNICATION_ERROR）是测试本身的问题**：压测工具在排空 10 秒后就关掉通道模拟器（10:53:29 RTVS1 断开），这时还没处理完的 MT 发送时都是"Session disconnected"，进了重试队列。今天每次测试结束都有这种情况（09:25、09:30、10:03、10:53 各几万条）。这次 Core 处理 MT 的积压比上次清得慢，关掉时剩得多，所以失败的多、DR 少。要比较 DR，压测工具应在 a2p 的积压清空以后再关通道模拟器。

## 7. DR 少和 Core 慢的原因（2026-11-18 第二次测，排空改为 120 秒）

用例 `cases/PF002_cmd` 的 `soak.drainSec` 10 → 120，通道模拟器一直开到 a2p 的积压清空；负载中 25、40、55 秒在两个 submit 主库上用一次 Lua 读出每个 `mt:pending` stream 的长度、已读未确认数、门铃分数，同时打 3 个 Core 的线程栈。目录 `/usr/local/a2p/log/hotmm6_*`。

结果：105 秒时所有积压清空，没有发送失败，通道收到 37.5 万段（含改道）；但客户只收到 26.2 万个 DR，**61566 条 MT 没有 DR**（1000 TPS 时是 0）。

### 7.1 DR 少

1. Core 处理 submit 结果落后（结果 stream 一直积压约 1 万条），通道 DR 进 Core 几乎不积压，所以很多 MT 的**通道 DR 比它的 submit 结果先到**：DR 匹配数据（`{outMsgId}`）要处理 submit 结果时才写，DR 找不到原消息，按原有逻辑存起来以后再配（`[VDR-STORE]`）。这次 3 个 Core 共存了 **79131 条**；
2. 存起来的 DR 写成 `INSERT INTO SDQ` 的 SQL 文件（`queue/sdq/`，每 20 秒切换到 `queue/sdq/link/`），要靠 `script/queueFile/queueFileLoad.sh` 导入 MySQL，MQM 的 `SendStoredDRTask` 再从 SDQ 表取出来配；
3. **测试服务器上导入脚本没有运行**（没有进程、没有 cron），而且它连的是旧 MySQL（`/usr/local/mysql/bin/mysql`，端口 33067），不是现在的 MySQL 8.0（3306）。`link/` 从 2026-04 起积了 7403 个文件、2.1 GB，SDQ 表一直是空的，这些 DR 永远到不了客户；
4. 就算导入正常，这条路也很慢：`SendStoredDRTask` 每次取 100 条，间隔 30～60 秒。

所以 DR 少的根本原因是第 7.2 节的"结果处理落后"，而存起来的 DR 在这个环境里又没有被导入。

### 7.2 Core 慢：门铃顺序让大客户的 stream 排不上

| 时间 | 大客户 rtcs1（9995） | 小客户 rtcs2、rtcs3（9996、9997） |
|---|---|---|
| 25 秒 | 64 个 stream 有积压，**20 个在读**；积压 8.1 万，其中 **6.7 万在没人读的 stream 里** | 102 个 stream 有积压（共 455 条），9 个在读 |
| 40 秒 | 64 个有积压，23 个在读；积压 12.1 万，**9.4 万没人读** | 87 个（328 条），13 个在读 |
| 55 秒 | 64 个有积压，21 个在读；积压 14.7 万，**10.6 万没人读** | 96 个（393 条），11 个在读 |

- 没人读的 stream 门铃都在（没有丢门铃），MT 工作线程池（最少 50）也只用了 8～20 个，调度线程每次线程栈都在 `popResponsibleDoorbell` 等 Redis；
- 原因：每次 XADD 都把门铃的分数改成当前时间（`ZADD`），调度线程每次取分数最小（最久没写）的。负载下所有门铃 0.1～0.2 秒内都被刷新过，排在前面的总是**写得少的小客户 stream**（每个只有几条，任务很快结束，马上又被新写入按响），**写得最频繁的大客户 stream 分数总是最新、排在最后**。一个大客户 stream 的任务处理满 10 批或 2 秒让出以后，又排到所有小客户后面；
- 结果的消费者每个 Core 正好 10 个线程在跑：`RedisStreamConsumer.CoreResult.WorkerCorePoolSize=10`，线程池的队列（1000）不满时不会超过核心线程数，所以结果处理被限制在每个 Core 10 个线程，这就是结果落后、DR 先到的原因。

### 7.3 建议（没有改）

| # | 办法 | 作用 |
|---|---|---|
| 1 | 门铃只在没有时才加（`ZADD NX`）：分数是这个 stream 第一次被按响的时间，调度按"等得最久的先处理"，不再因为写得频繁被往后排 | 解决大客户 stream 排不上；每次 XADD 的 ZADD 不再改数据（不写 AOF、不复制），8387、8397 的开销也降 |
| 2 | `RedisStreamConsumer.CoreResult.WorkerCorePoolSize` 10 → 30（配置） | 结果处理跟上，DR 就不会大量先于结果到达 |
| 3 | DR 先于结果到达时，不写 SDQ 文件，留在 `inbound-dr` 里过几秒再处理（或放进 Redis 的延时队列），超过一定时间才走原来的存储 | 正常情况下 DR 只晚几秒，不再依赖 SDQ 文件导入 |
| 4 | 测试服务器上配置 `queueFileLoad.sh`（改成 MySQL 8.0 的路径和端口，加 cron）；清理 `queue/sdq/link/` 里的旧文件 | 环境问题，存起来的 DR 至少能补发 |

## 8. 按 7.3 改（2026-11-18）

| # | 改动 | 位置 |
|---|---|---|
| 1 | 生产者写 stream 时门铃改为 `ZADD NX`：分数是 stream 第一次被按响的时间；消费者让出、处理完以后重按门铃仍是当前时间（排到后面，轮流） | `RedisConnection.xaddWithDoorbell`，`StreamQueueManager` 的 `RESULT_AND_ACK`、`PRODUCE_ONCE`、`RELEASE`、`RELEASE_TO`；门铃分数别处只用来判断有没有（积压监控） |

| 3 | 通道 DR 在 Redis 和 DB 都找不到原消息时，放进 state Redis 的延迟队列：`dr:early:{outMsgId}:{状态}:{msgId}`（hash：body、tries，TTL `EarlyDr.TtlSeconds`）、`zset:dr:early`（分数 = 到期时间）。active 的 MQM 线程 `EarlyDrDispatcher` 每 `EarlyDr.IntervalMs` 一次 Lua 取一批到期的移到 `zset:dr:early:processing`（分数 = 认领截止时间），写回 `stream:core:inbound-dr`，成功后移出并删掉 body；认领超时（MQM 停了）放回。Core 再匹配，还找不到就再放回（次数加一），试满 `EarlyDr.MaxTries` 次才按原来的方式存 SDQ | `EarlyDrQueue`、`mqm.EarlyDrDispatcher`、`MsgQueueMonitor`、`InternalCoreEngineSession.handleInboundDRInternal` |

测试 `EarlyDrIT`（10 项）：没有原消息的 DR 进延迟队列、不给客户发；原消息有了、到期后 MQM 写回，Core 匹配，客户收到一个 DR，队列里不留认领和 body；MQM 停在认领中的会被放回再写回；试满次数走原来的路；关掉开关不进队列。

2. **大客户的 stream 排不上的问题解决**：同时在处理的 stream 和线程多了一倍；
3. **现在受整机 CPU 限制**：负载期间 Core 每秒处理约 3500 条 MT、Client 每秒发约 1800 段；发送一停（Server、压测工具空出 CPU），Core 升到每秒约 6400、Client 约 4500。整个过程 36 万段用了约 112 秒，约每秒 3200 段（约 2700 TPS），和《模块规格评估》算的这台 16 核机器约 2800～3500 TPS 一致。这次结果和 DR 都跟上了，CPU 分给它们的多了，所以 Client 在负载期间比上次慢、`mt:routed` 积压更多；
4. 要真正跑满 5000 TPS，按《模块规格评估》第 5 节：压测工具、Redis 从库放到别的机器，或者用更多核的机器。

## 10. 营销大客户冲量时 OTP 客户的 Core 侧延时（2026-11-18）

用例（`regression/routetest/cases/`）：

- `PF003_fairness`：5 个营销客户 RTMK1～5（各 800 TPS，共 4000 TPS，连 MultiSmppServer1，号码 86138 → 营销通道 RTVM1，限速 2000 TPS）+ 5 个 OTP 客户 RTOT1～5（各 20 TPS，共 100 TPS，连 MultiSmppServer2，号码 86139 → OTP 通道 RTVO1，不限速）；60 秒，排空 150 秒；
- `PF003_otp_baseline`：只有 5 个 OTP 客户（共 100 TPS），作对照。

压测工具按模板（客户）分别统计延时（`RouteCase`：`latency after the warm-up by template`）。测试前清空 Redis、MySQL，`run_case` 重启 a2p 加载这两个用例的 cm.cfg 和路由。目录 `/usr/local/a2p/log/fair_*`。

| OTP 客户提交 → 通道 | 只有 OTP | 营销冲量时 |
|---|---|---|
| p50 | 50 ms | **1.7 秒** |
| p95 | 84 ms | **约 4 秒** |
| 最大 | 99 ms | **约 7 秒** |
| 提交 → 客户收到 DR p50 | 0.63 秒 | 2.7 秒 |

营销客户提交 → 通道 p50 约 22 秒（通道限速 2000、进来 4000，积压在 `mt:routed`，通道侧，正常）；两次都没有丢 DR（24.6 万条全部收到）。

**OTP 没有排在营销积压后面，但多了 1～7 秒**。原因：

- Core 跟得上营销：38 秒以后营销在 `mt:pending` 的积压只有约 3000 条，几乎都在 `mt:routed` 等营销通道；
- OTP 客户 5 个 × 64 分片 = 320 个 stream，任一时刻有 105～179 个各有 1～2 条，正在读的只有 1～8 个，约 130～260 条在等调度；
- 有积压的 stream 合计约 450 个（营销约 300 个），每个 Core 约 150～160 个，**一个调度线程每次 Redis 往返只派出一个 stream**，轮完一圈要 1～2 秒；OTP 的 stream 每个只有一两条，几乎每条消息都要等一次调度，所以 p50 约 1.7 秒。不是线程不够（营销正在读的 41～124 个），也不是被营销的量拖住。

**建议**（没有改）：

| # | 办法 | 作用 |
|---|---|---|
| 1 | 调度线程一次取多个：取门铃的 Lua 一次弹出最多 N 个（比如 32 个）本节点负责、有积压的 stream，一起交给线程池；线程池忙时只取空闲线程数那么多 | 一圈从约 160 次往返变成约 5 次，OTP 等调度的时间估计从秒级降到百毫秒级；分片多、客户多时都有用 |
| 2 | 按客户配置优先级（例如 `SMSOptionPriorityFlag`），高优先级客户的 `mt:pending` 门铃单独一个 zset，调度先取它 | OTP 不用和营销一起排队，冲量时也是几十毫秒 |

### 10.1 Core 调度一次取多个以后（`CoreMTDispatchBatch`=32，2026-11-18）

同样的用例重跑（目录 `/usr/local/a2p/log/fair2_*`，jar 备份 `a2p.jar.20261118d`）：

| OTP 客户提交 → 通道 | 只有 OTP | 冲量，一次取一个 | 冲量，一次取 32 个 |
|---|---|---|---|
| p50 | 50 ms | 1.7 秒 | **0.8 秒** |
| p95 | 85 ms | 约 4 秒 | 约 3.5 秒 |
| 最大 | 100 ms | 约 7 秒 | 约 5.5 秒 |
| 25 / 40 / 55 秒时 OTP 在 Core 等调度的条数 | — | 264 / 128 / 135 | **62 / 10 / 5** |

两次都没有丢 DR（24.6 万条全部收到）。剩下的延时：

1. **前 25 秒 Core 还在追**：营销 `mt:pending` 积压 0.6～2.6 万、OTP 65～306 条（刚开始压，Core 预热，第一次用到的 stream 也有初始化开销）；32 秒以后营销只剩几百条、OTP 个位数到十几条；
2. **Client 侧**：OTP 通道 RTVO1 不限速，但 `mt:routed` 一直有 34～212 条在等（100 TPS 下约 0.5～1 秒）。Client 的调度线程也是一次往返派一个 stream；营销通道限速，它的 64 个 stream 拿不到许可就暂存、过一会儿恢复，反复占用调度。OTP 通道虽然不同，但和营销共用同一个 Client 调度线程。

下一步：Client 的发送调度（`OutboundStreamConsumer`）也一次取多个（`popResponsibleDoorbells`），按空闲线程数取。

### 10.2 Client 调度也一次取多个以后（`ClientDispatchBatch`=32，2026-11-18）

同样的用例重跑（目录 `/usr/local/a2p/log/fair3_*`，jar 备份 `a2p.jar.20261118e`）：

| OTP 客户提交 → 通道 | 只有 OTP | 冲量，原来 | Core 一次取多个 | Core、Client 都一次取多个 |
|---|---|---|---|---|
| p50 | 53 ms | 1.7 秒 | 0.8 秒 | **0.27 秒** |
| p95 | 88 ms | 约 4 秒 | 约 3.5 秒 | 约 2.6 秒 |
| 最大 | 102 ms | 约 7 秒 | 约 5.5 秒 | 约 4.3 秒 |
| OTP 通道 `mt:routed` 在等的 | — | — | 34～212 条 | **3～19 条** |

DR 一个不少。剩下的 p95、最大值几乎都在前 25 秒：营销 4000 TPS 一下子进来，Core 刚开始跟不上（营销 `mt:pending` 积压 0.9～2.8 万），每个 Core 有积压的营销 stream 一百多个，比处理线程（50）多，线程被营销任务占满，OTP 要等营销任务让出线程（每个任务最长 2 秒）；32 秒以后 Core 追上，OTP 在 Core 侧只有十几条。要连这一段也保证，需要按客户配置优先级（第 10 节建议 2），或者让高优先级客户的 stream 不受线程占满的影响。
