# Server 会话登记批量写入与对账加固设计

## 1. 背景

每条 bind 连接都登记在 state Redis，Core 据此决定 DR 发往哪个 Server 模块。登记一次要 8 条命令（1 个 GET、2 个 SETEX、5 个 ZADD），每条同步等回复，由三处触发：

| 入口 | 频率 | 线程 |
|---|---|---|
| bind 成功 | 每次 bind | 处理 bind 的线程 |
| 收到 PDU（bind 除外） | 每条连接最多每 30 秒一次 | 收包 worker |
| 定时对账 | 上一轮结束后 60 秒 | 对账线程，逐条连接 |

本地测试 3731 条连接时，一轮对账约 3 万次操作，用时约 30 秒。按此估算，20000 条连接一轮约 2 分钟，超过 60 秒的间隔。客户基本都发 enquire_link 时，PDU 刷新还会多产生约 5300 条命令/秒，并占用收包 worker。

读代码还发现以下问题：

- 对账任务只捕获 `Exception`。抛 Error（例如线程耗尽时的 OOM）后定时任务被取消，不再运行，也没有后续日志。
- 取连接快照没有按客户隔离，一个客户出错，整轮跳过。
- `SmppServerSessionRegistryEnable` 启动时为 false，之后热加载打开，对账任务不会创建。
- `SmppServerSessionRegistryReconcileIntervalMs` 只在启动时读一次，文档却写热加载。
- 清理用的存活集合在一轮开始时确定。这一轮中新 bind 的连接不在集合里，可能被当成失效删除。
- `ZADD` 的结果没有检查；Redis 写失败时仍然把连接记为刚刷新过。

## 2. 目标

1. 减少网络往返：Redis 命令基本不变，一批发出、一次收回。
2. 对账正常时，PDU 路径不写 Redis；对账异常时，有 PDU 的连接能自己恢复。
3. 对账任务不会悄悄停止，出问题能从日志看到。

Redis key 结构和内容、Core 选模块的逻辑都不变。线程模型（每条连接 2 个线程）不在本次范围。

## 3. 批量写入

一批连接分两次往返：

1. `MGET` 所有 slot key，比较当前登记的会话。位置被别的会话占用时，单独清理旧会话（和现在一样）。
2. 一个 pipeline 写入：每条连接 `SETEX` 详情、`SETEX` slot、4 个 ZADD（客户、客户+模块、连接名、节点）；模块索引 `smpp:server:module:{ssid}` 同一批同一客户只写一次。仍然先写详情再写索引。

- bind 和 PDU 刷新走同一段代码，一批 1 条，8 次往返降为 2 次。
- 对账按 `SmppServerSessionRegistryBatchSize`（默认 200）分批。
- 每条连接只有所有命令都成功才算成功，`ZADD` 的结果也检查。
- 一批出错：打 WARN，这批都算失败。连接不受影响，也仍算存活，不会被清理，下一轮重写。

pipeline 不是事务，这一点和现在相同：现在的 8 条命令同样不是原子的。

## 4. PDU 路径改为低频兜底

对账成功时，更新这条连接的“上次刷新时间”，所以对账正常时 PDU 路径不写 Redis。

```
收到 PDU → 距上次成功刷新不足 N → 跳过
         → 距上次尝试不足 30 秒（不超过 N）→ 跳过
         → 否则这条连接自己刷新一次
```

- N = `min(SmppServerSessionRegistryRefreshIntervalMs, 有效期 / 3)`，配置默认值从 30000 改为 **180000**。默认有效期 660 秒，N 为 180 秒，能容忍错过两轮对账。
- 现在写失败也会把时间记为“刚刷新”，改为只有成功才更新。失败后最快 30 秒（不超过 N）重试一次，避免 Redis 故障时每个 PDU 都等超时。
- 模块有对账时，PDU 路径真的发生写入说明对账没覆盖到这条连接，打 WARN（限频）。
- `SslSmppServer` 没有对账，靠这条路径按 N 刷新，登记不会过期。

已知覆盖不到：对账挂了或卡住，同时这条连接没有任何 PDU。这时登记会在有效期后过期，靠第 5 节的日志发现。

## 5. 对账加固

- 对账任务改为“每轮结束后安排下一轮”，捕获 `Throwable`。间隔每轮读取，真正支持热加载。
- 启动时总是创建任务，每轮判断 `SmppServerSessionRegistryEnable`，热加载打开也能生效。
- 取快照按客户隔离。某个客户出错时打 WARN，**这一轮跳过清理**（存活集合不完整，清理可能误删），刷新照常。
- 清理时，详情的 `lastSeen` 不早于本轮开始时间的条目不算失效，解决一轮中新 bind 被误删的问题。
- 每轮打印 `live`、`ok`、`failed`、`removed`、`costMs`。连续 3 轮有失败打 ERROR。
- PDU 路径发现对账超过 5 个间隔没有结束时打 ERROR（限频），用于发现卡住的对账。

## 6. 配置项

| 配置项 | 默认 | 生效 | 说明 |
|---|---|---|---|
| `SmppServerSessionRegistryBatchSize`（新增） | `200` | 热加载 | 对账每批写多少条连接。1 表示一批 1 条（每条 2 次往返） |
| `SmppServerSessionRegistryRefreshIntervalMs`（改默认值） | `180000`（原 30000） | 热加载 | PDU 路径的兜底刷新间隔，实际不超过有效期的三分之一 |
| `SmppServerRegistryLegacyCleanupMaxKeysPerRun`（改默认值） | `5000`（原 2000） | 热加载 | 清理每轮最多检查多少个 key |

### 6.1 清理上限为什么可以调到 5000

- 上限只限制检查的 key 数。key 没有这么多时，SCAN 走完整个 keyspace 就结束，不会增加开销。
- 在存活集合里的 key 只查内存，不访问 Redis。普通一轮的 Redis 开销只有 SCAN，以及对失效 key 的 GET 和删除。
- SCAN 每次只处理约 200 个槽位，每次调用很短，不会像 `KEYS` 那样长时间阻塞 Redis，其他命令可以穿插执行。
- 每 5 分钟的旧格式清理轮会对每个检查的 key 多一次 GET。真要删除失效 key 时，每个约 7ms（多次同步命令），都在对账线程上，不影响消息路径。

20000 条连接时，2000 要 10 轮扫完，5000 只要 4 轮。

本地实测（state Redis 里有本模块 2 万个登记、另外 10 万个 key，全部存活，同时另一个客户端持续 PING）：

| 清理上限 | 一轮耗时 | SCAN 次数 | 另一个客户端 PING p50 / p99 |
|---|---|---|---|
| 不运行清理（基线） | - | - | 0.66 / 1.69 ms |
| 2000 | 110 ms | 61 | 1.20 / 1.76 ms |
| 5000 | 398 ms | 149 | 2.08 / 4.19 ms |
| 10000 | 451 ms | 299 | 1.22 / 3.03 ms |

单轮很短、样本少，p50 和 p99 的差异在几毫秒内，且不随上限单调变化。最坏情况是要删除大量失效 key：实测删除一个 key 约 7ms，上限 5000 时一轮约 33 秒，这期间 PING p99 仍是 1.58 ms，Redis 没受影响，只是对账这一轮变长。

## 7. 对外影响

- `lastSeen` 从约 30 秒更新一次变为约 1 分钟一次。Java 代码没有读取方；如果 portal 读这个字段，要按新频率理解。
- `smpp:server:module:{ssid}` 的分数决定备选模块的顺序：`selectActiveModule` 优先选最近刷新的模块。客户连在多个模块、原模块没有登记时，选中哪个模块可能和之前不同，这些模块都是有活跃连接的，不影响 DR 送达。
- 异常断开留下的登记，清理时间不变。
