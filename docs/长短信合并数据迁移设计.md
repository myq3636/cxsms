# 长短信合并数据从状态 Redis 迁到 submit Redis（设计）

> 2026-11-24。问题：长短信分段在 Core 里等齐的数据放在状态 Redis，放到 submit Redis 是否更合理。

**实施状态**：已实现，固定放在 submit Redis。商用都是全新部署，没有切换开关，也不回查状态 Redis 里的旧数据。同时删除了 legacy 合并方式（内存缓存 + CSMQ 表，`CsmReassembleMode=legacy`）。

## 1. 结论

- 分段本身就是消息体（整条序列化消息，约 1 到 2KB），和 `stream:mt:pending` 里的消息是同一种数据，应该和消息放在一起。
- 状态 Redis 是单实例、不能分片，前面专门把每条消息在它上面的命令从 10.3 降到 5.4（《Redis消息操作次数统计》）；它应该只放模块注册、分片、限流计数、控制频道这些小的控制数据。
- 没收齐的分段要留到 `CsmIntegrityCacheTimeout`（默认 1 小时）。通道或客户异常时会积压，放在状态 Redis 上会连带影响控制面；submit Redis 本来就按消息量配内存，可以配多个主分摊。
- 每组长短信的 Redis 操作次数不变，只是从状态 Redis 挪到 submit Redis。状态 Redis 每组省下"分段数 + 1"次 Lua（每次内部约 6 到 10 条命令）和这些消息体。

## 2. 数据和操作（不变，只换位置）

| key | 内容 |
|---|---|
| `csm:{ossid}:{sender}:{recipient}:{参考号}:{总段数}` | 合并缓冲（Hash：分段号 → 分段） |
| `csm:ids:{同上}` | 分段号 → msgId，收尾时改名为 `csm:done:*` |
| `csm:asm:{同上}` | 收齐后正在组装外发的占用（owner\|时间） |
| `csm:done:{同上}` | 已完成的组，识别重投的分段 |
| `csm:index` | 过期索引（ZSET：组 key → 到期时间），**每个 submit 主各一个** |

- 存一个分段：一次 `STORE_LUA`（存分段、存 msgId、首段设过期并加入 `csm:index`，收齐时取整组）。
- 收齐外发成功后：一次 `FINISH_LUA`（删整组、出索引、记为已完成）。
- 过期扫描：每个 Core（`CsmExpirySweeper`）和 MQM（`CsmExpiryTask`）每 `CoreCsmExpiryIntervalSec` 领取到期的组，回过期 DR。

## 3. 放在哪个 submit 主

- **按组 key 选**：`ShardHash.of(组 key, submit 主数)`（`RedisCsmReassembler.master`），一组的所有 key 和它在 `csm:index` 里的成员都在这个主上，Lua 里的多个 key 在同一实例，原子性不变。只有一个 submit 主时就是它。
- **不按分段所在的流选**：同一组的分段可能来自不同的流（Server 写的 `stream:mt:pending`、MQM 重发的流），按组 key 选才能保证一组在一处。
- **存分段和确认消费不合并**：只有分段和它的流在同一个主上才能合成一个 Lua，按组 key 选主时不能保证。现在先存、再确认消费，存分段可以重复执行（同一分段号覆盖），崩溃在两步之间只是重投一次。
- **过期扫描逐个主领取**：`claimExpired` 依次在每个 submit 主的 `csm:index` 上领取，每个主最多 `CoreCsmExpiryBatch` 个；读分段、收尾都到这个组所在的主。

## 4. 注意事项

- **submit Redis 必须是 `maxmemory-policy noeviction`**：分段被淘汰等于丢段。streams 本来就要求 noeviction，测试机 8387、8397 已经是。内存按"每秒长短信分段数 × 等待时间 × 每段 1 到 2KB"预留积压。
- **改 submit 主的个数会让组重新映射**：正在等分段的组会找不到，后到的分段另起一组，原来那组到期后回过期 DR。只在维护时改。
- **升级**：所有 Core 和 MQM 一起升级。全新部署不需要过渡期；如果状态 Redis 里还有旧的 `csm:*`，它们不再被读，到 TTL 后自动删除。
- **Redis 切换**：`SWITCH_REDIS` 把状态 Redis 和所有 submit、report 主一起切，不受影响。

## 5. 测试

- `MultiMasterIT` MM-00c：两个 submit 主时，分段落在 `ShardHash` 选出的主上（两个主都用到），`csm:index` 成员在同一主上，另一个主上没有；收尾后删除干净。
- `Batch7IT`、`CsmCdrIT`：合并、重投、过期 DR、CDR（单 submit 主时和状态 Redis 是同一实例，行为不变）。
