# 消息 ID 防重复设计

> 日期：2026-11-04。状态：**已实现，默认开启（`MessageIdFormat` 默认 `v2`），线上升级后就会切换，还没有上线**，测试结果见第 11 节。线上情况：单个 Server 目前 4000 TPS，目标 10000 TPS；客户只要求 10 位十进制，不依赖格式；SMPP 3.3 不再使用；HTTP Server 有 2 个模块；有效期超过 1 天的消息，ID 可以复用。第 2 节的重复频率是按公式做的模拟，不是线上数据。

## 1. 结论

`generateDecID` 生成的 10 位 message_id，在多个 Server 同时接流量时会重复，原因是模块号和时间直接相加，会互相覆盖。**按模拟，2 个 Server 各 4000 TPS 时约 13% 的 ID 会重复（2.2），和线上“没有发现重复”对不上，必须先核实。** 现有格式也支持不了 10000 TPS：序号每秒只有 9999 个。

**建议：**

1. **改 SMPP 格式：** 长度仍是 10 位，第一位放模块编号 1 到 9，后 9 位用只增不减的计数器（第 4 节）。默认开启，`MessageIdFormat=v1` 可以回到旧格式。开了 `SMSOptionSMPPIsGenHexMsgId` 的客户走十六进制新格式（4.4）。
2. **改 HTTP 格式：** 2 个 HTTP Server 同样会重复，而且内部 msgId 相撞可能让消息丢失（第 7 节）。

线上重复情况已决定不再统计，直接按这个设计切换。如果以后要核实，用第 6 节的命令。

**新格式的周期：** 单个模块长期 10000 TPS 时，约 27.8 小时一轮，长于“超过 1 天可以复用”的要求（4.2）。

## 2. 问题

### 2.1 现有格式

```text
(月内小时数 × 10000 + 小时内秒数 + 1000 × (模块号 + 4)) 取后 6 位 + 4 位序号
```

模块号和秒数都落在同一段数字里。模块号 0 的第 2000 秒，等于模块号 1 的第 1000 秒：

| 模块号 | 时间 | 序号 | ID |
|---|---|---|---|
| 0 | 05:33:20 | 123 | `2960000123` |
| 1 | 05:16:40 | 123 | `2960000123` |

### 2.2 重复的频率

模拟条件：2 个 Server，流量相同，24 小时，12 个随机起始相位。只计入模块号相差 1 的情况，所以模块更多时重复会更多。

| 每个 Server 的 TPS | 流量波动：每小时重复数（中位数） | 流量完全平稳 |
|---|---|---|
| 5 | 3 | 通常为 0 |
| 10 | 22 | 通常为 0 |
| 50 | 677 | 大多为 0，最多 1879 |
| 100 | 2533 | 大多为 0，最多 7397 |
| 500 | 64441 | 中位数约 60000 |

**接近线上流量时**（流量波动，每种情况 6 小时、6 个起始相位）：

| 两个 Server 的 TPS | 每小时重复数（中位数） | 占全部 ID |
|---|---|---|
| 4000 + 4000 | 约 380 万 | 13.3% |
| 4000 + 1000 | 约 98 万 | 5.5% |
| 4000 + 100 | 约 9.8 万 | 0.7% |
| 1000 + 1000 | 约 25 万 | 3.5% |
| 10000 + 10000 | 约 1520 万 | 21.4% |

这些比例很高，但线上目前没有发现重复。可能是还没有人统计，也可能流量集中在一个 Server 上，或者模拟漏了什么，这一点没有核实。

**同一模块自己也会撞：** 序号每秒只有 9999 个，单个模块超过约 10000 TPS 时，同一秒内就会重复。所以现有格式支持不了目标流量。

只有一个 Server 接流量，且每秒不超过 9999 条时，不会重复。

### 2.3 重复的影响

| 位置 | 用法 | 影响 | 跨客户 |
|---|---|---|---|
| 客户收到的 DR | `id:` 和 submit_sm_resp 的 message_id | 客户可能把 DR 对到另一条消息 | 否 |
| 队列表 | `DELETE`、`UPDATE ... WHERE InMsgID=`，条件里没有客户 | **可能删除或覆盖另一条消息的记录**，包括定时和重试队列 | 是 |
| DR 查询缓存 | `IQDR_` + inMsgID | 可能查到另一条消息的状态 | 是 |
| 延迟 DR | `DELAYDR_` + inMsgID | 延迟内容可能被覆盖。只有延迟超过相撞的时间差才会发生 | 是 |

队列表这一行最值得关注，因为即使客户不同也会互相影响。实际有多少消息会走到这些 SQL，还没有统计。

### 2.4 其他生成方法

| 方法 | 用途 | 问题 | 本设计 |
|---|---|---|---|
| `generateDecID` | SMPP 3.4 的 message_id，默认 | 见上 | **修复** |
| `generateHexID` | SMPP 3.3、`SMSOptionSMPPIsGenHexMsgId` | 模块号只有 2 位，模块号 4、5 会和 0、1 相差 2 秒相撞；序号每 2 秒 1024 个，单模块超过约 512 TPS 自己就会撞；一周一轮 | **修复**，见 4.4 |
| `generateMaxDecID` | `SMSOptionSupportMaxInMsgID`，13 位 | 字段分开，不同模块不会撞 | 不改 |
| `generateCommonMsgID(ssid, 模块)` | SMPP 的内部 msgId | 带 `位置 % 6`，超过 6 个模块会撞 | **修复**，v2 下用固定编号 |
| `generateCommonMsgID(ssid)` | HTTP 的内部 msgId | **不带模块号**。发送标记用它做 key，相撞可能让消息被当成已发送 | **修复**，第 7 节 |
| `generateCommonStringID` | HTTP 的 inMsgID 等 | **不带模块号**，同一秒、同一序号就相撞 | **修复**，第 7 节 |

## 3. 约束

| 约束 | 依据 | 对设计的要求 |
|---|---|---|
| 长度 10 位，全是十进制数字 | 已确认客户只要求这一点，不依赖内容格式 | 不改长度和字符集 |
| 单个模块支持 10000 TPS | 目标流量，目前 4000 TPS | 每秒序号不能被限制在 1 万以内 |
| 不能依赖每条消息访问 Redis | 这是收消息的主路径 | 生成 ID 只用内存 |
| 进程重启、时钟回拨后不能重复 | 见 4.3 | 要有保护 |
| 1 天内不能重复 | 已确认超过 1 天的消息 ID 可以复用 | 10000 TPS 时一轮约 27.8 小时，满足 |
| 每个模块独立 | 不能增加模块间协调 | 模块编号固定，见 `模块动态扩缩容设计.md` 5.4 |

代码没有按时间解析这个 ID：`parseHexMsgId` 对十进制 ID 原样返回，`MultiSmppSession` 只把它当成数字转十六进制。

## 4. 新格式

### 4.1 十进制（10 位）

```text
第 1 位：模块编号，1 到 9
后 9 位：计数器 % 10^9

计数器下一个值 = max(上一个值 + 1, 当前秒数 × K + 角色偏移)
```

- **K：** `MessageIdCounterPerSecond`，默认 5000，取值原因见 4.2。
- **角色偏移：** Server 是 0，Client 是 5 亿（半轮）。

**例子：** 2026-11-01 05:45:51，当前秒数 1793483151：

| 模块 | 计算 | ID |
|---|---|---|
| Server2 | 1793483151 × 5000，取后 9 位 | `2415755000` |
| Client1 | 同上，再偏移 5 亿 | `1915755000` |

**为什么这样设计：**

| 设计点 | 原因 |
|---|---|
| 第一位是模块编号 | 不同编号的 ID 不可能相同。只用 1 到 9，不用 0，**第一位不会是 0**，客户解析或存成数字时不会丢位。所以同类模块最多 9 个 |
| 计数器只增不减 | 同一模块在一轮内不可能重复 |
| 下限随时间走 | 重启后不用从 Redis 读也能接近上次的位置，低流量时周期也不会缩短 |
| 不按秒切分 | 瞬时超过 K 时不用等待，也不会重复，而是暂时“跑在时钟前面”，流量降下来后时钟追上 |
| Client 偏移半轮 | Server 和 Client 编号都是 1 到 9，加上偏移后不会同时用到相同的值 |

**放弃的方案：**

| 方案 | 放弃原因 |
|---|---|
| 模块号 1 位 + 时间 5 位 + 序号 4 位 | 按秒切分，超过每秒容量就要等待或重复，不适合 10000 TPS |
| Redis `INCR` | 每条消息多一次 Redis 访问，Redis 故障时不能收消息 |
| 所有客户都改 13 位 | 客户要求 10 位 |
| UUID 等长 ID | 同上，而且不是纯数字 |

### 4.2 K 的取值、周期和容量

**K 的取舍：** K 小，低流量时一轮更长；但平均流量一旦超过 K，计数器就一直跑在时钟前面，重启时完全依赖保存的位置。K 大则相反。

| K | 低流量时一轮 | 4000 TPS 时 |
|---|---|---|
| 1000 | 约 278 小时 | 一直跑在时钟前面，且越跑越远 |
| 2000 | 约 139 小时 | 同上 |
| **5000（建议）** | **约 55.6 小时** | **不会跑在时钟前面** |
| 10000 | 约 27.8 小时 | 不会，但一轮无谓地缩短 |

建议 5000：高于现在 4000 TPS 的流量，一轮又长于日志里见过的 46 小时有效期。

**不同流量下的一轮时长（K=5000）：**

| 单个模块的长期 TPS | 一轮时长 | 跑在时钟前面 |
|---|---|---|
| ≤ 5000 | 约 55.6 小时 | 否 |
| 7000 | 约 39.7 小时 | 每小时多 24 分钟 |
| 10000 | 约 27.8 小时 | 每小时多 1 小时 |

10000 TPS 只是高峰时，流量降到 5000 以下后时钟就会追上。**按一轮算的是长期平均流量，不是瞬时高峰。**

**可以接受的复用：** 一轮内不会重复。已确认有效期超过 1 天的消息，ID 可以复用，所以长期 10000 TPS 时的 27.8 小时也满足要求。只有长期超过约 11500 TPS（一轮短于 24 小时）才不满足。

### 4.3 边界情况

| 情况 | 处理 |
|---|---|
| **重启：** 没有跑在时钟前面 | 当前时间已过上次位置，不会重复 |
| **重启：** 跑在时钟前面 | 不保护的话，10000 TPS 跑 1 小时后重启，最多重用约 1800 万个。所以心跳时把当前位置写到 `system:msgid:mark:{模块}`，启动时取 `max(保存值 + 余量, 当前秒数 × K)`，余量按 `2 秒 × 最大 TPS` 算，默认 2 万个 |
| **时钟回拨** | 运行中：计数器只增不减，不受影响。重启后：同样靠保存的位置 |
| **Redis 不可用** | 收消息不受影响。只有启动时读不到位置才有重用风险，此时打告警 |
| **改 K** | 只在重启时生效，并且不建议修改。调小后下限可能落到用过的范围，要靠保存的位置兜底 |
| **模块编号变化** | 不允许。编号来自注册表；注册表上线前按列表位置 + 1，这期间不要删除列表中间的模块 |
| **编号超过 6** | 启动失败并报错，不生成 ID |

### 4.4 十六进制（8 位）

用于开了 `SMSOptionSMPPIsGenHexMsgId` 的客户。计数器和十进制分开，只有这些客户的流量才消耗它。

```text
最高 4 位：模块编号 1 到 9
低 28 位：计数器 % 2^28，计数器每秒至少增加 2000，Client 偏移半轮
```

| 设计点 | 原因 |
|---|---|
| 编号用 1 到 9 | 最高 4 位不为 0，所以始终是 8 位十六进制，不会变短。3 位最多放 7 个编号，放不下 9 个 |
| 总共 32 位 | DR 里按十进制显示，最大 `9fffffff` = 2684354559，不超过 10 位。不能再加长，否则 `parseHexMsgId` 不会转换 |
| 负数 | 编号 8、9 时 `int` 是负数，但调用方都用 `Integer.toHexString`，结果仍是 8 位 |

**周期：** 单个模块的十六进制流量 2000 TPS 以内约 37.3 小时一轮。**约 3100 TPS 以上会短于 1 天**，4000 TPS 约 18.6 小时，10000 TPS 约 7.5 小时。这是 32 位的容量决定的，所以这类客户的流量不能长期达到这个水平。超过 2000 TPS 较久时 `[MSGID] ahead` 会告警；`[MSGID] cycle` 只按十进制估算。

`Skytel_MN` 分支在结果上再加 10 亿，只在 SMPP 3.3 路径上，已确认 3.3 不再使用。

### 4.5 监控

| 日志或指标 | 条件 | 含义 |
|---|---|---|
| `[MSGID] ahead` | 跑在时钟前面超过 `MessageIdAheadWarnSeconds`（默认 3600 秒） | 长期超过 K |
| `[MSGID] cycle` | 按最近 1 小时的流量估算，一轮短于 `MessageExpireTime` | 老消息的 ID 可能被复用 |
| `[MSGID] no mark` | 启动时读不到保存的位置 | 重启后可能重用 |

## 5. 上线

### 5.1 开关

| 配置项 | 默认值 | 生效方式 | 作用 |
|---|---|---|---|
| `MessageIdFormat` | `v2` | 重启 | `v2` 是新格式，`v1` 是旧格式，SMPP（十进制、十六进制）和 HTTP 都由它控制。可以按模块配置（`{模块}.MessageIdFormat`） |
| `MessageIdCounterPerSecond` | `5000` | 重启 | K，见 4.2 |
| `MessageIdAheadWarnSeconds` | `3600` | 热加载 | 跑在时钟前面多久后告警 |

实现时要同步更新 `docs/配置项说明.md`。`MessageIdAheadWarnSeconds` 要加入 `GmmsUtility` 的热加载白名单。

### 5.2 步骤

**默认开启，所以升级新版本就是切换。** 要灰度的话，先在配置里加 `MessageIdFormat=v1`，升级后再逐个模块改成 `v2`。

1. **确认模块清单：** 模块名末尾的数字在 1 到 9 之间，大于 9 的启动失败。每个模块都在本机清单里，不在的继续用旧格式并打错误日志。
2. **确认 HTTP 供应商：** `generateCommonStringID` 也用于发给供应商的 ID，新格式一直是 15 位，现在最长也是 15 位，要抽查主要的 HTTP 供应商能否接受。
3. **灰度：** 选低峰，切换一个 Server 并重启。这期间客户重连，和现在重启一样。HTTP Server 同样逐个切换。
4. **观察：** 确认 DR 的 `id:` 和 submit_sm_resp 一致，日志和 DR 匹配正常。
5. **逐步切换：** 依次切换其他 Server，再切 Client。
6. **回退：** 配 `MessageIdFormat=v1` 并重启。已发出的 ID 不受影响，只是又回到现有的重复风险。

**切换期间的重复：** 新 ID 可能和还未过期的旧 ID 相同，因为旧 ID 的首位可能是任意数字。概率不高于现在，等旧消息过期后就消失。

**运维影响：** 新 ID 不能再直接看出时间。需要时用 `后 9 位 ÷ K` 反推，所以要提供一个小工具。

### 5.3 注意事项

- **模块编号：** 取模块名末尾的数字，所以注释、调整清单都不影响编号，多台机器的清单不同也没关系。名字里没有数字时才按清单位置。
- **模块名：** 同类模块的名字末尾数字不能相同，多台机器上也一样，否则编号相同，ID 会重复。这一点代码查不出来，要靠部署时保证。
- **13 位 ID：** `SMSOptionSupportMaxInMsgID=true` 不受影响，只有客户能接受时才用。

## 6. 核实线上是否已有重复（已决定暂不执行）

统计一天内 Core 日志里重复的 inMsgId，多个 Core 要把日志合起来：

```bash
zcat CoreEngine*.log.2026-11-01-*.gz | grep "type=IN_SUBMIT" \
  | sed -E 's/.*ossid=([0-9-]+).*inMsgId=([^ ]+).*/\2 \1/' | sort -u > /tmp/inmsgid.txt

# 重复的 ID 数
cut -d' ' -f1 /tmp/inmsgid.txt | sort | uniq -d | wc -l

# 同一客户里的重复数，影响客户匹配 DR
sort /tmp/inmsgid.txt | uniq -d | wc -l

# 总数
wc -l < /tmp/inmsgid.txt
```

抽样几条，再按 inMsgId 查日志，不同 msgId 才是真重复。这两种不算：同一条消息重投，记了两次 `IN_SUBMIT`；HTTP 客户自己传了相同的 ID。

## 7. HTTP

HTTP Server 商用时是 2 台，所以这部分**要做**。

| 方法 | 现有格式 | 相撞条件 | 影响 |
|---|---|---|---|
| `generateCommonMsgID(ssid)` | `ssid_毫秒数+序号` | 同一客户、同一毫秒、同一序号 | **可能丢消息**：发送标记的 key 是 msgId，第二条会被当成已发送 |
| `generateCommonStringID` | 去掉年份十位的 `yMMddHHmmss`（11 位）+ 序号（1～4 位，不补零） | 同一秒、同一序号 | 重复的 inMsgID，影响同 2.3 |

粗略估算：两个 HTTP Server 各 100 TPS 时，`generateCommonStringID` 约每秒 1 次相撞，`generateCommonMsgID` 约每小时 3.6 次（同一客户流量平均落到两个模块时）。这是用公式算的，没有模拟，也没有 HTTP 的真实流量。

### 7.1 新格式

生成器启动时记录模块编号，调用点不用改。

| 方法 | 新格式 | 长度 |
|---|---|---|
| `generateCommonMsgID(ssid)` | `ssid_毫秒数 + 模块编号 1 位 + 序号 4 位` | 和 SMPP 的 msgId 结构相同 |
| `generateCommonStringID` | `MMddHHmmss`（10 位）+ 模块编号 1 位 + 序号 4 位 | 固定 15 位，**不超过现有最大长度** |

- **不同客户不会撞：** msgId 带 ssid，每个客户块只有一个 `Protocol`，所以 SMPP 和 HTTP 的 msgId 不会落到同一个 ssid 上。
- **一年一轮：** `generateCommonStringID` 不带年份，一年后才可能重复，每秒每模块 9999 个。
- **长度：** 现在长度是 12 到 15 位，新格式固定 15 位。这个方法也用于发给供应商的 ID，序号到 1000 以上时现在就是 15 位，所以不会超过现有最大值。但是一直是最大值，要抽查主要的 HTTP 供应商。
- **HTTP Client：** 也用这两个方法，同样按自己的模块编号生成。

### 7.2 现有开关

`MessageIdIncludeNodeId=true` 可以在上线前解决 `generateCommonMsgID` 的相撞，但它不影响 `generateCommonStringID`，也没有用例。切到 v2 后不需要它，所以本期不用。

## 8. 相关问题：供应商的 ID 也可能相撞

这不属于本设计，但机制相似，建议单独评估：

- 提交结果写入 Redis 时，key 只有供应商的 outMsgID（`redis.setPipeline(omsgid, ...)`），DR 回来也只按它查（`redis.getString(outMsgID)`），数据库用 `WHERE OutMsgID =`。
- 两个供应商返回相同的 ID 时，后写入的会覆盖前面的，DR 可能匹配到另一个通道的消息。
- 之前日志里供应商的 ID `0292751777` 和这边的格式很像。如果上游也是同类系统，相撞的可能性会更高。发生频率没有统计。

## 10. 待确认

**已确认：**

- 客户只要求 10 位十进制，不依赖格式。
- 单个 Server 目前 4000 TPS，新版本目标 10000 TPS。
- SMPP 3.3 不再使用。
- 有效期超过 1 天的消息，ID 可以复用。
- HTTP Server 商用时是 2 台，启动时带 `-Dmodule`。
- 不用统计线上重复情况。

- 同类模块最多 9 个，第一位不能是 0。

**上线前还要确认：**

1. **十六进制客户的流量：** 单个模块长期超过约 3100 TPS 时，一轮短于 1 天（4.4）。
2. **HTTP 供应商：** 能接受固定 15 位的 ID（5.2）。
3. **第 8 节要不要单独排查。**

**10000 TPS 只覆盖 ID 这一层。** 整条链路（Server、Redis、Core、Client）能否撑住 10000 TPS，这里没有评估，也没有压测。

## 11. 实现和测试结果

新增 `MessageIdCheck`（真实生成器，受控时钟）和 `MessageIdIT`（2 个真实 Server 进程），已加入 `regression/suites.txt`。最终代码（默认 v2）的全量回归：54 个套件，通过 1451 项，失败 0 项，已知缺陷 28 项。

| 用例 | 结果 |
|---|---|
| ID-01 | 配 `v1` 时格式公式不变，HTTP、SMPP 的 msgId 和十六进制都不变；`{模块}.MessageIdFormat=v1` 能让单个模块回到旧格式 |
| 默认值 | 不配置 `MessageIdFormat` 时，真实 Server 开启 v2 |
| ID-02、ID-04 | 2 个真实 Server 各 1500 条：10 位数字，首位是模块编号，没有重复 |
| ID-03 | 9 个 Server + 9 个 Client，同一时钟，144 万个 ID，没有重复 |
| ID-05 | 生成器每秒 70 万个以上，不是瓶颈；超过 K 时跑在时钟前面，流量下降后时钟追上 |
| ID-06 | 真实 `kill -9`：有保存位置时 300 个 ID 重复 0 个；**对照组**没有保存位置时重复 285 个 |
| ID-07 | 时钟回拨 1 小时，运行中和重启后都不重复 |
| ID-09 | 线上用的 `GmmsLauncher`：第 10 个模块拒绝启动，退出码非 0；第 9 个通过。`HALauncher` 有同样的检查 |
| ID-10 | 跨过 10^9 后回到开头，长度不变 |
| ID-11 | 真实 deliver_sm 的 `id:` 和 submit_sm_resp 的 message_id 一致 |
| ID-12 | **对照组**：v1 下同一秒、同一序号的 HTTP ID 相同；v2 下不同，固定 15 位 |
| ID-13 | 13 位路径不变 |
| ID-16 | 真实 `GmmsLauncher`：注释 `Server1` 后 `Server3` 是 3，不和运行中的 `Server2` 相撞；清单只有本机模块时 `Server2` 仍是 2；名字没有数字时按位置 |
| ID-15 | SMPP 的内部 msgId 改用固定编号，第 7 个模块是 7；**对照组**：v1 下第 1、第 7 个模块相同 |
| ID-14 | 十六进制：9 个 Server + 9 个 Client、144 万个 ID 没有重复；2 个真实 Server 上 8 位、最高 4 位正确；DR 里转成十进制后正确；`kill -9` 后不重复；**对照组**：v1 的模块 4 超出模块位，没有保存位置时 1000 个 ID 全部重复 |

**和设计相比的差异：**

- **SMPP 的内部 msgId：** 设计里写的是不改，但它按 `位置 % 6` 计算，上限放宽到 9 个后第 7 个会和第 1 个相同，所以 v2 下改用固定编号。
- **`generateCommonInMsgID`、`generateCommonOutMsgID`：** 和 `generateCommonMsgID(ssid)` 有同样的问题，一起加了模块编号，设计里没有列。
- **例子：** 计数器第一个值就是下限本身，不是下限加 1，第 4.1 节的例子已更正。

**没有覆盖的：**

- **ID-05：** 只测了生成器的速度，没有让真实 Server 跑到 10000 TPS。`ID-04` 是逐条发送的 3000 条。
- **ID-14：** 真实进程上的十六进制重启用例没有跑在时钟前面，这种情况只由受控时钟的用例覆盖。
- **ID-08：** 只测了 Redis 里没有保存位置，没有测启动时 Redis 真的不可用。
- **ID-12：** 没有启动真实的 HTTP Server，只测了生成器，也没有测 msgId 相撞导致丢消息的路径。
- **`[MSGID] cycle`：** 只测了判断逻辑，1 小时窗口和告警日志没有实际运行。
- **上线流程：** 灰度切换和回退（5.2）没有在接近线上的环境里走过。

**测试环境发现的小问题，没有改：** `GmmsUtility.initUtility` 启动出错时用的 `log` 可能还是空的，缺 `phone.dat` 时会因为空指针直接启动失败，日志看不到原因。线上有 `phone.dat` 就不会触发。
