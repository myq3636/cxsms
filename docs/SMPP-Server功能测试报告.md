# SMPP Server 功能测试报告

> 用例见《SMPP-Server功能测试清单》。**本次只测试，没有修改产品代码**，失败项都是当前代码的实际行为。

## 1. 结论

| 范围 | 检查数 | 通过 | 失败 |
|---|---|---|---|
| 新设计的功能用例（`ServerFuncIT`） | 128 | 105 | 23 |
| TLS 用例（`ServerTlsIT`） | 8 | 7 | 1 |
| 已有 Server 套件（9 个） | 143 | 143 | 0 |
| **合计** | **279** | **255** | **24** |

> 上表是首次执行的结果。B-12 后来确认只是 DEF-03 偶发造成的，用例改为“连接已关闭也算拒绝”，不再单独计入失败；当前已知失败项共 23 项，登记在 `regression/known-defects.txt`。

主流程正常：bind、submit、限流、计费、DR、多连接、窗口、热加载、Redis 故障恢复都符合预期。24 项失败里，20 项确认是缺陷（8 类），4 项需要确认设计意图。

## 2. 测试环境

本地 Redis 7.2.5，JDK 17，8 核 6GB。测试进程内启动真实的 `MultiSmppServer` 或 `SslSmppServer`，客户端用原始 SMPP 字节通信，能精确校验响应和异常输入。测试配置追加到本地 `cm.cfg` 副本，结束后恢复。

## 3. 缺陷

| # | 级别 | 问题 | 相关用例 | 实际结果 |
|---|---|---|---|---|
| DEF-01 | **高** | **bind 密码明文写入日志**：`SmppPduLogEnable` 默认打开，错误密码也会记录 | SEC-01 | 日志中查到测试密码 |
| DEF-02 | **高**（使用 TLS 时） | **TLS 客户收不到 DR**：只有 `MultiSmppServer` 启动 `DRStreamConsumer`，`SslSmppServer` 没有 | TLS-05 | 4 秒内没有收到 deliver_sm。提供的启动日志没有 TLS 模块，线上可能未使用 |
| DEF-03 | **高** | **bind 被拒时响应可能丢失**：关闭连接时没等发送队列写完，客户端只看到断开，不知道原因 | B-05、B-12 | 1000 次错误密码丢失 71 次（7.1%）。这是竞争问题，比例不固定：另一次 300 次为 0，探测时 500 次丢 12 次。B-12 同样偶发 |
| DEF-04 | 中 | **未知或畸形 PDU 不回响应**：协议要求回 generic_nack，客户端只能等超时 | P-03、P-04、P-05、P-06c、P-08（4 项） | 3 秒内无应答，连接保持，之后的正常 PDU 还能处理 |
| DEF-05 | 中 | **超长的密码或 system_id，bind 不回响应** | B-04b、B-04c | 3 秒内无应答。客户配置了超长密码时，看到的是 bind 超时，不是密码错误 |
| DEF-06 | 中 | **接收方式连接能提交消息** | P-10 | bind_receiver 后 submit 返回成功。修复前要确认线上是否有客户依赖 |
| DEF-07 | 中 | **没有密码防暴力破解** | SEC-02 | 300 次错误约 1.4 秒，没有限制（18 次“断开”是 DEF-03 造成的） |
| DEF-08 | 低 | **状态码不符合协议** | B-13、P-06a、P-06b、P-06d | 重复 bind 回 `0x08`，应为 `0x05`；不支持的命令回 `0x08`，应为 `0x03` |

失败项计数：DEF-01 1 项，DEF-02 1 项，DEF-03 2 项，DEF-04 8 项，DEF-05 2 项，DEF-06 1 项，DEF-07 1 项，DEF-08 4 项，共 20 项。

## 4. 需要确认设计意图

这些行为和配置说明或协议不一致，但可能是有意的，所以不计入缺陷。

| 用例 | 实际行为 | 说明 | 需要确认 |
|---|---|---|---|
| B-06 | 账号只有一个连接时，**不校验来源 IP**，配了别的 `URL` 也能 bind | `checkIPAddress` 列表只有 1 项时直接返回，只有多个连接时才按 IP 筛选（B-06b、B-06c 通过） | `URL` 是否应作为 IP 白名单。如果是，这是安全问题 |
| B-09b | `BindMode=T` 时 bind_transmitter 也能成功 | 配置 `T` 时，连接工厂可能拆成收、发两个连接（`AbstractConnectionFactory.java:194-200`），这是读代码推断的，没有证实 | 配置说明写的是 `T/Transmitter`，是否要改说明 |
| S-12、S-13 | 空接收号、非数字接收号，Server 回成功 | Server 不校验，`ChannelRouter` 等 Core 代码里有接收号错误处理。本次没有走 Core 验证 | 是否接受“先收后判失败” |

## 5. 其他观察

- **`thcon` 是全局开关**：这个 Redis key 不存在时，所有 submit 都回 `ESME_RTHROTTLED`（T-02），状态最多缓存 50 秒。state Redis 清空或重建后要先写回这个 key，否则所有客户都发不了消息。
- **`SmppServerInboundQueueFullCommandStatus`**：只接受 `ESME_RTHROTTLED` 或十进制数字。写其他名称（如 `ESME_RMSGQFUL`）时，不报错，也不生效，静默回退成限流。
- **DELETED 状态**：`GmmsStatus.DELETED`（10300）的 DR 显示为 `UNDELIV`，`DELETED` 对应的是 10800。本次按代码作为预期，是否合理需要业务确认。
- **响应可能乱序**：同一包的多条 submit，响应顺序可能和请求不同，SMPP 异步模式允许。
- **unbind 没有复现响应丢失**：K-02c 连续 100 次都收到了响应。代码走同样的关闭路径，理论上仍有风险。

## 6. 性能基线

固定 500 条/秒，运行 30 秒（另有 15 秒预热），全部成功。客户端单独一个进程，都在同一台机器。

| 连接数 | 收发连接 | p50 | p95 | p99 | 最大 | Server 线程 | RSS | bind 用时 |
|---|---|---|---|---|---|---|---|---|
| 20 | 20 | 2.3 ms | 5.9 ms | 7.2 ms | 34.4 ms | 141 | 953 MB | 0.4 秒 |
| 1000 | 100（其余空闲） | 3.0 ms | 7.9 ms | 10.9 ms | 77.2 ms | 2101 | 1194 MB | 8.3 秒 |

连接数增加 50 倍时，p99 增加约 3.7 ms。两组都只跑了一次，收发连接数也不同，只能说明没有明显变差。这不是吞吐上限测试，20000 条连接也没有测。

## 8. 多 Server 用例（`MultiServerIT`）

后续新增，用两个真实的 Server 进程验证多个 Server 加载不同客户、切换和故障恢复，47 项全部通过，没有发现新缺陷。用例见清单第九-B 节。

| 场景 | 结果 |
|---|---|
| 不同 Server 只加载配置给它的客户 | 符合预期，其他 Server 回 `ESME_RBINDFAIL` |
| `RELOAD_CUSTOMER` 切换、扩大、收回 `SmppServerModules` | 符合预期，只影响改动的客户 |
| reload 新增、删除客户 | 符合预期 |
| DR 跟随客户实际连接的 Server | 符合预期 |
| kill -9 和重启 | 符合预期 |

需要了解的行为：

- **改 `SmppServerModules` 也会断开这个客户的连接**，包括只是增加一个 Server 的情况。这和“改动的客户可以断开重建”的决定一致，客户要重连。
- **切换后客户不会自动转移**：旧 Server 断开后，客户端要连到新 Server 的地址。
- **客户只配在已死的 Server 上时**，不能转到其他 Server。Core 拿不到 DR stream，把 DR 交给重试策略。重试策略之后的链路属于 Core，没有在这里验证。
- **DR 切换有延迟**：Server 被 kill 后，Core 要等心跳过期（`ModuleStatusTTLSeconds`，默认 30 秒）才知道它已离线。用例把它调成 5 秒。

## 9. 测试中修正的用例

第一轮 22 项失败里，有几项是用例本身的问题，修正后才作为结果：

| 用例 | 问题 | 修正 |
|---|---|---|
| SEC-01 | 测试密码 14 位，超过 SMPP 上限，PDU 没解析，日志里没有，造成**假通过** | 改用 8 位密码后确认失败，并新增 B-04b、B-04c |
| S-07 | 预期 Server 解析 UDH 的分段信息 | 改为校验 UDH 和正文分开保存 |
| T-07 | 配了不支持的状态码名称 | 改用数字；不支持名称的情况记在第 5 节 |
| D-02 | 预期 DELETED 显示为 `DELETED` | 改为代码实际映射；记在第 5 节 |
| D-09a | 日志基线在 DR 发出之后才取 | 调整顺序 |
| B-05 | 300 次可能碰不到竞争 | 增加到 1000 次 |
| B-10a 等 | DEF-03 会让被拒的 bind 偶尔收不到响应，导致这些用例时好时坏 | “连接已关闭”也算拒绝，响应丢失只由 B-05 统计 |
| MS-* | 模块清单第一列写成节点号，Server 2 没加载自己的类型，看起来像切换失败 | 改正配置。第一列是启用标记 |
| MS-12、MS-21、MS-22 | 预期不符合已定的设计（改动的客户会重建连接、心跳过期前无法判断离线、无宽限期） | 按设计修正 |
