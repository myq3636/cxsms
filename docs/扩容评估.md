# 扩容评估：加机器、扩模块和 Redis 能提升多少

> 日期：2026-11-25。代码：`2eb4805`（ShardHash 间隔修正、DR 消费减少 Redis 往返）。
> 依据：4000 TPS 1 小时 `perf_long_PF007H_1125_0918`；5000 TPS `perf_long_PF002_1125_1202`（见 5.1，单机 CPU 和报告 Redis 已满，没有跑完，只能作为上限参考）。
> 相关：《模块规格评估》（单个模块的规格）、《Redis集群方案设计》（Redis Cluster 和应用层分片两种做法）、《Redis多主分片设计》。

## 1. 结论

- 加机器、加模块进程、加 Redis 主库，吞吐大体按比例增长，但**不能无限提升**。
- 现在单台 16 核在 4000 TPS 时已经用了约 11.4 核。先到上限的是**报告 Redis 单个主库的 CPU**（两个主库都在 91%）和整机的 CPU 总量。
- 按现在的代码，扩容的上限主要卡在以下几处：
  - 只有一个状态 Redis，估计上限在 2–3 万 TPS；
  - 分片总数固定 64，单个通道的并发最多 64；
  - 拆到多台机器后，访问 Redis 的往返时间变长，每个分片的吞吐会下降。
- 最佳组合不是一个固定个数，按第 5 节的原则配：报告 Redis 主库最先加；Core、Server、Client 按 CPU 跟上；Redis 单独放在同一可用区的机器上。

## 2. 现状：每 1000 TPS 的资源

测试环境是单台 16 核、61 GB 内存，模块和所有 Redis 都在 172.19.4.38 这一台上。

4000 TPS 1 小时的稳定期平均值如下（100% = 1 核）：

| 组件 | 进程数 | 4000 TPS 时 CPU | 每 1000 TPS | 说明 |
|---|---|---|---|---|
| Core | 3 | 415%（每个约 140%） | ~104% | 多线程 |
| Server | 2 | 217%（Server1 166%，Server2 52%） | ~54% | 客户连接集中在 Server1 |
| Client | 2 | 168%（每个约 84%） | ~42% | |
| 报告 Redis | 2 主（8388、8398） | 182%（每个 91%） | ~45% | 单线程，每个主库最多 100% |
| 提交 Redis | 2 主（8387、8397） | 134%（每个 67%） | ~34% | |
| 状态 Redis | 1（8386） | 12% | ~3% | 每秒 1.15 万条命令 |
| 压测工具 | 1 | 38% | ~10% | 生产环境没有 |
| **合计（不含压测工具）** | | **约 11.3 核** | **约 2.8 核** | 整机空闲中位 29%、最低 12% |

Java 模块是多线程的，一个进程可以用好几核；Redis 是单线程的，一个主库最多用 1 核。所以 Redis 只能靠加主库来扩，Java 模块既可以加进程，也可以给更多核。

## 3. 按线性推算的扩容规格

前提：
- 每个 Redis 主库的 CPU 不超过 60%，留出波峰和故障切换的余量；
- 每个 Core 约 150% CPU；
- Redis 单独放机器；
- 流量构成和 PF007 相近。

| 目标 TPS | 报告 Redis 主库 | 提交 Redis 主库 | 状态 Redis | Core / Server / Client | 总核数（约） | 机器（16 核） |
|---|---|---|---|---|---|---|
| 4000（现状） | 2 | 2 | 1 | 3 / 2 / 2 | 11.3 | 1 台（快到上限） |
| 5000 | 4 | 3 | 1 | 4 / 2 / 2 | 15 | 2 台：Redis 1，应用 1 |
| 10000 | 8 | 6 | 1 | 7 / 4 / 3 | 30 | 3 台：Redis 1，应用 2 |
| 20000 | 16 | 12 | 1（接近上限） | 14 / 8 / 6 | 60 | 5–6 台：Redis 2，应用 3–4 |

计算方法：
- 报告主库数 = 目标 TPS / 1000 × 45% / 60%；
- 提交主库数 = 目标 TPS / 1000 × 34% / 60%；
- Core 进程数 = 目标 TPS / 1000 × 104% / 150%；
- Server、Client 按每 1000 TPS 的 CPU 折算，各留约 30% 余量。

这张表没算第 4 节的损耗，实际要多配一些；拆到多台机器后尤其要考虑 4.3 的往返时间。

## 4. 为什么不能无限提升

### 4.1 状态 Redis 只有一个

- 状态 Redis（客户会话登记、限流计数、控制命令等）没有分片。
- 4000 TPS 时它每秒 1.15 万条命令、12% CPU。按比例推，单个实例在 70% CPU 时约能撑 2.3 万 TPS，100% 时约 3.3 万 TPS。
- 再往上要把状态 Redis 也按客户分到多个实例，需要改代码。可以参照报告 Redis 和提交 Redis 的多主做法（《Redis多主分片设计》）。

### 4.2 分片总数固定 64

- `TotalShards=64`，每个流同一时刻只有一个处理线程（`processingMap`），一批里的消息逐条处理。
- 一个通道的 DR 并发上限就是它的分片数：默认 `StreamShardsDefault=8`，最多 64。
- 4000 TPS 时 9981 每秒约 3200 条 DR，8 个分片每个约 400 条/秒。一个流量很大的通道，最多也只能分到 64 个分片；而且每个分片固定落在一个 Redis 主库上，热点通道还会把压力集中到部分主库。
- Core 进程认领分片，64 个分片要能平均分给每个 Core，所以 Core 进程数最好是 64 的约数（2、4、8、16），或者接近平均。
- 再往上要改 `TotalShards`。它决定数据在主库上的分布，改动时要先停流量迁移数据，或者做双写过渡。

### 4.3 拆到多台机器后往返时间变长

- 现在 Redis 和模块在同一台机器上，一次往返不到 0.1 ms。
- 云内网跨机器通常 0.2–0.5 ms，跨可用区更长。
- 4000 TPS 前的 jstack 显示，DR 处理线程 92% 的时间在等 Redis（《DR消费减少Redis往返设计》第 1 节）。每条 DR 的 Redis 往返这次已经减少，但处理线程还是以等 Redis 为主。所以往返时间每翻一倍，一个分片每秒能处理的条数就接近减半。
- 应对办法：
  - Redis 和应用放在同一可用区，尽量用低延迟网络；
  - 给热点通道调大 `StreamShards`，比如 16 或 32；
  - 继续减少每条 DR 的往返次数（4.5）。
- 这一项要靠实测确定（第 6 节）。拆到多台机器后单分片吞吐降多少，直接决定第 3 节要多配多少。

### 4.4 客户和通道一端的上限

- 每个连接的窗口（`WindowSize`）、限速（`SMSOptionOutgoingThrottlingNum`、`SMSOptionIncomingThrottlingNum`）、bind 数（`SessionNumber`）；
- 对方系统本身的处理能力；
- 系统总的入口阈值（`ThrottlingControl.SystemIncomingThreshold`）。

这些都和网关有多少机器无关。一个通道的上限要和对方一起定。

### 4.5 每条 DR 的报告 Redis 命令还可以再少

- 报告 Redis 是现在最先满的。这次的改动后，粗算每条 DR 的报告 Redis 命令少了约 1/5。
- 《DR消费减少Redis往返设计》3.4（一批的客户 DR 合并写入）已做。4000 TPS 时报告 Redis CPU 从 91% 降到 87%，命令数不变；合并的是往返，不是命令。见该文档第 8 节。
- 剩下能少的是命令本身，例如每条 DR 的 SADD、ZADD 在同一个流上只做一次。这要改流的登记方式，改动比 3.4 大，建议在扩到 1 万 TPS 以上之前再评估。

### 4.6 其他

- **MySQL、CDR 文件和 smsui**：现在占用很少，但都是单点。规模大了之后，要看写 CDR 的磁盘和数据库。
- **Redis 从库**：压测时停了从库（`--no-replicas`），生产环境要开。主从复制会给主库再加一些 CPU 和网络，第 3 节的 60% 余量里包含了这部分。
- **内存**：DR 能当场处理完时，报告 Redis 内存很小（4000 TPS 时 21 MB）。一旦积压就涨得很快：改动前 1 小时涨到 2652 MB，上次 5000 TPS 也是因为 8388 内存超过 90% 被保护停了。所以每个主库的 `maxmemory` 要能容纳几分钟的积压。

## 5. 最佳组合的原则

| 项 | 原则 |
|---|---|
| 报告 Redis 主库数 | 最先加。按每 1000 TPS 约 45% CPU 算，每个主库控制在 60% 以内 |
| 提交 Redis 主库数 | 约为报告主库数的 3/4，每个主库控制在 60% 以内 |
| 状态 Redis | 保持 1 个，到 2 万 TPS 左右再考虑分片（4.1） |
| Core | 每个约 150% CPU；数量约为报告主库数的 0.8–1 倍；64 个分片能平均分给每个 Core |
| Server | 约为 Core 数的一半；还要按客户连接数和分布来配，避免像现在一样集中在一个 Server 上 |
| Client | 约为 Core 数的 0.4 倍；还要按通道连接数来配 |
| 机器 | Redis 单独放机器，和应用在同一可用区；一台 16 核的机器上，Redis 主库数不超过 12–14 个，留出系统和复制的核 |
| 热点通道 | 单独调大 `StreamShards`（16 或 32），保证一个通道的流量能分到足够的分片和主库上 |

## 5.1 5000 TPS 实测（2026-11-25，单台 16 核）

用例 `PF002_5000tps_1h`：客户 RTCS1（9995）占约 75% 的 MT，大部分 DR 来自通道 RTVS1（9991）。每个 ssid 默认 8 个分片。不抓包，停 Redis 从库。

| 项 | 改动前 `perf_long_PF002_1124_2129` | 本次 `perf_long_PF002_1125_1202`（ShardHash 修正 + DR 3.1–3.3） | 对照：4000 TPS `perf_long_PF007H_1125_0918` |
|---|---|---|---|
| 结果 | 保护停止（发送 36 分钟，报告 Redis 8388 内存 > 90%） | 保护停止（发送 39 分钟，原因相同） | 通过 |
| `core:inbound-dr:9991` 积压增长 | +1490/s | +1399/s | 0 |
| `mt:pending:9995` 积压增长 | +1270/s | +1133/s | 0 |
| 积压最多 | 601 万 | 587 万 | 5742 |
| 整机 CPU 空闲 平均 / 最低（采样） | 20% / 14% | 16% / 8% | 26% |
| Core 三个 CPU（%） | 155 / 149 / 148 | 179 / 133 / 136 | 142 / 137 / 138 |
| Client 两个 CPU（%） | 111 / 112 | 138 / 86 | 84 / 84 |
| Server 两个 CPU（%） | 150 / 32 | 177 / 37 | 166 / 52 |
| 报告 Redis 8388 / 8398 CPU，每秒命令 | 84% / 84%，9.1 万 | 96% / 95%，10.3 万 | 91% / 91%，11 万 |
| 提交 Redis 8387 / 8397 CPU，每秒命令 | 85% / 85%，9.3 万 | 87% / 87%，9.3 万 | 67% / 67%，6.9 万 |
| 状态 Redis 8386 CPU，每秒命令 | 17%，8700 | 6%，3000 | 12%，1.15 万 |

平均值取预热后到保护停止前（改动前 30 分钟，本次 33 分钟）。

- 本次比改动前好一些：两个积压的增长各少 6%–11%，多跑了 3 分钟；状态 Redis 降到 6%。
- 但 5000 TPS 在这台机器上同时碰到三个上限，单靠减少 Redis 往返解决不了：
  1. **整机 CPU**：平均空闲只有 16%，最低 8%，和第 3 节估算的 5000 TPS 约需 15 核一致。
  2. **报告 Redis**：两个主都在 95% 以上。
  3. **热点 ssid 的分片数**：9995 的 MT 和 9991 的 DR 都只有 8 个分片（4.2），MT 也积压了。所以这次连 submit 也受影响，这是 4000 TPS 时没有的。
- 结论：要在单台机器上跑 5000 TPS 这种集中流量，至少要给 9995、9991 配 `StreamShards:16`，报告 Redis 再减负（3.4 合并写入）；要稳定跑，需要按第 3 节拆出 Redis 机器。

### 加 16 分片和 3.4 合并写入后再跑（`perf_long_PF002S_1125_1515`）

用例 `PF002_5000tps_1h_shards16`，和 PF002 只差 9995、9991 配 `StreamShards:16`，代码加了 3.4。15:41 因为**日志盘剩余低于 20 GB** 被保护停止，测试机的 CDR 文件占满了盘。所以三次都只取预热后同样的 19 分钟来比：

| 项（预热后 19 分钟） | `PF002_1124_2129` | `PF002_1125_1202` | `PF002S_1125_1515`（16 分片 + 3.4） |
|---|---|---|---|
| `core:inbound-dr:9991` | 51 万 → 215 万，+1.5k/s | 38 万 → 193 万，+1.4k/s | 不积压（最多 1648） |
| `mt:pending:9995` | 37 万 → 167 万，+1211/s | 36 万 → 153 万，+1083/s | 23 万 → 103 万，+744/s |
| `mt:routed:9991` | 无 | 无 | 10 万 → 41 万，+287/s |
| 发给通道的 MT（估算） | 约 3800/s | 约 3920/s | 约 3970/s |
| 发给客户的 DR（估算） | 约 2300/s | 约 2500/s | 约 3970/s |
| 报告 Redis 内存（8388） | 433 → 1846 MB | 346 → 1690 MB | 89 → 344 MB |
| 提交 Redis 内存（8387） | 227 → 1017 MB | 218 → 979 MB | 271 → 1317 MB |
| 报告 Redis CPU，每秒命令 | 84%，9.3 万 | 96%，10.5 万 | 97%–98%，12.1 万 |
| 提交 Redis CPU，每秒命令 | 85%，9.5 万 | 87%，9.4 万 | 91%，10.2 万 |
| 状态 Redis CPU | 17% | 6% | 7% |
| 整机 CPU 空闲 平均 / 中位 / 最低 | 20% / – / 14% | 16% / 17% / 8% | 15% / 16% / 9% |
| Core 三个 CPU（%） | 156 / 149 / 150 | 180 / 135 / 136 | 170 / 151 / 140 |
| Client 两个 CPU（%） | 111 / 112 | 138 / 87 | 125 / 102 |
| Server 两个 CPU（%） | 149 / 32 | 178 / 36 | 190 / 40 |

“发给通道的 MT”按 5000 减去 `mt:pending` 和 `mt:routed` 的增长估算，“发给客户的 DR”再减去 `inbound-dr` 的增长估算。这次保护停止后测试工具没有输出延迟统计。

- **16 分片解决了 DR 一侧**：9991 的 DR 当场处理完，发给客户的 DR 和发出的 MT 持平，报告 Redis 内存不再上涨。前两次都是因为报告 Redis 内存超过 90% 被停的，这次即使盘够，报告 Redis 也不会先触发保护。
- **MT 一侧仍然跟不上**：Core 路由得比上次多，但 Client 发给 9991 的又积压了。发出的 MT 总量约 3970/s，和前两次差不多。
- **原因是整机资源用完了**：
  - 4 个 Redis 主的 CPU 是：提交 91%，报告 97%–98%，单线程已经到顶。
  - 整机空闲中位 16%。
  - 同样的资源原来有 1/3 被积压浪费在了排队上，现在 MT 和 DR 都做完整，总处理量（MT + DR）从每秒约 6100–6400 条升到约 7900 条，但到不了 1 万条（5000 MT + 5000 DR）。
- 提交 Redis 内存每分钟涨约 55 MB，如果磁盘够，大约在开始后 50 分钟会因为提交 Redis 内存超过 90% 被保护停止。
- **结论**：这台 16 核机器上完整处理（MT + DR）的上限约为 4000 TPS。和第 3 节的估算一致：5000 TPS 需要约 15 核加 5–6 个 Redis 主。要跑 5000 TPS 或以上，需要按第 3 节把 Redis 拆到单独的机器上。热点 ssid 配 `StreamShards:16` 在拆开后也要保留。

## 6. 要补的测试

1. **5000 TPS 1 小时**：已跑三次，见 5.1。最后一次（16 分片 + 3.4）因测试机磁盘不足只跑了 24 分钟。单台机器的结论已经清楚，不必在这台机器上再跑满 1 小时；要再跑的话，先清理 `/mnt/a2p/cdr/link`。
2. **两台机器的阶梯测试**：
   - Redis 放一台、应用放一台，按 4000、6000、8000 TPS 逐级跑，每级 10–20 分钟；
   - 测拆开后的 Redis 往返时间、每个分片每秒的 DR 处理数，以及每 1000 TPS 的资源；
   - 用结果修正第 3 节的表。
3. **热点通道测试**：一个通道占大部分流量，分别配 `StreamShards` 8、16、32，看单个通道的上限和主库负载是否均衡。
