# 流模式下 SystemManager、模块间连接代码的清理分析

> 2026-11-24。只做分析，没有改代码。问题：系统已经用 Redis 流在模块间传消息，SystemManager（系统管理模块）的控制线程、ModuleManagement 和模块之间的 TCP 连接相关代码还在不在运行、还有没有用、哪些可以优化。

## 1. 运行时：已经都没在跑

测试机（`SystemManager.enable=false`，没有 SystemManager 进程）上，对 CoreEngine1、MultiSmppClient1、MultiSmppServer1、MsgQueueMonitor1、CommonHttpClient1 抓线程转储（`jstack`，按线程名和栈上第一个 `com.king` 类归类）、看监听端口：

- **没有** SystemManager 的线程（`SystemClientSessionThread`、`SystemServerSessionThread`、`ReportInMsgCountTimer` 等），**没有**模块间内部连接的线程（`InternalAgentSession` 等）；匿名线程池全部是 Redis 流的消费者（`MTStreamConsumer`、`ResultStreamConsumer`、`InboundDRStreamConsumer`、`OutboundStreamConsumer`、`DRStreamConsumer`、`RedisStreamAutoClaimRunner`、`CoreMQMStreamConsumer`）。
- 监听端口：只有 MultiSmppServer1 的客户 SMPP 端口 16272；Core、Client、MQM、HTTP Client 都不再监听模块间连接的端口。

所以问题不在多占线程，而在：代码量大、启动和重载时还做一些无用功、几条仍在走老路径的功能实际已经坏了（第 3 节）。

## 3. 优化点

### 3.1 仍在走老路径、实际已经坏了的功能（优先）

| # | 功能 | 现在 | 后果 | 改法 |
|---|---|---|---|---|
| 1 | **HTTP 通道主动查询 DR / MO**（`QueryHttpMessageThread`，cm `HttpQueryMessageFlag` 为 MtDr、WemediaDr、Mo、SouthDR 等的通道） | 查回来的 DR（`CommonHttpSession` 设为 `DELIVERY_REPORT`）、MO 走 `HttpSession.putGmmsMessage2RouterQueue`：应答类型已改到结果流，DR、MO 仍找内部路由 | 日志 "Can not find the alive delivery router"，**DR / MO 丢失**（那里的日志写的是"没写进 Redis"，但它根本没去 Redis） | DR → `produceInboundDeliveryReport`，MO → `produceSubmitMessage`（和 HTTP Server 的 servlet 一样） |
| 2 | 同样的模式：`CommonRESTHttpSession`、`ClickatellSession`、`WebServiceSession`、`SpringSession`、`AcceletSession`、`PeeringTcp2Session` | 非应答类型（DR、MO）走内部路由 | 同上（只影响用这些协议的通道） | 逐个改到流；统一到一个公共方法 |
| 3 | **HTTP 客户查询 DR**（`CommonRESTHttpDRQueryServlet`，`DELIVERY_REPORT_QUERY`） | 等 Core 通过内部连接回答；`AbstractHttpServer.putGmmsMessage2RouterQueue` 对这个类型保留了老路径 | 查询没有回答 | 设计一个流上的请求 / 应答（或者直接查 DB / Redis 的 DR 状态） |
| 4 | **HTTP 查询的单节点运行**：SystemManager 打开时由它分配"谁去查这个通道"（`applyHttpQueryFlag`） | 关闭时每个 CommonHttpClient 模块都去查 | 部署 2 个以上 CommonHttpClient 时，**同一个通道被重复查询，DR / MO 重复** | 用 Redis 锁（和 MQM 主备 `MqmActiveCoordinator` 一样）选一个节点查 |
| 5 | **Redis 切换命令 `SWITCH_REDIS`**：可以通过 Redis 控制命令发出（`RedisControlSubscriber`） | 只有 SystemManager 监听；DB 切换有 SystemManager 关闭时用的 `DbSwitchListener`，Redis 没有 | 发了不生效 | 确认 Redis 切换现在靠什么（`RedisMonitor` / `setRedisHaFlag`），需要就加一个和 `DbSwitchListener` 一样的监听，或者去掉这个命令 |

### 3.2 删掉 SystemManager（确认替代后）

SystemManager 的功能和现在的替代：

| SystemManager 做的 | 现在 | 状态 |
|---|---|---|
| 模块注册、状态、停止（`ModuleRegister*`、`ModuleStop*`） | `ModuleRegistry`、`ModuleStatusReporter`、`ModuleOps`、`A2pCtl`、`GracefulStop` | 已替代 |
| 停机、各类重载命令 | `RedisControlSubscriber`（`SHUTDOWN`、各 `*_RELOAD`、`GMMS_CONFIG_RELOAD`） | 已替代 |
| DB 切换（`ChangeDB`） | `DbSwitchListener` | 已替代 |
| Redis 切换（`ChangeRedis`） | 无 | **3.1 第 5 项** |
| 客户 bind 汇总（`InBind*`、`OutBind*`、`ConnectionStatusNotification`、`ConnectionConfirm`） | `SmppServerSessionRegistry`（Redis） | 已替代 |
| 收侧限流配额（`ApplyInThrottleQuota`、`ReportInMsgCount`） | 收侧限流用 Redis 计数（`throttle:in:{ssid}:{秒}`） | 已替代（实施时核对 `ThrottlingControl` 两个分支的差别） |
| HTTP 查询分配（`QueryHttpRequest`） | 无 | **3.1 第 4 项** |

替代都有了之后：删 `gmms/ha/systemmanagement`、`connectionpool/systemmanagement` 中只为它服务的部分、41 处 `isEnableSysMgt` 分支、`SystemManager.*` 配置项和 `SystemManager1.sh`、`SystemManager2.sh`，约 1 万行。

### 3.3 启动、重载时的无用功（小改动，可以先做）

- **Client 启动**：`MultiSmppClient`、`CommonHttpClient`、`SslSmppClient`、`PeeringTcp2Client`、`SpringClient` 仍对每个 Core 调 `InternalAgentConnectionFactory.initInternalConnectionFactory`，建 `ConnectionManager`、`Connection`、`InternalAgentSession` 对象（不连接）。去掉。
- **Core 配置重载**：`A2PCustomerManager` 重载客户时无条件调 `ConnectionManagementForCore.getInstance().clearConnection / initConnection`；第一次调用时 `ConnectionManagement` 的构造函数按 `LongConnectionProtocols`（默认 SMPP）给**所有**这类客户建连接管理（测试机 4000 多个），`ForCore` 的构造函数随即又清空。只在 SystemManager 打开时调用（或者直接去掉）。
- `MultiSmppSession` 构造时取 `InternalAgentConnectionFactory`，它的 `putGmmsMessage2RouterQueue` 唯一的调用在注释里：删掉。

### 3.4 内部连接代码和 `InternalCoreEngineSession` 的重构（之后）

- 把 Core 的处理逻辑（`processSubmit`、`handleOutboundResult`、`handleInboundDRInternal`、`processDeliveryReport` 等）从 `InternalCoreEngineSession` 搬到一个不带 TCP 会话的类（例如 `CoreMessageProcessor`），流消费者调它；`InternalCoreEngineSession`、`AbstractInternalSession`、`InternalAgentSession`、两个内部连接工厂、`OperatorMessageQueue` 路由队列、各会话的 `putGmmsMessage2RouterQueue`（3.1 改完后）、INNER_ACK 一起删掉。
- `ModuleManager`：去掉 `selectRouter`、`selectAliveRouter`、`getRouterConnectionInfo` 等只为内部连接用的方法和 `ModuleManagement.xml` 里连接信息的解析；模块列表只来自 `a2p_modules.conf` + Redis 模块注册。部署时不再需要 `ModuleManagement.xml`（先确认 HTTP Server 的命令端口等还用到的字段都能从 `a2p_modules.conf` 取到）。
- 改动面大、牵涉的回归测试多，等 3.1～3.3 做完再做。

### 3.5 建议的顺序

1. **3.1 第 1～4 项**（功能问题；先确认线上有没有用主动查询 DR / MO 的 HTTP 通道、REST DR 查询、多个 CommonHttpClient）；第 5 项确认 Redis 切换的现状。
2. **3.3**：改动小，去掉启动和重载的无用功。
3. **3.2**：替代都确认后删 SystemManager。
4. **3.4**：重构 Core 的处理逻辑，删内部连接代码和 `ModuleManagement.xml`。
5. 确认 `com.king.mgt` 和 `smsui` 还用不用，不用就一起删。

|---|---|---|
| HTTP 通道主动查询 DR / MO | 不需要 | 第 1、4 项不修；`QueryHttpMessageThread` 和各会话里查询相关的代码可以在 3.4 里一起删 |
| 客户用 REST 查询 DR | 没有 | 第 3 项不修；`CommonRESTHttpDRQueryServlet` 可以删 |

| `com.king.mgt` | 在用：smsui 通过 telnet 执行命令，reload 后发布命令 | 保留；`TelnetSession` 把命令转成 Redis 控制命令发到 `channel:gmms:control`，不经过 SystemManager |
| Redis 切换命令 | 见 4.1 | 第 5 项 |

### 4.1 Redis 切换

现状：
- telnet `switchredis master|slave` → mgt 的 `TelnetSession` 发布 `SWITCH_REDIS:master|slave` 到状态 Redis 的 `channel:gmms:control` → **所有模块**的 `RedisControlSubscriber` 都收到，转成 `TYPE_SWITCHREDIS` 事件；但只有 SystemManager 监听这个事件，模块里没有监听（DB 切换有 `DbSwitchListener`，Redis 没有），所以**发了不生效**。
- SystemManager 打开时，切换由它的 `RedisMonitor` 做：监测主、把从提升为主（`SLAVEOF NO ONE`）、再用 TCP 的 `ChangeRedis` 通知各模块调 `RedisClient.setRedisHaFlag`。SystemManager 关闭后，**现在没有任何 Redis 主备切换**（自动、命令都没有）。
- 模块切换本身已经有：`setRedisHaFlag(true/false)` 把状态 Redis 和所有 submit / report 主一起换到主或从的地址，旧连接池延迟销毁。

能不能把切换命令直接发给所有模块：**发送已经是发给所有模块的**，补一个和 `DbSwitchListener` 一样的 `RedisSwitchListener`（收到后调 `setRedisHaFlag`）就能用于**计划内切换**（主还活着，比如维护）。但用于**主故障**还不够：

| 问题 | 说明 | 办法 |
|---|---|---|
| 命令通道在要切走的那台 Redis 上 | 控制频道在当前状态 Redis 主上；主挂了，mgt 发不出去，模块也收不到 | 模块同时订阅主、从两边的控制频道；mgt 两边都发（或者发到能连上的那台） |
| 从要先提升为主 | 从是只读的，不提升就切过去，写入全部失败 | mgt 处理 `switchredis` 时先对目标执行 `SLAVEOF NO ONE`（由一处执行），再发布 |
| 重启的模块回到旧的一边 | 模块启动时写死 `initRedisClient("M")`；切换后重启的模块会连回旧主，两边同时在写 | 把"当前用哪一边"记下来（每台机器的文件，或者两边 Redis 都写一个键，以 `INFO replication` 里的角色为准），启动时读 |
| 旧主恢复后 | 没收到命令的模块、或者恢复的旧主仍当自己是主，可能两边同时写 | 旧主恢复后先执行 `SLAVEOF` 新主再放回；模块切换后核对目标的角色是 master |
| 异步复制 | 切换瞬间主上最后的写入可能没复制到从：流里的少量消息、消费组进度 | 属于 Redis 故障时的影响，符合"只在系统或 Redis 异常时受影响"；切换后 MQM、自动认领会补处理已复制的未确认条目 |
| 多主 | `setRedisHaFlag` 是所有主一起切；一个 report 主坏了也要全部切换 | 需要时按实例切换（每个主各自的主从） |

建议：计划内切换可以先补 `RedisSwitchListener`（改动小）；主故障的自动切换，与其补齐上面这些自己做，不如用 Redis Sentinel（Jedis 有 `JedisSentinelPool`，客户端自动发现新主，提升和旧主降级都由 Sentinel 做；多主时每个主一组）。

### 4.2 手动切换已实现（2026-11-24）

和 reload cm、routing 一样的模式：telnet `switchredis master|slave` → mgt 发布 `SWITCH_REDIS:master|slave` 到 `channel:gmms:control` → 每个模块（含 mgt 自己、Tomcat 里的 CommonHttpServer）的 `RedisControlSubscriber` 转成 `TYPE_SWITCHREDIS` → **`RedisSwitchListener`**（和 `DbSwitchListener` 一起在 SystemManager 关闭时注册）：

1. 已经在目标一边：只更新 `ha/RedisStatus`。
2. 目标一边的每个 Redis（状态 Redis、所有 submit / report 主或从）都要回答 `role:master`，否则**不切**，打 `[REDIS-SWITCH] not switched … (promote it first: SLAVEOF NO ONE)` ERROR：模块不会切到只读的从上。所以切换前，运维先把目标一边提升为主。
3. `RedisClient.setRedisHaFlag`：状态 Redis 和所有 MQ 实例一起换，旧连接池延迟销毁。
4. 写 `ha/RedisStatus`（`Used=M|S`）。
5. 控制频道马上在新的状态 Redis 上重新订阅（`RedisControlSubscriber.resubscribe`），之后的 reload、切换命令照样收得到（mgt 自己也切了，之后发布在新的状态 Redis 上）。

启动：模块原来一律写死 `"M"`；现在 `GmmsUtility.initRedisClient` 先看哪一边的状态 Redis 回答 `role:master`（先问主一边），用那一边；两边都不是 master（都连不上）时用 `ha/RedisStatus`，再没有就用调用方给的（`M`）。切换后重启的模块不会连回旧主（前提：旧主恢复后已降为从）。

回归：`RedisSwitchIT`（8 项）：目标不是 master 时拒绝；切到从一边、写 `ha/RedisStatus`；切换后 Redis 正常读写；控制频道切换后仍收得到（再切回主）；重复命令不做事；启动时以回答 master 的一边为准，都不回答时用 `ha/RedisStatus`。

**操作步骤**（计划内切换，例：切到从）：
1. 对从一边的每个 Redis 执行 `SLAVEOF NO ONE`（状态 Redis、每个 submit / report 主对应的从）；
2. smsui / telnet：`switchredis slave`；看各模块日志 `[REDIS-SWITCH] on the slave side now`；
3. 原来的主一边改为新主的从（`SLAVEOF {新主}`），避免两边都是 master；
4. 切回：等原主追平后，反过来做一遍（提升原主、`switchredis master`、再把从降回去）。

### 4.3 自动切换（未做）

MQM 现在**没有**监测 Redis 状态的逻辑，只有 DB 的 `DbHealthDetector`（只在 active MQM 上探测，主连续失败达阈值、从可达时发布 `SWITCH_DB:slave`，切回只手动）。照它做一个 `RedisHealthDetector` 有两个不同：

- MQM 的 active 选举（租约、fence）本身放在状态 Redis 上；状态 Redis 主挂了，active MQM 续不了租，探测器也就停了。需要不依赖状态 Redis 的选举（例如 DB 锁），或者两个 MQM 都探测、都发（命令是幂等的）。
- 主挂了，控制频道也在它上面：探测器要先提升从（`SLAVEOF NO ONE`），再发布到**从**上的控制频道；模块要同时订阅主、从两边的控制频道才收得到。

所以建议自动切换用 Redis Sentinel（Jedis `JedisSentinelPool`），而不是在 MQM 里自己做。
