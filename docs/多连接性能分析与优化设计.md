# 多连接性能分析与优化设计

> 依据：2026-11-20 `PF008_multiconn`（2000 个客户、2000 个通道，各 8 个 bind；每个 Server 8000 个客户连接，每个 Client 8000 个通道连接），1000 TPS 一档 10 分钟（`/usr/local/a2p/log/perf_step_PF008_1120_1522`）；对照 `PF005_step` 3000 TPS（2 个客户组、2 个通道，`perf_step_PF005_1119_2023`）。系统配置见《多连接部署系统配置》。本文只是分析和设计，没有改代码。

## 1. 这次的结果

| 项 | 结果 |
|---|---|
| 发出 MT / submit 被拒 | 599,999 / 0 |
| DR / 预热后没收到 DR 的 | 599,999 / 0 |
| 积压 | 稳定（每秒 -1），最多 1.7 万（都是在途） |
| 提交 → 通道 | p50 55 ms，p95 134 ms，p99 554 ms |
| 整机 CPU 空闲 | 中位 49%，最低 8% |
| 启动 | 两个 Client 建 1.6 万个通道连接约 2～3 分钟；测试工具并行建 1.4 万个客户 bind 18 秒 |

结论：这个规模下 1000 TPS 稳定，但**每条消息的成本比少连接时高很多**，见第 2 节。

## 2. 成本在哪里

### 2.1 每 1000 TPS 的 CPU（%，100 = 一个核）

按两边的发送区间计算：PF008 是 15:27～15:35，PF005 3000 TPS 取开始后 90～570 秒。`report.md` 里的"稳定期平均 CPU"不能直接用：`perf_step.sh` 跑完一档就删掉这一档的用例副本，`phases.txt` 也跟着没了，报告只能按整个监控文件平均，启动时各模块约 100% 的 CPU 也被算了进去。这一点已经修复，见 3.4。

| 角色 | PF005（3000 TPS，折算到每 1000） | PF008（1000 TPS） | 倍数 |
|---|---|---|---|
| Core | 163 | 344 | 2.1 |
| Client | 48 | 115 | 2.4 |
| Server | 65 | 157 | 2.4 |
| Redis | 120 | 252 | 2.1 |
| MQM | 1 | 2 | — |
| 合计 | 约 4 个核 | **约 8.7 个核**（整机空闲 42%） | **2.2** |

### 2.2 每条消息的 Redis 命令

| 用例 | 稳定期每秒命令 | TPS | 每条消息 |
|---|---|---|---|
| PF005 | 33.7 万 | 3000 | 112 |
| PF008 | 21.7 万 | 1000 | **217** |

另外，负载结束后（15:38:57～15:39:37）没有消息，report MQ 仍有每秒 6 万～10 万条命令，是每 5 分钟一次的全量扫描（2.4 节）。

### 2.3 流太多：每个流平均两分钟一条消息

每类 stream 都是"ssid × `TotalShards`（64）"个。每个客户每档约 300 条、号码随机，几乎落满 64 个分片：

| 流 | 按什么分 | 个数 |
|---|---|---|
| `mt:pending`（Server → Core） | 客户 × 64 | 约 12.8 万 |
| `mt:routed`（Core → Client） | 通道 × 64 | 约 12.8 万 |
| `core:results` | submit 结果按通道、DR 结果按客户，× 64 | 最多约 25.6 万 |
| `core:inbound-dr` | 通道 × 64 | 约 12.8 万 |
| `dr:pending`（Core → Server） | 客户 × 64 | 约 12.8 万 |
| 合计 | | **约 77 万** |

1000 TPS 时每个流平均 128 秒才来一条。于是每条消息每经过一段，都要单独走一遍完整的流程：按门铃、调度线程弹出、提交任务、`XREADGROUP` 读到 1 条、确认、看要不要再按门铃。少连接时一次能取 100 条、按批处理的优化，在这里全部失效。这是每条消息的 Redis 命令翻倍、Core 和 Client CPU 翻倍的主要原因。

### 2.4 和流数量成正比的后台扫描

| 扫描 | 频率 | 每次做什么 | 77 万个流时 |
|---|---|---|---|
| 自动认领 `RedisStreamAutoClaimRunner` | `RedisStreamAutoClaimIntervalMs`（服务器 60 秒），每个消费者类型一个 | 本模块负责的**每个流**一次 `XPENDING`（逐个往返，不走 pipeline） | 每个 Core 每分钟约 17 万次往返（MT、结果、通道 DR 三类），Client、Server 各约 6 万次 |
| backlog 监控 `scanBacklogPattern` | `RedisStreamMonitor.IntervalSeconds`（30 秒）；每 `FullScanEveryCycles`（10）轮扫一次全部流 | 每个流 `XLEN`、`XPENDING`、`ZSCORE`（pipeline） | 每 5 分钟每个模块对它的流各 3 条命令，合计几百万条 |
| 流索引 `idx:streams` | 生产时 `SADD`；每 `RedisStreamIndexFullScanMinutes`（60）分钟 `SCAN` 全部 key | — | 集合 77 万个成员；流用完后 key 不删，只增不减 |

这些开销和消息量无关，只和流的数量有关。

### 2.5 线程

| 模块 | 每个会话的线程 | 8000 个会话 |
|---|---|---|
| Client | `Receiver`（阻塞读）、`Sender`（异步写队列）、2 个 `CustReceiver`（处理收到的 PDU，cm 的 `Min/MaxReceiverNumber`）、`ClientSessionThread`（连接维护：重连、bind、enquire_link） | 约 4 万个 |
| Server | `Receiver`、`Sender`（收到的 PDU 已经走共享池 `SmppServerInboundSharedPoolEnable`，不再每会话建 `CustReceiver`） | 约 1.6 万个 |

线程绝大多数时间在等待，CPU 不在线程本身。问题是：线程数让 `vm.max_map_count`、`nproc` 成为硬限制（《多连接部署系统配置》），每个线程的栈和 TLAB 占内存，以及大量的线程切换。

### 2.6 其他

- **Client 启动**：`MultiSmppClientFactory` 每建一个会话都 `Thread.sleep(10)`，8000 个会话就是 80 秒以上。
- **Server 监听 backlog**：`AbstractServer` 用 `new ServerSocket(port)`，Java 默认值 50，**实测会丢 SYN**：同时向 MultiSmppServer1 发起 4000 个连接，accept 队列溢出 8604 次、SYN 被丢 12087 个，建连 p50 1.27 秒、p90 3.27 秒、p99 7.27 秒（SYN 重传的 1、2、4 秒），99% 超过 0.9 秒。对照：同样的 4000 个连接打一个 backlog 4096 的监听，SYN 丢 0 个，最长 0.63 秒；打 backlog 50 的同一个监听，丢 2782 个、最长 3.5 秒（a2p Server 每接受一个连接要建线程，accept 慢，所以更差）。开机 4 天的内核计数是溢出 40522 次、丢 SYN 41377 个，大部分应该来自测试工具的通道监听 27001（同样是 backlog 50，Client 启动时 1～2 分钟内连 1.6 万个），这会拖慢 Client 建通道连接；测试工具已改为 backlog 4096（`vendor.backlog`）。
- **MQM**：报告里的 23% 是统计口径问题（2.1）。MQM 只在启动加载 4000 个 cm 块时约 100%（有一刻 300%），发送期间 0～4%，和少连接时一样。

## 3. 优化设计

按收益和风险排序。

### 3.1 分片数按 ssid 配置（收益最大）

**现状**：每个 ssid 的每类 stream 都分 `TotalShards`（64）个分片。

**改为**：每个 ssid 用 `S` 个分片，`S` 按 ssid 配置（cm 新增 `StreamShards`）；没配时用默认值 `StreamShardsDefault`，**默认 8**（0 = `TotalShards`）。

默认取 8 的理由（一个 ssid 的流量落在 3 个 Core、2 个 Client 上，对所有偏移统计最忙的那个分到多少）：

| S | 间隔 | 最忙的 Core（理想 33%） | 最忙的 Client（理想 50%） | 4000 个 ssid 每类流的数量 |
|---|---|---|---|---|
| 3 | 21 | 平均 34%，最差 67% | 总是 67%（2:1） | 1.2 万 |
| 4 | 16 | 50% | 50% | 1.6 万 |
| 6 | 10（除不尽 64） | 平均 37%，最差 50% | 平均 53%，最差 67% | 2.4 万 |
| 8 | 8 | 38%（3:3:2） | 50%（4:4） | 3.2 万 |
| 64 | 1 | 34% | 50% | 25.6 万 |

**中途调大**（如 8 → 32 或 64，cm 重新加载即生效）：已在流里的消息照常处理、不丢；取能整除 `TotalShards` 的值时，原来的分片包含在新的里。切换那一刻同一个号码的消息可能乱序（旧流还没排空，新消息进了别的流）；跨过那一刻的长短信各段可能分到两个 Core，仍在 Redis 里合并（`RedisCsmReassembler`）。各模块加载 cm 的时间不一致也没关系：只有多主时"Server 写 DR 结果"和"发给 Server 的 DR"要在同一个主库，分片不同时 `produceResultAndAck` 自动改成分两步写。建议在流量低时改。

**待补的验证用例**（还没有做）：持续发送中，把一个客户和一个通道的 `StreamShards` 从 8 改成 64，并 reload cm。要验证：改之前已经在 8 个旧流里的消息全部送达、DR 全部回来，不丢、不重、不卡在旧流里；改之后新消息分布到 64 个分片；跨过切换时刻的长短信能正确合并、各段只发一次；统计同一个号码前后两条的乱序条数，只应出现在切换那一刻。

```
本地分片 = ShardHash.of(原来的键, S)              （同一个键仍然总在同一个本地分片：长短信、FIFO 不变）
全局分片 = (ShardHash.of("ssid", TotalShards) + 本地分片 × (TotalShards / S)) % TotalShards
流名不变：stream:xxx:{ssid}:{全局分片}
```

- **为什么要加偏移**：Core、Client 是按全局分片号的范围分工的（0～21、22～42、43～63）。如果小客户只用 0～3 号，就全落在 CoreEngine1 上。按 ssid 偏移、等间隔分布后，每个 ssid 的 S 个分片会落到不同的 Core 和 Client 上。
- **流数量**：4000 个 ssid × 4 = 1.6 万个，现在约 77 万个，少了约 50 倍。每个流的消息密度高了 16 倍，按批处理重新起作用；2.4 节的扫描开销也同比例下降。
- **大客户、大通道**：配 `StreamShards:64`（或 16、32），和现在一样。每个流同一时间只有一个工作线程处理，S 决定这个 ssid 最多能同时由几个线程处理。按实测每个流每秒能处理上千条，S=4 对每秒几百条以下的 ssid 足够。
- **影响面**：所有调用 `ShardHash.of(…, totalShards)` 的地方（9 处）都改成按 ssid 取 S。结果流和发给 Server 的 DR 在多主时要在同一个分片（`calculateDrShardId`），两处要用同一个 ssid 的 S。所有模块要一起升级。
- **风险**：按 ssid 取 S 要读 cm，各模块在 cm 重新加载时必须一致。可以先只按配置项生效、不支持热加载，改了要重启。

### 3.2 自动认领和扫描只看"可能有事"的流

- **自动认领**：现在逐个流执行 `XPENDING`，改成 pipeline 批量查（每 500 个流一次往返）；再进一步只查最近有过消费的流（消费者读到条目时记在内存里，确认完、PEL 为空后移除）。工作进程重启时内存里的记录会丢，但重启后的第一轮仍然扫全部流，所以重启丢下的 PEL 条目能找回来。
- **backlog 监控的全量扫描**：`RedisStreamMonitor.FullScanEveryCycles` 从 10 提高到 60（30 分钟一次），或者只在门铃数和有积压的流数对不上时才做。
- **空流清理**：一个流空了（`XLEN=0`、PEL 为空）超过 N 小时后，删除这个 key 并从 `idx:streams` 移除。风险：删除的同时生产者又写入，会把流重新建出来，但消费组没了；而消费者的 `createGroup` 本地缓存认为组还在，会读到 `NOGROUP`。所以必须同时处理 `NOGROUP`（清掉缓存并重建组）。这一项放到 3.1 之后，流数量降下来以后不一定需要。

### 3.3 Client 每个会话的线程从 5 个降到 1 个（第一期）

| 线程 | 改法 |
|---|---|
| 2 个 `CustReceiver` | 和 Server 一样，改成共享线程池：Client 收到的 PDU（submit_resp、deliver_sm）按会话放进共享队列，由固定大小的线程池处理，每个会话内保持顺序 |
| `ClientSessionThread` | 改成一个共用的 `ScheduledExecutorService`，按会话调度状态机（重连、bind、enquire_link 检查），状态机本身不变 |
| `Sender` | 写 socket 改成调用方在会话的写锁内直接写，或者用一个共用的写线程池；发送窗口和限速逻辑不变 |
| `Receiver` | 第一期保留（阻塞读） |

效果：每个 Client 8000 个会话时，线程从约 4 万个降到约 8000 个；Server 去掉 `Sender` 后，从约 1.6 万个降到约 8000 个。`vm.max_map_count` 的压力降为原来的 1/5。

**第二期**：`Receiver` 也改成 NIO（一个 selector 管很多连接），线程数和会话数脱钩。这是 SMPP 会话层的重写，改动大，等第一期的效果和需要再定。

### 3.4 小项

| 项 | 改法 |
|---|---|
| Client 启动每个会话 sleep 10 ms | 改成配置项 `ClientSessionStartIntervalMs`，默认 1；或者按通道并行启动、同一个通道内保留间隔（避免同时对同一个 SMSC 发起大量 bind） |
| Server 监听 backlog 50 | 新增配置项 `SmppServerListenBacklog`，默认 4096（需 `somaxconn` 不小于它，测试机已是 4096）；SMPP over TLS 的监听（`SslSmppServer`）一起改 |
| 报告的 CPU 按整个文件平均 | 已改：`perf_step.sh` 删用例副本前把 `phases.txt` 存为 `phases_{TPS}.txt`，`rt.PerfReport` 找不到结果目录时读它 |

## 3.5 实测：3.1 + 3.4 之后（2026-11-20 17:24，`perf_step_PF008_1120_1724`）

`StreamShardsDefault=8`、`SmppServerListenBacklog=4096`、`ClientSessionStartIntervalMs=1`，其余同第 1 节，PF008 1000 TPS 10 分钟。

| 项 | 改前（64 个分片） | 改后（8 个分片） |
|---|---|---|
| stream 数（实测 / 估算） | 约 77 万 | 9.6 万（`mt:pending`、`mt:routed`、`core:inbound-dr`、`dr:pending` 各 1.6 万，`core:results` 3.2 万） |
| 积压最多 | 1.7 万 | 446 |
| 提交 → 通道 p50 / p95 / p99 | 55 / 134 / 554 ms | 53 / 89 / 103 ms |
| 每条消息的 Redis 命令 | 217 | 156 |
| CPU：Core / Server / Redis / Client | 344 / 157 / 252 / 115 | 222 / 92 / 181 / 100 |
| 合计 | 约 8.7 个核 | 约 6 个核（整机空闲中位 62%） |
| Redis 最高内存：submit / report MQ | 160 / 200 MB | 65 / 44 MB |

少连接时每 1000 TPS 约 4 个核（2.1 节），现在多出约 50%（改前多出约 120%）。剩下的主要是：每个流仍很稀疏（每个客户 0.5 TPS，8 个分片，每条消息仍是单独一批），以及每个会话的线程（《会话线程优化设计》）。

## 3.6 升档：1500 / 2000 / 2500 TPS（2026-11-24，`perf_step_PF008_1124_0545`，`391f42b`）

一台 16 核测试机上跑全部模块（Core ×3、Server ×2、Client ×2、MQM、Redis、压测工具），2000 个客户、2000 个通道各 8 个 bind，StreamShardsDefault=8，Client 收包共享池和连接维护都已开。延时都只算预热之后。

| 档 | MT / DR | submit 被拒 | 提交 → 通道 p50 / p95 / p99（ms） | 提交 → 客户收到 DR p50 / p95 / p99 | 积压（预热后） | CPU 空闲中位 / 最低 | 稳定期 CPU（100 = 1 核） |
|---|---|---|---|---|---|---|---|
| 1500 | 全部 / 全部 | 0 | 60 / 95 / 108 | 0.65 / 0.75 / 0.9 s | 几百 | 39% / 17% | Core 380、Redis 280、Server 176、Client 151，约 10 核 |
| 2000 | 全部 / 全部 | 0 | 60 / 99 / 130 | 4.2 / 10.6 / 14.4 s | 4500～15000 来回，不增长 | 19% / 12% | Core 507、Redis 350、Server 206、Client 189，约 13 核 |
| 2500 | 全部 / 全部 | 0 | 57 / 134 / 216 | 28.6 s / ≥60 s / ≥60 s | 6.5 万～12 万来回（主要是 DR 和 submit 结果） | 12% / 9% | Core 524、Redis 355、Server 212、Client 237，约 14 核 |

- **MT 一直不受影响**：到 2500 TPS 提交 → 通道 p99 仍在 216 ms，submit 没有被拒，消息全部送达、DR 全部回到客户。
- **先到瓶颈的是 DR 和 submit 结果的处理**，原因是整机 CPU：2000 档起空闲不到 20%，Core、Redis 的 CPU 从 2000 到 2500 几乎不再增长（507→524、350→355），拿不到更多 CPU；系统先保 MT，DR 排队。压测停止后 2500 档的近 10 万积压 12 秒内就清空，说明是 CPU 被 MT 占着，不是 DR 流程本身的上限。
- **结论**：这台机器上多连接场景（1.6 万个 SMPP 会话）能稳定支撑约 **1500 TPS**（DR 延时 1 秒内）；2000 TPS 可以跑，DR 延时几秒到十几秒；2500 TPS 已过载，DR 延时半分钟以上。每 1000 TPS 约 6.5 核，少连接时约 4 核。
- 线上要更高的 TPS，按模块拆到多台机器（Redis、Core 各自独立），或继续减少每条消息的开销（3.2 扫描等）。

## 4. 建议的顺序

1. **3.1 分片数按 ssid 配置**：收益最大，直接针对 2.2、2.3、2.4 的主要成本。改完用 PF008 跑同样的 1000 TPS 对比，预计每条消息的 Redis 命令回到 100 条左右，Core、Client 的 CPU 明显下降。然后再按阶梯测上限。
2. **3.2 扫描**：3.1 之后流少了，扫描开销已经同比例下降；剩下的用 pipeline 改自动认领即可，空流清理视需要再做。
3. **3.4 小项**：改动小，可以和 1 一起做。
4. **3.3 线程**：不直接影响 TPS，影响的是能撑多少连接、对系统配置的依赖和内存。等确定线上的连接数规模后再做第一期。

每一步改完都跑全量回归，再在服务器上跑 PF008 的 1000 TPS 对比：每条消息的 Redis 命令数、各角色的 CPU、延时，以及线程、内存。
