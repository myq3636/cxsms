# 长短信处理流程说明

> 日期：2026-11-10。依据 `main`（`0533417`）的代码。默认 `CsmReassembleMode=redis`。以客户从 SMPP Server 发来 3 段的长短信为例。

## 1. 总览

```text
客户 ──submit_sm×3──> Server
  │ ① 每段一条 → stream:mt:pending:{ossid}:{分片}            （3 段同一分片）
  ▼
Core（CoreMTGroup）
  │ ② 每段：检查、解析 UDH、IN_SUBMIT_PARTIAL CDR
  │ ③ 每段存进 Redis Hash csm:{ossid}:{发送方}:{接收方}:{参考号}:{总段数}，IN_SUBMIT CDR
  │ ④ 集齐：拼成一条整消息 → 路由 → 按通道长度重新拆分（可能 1 条，也可能多条）
  │ ⑤ → stream:mt:routed:{rssid}:{分片}
  │    （通道限速：先进 stream:core:hold:{rssid}；HTTP 通道：stream:http:submit:{rssid}:{分片}）
  ▼
Client（ClientOutboundSubmitGroup）
  │ ⑥ 每条发一个 submit_sm 给供应商
  │ ⑦ submit_sm_resp → stream:core:results:{rssid}:{分片}
  │ ⑧ 供应商 DR    → stream:core:inbound-dr:{rssid}
  ▼
Core（CoreResultGroup / CoreInboundDRGroup）
  │ ⑨ 结果：OUT_SUBMIT CDR，按 outMsgId 存一份供 DR 匹配
  │ ⑩ DR：按 outMsgId 找到原消息，OUT_DELI_REP CDR，按客户的 3 段拆成 3 条 DR
  │    → stream:dr:pending:{ossid}:{Server模块}:{分片}
  ▼
Server ──deliver_sm×3──> 客户
```

## 2. Server：每段单独写 `stream:mt:pending`

`MultiSmppSession` 收到每个 submit_sm：

- 打 `[SUBMIT-IN]` 日志，做计费、入向限速等检查。
- `StreamQueueManager.produceSubmitMessage`：**每段一条**写进 `stream:mt:pending:{ossid}:{分片}`。写成功后给这一段回 submit_sm_resp，带它自己的 msgId。
- Server 不合并分段。

**3 段落在同一个分片**（`StreamQueueManager.calculateShardId`）：哈希键是 `ossid_发送方_接收方`，有参考号时再加 `_参考号`。

- **SAR 可选参数**（0x020C / 0x020E / 0x020F）：Server 在 `Smpp.java:225` 解析出参考号、总段数、段号，哈希键带参考号。
- **UDH**（esm_class 0x40）：Server 只把 UDH 字节分出来放进 `udh`（`Smpp.removeUdhFromContent`），不解析参考号。哈希键没有参考号，3 段一样落在同一个分片。

## 3. Core：逐段预处理

`MTStreamConsumer`（消费组 `CoreMTGroup`）读到分段后，调 `InternalCoreEngineSession.processSubmitFromStream`：

1. **检查**：黑白名单、内容检查、过期时间等，每段单独处理，失败的那一段直接回失败。
2. **`prepareInSubmit` → `MessageStoreManager.parseCsmUdh`**：把 UDH 里的拼接元素（IEI 0x00，8 位参考号）解析成参考号、总段数、段号，并从 UDH 里去掉这个元素。从这里起两种发法一样处理。
3. **`processInnerAck`**：每段写一条 `IN_SUBMIT_PARTIAL` CDR。
4. **判断长短信**：`CsmUtility.isConcatenatedMsg`（参考号、总段数、段号都有）且接收运营商还没确定（`rOperator < 0`），进入 `SyncSubmitRouter.routeCsmSegmentSync`。

## 4. Core：Redis Hash 合并（`RedisCsmReassembler`）

每条长短信一组键，`{组}` = `{ossid}:{发送方}:{接收方}:{参考号}:{总段数}`：

| 键 | 内容 |
|---|---|
| `csm:{组}` | Hash：段号 → 整段消息（和 Stream body 同一种序列化） |
| `csm:ids:{组}` | 段号 → msgId |
| `csm:asm:{组}` | 集齐后谁在组装外发（owner\|开始时间），另一个 Core 在 `CoreMtLeaseMs` 内不重复外发 |
| `csm:done:{组}` | 已完成的组：重投的旧段（msgId 相同）只确认，不再建残缺的组；客户复用参考号发的新消息（msgId 不同）照常合并 |
| `csm:index` | ZSET，按到期时间排序，没集齐的组由 `CsmExpirySweeper` 处理 |

每段一段 Lua 原子执行：存进 Hash，第一次时设置过期，再看是否集齐。结果：

| 结果 | 处理 |
|---|---|
| WAIT（没集齐） | 这一段已持久化，写 `IN_SUBMIT` CDR（每段一条），确认消费（ACK） |
| DONE（组已完成过） | 只 ACK |
| BUSY（另一个 Core 正在外发这组） | 不 ACK，等重投 |
| FULL（集齐） | 读出所有段，在内存里拼成一条整消息：msgId 用第 1 段的，`InMsgID` 是 3 段的 InMsgID 用逗号连起来 |

- **先发后删**：整消息成功写进下游 Stream 后才删 Hash（`complete`），再 ACK 最后一段。在写下游之前崩溃，Hash 还在，最后一段被重投，重新拼、重新发。
- **组装失败**：DB 兜底，删 Hash，ACK（避免反复重投）。
- **没集齐就过期**：`CsmExpirySweeper` 扫 `csm:index`，给客户回过期 DR。
- **24 小时发送上限**（`SMSOptionRecipientMaxSendCountIn24H`）：拼好后按整条消息算一次，超了拒绝。
- 依赖 STATE Redis，且必须 `maxmemory-policy noeviction`（Hash 被淘汰 = 丢段）。

## 5. Core：路由、重新拆分、写给 Client

整消息走 `SyncSubmitRouter.routeSubmitSync` → `MessageProcessorThread.processSync`：

1. **路由**选出通道（`[MT-ROUTE]`）。路由失败、没有通道等走 DB 兜底（`[MT-FALLBACK]`）。
2. **按通道重新拆分**（`MessageProcessor`）：
   - 通道配了 `ChlMsgSplit` / `MsgSplitLen` 且超长时，按通道长度拆，条数可以和客户的段数不同（例如客户 3 段 180 字符，通道按 100 拆成 2 条）。
   - 没配 `MsgSplitLen` 时：GSM 7-bit、ASCII 按 `ContentLength`（160），8 位 ISO 文本按 140（`ContentLength` 更小时用它）。
   - 参考号沿用客户的，没有就随机生成。
   - 通道 `ChlUdhConcatenated=true` 用 UDH，否则用 SAR 可选参数。
   - 拆出的每条有自己的 `splitStatus`（1、2、…）；不需要拆就是 1 条整消息。
3. **写下游**（`StreamQueueManager.produceOutboundMessage`，`[MT-TO-CLIENT]`）：
   - SMPP 通道：`stream:mt:routed:{rssid}:{分片}`，分片按 `rssid_发送方_接收方` 算，拆出的几条进同一个分片。
   - 通道配了 `SMSOptionCoreProcessorThrottlingNum`：先进 `stream:core:hold:{rssid}`（`[MT-HOLD]`），按速率放到 routed 流（`[MT-RELEASE]`）。
   - HTTP 通道：`stream:http:submit:{rssid}:{分片}`。
   - 写入防重：outbox 键 `core:outbox:submit:{msgId}:{splitStatus}:…`，重投不会写两次。

## 6. Client：发给供应商，结果和 DR 写回 Core

`OutboundStreamConsumer`（消费组 `ClientOutboundSubmitGroup`）读 routed 流：

- 选会话，过窗口和限速（账号级 `SMSOptionOutgoingThrottlingNum`、bind 级 `SMSOptionOutgoingThrottlingNumPerBind`），每条发一个 submit_sm（`[MT-OUT]`）。
- submit_sm_resp → `stream:core:results:{rssid}:{分片}`，分片按 msgId 算，同一条长短信拆出的几条结果进同一个流。
- 供应商 DR（deliver_sm）→ `stream:core:inbound-dr:{rssid}`。

HTTP 通道由 HTTP Client 读 `stream:http:submit:*`，结果同样写回 `stream:core:results:*`。

## 7. Core：结果和 DR，DR 回到客户

**结果**（`ResultStreamConsumer`，消费组 `CoreResultGroup`）：

- 每条外发一条 `OUT_SUBMIT` CDR。
- 按供应商 outMsgId 在 Redis 存一份消息，供 DR 匹配。

**DR**（`InboundDRStreamConsumer`，消费组 `CoreInboundDRGroup`，`InternalCoreEngineSession.handleInboundDRInternal`）：

1. 用 outMsgId 找原消息：先 Redis，没有再查 DB；都没有先存起来以后再匹配（`[VDR-STORE]`）。找到时 `[VDR-MATCH]`。
2. 写 `OUT_DELI_REP` CDR。
3. 通道拆分过的，只有第 1 条（`splitStatus < 2`）的 DR 回给客户，后面几条的 DR 只记 CDR。
4. `CsmUtility.splitCsmDr` 按客户发来的段数拆成 3 条 DR，每条带对应那一段的 InMsgID。重投防重的键带段号（`StreamQueueManager.produceDrOnce`），3 条都会写入。
5. 写 `stream:dr:pending:{ossid}:{Server模块}:{分片}`（`[DR-TO-SERVER]`）。Server 模块取 MT 进来时记下的 Server（innerTransaction），DR 原路回去；那个 Server 不在线时由 `SmppServerDrRouteResolver` 另选。

**Server** 读到 DR，按客户的 bind 发 3 个 deliver_sm（`[DR-OUT]`）。客户的 deliver_sm_resp 结果写回 Core 的结果流，Core 写 `IN_DELI_REP` CDR。

## 8. CDR 汇总（3 段，通道不拆分）

| CDR | 条数 | 写的时机 |
|---|---|---|
| `IN_SUBMIT_PARTIAL` | 3 | Core 每段预处理（`processInnerAck`） |
| `IN_SUBMIT` | 3 | 每段存进 Hash 后（`handleInSubmit4Csm`） |
| `OUT_SUBMIT` | 1 | 外发结果回到 Core（通道拆成 N 条就是 N 条） |
| `OUT_DELI_REP` | 1 | 供应商 DR（通道拆成 N 条就是 N 条） |
| 回给客户的 DR | 3 | 每段一条 |

外发和 DR 的 CDR 记在拼好的消息上：msgId 是第 1 段的，`InMsgID` 是 3 段用逗号连起来。CDR 的 `DeliveryChannel` 列是经过的模块，用 `:` 分隔（见 `docs/消息经过模块路径设计.md`）。实测见 `docs/长短信CDR与DR测试报告.md`。

## 9. 旧模式 `CsmReassembleMode=legacy`

分段不进 Redis Hash，交给内存里的 `csmHandler` 在后台线程合并。分段放进内存时 Stream 条目就已 ACK，Core 重启会丢正在合并的段。默认是 redis 模式。

## 10. 排查一条长短信

| 环节 | Redis 键 |
|---|---|
| Server → Core | `stream:mt:pending:{ossid}:*` |
| Core 合并中 | `csm:{ossid}:{发送方}:{接收方}:{参考号}:{总段数}`、`csm:ids:…`、`csm:asm:…`、`csm:done:…` |
| Core → Client | `stream:mt:routed:{rssid}:*`（限速 `stream:core:hold:{rssid}`，HTTP `stream:http:submit:{rssid}:*`） |
| Client → Core | `stream:core:results:{rssid}:*`、`stream:core:inbound-dr:{rssid}` |
| Core → Server | `stream:dr:pending:{ossid}:{Server模块}:*` |

按 msgId 查日志的顺序：

`[SUBMIT-IN]` → `[STREAM-PUT]` → `[STREAM-GET]` → `[CDR] IN_SUBMIT_PARTIAL` → `[CDR] IN_SUBMIT` → `[MT-ROUTE]` → `[MT-TO-CLIENT]` → `[MT-OUT]` → `[VDR-MATCH]` → `[DR-TO-SERVER]` → `[DR-OUT]`

其中 `[MT-TO-CLIENT]`、`[MT-OUT]`、`[DR-TO-SERVER]`、`[DR-OUT]` 带 `path=`，可直接看到经过的 Server、Core、Client。
