# 5000 TPS 一小时测试：瓶颈分析

> 日期：2026-11-17。测试服务器 8.219.93.186。用例 `regression/routetest/cases/PF002_5000tps_1h`（《高TPS一致性和内存测试设计》的混合流量：普通 MT、改道、3 段长短信、无路由、假 DR），由 `bin/run_hightps.sh` 运行：测试前 Redis 只保留 `thcon`、MySQL gmms 库清空；5000 TPS × 60 分钟，之后排空 2 分钟、空闲 10 分钟；两侧抓包和 CDR 对账、内存采样，每 10 秒记录各类 stream 的积压、各进程 CPU、Redis 内存和每秒命令数。
>
> 代码是当天的版本：通道 DR 分片、消费者不再空转、EVALSHA、stream 索引、会话登记索引、消费组只建一次、取门铃一次脚本、outbox `:done` 30 分钟；Redis 不做 RDB、`maxmemory 8gb`。

## 1. 结论

1. **系统处理不了 5000 TPS，上限由 Redis 主线程 CPU 决定**：从流量开始到结束，8387（submit）和 8388（report）一直在 90%～98%，每秒各约 11～12 万条命令。实际处理能力：

   | 环节 | 每秒 | 说明 |
   |---|---|---|
   | 客户提交（工具发出） | 约 3950 段 | 计划 6000 段/秒（5000 条 × 1.2）；Server 读得慢，TCP 把工具顶住 |
   | Core 处理 MT（读 `mt:pending`） | 约 2400～2750 段 | `mt:pending` 匀速增长约 1530 条/秒，到 17:55 积了 597 万 |
   | 发到通道 | 约 1860 条 MT | 993 万个 submit_sm |
   | Core 处理通道 DR、submit 结果 | 跟得上 | `core:results`、`core:inbound-dr` 基本没有积压 |
   | **Server 发 DR 给客户** | **约 660 条** | **最慢的一段**：`dr:pending` 匀速增长约 1450 条/秒，到 17:55 积了 566 万 |

2. **最慢的是 Server 给客户发 DR**（约 660/s，只有 Core 产生 DR 速度的 1/3）。它和 Core 的结果、通道 DR 共用 8388，8388 一直在 95% 以上；Core 读这两个 stream 时能及时取完，Server 读 `dr:pending` 却跟不上。Server1 承担了 75% 的流量（客户 rtcs1），CPU 约 110%。需要单独查 Server 发 DR 的路径：每条 DR 的 Redis 往返次数（读、StreamAttempt、结果写回和确认的 Lua）、窗口（`WindowSize` 1000，2 个 bind）、每个 stream 同时只有一个任务。
3. **其次是 Core 处理 MT**，同样受 8387 和 8386 的速度限制；Core 的 CPU 只有 100%～120%（16 核的机器），大部分时间在等 Redis。
4. **内存没有泄漏**（`MEMORY: PASS`）：9 个模块 Full GC 后的堆、线程、句柄、Metaspace 都正常；Redis 没有不过期的 key 堆积。Redis 内存随积压线性增长（8388 每秒约 1 MB，结束时 4.5 GB；8387 3.6 GB；8386 1.5 GB），没有到 7 GB 的保护线。
5. **测试中 17:56 根分区写满**（见第 3 节），之后的结果无效：客户 submit 被拒的 235 万次、"会话不存在"等错误都出现在 17:56 以后；**磁盘写满之前 Server1 没有一条告警**。

## 3. 根分区写满（17:56）

- Redis 的数据目录在根分区 `/usr/local/redis-7.4.9/data`（99 GB，测试前剩 37 GB），不在 `/mnt`（296 GB）。
- 不做 RDB 以后，AOF 只靠重写压缩。积压的 stream 让 AOF 涨得很快：到结束时 8388 的 AOF 12 GB、8387 9 GB、从库 8378 8.8 GB、8377 8 GB，合计约 40 GB。17:56 磁盘写满，AOF 重写也失败（重写要额外的空间）。
- 之后 3 个主库写 AOF 一直失败（`aof_last_write_status:err`），拒绝写命令：Server 写 `mt:pending` 失败、拒绝客户的 submit（235 万次），DR 找不到会话等。**3 个从库（8376～8378）都退出了**。
- 18:20 处理：停 a2p；把 `data/` 下 11-16 留下、没有任何实例使用的旧文件（`appendonlydir` 4.1 GB、`redis8379.log` 2.1 GB 等）移到 `/usr/local/a2p/log/redis_old_files_20261116/`；主库恢复可写（`aof_last_write_status:ok`）。根分区还剩约 1.8 GB。

**现在的状态**：a2p 停着；3 个主库正常、从库停着；Redis 里还有测试积压（`mt:pending` 628 万、`dr:pending` 590 万条，约 9.5 GB 内存）。

## 4. 抓包和 CDR 对账

这次的对账**不能作为结论**：积压到结束都没有处理完（1079 万条 MT 没有 DR），17:56 以后还有磁盘写满造成的失败。两个 tcpdump 都是 0 丢包，但重组时有 141 处缺口（共 161 KB，约占 9.6 GB 的十万分之二），可能是高负载下回环接口的乱序被当成了缺口，要改进重组再确认。

可以确定的部分：

- 通道侧：CDR 里的通道 MsgID 都在抓包里（`only in the CDRs 0`），没有重复；
- 发给客户的 DR：抓包 351.4 万、CDR 351.2 万，**抓包里同一个 DR 发了两次的有 6 条**，CDR 里重复 106 条，需要在流量能处理完的那次测试里确认是否真的重复、发生在哪个时间段。

## 5. 建议

1. **先修磁盘**：把 6 个 Redis 实例的数据目录移到 `/mnt`（改 `dir`、重启）；调大 `auto-aof-rewrite-min-size`；加磁盘和 AOF 大小的监控。
2. **清理 Redis 里的测试积压**，然后 `BGREWRITEAOF` 把 AOF 压回去，再启动从库全量同步。
3. **一致性和内存测试改用系统能处理完的速率**（例如 2000 TPS × 1 小时），积压能及时清空，对账结果才有意义。
4. **吞吐**：
   - 先查 Server 发 DR 的路径（最慢的一段）；
   - 试 Redis `io-threads`（把网络收发移出主线程，现在系统态 CPU 约占三分之一）；
   - 再做《Redis CPU瓶颈分析》第 5 节的 5、6（按批处理 StreamAttempt、合并 FLUSH）。

## 6. 2026-11-24 复测（2+2 主，不抓包，`b61d0d1`）

用例同上（`PF002_5000tps_1h`），`bin/perf_long.sh --no-capture --no-replicas`：Redis 从库停掉，HTTP Server、HTTP Client 模块停掉；Redis 每个实例 `maxmemory 3gb`，任一实例超过 90% 时保护停止发送。两次都没跑满一小时。稳定期每秒（CDR 统计，15 分钟）：

| | 11-17（单主，抓包） | 11-24 第 1 次（默认 8 个分片） | 11-24 第 2 次（cm `StreamShards:64`） |
|---|---|---|---|
| 发到通道（submit_sm） | 约 2760 | 3961 | 5134 |
| Core 处理 MT（`IN_SUBMIT` / 长短信分段） | 约 2400～2750 段 | 3703 / 774 | 4764 / 1110 |
| Core 处理通道 DR | 跟得上 | 2242 | 2906 |
| Server 发 DR 给客户 | 约 660 | 1613 | 2572 |
| `mt:pending` 积压增长 | +1530 | +2259（全在客户 9995） | +1275 |
| `core:inbound-dr` 积压增长 | 无 | +1422（全在通道 9991） | +1497 |
| `dr:pending` 积压 | +1450 | 无 | 无 |
| 4 个 MQ Redis CPU | 两个单主 90～98% | 94 / 96 / 29 / 49% | 都是 84% |
| MQ Redis 每秒命令合计 | 约 23 万 | 30.8 万 | 37.3 万 |
| 状态 Redis | 约 55%、每秒约 4 万条 | 16%、0.68 万条 | 17%、0.88 万条 |
| Core / Client / Server CPU（100 = 1 核） | 约 330 / 135 / 140 | 365 / 182 / 191 | 454 / 224 / 182 |
| 整机 CPU 空闲 | — | 33% | 19%（最低 2%） |
| 跑了多久 | 66 分钟（磁盘写满） | 27 分钟（8397 内存保护） | 36 分钟（8388 内存保护） |

- **第 1 次的瓶颈**：`StreamShardsDefault=8` 时一个 ssid 的 8 个分片间隔 8（奇偶相同），流按分片号 % 主数放在 MQ 主上，2 个主时**一个客户或通道的流全在同一个主上**：客户 9995（约 75% 流量）的 MT 全在 8397，通道 9991 的 DR 全在 8398，这两个 CPU 94～96%，另外两个只有 29～49%，整机还空闲 33%。
- **第 2 次**给 3 个客户、3 个通道配 `StreamShards:64` 后负载平均到 4 个 MQ 主，发到通道 +30%、Server 发 DR +60%；瓶颈变成整机 CPU（空闲 19%，最低 2%，Redis 都在 84%），先跟不上的是 Core 处理通道 DR，DR 积压把 report 主的内存撑满。
- **改进**：分片间隔改为 `TotalShards / S + 1`（`ShardHash`，2026-11-25），默认配置下同一 ssid 的流也在各 MQ 主之间平均，不用给大客户单独配 `StreamShards`。
- 和 11-17 比，吞吐约翻倍，Server 发 DR 不再是瓶颈，状态 Redis 负载降约 80%；这台 16 核机器（全部模块、5 个 Redis、压测工具在一起）撑不住 5000 TPS 一小时，要更高需要把 Redis 或 Core 分到别的机器。
