# 配置项说明

> 收录本次重构和优化中**新增或改变了行为**的配置项，并附带配置时经常一起用到的已有配置。
> **维护规则**：今后代码里新增配置项，要同时更新本文件（写明作用、默认值、所在文件、生效方式）；GmmsConfig 里需要支持热加载的项，还要加进 `GmmsUtility` 的热加载白名单（见第 1 节）。

## 1. 配置文件与生效方式

| 文件 | 写法 | 生效方式 |
|---|---|---|
| `Gmms/GmmsConfig.properties` | `Key=Value`，全局生效，各模块共用 | **热加载**：执行 `reload GmmsConfig -a`（`GmmsUtility.reloadGmmsConfig`）。只有在热加载白名单里的 key 才会生效（`isRuntimeConfigKey`），其他 key 会在日志里列为 `Restart required` 或 `Unknown`，需要重启。本文件中标"热加载"的 key 都已在白名单里 |
| `conf/cm.cfg` | 在客户或通道块 `[ShortName]` 下写 `Key: Value` | 热加载 cm.cfg（客户配置重新加载）后，只有这个块的客户对象会被替换，其他客户不受影响 |

热加载 GmmsConfig 的注意事项：

- **数值或布尔值写错时，整次热加载被拒绝**，所有配置保持原值。日志里有 `GmmsConfig reload failed`。
- **从文件里删掉某个 key，热加载不会把它恢复成默认值**，内存里仍然是上一次的值。要恢复默认值，请把默认值显式写进文件再热加载。如果确实要删除，需要重启才生效。
- 配置每次被用到时才读取，所以热加载后的下一次处理就会按新值执行，不需要额外动作。

## 3. Server 模块

| 配置项 | 文件 | 默认值 | 生效 | 作用 |
|---|---|---|---|---|
| `ServerDrStreamShardFilter` | GmmsConfig | `false` | 热加载 | Server 消费 DR stream（`stream:dr:pending:{ossid}:{模块}:{分片}`）时，是否只消费 `MyShards` 里的分片。<br>**false（默认）**：本模块名下的所有分片都消费。<br>**true**：只消费 `MyShards` 里的分片，仅在**多个 Server 节点共用同一个模块名、靠分片分担**时使用；启动时如果 `MyShards` 没覆盖全部分片，会打 warn 并列出没人消费的分片号 |

## 4. Core 模块：DR 转发

| 配置项 | 文件 | 默认值 | 生效 | 作用 |
|---|---|---|---|---|
| `CoreDrInlineDispatch` | GmmsConfig | `true` | 热加载 | 发给客户的 DR 是否在当前线程同步写入 `stream:dr:pending`。<br>**true（默认）**：所有发 DR 的地方都同步写出，不经过 `MessageProcessorHandler` 内存池（默认 1 到 5 个线程）。<br>**false**：只有"供应商 DR 转发"和"MT 被拒绝时的拒绝 DR"这两条路径同步写出（这两条始终同步，保证先写出再确认消费），其他路径（假 DR、结果处理里的失败 DR 等）回到内存池。<br>结果流积压或 MT 时延明显上升时，可以先改成 false |

## 5. Core 模块：MT 处理去重

一条 MT 被重新投递（确认消费失败、进程在确认前崩溃、被自动重投领走）时，用 `core:mt:{msgId}` 标记已经做过的事，重投时不再重复写 CDR、发 DR、计数、外发。

| 配置项 | 文件 | 默认值 | 生效 | 作用 |
|---|---|---|---|---|
| `CoreMtIdempotency` | GmmsConfig | `true` | 热加载 | 是否开启 MT 处理去重。**false** 时完全回到原来的逻辑（不写标记，重投时会重复处理），用于出问题时快速回退 |
| `CoreMtLeaseMs` | GmmsConfig | `60000`（毫秒） | 热加载 | （MT、供应商 DR、出向结果共用）一个 Core 线程开始处理某条 MT 后，"占用"多久内不允许别的线程处理同一条。超过这个时间仍未完成，视为原处理者已挂掉，其他线程可以接手。应不小于单条 MT 的最长处理时间，建议与 `RedisStreamAutoClaimIdleMs` 一致 |
| `CoreDrResultIdempotency` | GmmsConfig | `true` | 热加载 | 是否对**供应商 DR**（`InboundDRStreamConsumer`）和**出向结果**（`ResultStreamConsumer`）做重投去重。去重以 stream 里的一条记录为单位（标记 `core:att:{stream}:{条目id}`，在 reportMq 上），重投时不再重复写 CDR 和统计、重复给客户发 DR、重复写重试队列（RMQ/RDQ/SMQ 等）和 SDQ、重复改道。正常的重试（每次重发都会产生新的结果记录）不受影响，每次仍写 CDR、仍进重试队列。**false** 恢复原来的行为。每条 DR / 结果多 2 次 Redis 访问 |
| `CoreMtMarkerTtlSeconds` | GmmsConfig | `604800`（7 天） | 热加载 | 去重标记的兜底过期时间。正常情况下确认消费时就删除标记，只有确认消费失败、一直没有重投成功的消息才会留到过期。应大于消息在 `stream:mt:pending` 里可能停留的最长时间 |

## 6. Core 模块：外发 outbox 与超时

每次外发到 `stream:mt:routed` 都会登记一条 outbox：`core:outbox:submit:{msgId}:{段号}:{第几次尝试}`，存在 submitMq 所在的 Redis 上。每次外发只认第一个结果，迟到或重复的 submit_resp 会被丢弃。Client 迟迟没有回结果时，Core 按消息状态判超时：

| 配置项 | 文件 | 默认值 | 生效 | 作用 |
|---|---|---|---|---|
| `CoreOutboundUnreadStallMs` | GmmsConfig | `120000`（2 分钟） | 热加载 | **Client 停止读取多久算故障**。消息还在 routed 里没被读走，并且 Client 的消费者已经这么久没有读取（或者消费组不存在），就把消息从 routed 里**删除收回**，回 COMMUNICATION_ERROR（2500）。Client 还在正常读前面的消息时不会收回 |
| `CoreOutboundRespTimeoutMs` | GmmsConfig | `180000`（3 分钟） | 热加载 | **已发出后等结果的时长**。Client 已经读走并确认消费（已发给供应商），超过这个时间还没有结果，就回 SUBMIT_RESP_ERROR（2700）。应大于 Client 的发送窗口超时（客户配置 `BufferTimeout`，默认 60 秒） |
| `CoreOutboundOutboxRecheckMs` | GmmsConfig | `60000`（1 分钟）<br>（原为 300000） | 热加载 | 还没到超时条件的 outbox，隔多久再检查一次 |
| `CoreOutboundOutboxHardTimeoutMs` | GmmsConfig | `10800000`（3 小时） | 热加载 | 硬超时。到达后不论状态：消息还没被读就收回并回 2500；已读未确认，或已发出没结果，就回 2700 |
| `CoreOutboundOutboxPayloadTTLSeconds` | GmmsConfig | `14400`（4 小时） | 热加载 | outbox 条目在 Redis 里的过期时间，实际取值不小于"硬超时 + 复查间隔 + 60 秒" |
| `CoreOutboundOutboxResultRetryMs` | GmmsConfig | `5000` | 热加载 | 超时结果写入结果流失败后，隔多久重试 |
| `CoreOutboundOutboxScanBatchSize` | GmmsConfig | `100` | 热加载 | 扫描线程每轮最多检查多少条 outbox |
| `CoreOutboundOutboxScanIntervalMs` | GmmsConfig | `1000` | **重启** | 扫描线程多久运行一轮 |
| `CoreOutboundOutboxEnable` | GmmsConfig | `true` | 热加载 | 是否启用 outbox。关闭后不登记、不判超时，结果也不做"只认一个"的判断 |

超时之后**是否重发**，由供应商的 `SMSOptionSubmitRetryCode`（cm.cfg）决定：

- 2500 表示**确定没有发出去**，重发是安全的，建议放进重试码。
- 2700 表示**可能已经发出去**，重发可能导致重复，按供应商分别决定。

## 7. Core 模块：通道限速放行

配了限速的通道，消息先进入 Core 的暂存队列 `stream:core:hold:{rssid}`，再按速率放行到 `stream:mt:routed`（或 HTTP 通道的 `stream:http:submit`），积压留在 Core 的 Redis 里。

### 7.1 按通道配置（cm.cfg，写在供应商/通道块里）

| 配置项 | 默认值 | 生效 | 作用 |
|---|---|---|---|
| `CoreOutboundTps` | `0`（不限速） | cm.cfg 热加载 | **单个 Core 节点**每秒放行多少条到这个通道。0 或不配置：不进暂存队列，直接外发（和以前一样）；从大于 0 改成 0 后，新消息直接外发，暂存队列里剩下的消息不再限速、尽快放完。<br>**实际总速率 = 这个值 × Core 节点数**，配置时按"供应商能力 ÷ Core 节点数"填写 |
| `CoreHoldMaxSeconds` | `21600`（6 小时） | cm.cfg 热加载 | 消息在暂存队列里最多等多久，超过就不再发出，按 **EXPIRED（10200）** 失败（写 OUT_SUBMIT CDR，给客户回失败 DR）；消息自身的过期时间先到时同样处理。<br>同时决定**积压上限 = `CoreOutboundTps` × `CoreHoldMaxSeconds`**：达到上限后新消息不进暂存队列，直接按 **Throttled（2600）** 失败 |

示例：

```
[VENDOR9]
CCBSSID: 9
...
CoreOutboundTps: 2        # 每个 Core 每秒 2 条；3 个 Core 合计每秒 6 条
CoreHoldMaxSeconds: 600   # 最多等 10 分钟；积压上限 2 × 600 = 1200 条
```

容量参考（每条约 1 到 2KB）：每秒 1 条 × 6 小时 = 2.16 万条，约 20 到 40MB；每秒 500 条 × 6 小时 = 1080 万条，约 10 到 20GB。高速通道建议把 `CoreHoldMaxSeconds` 配小一些。

注意：如果供应商的 `SMSOptionSubmitRetryCode` 里有 2600 或 10200，这两种失败会进入重试流程，而不是直接给客户回失败 DR。

### 7.2 全局（GmmsConfig）

| 配置项 | 默认值 | 生效 | 作用 |
|---|---|---|---|
| `CoreHoldReleaseTickMs` | `100`（毫秒） | 热加载 | 放行线程多久运行一轮。每轮每个通道最多放行 100 条，所以不限速时单节点每通道最多每秒约 1000 条 |
| `CoreHoldRecoverIntervalMs` | `30000` | 热加载 | 多久检查一次"被已挂掉的 Core 读走、还没放行"的暂存条目 |
| `CoreHoldRecoverIdleMs` | `60000` | 热加载 | 暂存条目被读走后，空闲超过多久才视为原 Core 已挂掉、由本节点接手。接手只转移归属、不消耗令牌，之后仍按速率放行 |

## 7A. 所有模块：stream 重投与死信队列

| 配置项 | 文件 | 默认值 | 生效 | 作用 |
|---|---|---|---|---|
| `RedisStreamMaxDeliveries` | GmmsConfig | `10` | 热加载 | 一条待确认消息最多被投递几次（第一次读取算 1 次，每次自动重投加 1 次）。达到后不再重投，移入死信 stream（`stream:dlq:submit` 或 `stream:dlq:report`，带 `reason=max_deliveries`、来源 stream、id、投递次数），并从原 stream 删除，打 ERROR 日志 `[STREAM-DLQ]`。**不回失败 DR，也不产生结果**；`stream:mt:routed` 的消息进死信队列后，仍由 Core 的 outbox 按超时规则处理。0 表示不限次数（原来的行为）。按默认的重投间隔（5 分钟），大约 50 分钟后进入死信队列。Core、Server、Client 的自动重投都会生效 |

## 7B. Core 模块：消费线程公平性

| 配置项 | 文件 | 默认值 | 生效 | 作用 |
|---|---|---|---|---|
| `CoreStreamTaskMaxBatches` | GmmsConfig | `10` | 热加载 | Core 的 MT、入向 DR、结果、MQM 四个消费者，每个处理任务连续处理多少批（每批最多 `RedisStreamConsumer.*` 配置的 batch 条）后，把 stream 让出来、重新排队，避免积压大的 stream 长期占住线程 |
| `CoreStreamTaskMaxMs` | GmmsConfig | `2000`（毫秒） | 热加载 | 同上，按时间计算：每个任务处理超过这个时长后让出 stream（当前这一批会先处理完） |

线程池满了以后，分发线程不再自己执行任务，而是把 stream 放回等待队列，休眠一个空闲间隔后继续分发。这一点没有配置项。

## 7C. 所有模块：出向结果 stream

| 配置项 | 文件 | 默认值 | 生效 | 作用 |
|---|---|---|---|---|
| `CoreResultStreamSharded` | GmmsConfig | `true` | 热加载 | 出向结果（submit_resp、DR_resp、超时结果等）写到哪里。<br>**true（默认）**：写入 `stream:core:results:{ssid}:{shard}`。DR 类结果的 ssid 取 ossid，其他结果取 rssid；shard 按 msgId 计算，同一条消息的各段落在同一个 stream。所有 Core 都可以处理任意结果 stream，可以并行。<br>**false**：写回原来的单个 `stream:core:results`，用于回退。<br>Core 总是同时消费新旧两种 stream。**逐个模块滚动升级时必须先升级 Core**；做不到时，先在 Server 和 Client 上设为 false，等 Core 升级完成后再打开 |

## 8. 相关的已有配置（配置上面各项时经常一起用到）

| 配置项 | 文件 | 默认值 | 说明 |
|---|---|---|---|
| `TotalShards` | GmmsConfig | `1` | stream 的分片总数。**Server、Core、Client 必须一致**；Server 不配置时默认为 1，所有 MT 都会进 0 号分片。修改前先清空积压 |
| `MyShards` | GmmsConfig | `0` | 本节点负责的分片，例如 `0-15`。Core 优先读 `CoreShard.*`，Client 优先读 `ClientShard.*` |
| `CoreShard.{模块名或 NodeID}` | GmmsConfig / Redis `system:core:shards:{模块}` | — | 各个 Core 负责的分片。多个 Core 之间不要重叠，合起来要覆盖 `0..TotalShards-1` |
| `ClientShard.{模块名或 NodeID}` | GmmsConfig | — | 各个 Client 负责的分片，规则同上 |
| `RedisStreamAutoClaimIdleMs` | GmmsConfig | `60000` | 待确认消息空闲多久后被自动重投领走 |
| `RedisStreamMaxLen` | GmmsConfig | `1000000` | stream 写入时的 MAXLEN（近似裁剪）。超出后最老的消息会被删除，**不管有没有被消费过**，不要靠它控制积压 |
| `Redis_pool_maxActive` | GmmsConfig | `50` | 每个 Redis 实例的连接池大小（重启生效）。DR 改为同步转发后，如果出现获取连接等待，就调大这个值 |
| `SMSOptionSubmitRetryCode` | cm.cfg（通道块） | 空 | 哪些外发失败码会触发重试（写入 RMQ 后重新外发），见第 6、7 节 |
| `SMSOptionRecipientMaxSendCountIn24H` | cm.cfg（客户块） | `0`（不限） | 同一接收号码 24 小时内最多发几条。计数已改为原子操作，重投时不会重复计数 |

## 9. 新增的 Redis key（运维排查用，不是配置）

| key | 所在实例 | 说明 |
|---|---|---|
| `core:mt:{msgId}` | submitMq | MT 处理去重标记（Hash），确认消费时删除；长时间存在说明这条 MT 一直没处理成功 |
| `core:att:{stream}:{条目id}` | reportMq | 供应商 DR、出向结果的处理去重标记（Hash，含 `_done`），确认消费时删除 |
| `core:outbox:submit:{msgId}:{段号}:{第几次尝试}` | submitMq | 外发 outbox，结果到达时删除 |
| `…:meta` / `…:done` | submitMq | outbox 元数据（stream、id、创建时间）；结果已处理的记录（用来识别迟到的结果） |
| `zset:core:outbox:submit:timeout` | submitMq | outbox 超时扫描队列 |
| `stream:core:hold:{rssid}` | submitMq | 通道暂存队列，消费组 `CoreHoldGroup` |
| `zset:core:hold:active` | submitMq | 非空暂存队列的门铃 |
| `stream:core:results:{ssid}:{shard}` | reportMq | 出向结果 stream（第 5 批起）；原来的单个 `stream:core:results` 仍会被消费，门铃 `zset:core:results:active` |
| `stream:dlq:submit` / `stream:dlq:report` | submitMq / reportMq | 死信 stream：反序列化失败（`reason=deserialize_failed`），或投递次数达到上限（`reason=max_deliveries`）的消息 |
| `system:shards:{role}:{module}:{node}` | state | 各节点的分片配置（`TotalShards|负责的分片`），随模块心跳刷新，过期时间为 3 次心跳；server、core、client 各模块据此每分钟各做一次跨模块校验，问题打 `[SHARD-CHECK]` 日志 |
