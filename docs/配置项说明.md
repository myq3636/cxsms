## 1. 配置文件总览

`$A2P_HOME` 为启动参数 `-Da2p_home` 指定的目录（默认 `/usr/local/a2p/`）。

## 2. 生效方式

热加载命令通过 Redis 发布到频道 `channel:gmms:control`，各模块收到后在本地执行（`RedisControlSubscriber`）。消息格式：

```
命令                      所有模块执行，例如 RELOAD_CUSTOMER
命令@模块名[,模块名...]    只在指定模块执行，例如 RELOAD_GMMS_CONFIG@CoreEngine1,CoreEngine2
命令:参数                 带参数，例如 SWITCH_DNS:master
```

可用命令：`RELOAD_GMMS_CONFIG`（别名 `RELOAD_GMMSCONFIG`、`RELOAD_CONFIG`）、`RELOAD_MODULES`、`RELOAD_CUSTOMER`、`RELOAD_ROUTING`、`RELOAD_ANTISPAM`、`RELOAD_CONTENT_TEMPLATE`、`RELOAD_PHONE_PREFIX`、`RELOAD_BLACKLIST`、`RELOAD_WHITELIST`、`RELOAD_SENDER_BLACKLIST`、`RELOAD_SENDER_WHITELIST`、`RELOAD_CONTENT_BLACKLIST`、`RELOAD_CONTENT_WHITELIST`、`RELOAD_RECIPIENT_RULE`、`RELOAD_VENDOR_REPLACE`、`RELOAD_SYSTEM_REPLACE`、`RELOAD_RECIPIENT_BLACKLIST`、`RELOAD_CORE_SHARDS`、`RELOAD_CLIENT_SHARDS`、`SWITCH_DB`、`SWITCH_REDIS`、`SWITCH_DNS`、`SHUTDOWN`。

### 2.1 GmmsConfig 的热加载

执行 `RELOAD_GMMS_CONFIG` 后（`GmmsUtility.reloadGmmsConfig`），只有热加载白名单（`isRuntimeConfigKey`）里的 key 会更新，其他 key 在日志里列为 `Restart required GmmsConfig` 或 `Unknown GmmsConfig`，要重启才生效。

本文件"热加载"一列的含义：

| 标记 | 含义 |
|---|---|
| **热加载** | 在白名单里，而且每次用到时读取，热加载后下一次处理就按新值执行 |
| **热加载（新连接）** | 在白名单里，但只在建立连接或会话时读取：已有连接保持旧值，之后新建的连接按新值 |
| **重启** | 不在白名单里，改了要重启模块 |

注意事项：

- **能热加载的项按类型校验，写错时整次热加载被拒绝**，所有配置保持原值，日志有 `GmmsConfig reload failed`：数值必须是数字，布尔值只接受 `true`/`false`，分片配置（`MyShards`、`CoreShard.*`、`ClientShard.*`）格式错误、超出 `0..TotalShards-1` 或为空都会被拒绝，`none` 是合法值。改小 `TotalShards` 时，现有的分片配置也必须在新范围内。
- **从文件里删掉能热加载的项，热加载后恢复为默认值**（日志里 `Applied GmmsConfig: key 旧值 -> null`）。删掉需要重启的项，内存里保持原值，重启后才是默认值。
- **需要重启的项写错时不拒绝热加载，但会打 ERROR** `... the module will fail at next restart: key=... old=... new=...`（原值是数字或 true/false、新值不是时）。启动时这类错误会让模块退出，请在重启前改正。
- 每次启动和热加载后，本模块生效的配置会写到 Redis（见 2.3）。

### 2.2 cm.cfg 的热加载

执行 `RELOAD_CUSTOMER` 后，只重新解析有变化的客户块，没变的客户不受影响（重构设计见《A2P客户配置模块重构设计》）：

- **第 5 节的所有配置项都随 reload 生效**，不需要重启。
- **改了的客户，它在 Server、Client 上的连接会被断开并重建**（客户需要重新 bind，供应商连接会重连），本地限流和去重缓存会被清空。所以即使只改一个与连接无关的项，也会让这个客户的连接重连一次。**没改的客户不受影响**：连接不断开，对象也不重建。
- **可以改 shortName 和 `CCBSSID`**（改名、改 ssid、两个都改、两个客户互换 ssid）。旧连接断开，客户重新 bind 后正常收发。
- **路由不随 cm.cfg 变化**：路由表只由 `RELOAD_ROUTING` 重建（senderReplacement 只由 `RELOAD_PHONE_PREFIX` 重载）。`RELOAD_CUSTOMER` 不读路由文件。改了通道的 shortName，要先改好引用它的路由文件（`Relay=` 写的是通道名）；改了通道的 ssid，路由文件内容不用变，但要 `touch` 引用它的路由文件（`RELOAD_ROUTING` 只加载有变化的文件，详见 6.1），或者用 `RELOAD_ROUTING:-f` 全部重新加载。然后同时执行 `RELOAD_CUSTOMER` 和 `RELOAD_ROUTING`。这两个命令之间，路由表可能还指向已不存在的通道，这样的 MT 按未路由失败（写 OUT_SUBMIT CDR，状态 2120，按重试策略处理或给客户回失败 DR；日志 WARN `[MT-ROUTE] routing points to rssid=...`，同一通道每 10 分钟最多一行）。
- **新块加载失败时不会丢通道**：如果有新名字的块加载失败（例如改名时新 ssid 已被占用），文件里已经没有的旧客户先保留，`cm.result=partial`，`cm.failed` 是加载失败的新块，`cm.kept` 是被保留的旧客户；修正文件后再 reload 按新文件处理。
- 某个客户块写错时，这个客户继续使用旧配置，其他客户的修改照常生效，日志里有这个客户的 shortName。
- `SMSOptionOutgoingThrottlingNum` 改动后，分布式限流的速率同步更新。
- **reload 会先确认文件已写完**：文件最后修改时间距现在不足 `ConfigFileStableCheckMs` 时，等到大小和修改时间不再变化才读取（最多等约 10 个间隔）；一直在变，或读取期间发生变化，这次 reload 被拒绝。**推荐的更新方式**：先写临时文件，再用 `mv` 替换，写完再发命令。
- **防止误删**：文件为空或读不到，或者这次要删除的客户超过当前客户数的 `ReloadCustomerMaxRemovePercent`（默认 20%），这次 reload 被拒绝。批量改 shortName 也算删除（旧名字不在文件里）。真要批量修改时，先把这个配置改大（100 表示不限制），热加载 GmmsConfig 后再 reload。
- **被拒绝时**：所有客户保持原配置，连接不受影响，日志 ERROR，`config:files:*` 里 `cm.result=failed`，`cm.failReason` 写明原因。修正后要重新发命令。

### 2.3 查看各模块当前生效的 GmmsConfig

启动连上 Redis 后、以及每次热加载后（成功、失败、没有变化都会写），各模块把自己正在使用的 GmmsConfig 写到 state Redis：

| key | 类型 | 内容 |
|---|---|---|
| `config:effective:{模块名}:{NodeID}` | Hash | 生效配置的每一项（`key → value`），密码类的值（key 含 password、passwd、pwd）写成 `******`。文件里没写的项不出现，表示使用代码默认值 |
| 同上的 `_meta.*` 字段 | | `_meta.module`、`_meta.nodeId`、`_meta.file`（配置文件路径）、`_meta.loadedAt`（写入时间）、`_meta.source`（`startup`/`reload`）、`_meta.reloadResult`（`ok`/`failed`/`unchanged`）、`_meta.pendingRestart`（文件里的值与正在使用的值不同、要重启才生效的项，逗号分隔） |
| `config:effective:modules` | Set | 写过生效配置的 `{模块名}:{NodeID}` |

```
redis-cli SMEMBERS config:effective:modules
redis-cli HGETALL config:effective:CoreEngine1:1
redis-cli HGET config:effective:CoreEngine1:1 _meta.pendingRestart
```

- 写入是原子的（一段 Lua 先删除再写入），不会读到写了一半的内容。
- 没有过期时间：模块下线后 key 会保留，可以按 `_meta.loadedAt` 判断，或手工删除。
- Redis 不可用时只打 WARN，不影响启动和热加载。开关 `GmmsConfigPublishEnable`（4.17）。

### 2.4 查看各模块当前生效的其他配置文件

cm.cfg、路由、`senderReplacement.cfg`、`vendorTemplateReplacement.cfg`、`vendorRoutingReplacement.cfg`、`recipientRuleFile.cfg`、`antiSpam.cfg`、内容模板（3 个文件）、`OperatorMode.properties`、`MQMTaskConfig.properties` 在启动加载完、以及每次 reload 后，把模块**实际在用**的内容写到 state Redis（cm.cfg 里加载失败的客户写的是它仍在用的旧配置）。**黑白名单不写**。设计见《配置文件生效内容写入Redis设计》。

| key | 内容 |
|---|---|
| `config:files:{模块名}:{NodeID}` | 这个模块在用的每个文件：`{名称}.version`、`{名称}.loadedAt`、`{名称}.result`（`ok`/`partial`/`failed`）、`{名称}.file`、`{名称}.entries`；cm 另有 `cm.failed`、`cm.kept`、`cm.fileMd5` |
| `config:file:{名称}:{版本}` | 内容（Hash）。块文件：块名 → JSON；Properties：key → value；其他：6 位行号 → 这一行 |
| `config:file:{名称}:{版本}:meta` | `name`、`version`、`file`、`format`、`entries`、`writtenAt`、`writer`。**有 meta 才表示内容已写完整** |
| `config:file:cm:{版本}:ssid` | ssid → shortName |
| `config:file:routing:{版本}:channel` | 通道名 → 使用它的客户（`[{"customer","ssid","routes":条数}]`） |
| `config:file:routing:{版本}:channelRoutes` | `通道名\|客户名` → 这个客户走这个通道的路由明细 |

名称：`cm`、`routing`、`phonePrefix`、`vendorTemplate`、`systemVendorReplace`、`recipientRule`、`antiSpam`、`contentTemplate`、`portalContentTemplate`、`templateId`、`operatorMode`、`mqmTask`。

```
HGET config:files:CoreEngine1:1 cm.version          # 得到版本
HGET config:file:cm:{版本} VENDOR9                  # 客户配置（JSON，key 为文件里的写法）
HGET config:file:cm:{版本}:ssid 9                   # ssid -> shortName
HGET config:file:routing:{版本}:channel VENDOR8     # 哪些客户使用通道 VENDOR8
```

- 版本是内容的 md5，内容相同的模块共用一份；某个旧版本没有模块再用时立即删除，另设 7 天过期兜底（在用的版本每小时续期）。
- 密码类的值写成 `******`（含连接定义里的 `password=...`）。
- 写入在后台线程完成，不占用 reload 线程；Redis 不可用时每 5 秒重试。开关 `ConfigFilePublishEnable`（4.17）。
- `{名称}.failReason`：最近一次 reload 被拒绝或失败的原因，成功后清空。
- 路由只在启动和 `RELOAD_ROUTING` 时写入，senderReplacement 只在启动和 `RELOAD_PHONE_PREFIX` 时写入，这样 Redis 里的内容与实际生效的表一致。

## 4. Gmms/GmmsConfig.properties

写法为 `Key=Value`。有三种 key：

| 写法 | 例子 | 说明 |
|---|---|---|
| 全局 | `RedisStreamMaxLen=1000000` | 所有模块共用 |
| `{模块名}.Key` | `MultiSmppServer1.Port=16272` | 只对这个模块生效（`getModuleProperty`），模块名即启动参数 `-Dmodule`。下表写作 `{模块}.Key` |
| `{模块类型}.Key` | `CoreEngine.MaxMessageProcessorNumber=5` | 对同一类型的所有模块生效（`getFullModuleTypeProperty`），模块类型来自模块清单（6.5）。下表写作 `{类型}.Key` |

### 4.1 节点与模块基础

### 4.8 Core：外发 outbox 与超时

每次外发到 `stream:mt:routed` 都会登记一条 outbox：`core:outbox:submit:{msgId}:{段号}:{第几次尝试}`（submitMq）。每次外发只认第一个结果，迟到或重复的 submit_resp 被丢弃（`[RESULT-DROPPED]`）。Client 迟迟没有回结果时，Core 按消息状态判超时。

| 配置项 | 默认值 | 热加载 | 作用 |
|---|---|---|---|
| `CoreOutboundOutboxEnable` | `true` | 热加载 | 是否启用 outbox。关闭后不登记、不判超时，也不做"只认一个结果" |
| `CoreOutboundUnreadStallMs` | `120000` | 热加载 | **Client 停止读取多久算故障**。消息还在 routed 里没被读走，并且 Client 消费者已经这么久没读（或消费组不存在），就把消息从 routed **删除收回**，回 COMMUNICATION_ERROR（2500）。Client 还在正常读前面的消息时不会收回 |
| `CoreOutboundRespTimeoutMs` | `180000` | 热加载 | **已发出后等结果的时长**。Client 已经读走并确认消费，超过这个时间还没有结果就回 SUBMIT_RESP_ERROR（2700）。应大于 Client 的发送窗口超时（客户配置 `BufferTimeout`，默认 60 秒） |
| `CoreOutboundOutboxRecheckMs` | `60000` | 热加载 | 还没到超时条件的 outbox，隔多久再检查一次 |
| `CoreOutboundOutboxHardTimeoutMs` | `10800000`（3 小时） | 热加载 | 硬超时。到达后不论状态：没被读就收回并回 2500；已读未确认，或已发出没结果，就回 2700 |
| `CoreOutboundOutboxPayloadTTLSeconds` | `14400`（4 小时） | 热加载 | outbox 在 Redis 里的过期时间，实际取值不小于"硬超时 + 复查间隔 + 60 秒" |
| `CoreOutboundOutboxResultRetryMs` | `5000` | 热加载 | 超时结果写入失败后隔多久重试 |
| `CoreOutboundOutboxScanBatchSize` | `100` | 热加载 | 扫描线程每轮最多检查多少条 |
| `CoreOutboundOutboxScanIntervalMs` | `1000` | 重启 | 扫描线程多久运行一轮 |

HTTP 通道的失败码不同：连不上和读超时回 9000，HTTP 500、504 回 2300，HTTP 503 回 2600，要按需要配进重试码。

超时之后**是否重发**由供应商的 `SMSOptionSubmitRetryCode`（cm.cfg）决定：2500 表示确定没有发出去，重发安全，建议放进重试码；2700 表示可能已经发出去，重发可能重复，按供应商决定。

### 4.9 Core：通道限速放行

通道配了 `SMSOptionCoreProcessorThrottlingNum`（cm.cfg，5.4）时，消息先进入 Core 的暂存队列 `stream:core:hold:{rssid}`，再按速率放行到 `stream:mt:routed`（或 `stream:http:submit`）。

|---|---|---|---|

| `CoreHoldRecoverIntervalMs` | `30000` | 热加载 | 多久检查一次"被已挂掉的 Core 读走、还没放行"的暂存条目 |

每条消息在 INFO 级别的业务日志（用 msgId grep 即可串起来，详见《Core与Client日志优化设计》）：

- Server：submit 为 `[SUBMIT-IN]` → `[STREAM-PUT]` → `[SUBMIT-TO-CORE]`；DR 为 `[STREAM-GET]` → `[DR-OUT]` → `[DR-RESP]` → `[DR-RESULT-TO-CORE]` → `[STREAM-ACK]`
- Core MT：`[STREAM-GET]` → `[CDR] type=IN_SUBMIT` → `[MT-ROUTE]` → `[STREAM-PUT]` → `[MT-TO-CLIENT]`（或 `[MT-HOLD]`/`[MT-RELEASE]`、`[MT-REJECT]`、`[MT-FALLBACK]`、`[MT-STORE]`）→ `[STREAM-ACK]`
- Core 结果：`[STREAM-GET]` → `[RESULT]`（或 `[RESULT-DROPPED]`）→ `[CDR] type=OUT_SUBMIT` → `[STREAM-ACK]`
- Core 供应商 DR：`[STREAM-GET]` → `[VDR-MATCH]` → `[CDR]` → `[DR-TO-SERVER]`/`[DR-TO-HTTP]` → `[STREAM-ACK]`
- Client：SMPP `[MT-OUT]` → `[SUBMIT-RESP]`；供应商 DR `[VDR-IN]` → `[VDR-TO-CORE]`；没等到响应为 WARN `[RESP-TIMEOUT]`；HTTP `[HTTP-OUT]`、`[HTTP-RESP]`

`[STREAM-*]` 受 `RedisStreamTraceLogEnable` 控制，其余业务日志不受开关影响。

## 5. conf/cm.cfg（客户与通道）

> 同一块里不要重复写同一个键：值会用逗号拼起来（如 `20,2`），数值和布尔项解析失败后退回默认值，不会报错。

每个客户或通道一个块，块名为客户的 shortName：

```
[VENDOR9]
CCBSSID: 9
A2PPlayerType: operator
Protocol: SMPP
SMSOptionCoreProcessorThrottlingNum: 2
```

- 写法 `Key: Value`。布尔值写 `true`/`false`（部分旧项写 `yes`/`no`，见说明）。
- 多值项写成 `(k1=v1,k2=v2)`，多组之间用分隔符连接，如 `IncomingConnection: (ConnName=c1,userName=u,...)`。
- **生效方式**：全部随 `RELOAD_CUSTOMER` 生效；改了的客户会重建连接（2.2）。下表不再单列"热加载"。
- 下表中"客户"指提交消息的一方（Server 侧），"通道/供应商"指外发的一方（Client 侧）；同一个块可以两种角色都有。

#### 假 DR 配置示例

四种方式（详见 `docs/假DR逻辑重新设计.md`）。只写和假 DR 有关的行，其他配置照旧。

```text
# 方式 1：收到客户消息（路由成功）就回假 DR，按客户配置延迟和成功比例
[CUST_A]
CCBSSID: 1001
SMSOptionSendDRByInSubmitInCU: true            # 全部号码；只想按国家回就改用下一行
#SMSOptionSendFakeDRByInSubmitRecPrefixInCU: 86,852
SMSOptionDRDelayTimeMinMaxInSec: 5,30          # 5～30 秒随机延迟；0 或不配 = 立即
SMSOptionFakeDRSuccessRatio: 95                # 95% 回 DELIVERED，其余 UNDELIVERABLE；不配 = 100
SMSOptionDRSuccessBiasValue: 3                 # 每条按 92～98 之间的比例随机

# 方式 2：通道回 submit_sm_resp 成功就回假 DR（开关在通道上）
[VENDOR_X]
CCBSSID: 2001
SMSOptionSendDRByOutSubmit: true
SMSOptionRecPrefixForFakeDR: 62,63             # 只对这些号码前缀回；不配 = 全部
SMSOptionDRDelayTimeMinMaxInSec: 10,60         # 方式 2 的延迟配在通道上

# 走 VENDOR_X 但不能收假 DR 的客户
[CUST_B]
CCBSSID: 1002
SMSOptionFakeDRDisable: true

# 方式 3：通道真实 DR 不是 DELIVERED 时，按比例改成 DELIVERED 再回客户
[CUST_C]
CCBSSID: 1003
SMSOptionDRSuccessRatio: 30                    # 失败的真实 DR 中 30% 改成 DELIVERED；不配 = 不改
SMSOptionDRSuccessRatioPrefix: 91              # 只改这些号码前缀；不配 = 全部

# 方式 4：通道接收后 600 秒还没回最终 DR，就给客户回 DR；之后的真实 DR 只记 CDR
[CUST_D]
CCBSSID: 1004
SMSOptionFakeDRTimeoutSec: 600
SMSOptionFakeDRTimeoutStatus: success          # success / fail / ratio（ratio 按 SMSOptionFakeDRSuccessRatio）
```

- 同一条消息方式 1 优先；方式 1 没回、方式 2 命中就不再计时（方式 4）。方式 3 只改写通道的真实 DR，和前三种互不影响。
- 客户在 submit 里没有要 DR（registered_delivery=0）时，方式 1、2、4 都不回。
- 从旧配置升级：客户上的 `SMSOptionSendFakeDR: true` 不再生效，要在客户走的通道上配 `SMSOptionSendDRByOutSubmit: true`；原来用 `SMSOptionDRSuccessRatio` 控制假 DR 比例的客户，改配 `SMSOptionFakeDRSuccessRatio`（`SMSOptionDRSuccessRatio` 现在只改写真实 DR）。

## 6. 其他配置文件

### 6.1 conf/routing/（路由）

文件名为 `{名称}_routingInfo.cfg`，写法与 cm.cfg 相同，按客户块配置。修改后执行 `RELOAD_ROUTING`，路由表只由这个命令（以及启动）重建。所有路由表合并好后一次替换，查询不会读到空表或新旧混合的表。

- **增量加载**：`RELOAD_ROUTING`（`-a`、`-r` 相同）只加载大小或修改时间有变化的文件，以及新增的文件，并去掉已删除的文件。没有变化的文件不读取；所有文件都没有变化时不重建路由表。`RELOAD_ROUTING:-f` 重新加载全部文件。
- **通道 ssid 变化**：路由文件没有变化时不会重新解析通道名，要 `touch` 引用这个通道的路由文件，或执行 `RELOAD_ROUTING:-f`。
- **单个文件失败**：文件为空或读不出、`CCBSSID` 不是数字或缺失（只有 `{业务类型}_default` 文件可以不写）、路由项格式错误或缺少 `Relay`、文件还在写时，只有这个文件失败，它保留旧路由（新文件则没有路由），其他文件照常生效。此时 `routing.result=partial`，`routing.failed` 列出文件和原因，日志 ERROR，下次 reload 重试。
- **整次拒绝**：目录读不出或没有路由文件，或者要删除的文件超过 `ReloadCustomerMaxRemovePercent`。路由保持不变，`routing.result=failed`，`routing.failReason` 写明原因。

`RELOAD_CUSTOMER` 不读路由文件（见 2.2）。

| 配置项 | 作用 |
|---|---|
| `A2PRoutingRelay` / `A2PBackupRoutingRelay` | 按国家/前缀的路由、备用路由。外发失败或 DR 改道时走备用路由；`Relay=a;b` 的 `;` 后面部分不生效 |
| `A2PSenderRoutingRelay` / `A2PBackupSenderRoutingRelay` | 按发送方的路由、备用路由 |
| `A2PContentKeywordRoutingRelay` / `A2PBackupContentKeywordRoutingRelay` | 按内容关键字的路由、备用路由 |
| `A2PSec*RoutingRelay`（6 个，同上加 `Sec`） | 第二次路由（失败后改道） |
| `A2POP*RoutingRelay`（6 个，同上加 `OP`） | 按运营商的路由 |
| `A2PNumberRoutingRelay` | 按号码的路由。`Relay` 写通道 ssid（如 `(Number=8613800000000,Relay=405,Priority=1)`），`Priority` 小的优先 |
| `A2PServiceTypeIDRoutingRelay` | 按 service type id 的路由 |
