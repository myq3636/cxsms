## 2. 当前配置和理由（2026-11-19 整理）

备份：`Gmms/GmmsConfig.properties.bak.20261119_tune`、`conf/log4j2.xml.bak.20261119_tune`、`bin/a2pStart.sh.bak.20261119_tune`、`redis-7.4.9/conf/*.conf.bak.20261119_tune`。

### 2.1 这次改的

| 文件 | 配置 | 原来 → 现在 | 理由 |
|---|---|---|---|
| `conf/log4j2.xml` | `com.king` 日志级别 | trace → **info** | trace 每条消息写大量调试日志；压测一直是 INFO（用例的 `conf.sed`），容量数据都是 INFO 下测的 |
| `bin/a2pStart.sh` | `A2P_JVM_SERVER` | 1g → **2g** | Server1 扛八成客户流量，4000 TPS 时 GC 后的堆到 635 MB |
| GmmsConfig | `SmppServerInboundGlobalQueueLimit` / `SmppServerInboundPerSsidQueueSize` | 2000000 / 50000 → **200000 / 10000**（代码默认） | Server 内存里等写 Redis 的 MT 上限；200 万条放不进堆。20 万约 5000 TPS 的 40 秒，超出回 `ESME_RTHROTTLED` |
| GmmsConfig | `RedisStreamMaxLen` | 1000000 → **20000000** | XADD 按 MAXLEN 裁剪会悄悄删掉没读的消息（按通道的 hold stream 不分片）；内存改由 Redis `maxmemory` 限制，满了写入失败、客户看得到 |
| GmmsConfig | `RedisStreamMonitor.Enable` | false → **true** | 每个模块每分钟一次积压检查（`[METRICS-GAUGE]` 的 `redis.stream.*`、超阈值 `[STREAM-BACKLOG]`） |
| GmmsConfig | `RedisStreamAutoClaimIntervalMs` | 300000 → **60000** | 模块崩溃后在途消息最多约 2 分钟被别的节点接手（原来最多 6 分钟） |
| GmmsConfig | `DS_gmms_MaxPoolSize` | 3 → **10** | 通道故障、重试大量写 DB 时，3 个连接会让 Core 的处理线程排队；12 个模块共 120 个，MySQL `max_connections` 500 |
| GmmsConfig | `Redis_connect_timeout_ms` | 未配（默认 2000）→ **30000** | a2p 刚启动、连接池还空着时马上来大流量，几百个线程同时新建 Redis 连接，有的超过 2 秒，那几条 submit 失败（2026-11-18 3000 档 117 条、11-19 29 条，`Connect timed out`）。**注意：Jedis 用这一个值同时作连接超时和每次调用的读超时**，Redis 卡住（AOF fsync 卡、主库挂掉连接没断）时处理线程最多等 30 秒才报错；局域网通常 1～5 秒。启动时读取 |
| GmmsConfig | 重复的 `NodeID`、`SystemManager.enable` | 各保留一个 | 值相同 |
| Redis 10 个实例 | `maxmemory` | 8gb → **3gb** | 10 × 8 GB 超过整机内存（PF004 被 OOM 杀）；10 × 3 GB + a2p 约 18 GB + MySQL 约 5 GB 放得下 |
| Redis 8386/8387/8388/8376/8377/8378 | 数据目录 | 根分区 → **`/mnt/redisdata`** | 和 MySQL 分开盘（8387 日志里有 AOF fsync 太慢），也避免根分区被 AOF 写满 |

### 2.2 前几天调好的（保留）

| 配置 | 值 | 来由 |
|---|---|---|
| `Redis_submit_masters` / `_slaves` | 8387,8397 / 8377,8367 | 多主（《Redis多主分片设计》） |
| `Redis_report_masters` / `_slaves` | 8388,8398 / 8378,8368 | 同上 |
| `TotalShards` | 64 | 大客户的 MT 分到更多 stream |
| `CoreShard.CoreEngine1/2/3` | 0-21 / 22-42 / 43-63 | 和 `TotalShards` 一致（改分片要先清空积压） |
| `ClientShard.MultiSmppClient1/2`、`CommonHttpClient1/2` | 0-31 / 32-63、0-63 | 同上 |
| `RedisStreamConsumer.CoreResult.WorkerCorePoolSize` | 30 | 结果跟上，通道 DR 不再大量先于结果到达 |
| `SmppServerInboundSharedPoolEnable` | true | Server 发 DR 不被收 MT 堵住 |
| 代码默认（不用配）：`CoreStreamAttemptBatch`、`CoreStreamAttemptBatchFlagsInMemory`、`ClientSendMarkerBatch`、`CoreMTDispatchBatch`=32、`ClientDispatchBatch`=32、`EarlyDr.*`、`ThrottleInSyncIntervalMs`=500 | — | 《配置项说明》 |

不建议开：`RedisStreamBackPressureEnable`（每条写入多一次 XLEN）、Redis `io-threads`（实测吞吐下降）。

## 3. 压测工具

都在 `/usr/local/a2p/routetest`（仓库 `regression/routetest`，同步方式见 8.1）。

| 组成 | 作用 |
|---|---|
| `rt.RouteCase`（`bin/run_case.sh CASE`） | 按用例改 a2p 配置（`cm.extra.cfg`、`routing/`、`gmms.append/`、`conf.sed/`，结束放回）、重启 a2p（`--no-restart` 不重启）、模拟客户和通道收发、统计（含按客户的延时 `latency after the warm-up by template`） |
| `bin/run_hightps.sh CASE` | 两边抓包（`tcpdump -i lo`）+ `rt.FlowCheck` 逐条对账（抓包和 CDR 一致、无多发无丢失）+ `run_case.sh` + `memwatch.sh`/`rt.MemReport`（内存） |
| `bin/perf_clean.sh [--logs]` | 停 a2p，清空所有 Redis（保留 `thcon`，按 GmmsConfig 找 state 和各 MQ 主库）和 MySQL；`--logs` 连日志、CDR、SDQ 文件一起清 |
| `bin/perf_watch.sh 前缀` | 监控（第 5 节） |
| `bin/perf_step.sh CASE "TPS..." [--no-replicas]` | 阶梯测试 |
| `bin/perf_long.sh CASE [--no-capture] [--no-replicas]` | 长时间测试（抓包对账 + 内存 + 监控）；`--no-capture` 不抓包（几千万条 MT 时 `rt.FlowCheck` 放不进内存），`--no-replicas` 压测期间停掉 Redis 从库、结束后启动 |
| `rt.PerfReport 目录...` | 报告和对比（第 6 节） |

用例（`cases/`）：

| 用例 | 内容 |
|---|---|
| `PF005_step` | 阶梯：5 个营销客户（80%，Server1，号码 86138 → 营销通道 RTVM1）+ 5 个 OTP 客户（20%，Server2，86139 → OTP 通道 RTVO1），每个客户 6 个 bind、每个通道 6 个 bind（两个 Client 各 3 个），都不限速；每档预热 60 秒、压 10 分钟、排空 3 分钟 |
| `PF006_4000tps_5h` | `PF005_step` 的流量和 bind，4000 TPS × 5 小时（预热 5 分钟、排空 30 分钟、空闲 10 分钟），内存；不抓包 |
| `PF004_mixed_1h` | 同样的流量 5000 TPS × 1 小时（预热 5 分钟、排空 30 分钟、空闲 10 分钟），抓包对账和内存；每个客户、通道 2 个 bind |
| `PF003_fairness` / `PF003_otp_baseline` | 营销冲量（4000 TPS，营销通道限速 2000）时 OTP 客户的延时 / 只有 OTP 的对照 |
| `PF002_5000tps_1h` | 混合流量（普通、改道、长短信、无路由、假 DR）1 小时 |

## 4. 执行步骤

```bash

```

```bash
cd /usr/local/a2p/routetest

# 只测 a2p 自己的容量时加 --no-replicas（压测期间停掉 Redis 从库，结束后自动启动）
```

每档约 15 分钟。结束时脚本清空数据、启动 a2p，报告在 `/usr/local/a2p/log/perf_step_PF005_{时间}/report.md`。

### 4.3 长时间测试（一致性、内存）

```bash
cd /usr/local/a2p/routetest
# 先把用例的 soak.tps 改成这台机器能承受的值（第 7 节，约 3000～3500），否则积压持续增长、内存耗尽
```

## 5. 监控

`bin/perf_watch.sh 前缀` 每 10 秒（`PERF_WATCH_SEC`）写一行，第一列是 epoch 秒，`perf_step.sh`、`perf_long.sh` 自动启动：

| 文件 | 内容 |
|---|---|
| `前缀.streams` | 各 MQ 主库上每类 stream 按 ssid 的条数（`mt:pending:{ossid}`、`mt:routed:{rssid}`、`core:results:{ssid}`、`core:inbound-dr:{ssid}`、`dr:pending:{ossid}` 等），一次 Lua 汇总 |
| `前缀.cpu` | a2p 各模块、各 Redis、mysqld、压测工具的 %CPU（100 = 一个核），`idle=` 整机空闲 |
| `前缀.redis` | state 和各 MQ 主库的 `usedMB`、`maxMB`、`ops` |
| `前缀.disk` | `/` 和日志盘剩余 GB |
| `前缀.guard` | 保护触发的原因（有这个文件说明测试被提前停止） |

**保护**：任一 Redis 超过 `maxmemory` 的 `PERF_GUARD_REDIS_PCT`（默认 90）%，`/` 剩余少于 `PERF_GUARD_ROOT_GB`（默认 8）GB，或日志盘（日志、CDR）剩余少于 `PERF_GUARD_LOG_GB`（默认 20）GB，停止压测工具发送。4000 TPS 一小时的 CDR 和日志约二三十 GB。

运行中查看：

```bash
D=$(ls -dt /usr/local/a2p/log/perf_* | head -1)
tail -1 $D/watch*.streams; tail -1 $D/watch*.cpu; tail -5 $D/watch*.redis; cat $D/notes.txt
grep -h "STREAM-BACKLOG" /usr/local/a2p/log/CoreEngine1.log | tail -3      # 积压告警（RedisStreamMonitor）
grep -h "redis.stream" /usr/local/a2p/log/*_metrics.log | tail -5         # 积压指标
dmesg -T | grep -i "out of memory" | tail -3                              # OOM
```

## 6. 结果和对比

`java -cp /usr/local/a2p/routetest/lib/routetest.jar rt.PerfReport 目录 [目录...]`（`perf_step.sh`、`perf_long.sh` 结束时自动生成 `report.md`）。几个目录一起给就是并排对比，例如这次和上一次：

```bash
java -cp lib/routetest.jar rt.PerfReport /usr/local/a2p/log/perf_step_PF005_1119_1951 /usr/local/a2p/log/perf_step_PF005_{新的}
```

报告三张表：

1. 每次（每档）：计划 TPS、发出的 MT 和段、submit 被拒、DR 和预热后没 DR 的、**稳定期（预热结束到负载结束）积压总数的斜率**、积压最多的时刻和最多的三类、结论、CPU 空闲中位和最低、提交 → 通道 p50/p95/p99；
2. 按客户组（客户名去掉数字，如 `rtmk`、`rtot`）的提交 → 通道延时；
3. 稳定期各角色平均 CPU（Core、Server、Client、MQM、Redis、mysqld、压测工具）和各 Redis 的最高内存。

判断标准：

| 项 | 通过 |
|---|---|
| 积压 | 稳定期斜率不超过 max(20, TPS × 0.5%) 条/秒（报告写"稳定"） |
| 延时 | 普通客户提交 → 通道 p99 小于 1 秒（3000 TPS 时约 0.1 秒） |
| 消息 | `submit 被拒` 为 0；预热后没 DR 的为 0（排空时间要够） |
| 一致性（长时间测试） | `flow/report.txt` 为 `RESULT: PASS` |
| 内存（长时间测试） | `mem_report.txt` 为 `MEMORY: PASS`；疑似时按《5000TPS多主测试慢的环节分析》11.2 用 `jcmd PID GC.run` 后看堆、线程、句柄 |

## 7. 这台机器的基准（2026-11-18、19）

| 档 | 条件 | 积压 | 营销 p50 / p99 | OTP p50 / p99 | CPU 空闲 |
|---|---|---|---|---|---|
| 3000 | 6 个 bind，停从库 | 稳定 | 52 ms / 106 ms | 54 ms / 108 ms | 24% |
| 3500 | 同上 | 稳定（阵发） | 49 ms / 8 秒 | 51 ms / 195 ms | 16% |
| 4000 | 同上 | 总体稳定，阵发大 | 3.7 秒 / 60 秒以上 | 196 ms / 1.0 秒 | 15% |
| 4500 | 同上 | **增长** | 60 秒以上 | 492 ms / 2.2 秒 | 15% |
| 5000 | 同上 | **增长** | 60 秒以上 | 1.2 秒 / 4.1 秒 | 13% |

### 7.1 按第 2 节配置的验证（2026-11-19）

`bin/perf_step.sh cases/PF005_step "3000 3500"`，先不停从库，再 `--no-replicas`（目录 `/usr/local/a2p/log/perf_step_PF005_1119_1951`、`perf_step_PF005_1119_2023`，对比报告 `rt.PerfReport` 两个目录）：

| 档 | Redis 从库 | 营销 p50 / p95 / p99 | OTP p50 / p99 | 积压最多 | CPU 空闲 中位 | Redis 合计 CPU | submit 被拒 |
|---|---|---|---|---|---|---|---|
| 3000 | 开 | 51 ms / 133 ms / **4.9 秒** | 52 ms / 157 ms | 6.0 万 | 15% | 3.5 核 | 29（启动时连 Redis 超时） |
| 3000 | 停 | 53 ms / 93 ms / **106 ms** | 54 ms / 106 ms | 5.2 万 | 25% | 2.6 核 | 0 |
| 3500 | 开 | **15.3 秒** / 60 秒以上 / 60 秒以上 | 189 ms / 1.1 秒 | 16.9 万 | 14% | 3.8 核 | 0 |
| 3500 | 停 | 51 ms / 1.1 秒 / 13 秒 | 51 ms / 202 ms | 7.3 万 | 16% | 2.8 核 | 0 |

四次都没有丢 DR。

- **第 2 节的配置本身不比原来差**：停从库的 3000 档和 2026-11-18 的旧配置（p99 106 ms、空闲 24%）一样；
- **Redis 从库和主库在同一台机器上，代价很大**：5 个从库在 3000 TPS 时多用约 0.85 个核，主库还要同步给从库，每次 Redis 往返变慢，营销 p99 从 0.1 秒变成 5 秒、3500 档营销 p50 从 51 ms 变成 15 秒。正式部署时从库要放在另一台机器上；
- 启动时 submit 被拒：已把 `Redis_connect_timeout_ms` 改成 30000（7.1 之后，它同时是读超时，见第 2.1 节）。

结论：16 核、压测工具在同一台机器上时，**延时稳定的上限约 3500 TPS，4000 能扛住但有阵发积压，4500 起积压持续增长**。每 1000 TPS 约需 4.5 个核（a2p 2.65、Redis 1.85，《模块规格评估》）；要稳定 5000 TPS，压测工具、Redis 放到别的机器，或用 24 核以上的机器。

- 中途停掉的（`Ctrl-C`、保护触发）：`pkill -f rt.RouteCase; pkill -f rt.FlowCheck`，再 `bin/perf_clean.sh --logs`，确认从库在跑（第 1.3 节），`a2pStart.sh` 启动；
- 测试目录 `/usr/local/a2p/log/perf_*` 不自动删，结论记进 `docs/` 以后可以删；抓包 `/usr/local/a2p/log/pcap_*` 占空间大，用完就删。

## 9. 已知问题和注意

| 问题 | 说明 |
|---|---|
| 超过容量长时间压测会耗尽内存 | PF004（5000 TPS 1 小时）时 Redis 和压测工具被 OOM 杀；现在 `maxmemory 3gb` 和监控保护会先停下来，长时间测试的 TPS 要在容量以内 |
| 存起来的 DR（SDQ）不会补发 | 服务器上的 `script/queueFile/queueFileLoad.sh` 没有运行，而且连的是旧 MySQL（端口 33067）；正常情况下早到的 DR 走 Redis 延迟队列（`EarlyDr.*`），不会进 SDQ |
| 压测工具和被测系统在同一台机器 | 压测工具约占 1～3 个核（长时间测试加上对账程序和抓包更多），测出的容量偏低 |
| Redis 从库和主库在同一台机器 | 3000 TPS 时营销 p99 从 0.1 秒变成 5 秒（7.1）；测 a2p 自己的容量用 `--no-replicas`，正式部署从库放到别的机器 |
| 改分片（`TotalShards`、`CoreShard.*`、`ClientShard.*`）或主库个数 | 要先清空积压，所有模块一致 |
| 回归测试 | 用本机 16379、16382、16383，不要和性能测试同时跑 |
