# 模块规格评估：一个 Server、一个 Core、一个 Client 能不能撑 5000 TPS

> 日期：2026-11-18。代码：Redis 多主（submit 8387 + 8397，report 8388 + 8398）、StreamAttempt 按批、标记放内存、限流本地计数。测试服务器 16 核。

## 1. 结论

**不能，而且和模块个数基本无关。** CPU 几乎全部花在处理消息上，每个模块空闲时只用 1%～4% 的核；把 3 个 Core 合成 1 个、2 个 Server 合成 1 个、2 个 Client 合成 1 个，总共只省约 0.15 个核。

按实测，这种混合流量每 1000 TPS 要约 **4.5 个核**（a2p 2.65 个，Redis 1.85 个）。5000 TPS 要约 **22～23 个核**，超过这台 16 核机器；这台机器上 a2p 和 Redis 合计最多约 3500 TPS（不留余量、不算压测工具），留 15% 余量并且压测工具在同一台机器上时约 2800～3000 TPS。

## 2. 测量

用例 `cases/PF_SIZE`：和 PF002 相同的混合流量（普通 MT、改道、3 段长短信、无路由、假 DR），1000 TPS × 60 秒（每秒约 1200 段），没有积压，客户提交 → 通道 p50 44 ms，测试结束时每条 MT 都有 DR。先空闲 30 秒，再在负载稳定的 50 秒里从 `/proc/{pid}/stat` 读每个进程用掉的 CPU。结果目录 `/usr/local/a2p/log/size_*`。

| 进程 | 空闲 | 1000 TPS | 每 1000 TPS（减去空闲） |
|---|---|---|---|
| CoreEngine1 / 2 / 3 | 4% / 4% / 4% | 53% / 51% / 49% | **合计 141%** |
| MultiSmppServer1 / 2（Server1 收 85% 的流量） | 1% / 1% | 48% / 21% | **合计 67%** |
| MultiSmppClient1 / 2 | 1% / 1% | 30% / 29% | **合计 57%** |
| submit 主库 8387 / 8397 | 1% / 1% | 26% / 26% | 51% |
| report 主库 8388 / 8398 | 2% / 2% | 30% / 30% | 55% |
| state 8386 | 2% | 20% | 18% |
| 5 个从库 | 0%～1% | 7%～15% | 61% |
| MQM、MySQL | 0%～1% | 0%～1% | 0% |

（100% = 一个核）

## 3. 推到 5000 TPS

按线性推算（TPS 高时每批读到的条数多，每条的开销会略低，实际可能少 10%～20%）：

| 部分 | 5000 TPS 需要的核 |
|---|---|
| Core | 7.0 |
| Server | 3.4 |
| Client | 2.9 |
| Redis 主库（submit 2.6、report 2.8、state 0.9） | 6.2 |
| Redis 从库 | 3.0 |
| **合计** | **约 22.5**（不含压测工具） |

和 5000 TPS 的实测对得上：那次整机 CPU 满了，a2p 用了约 10 个核、Redis 约 4.5 个核，实际处理了约 3000～3500 TPS 的量。

## 4. 只用一个 Server、一个 Core、一个 Client 的其他问题

| 模块 | 单个时要多少 | 能不能做到 | 问题 |
|---|---|---|---|
| Core | 约 7 个核 | 一个 JVM 可以用到，但要把堆从 2 GB 加到 4～6 GB（G1，分配速率是现在单个 Core 的 3 倍） | 处理 MT 的并发由 stream 个数决定（`TotalShards` 16，大客户最多 16 个 stream 同时处理），和 Core 个数无关，合成一个不会更快也不会更慢；**挂掉时所有 MT、结果、DR 都停**，直到重启后自动认领接上 |
| Server | 约 3.4 个核 | 可以（Server1 现在一个就承担了 85% 的流量） | 所有客户的 bind 都在一个进程上；挂掉时所有客户断开重连，没有另一个 Server 接 |
| Client | 约 2.9 个核 | 可以 | 通道的 bind 数（`SessionNumber`）要按一个 Client 重新配，否则通道侧的窗口少一半；挂掉时所有通道都停 |

所以一个 Server、一个 Core、一个 Client 省不了 CPU，反而丢了高可用。

## 5. 5000 TPS 的建议规格（这种流量构成）

| 机器 | 放什么 | 核 |
|---|---|---|
| 应用服务器 | 2 个 Core（各约 4 核，堆 4 GB）、2 个 Server（各约 2 核）、2 个 Client（各约 2 核）、MQM | 约 13.5 核在用，**16 核机器约 85%**；要留余量用 20～24 核 |
| Redis 服务器 | submit 2 主、report 2 主、state | 约 6.2 核，8 核以上 |
| 另一台（或和 Redis 主库错开） | 5 个从库 | 约 3 核 |
| 压测机 | 客户和通道模拟器 | 不和被测系统放在一起 |

要在现有的 16 核上跑到 5000 TPS，就要把每条消息的开销降到现在的约 60%。最大的是 Core（每 1000 TPS 1.41 个核，占 a2p 的一半多），其次是 Redis（主库加从库 1.85 个核）；《Redis消息操作次数统计》第 4 节第 4～6 项（Client 发送标记按批、Server 和 Client 按批写 stream、未读检查）主要降 Redis 和 Client、Server 等 Redis 的开销，Core 自身的 CPU 要另外做 profiling 再看。
