# 性能监控埋点：现状评估与改进设计

> 日期：2026-11-11。状态：**已实现**（第 4 节的 1～4 步，见第 9 节实现记录）。第 6 节已确认（2026-11-11）；第 7 节是告警（只打日志），第 8 节是性能影响。

## 1. 现在有什么

### 1.1 机制

| 部分 | 文件 | 做什么 |
|---|---|---|
| 采集 | `metrics/MetricsCollector` | 进程内三种指标：计数（counter，只增）、瞬时值（gauge）、耗时（timer：累计纳秒 + 次数 + 6 个区间 `≤10ms / ≤50ms / ≤100ms / ≤500ms / ≤1000ms / >1000ms`），都是 `ConcurrentHashMap<String, AtomicLong>` |
| 命名 | `metrics/MetricsNames` | `模块.组件.流向.消息类型.动作`，例 `coreengine1.business.core.submit.routing_success`；按 ssid 的 `模块.ssid.{ssid}.{阶段}.{动作}`（`Metrics.Ssid.Enable`） |
| 输出 | `metrics/MetricsReporter` | 每 `Metrics.ReportIntervalSeconds` 秒一行 `[METRICS] module=... window=30s tps="..." gauge="..." timer="..."` 写到 logger `metrics.logger`：计数换算成本窗口的每秒值，耗时是本窗口的次数、平均值和各区间次数 |
| 配置 | GmmsConfig `Metrics.*`（热加载） | `Enable=true`、`ReportIntervalSeconds=30`、`LogLevel=DEBUG`、`PrintZero=false`、`PrintGauge=false`、`MinTPS=0.01`、`Ssid.Enable=false` |

### 1.2 埋了哪些点

| 类型 | 数量 | 内容 |
|---|---|---|
| 计数 | 约 120 处 | Server 收到 / 写入 Redis / 拒绝；Core 读到 / 路由成功失败 / 写给 Client；Client 读到 / 发出 / 窗口满 / 限速 / bind 限速 / 结果写回；DR 各阶段；Stream 读写确认失败；DR 选 Server 的兜底。按 ssid 的同一套（开关打开时） |
| 耗时 | 7 处 | 每个 Stream 消费者处理**一条消息**的时间：`consumer.process.{类型}.latency`（MT、结果、入向 DR、给 Server 的 DR、HTTP 外发、MQM、Client 外发） |
| 瞬时值 | 约 27 处 | Server 入向队列（排队数、处理中、活跃 ssid）；Client 共享发送队列；SMPP 等待响应 / 等待 DR 的数量和超时队列；Redis Stream 的长度和待确认数（`RedisStreamMonitor.Enable`）；DB 连接池（`DB.PoolStats.Enable`）；JVM 线程数 |

### 1.3 其他和性能有关的日志

- `[STREAM-PUT] / [STREAM-GET] / [STREAM-ACK]`：每条消息每个环节一行 INFO（`RedisStreamTraceLogEnable`，默认开）。
- 业务日志 `[SUBMIT-IN]`、`[MT-ROUTE]`、`[MT-TO-CLIENT]`、`[MT-OUT]`、`[SUBMIT-RESP]`、`[DR-...]`：每条消息每个环节一行 INFO。
- `[STREAM-BACKLOG]`：Stream 积压超过阈值时 WARN（`RedisStreamMonitor.Enable`，默认关）。
- DB 连接池统计（`DB.PoolStats.Enable`，默认关）。
- SMPP PDU 日志（`SmppPduLogEnable`，默认开），带会话名，可以算响应延迟，但要离线处理。

## 2. 评估

### 2.1 默认配置下基本看不到（最主要的问题）

| 问题 | 原因 |
|---|---|
| `[METRICS]` 这一行不出现 | `Metrics.LogLevel` 默认 `DEBUG`，而 log4j2 的 root 是 `INFO`，`metrics.logger` 没有单独配置。采集一直在做（`Metrics.Enable=true`），结果却丢掉了。回归环境的日志里一行 `[METRICS]` 都没有 |
| 队列、积压、连接池看不到 | `Metrics.PrintGauge=false`；Stream 长度、待确认数要 `RedisStreamMonitor.Enable=true` 才采集；连接池要 `DB.PoolStats.Enable=true` |

### 2.2 缺最关键的几种延迟

现在只量了“消费者处理一条消息花了多久”。短信网关最常被问的几个问题，这套指标回答不了：

| 想知道 | 现在 |
|---|---|
| 消息在 Redis Stream 里**排队**了多久（Server→Core、Core→Client、结果、DR） | 没有。Stream 积压只有条数，没有时间 |
| 供应商回 submit_sm_resp 要多久（按通道、按 bind） | 没有。只能离线分析 PDU 日志（之前查 bind 发送不平均时就是这么做的） |
| 供应商回 DR 要多久（按通道） | 没有 |
| 一条消息从客户提交到发给供应商一共多久（端到端） | 没有 |
| Redis、DB 一次操作多久；异步写库队列积压多少 | 没有 |
| 被限速、窗口满推迟的消息等了多久 | 只有推迟次数 |

### 2.3 耗时统计太粗

- 只有平均值和 6 个区间，没有最大值、p95、p99。平均值会被大量很快的请求拉低，看不出尾部。
- 区间下限是 10 ms：Core 处理一条消息大多在几毫秒内，全挤在 `≤10ms` 里，分不出 2 ms 和 9 ms。
- 名字会撞：Core 的 MT 消费者和 MQM 消费者都是 `consumer.process.submit.latency`，两种消息混在一起。

### 2.4 输出形式

- 所有指标挤在一行。开了按 ssid 统计后，一行几千个键，人很难看，日志采集也容易截断。
- 只在本节点的日志里，多节点时要逐台看；没有“全系统现在怎样”的汇总。
- 不是结构化格式（key=value 嵌套 `{}`），接 ELK / Prometheus 要另写解析。

### 2.5 开销

- 每次记指标都现拼一遍名字字符串（`MetricsNames.build`：4 段拼接），每条消息有十来个指标，1000 TPS 就是每秒上万次小字符串分配。
- 热点计数用的是 `AtomicLong`，多个线程同时加同一个计数会互相等待；`LongAdder` 更合适。
- 每条消息每个环节一行 INFO（1.3），高流量时日志写入本身是不小的开销，但它是排查问题的主要手段，不建议关，建议用异步日志（第 3.6 节）。

### 2.6 小问题

- 事件驱动的瞬时值（比如等待响应的数量）只在有事件时更新，没有事件时一直保持最后的值，看起来像“卡住了”。
- 计数从进程启动开始累加，只能看每个窗口的增量；进程重启后从 0 开始（对每秒值没有影响）。

### 2.7 结论

框架本身（进程内无锁采集 + 定时汇总输出）是合适的，开销也可控；问题集中在：**默认不输出**、**缺排队 / 供应商 / 端到端延迟**、**耗时只有平均值**、**输出不好用**。建议按第 4 节分步改，第 1 步只改配置就能看到现有的数据。

## 3. 改进设计

### 3.1 默认可见

- `Metrics.LogLevel` 默认改为 `INFO`（每个模块每 30 秒几行，量很小）。
- log4j2 给 `metrics.logger` 单独一个文件 `log/metrics.log`（不混在业务日志里，按天滚动，保留 7 天）：

  ```xml
  <RollingFile name="M" fileName="${sys:a2p_home}log/metrics.log" filePattern="${sys:a2p_home}log/metrics.%d{yyyy-MM-dd}.log">
    <PatternLayout pattern="%d{yyyy-MM-dd HH:mm:ss} %m%n"/>
    <TimeBasedTriggeringPolicy/><DefaultRolloverStrategy max="7"/>
  </RollingFile>
  <Logger name="metrics.logger" level="info" additivity="false"><AppenderRef ref="M"/></Logger>
  ```

- `Metrics.PrintGauge` 默认 `true`；`DB.PoolStats.Enable` 默认 `true`（读连接池对象，没有 DB 操作）。
- `RedisStreamMonitor.Enable` 默认 `true`，**但要先改实现**（第 8.2 节）：现在每个周期用 SCAN 扫一遍整个 Redis 库找 Stream，每个 Stream 再发 XLEN、XGROUP CREATE、XPENDING、ZSCORE 四条命令。改为从已有的“活跃流”ZSET（doorbell，`zset:mt:routed:active` 等）取 Stream 名、不再每次建消费组、四条命令用 pipeline 一次发；周期改为 60 秒。

### 3.2 输出格式

- 一个窗口分几行，每行一类：`[METRICS-TPS]`、`[METRICS-GAUGE]`、`[METRICS-TIMER]`、`[METRICS-SSID]`（按 ssid 的单独一行或每个 ssid 一行），一行太长时按 4KB 自动分行。
- 新增 `Metrics.Format=json|kv`（**默认 `json`**，已确认）：每行一个 JSON 对象，方便直接进 ELK；`kv` 是现在的格式。
- 汇总到 Redis（可选，`Metrics.Redis.Enable`）：每个窗口把本节点的快照写进 `metrics:{模块}:{节点}`（Hash，TTL 3 个窗口）。`a2pctl metrics` 一条命令列出所有节点的 TPS、积压、延迟 p95，不用登录每台机器。

### 3.3 新增的延迟指标

大多用已有的时间戳计算，不加网络请求，开销是每条消息几次加法（个别需要在消息上补一个时间，表里注明）：

| 指标 | 在哪里量 | 怎么算 | 维度 |
|---|---|---|---|
| `stream.lag.{流向}` | 每个 Stream 消费者读到消息时 | 当前时间 − Stream 条目 id 里的毫秒数（XADD 的时间） | 流向 |
| `client.vendor.submit_rtt` | Client 收到 submit_sm_resp 时 | 收到时间 − 放进等待响应表的时间（`SmppPendingSubmitManager` 已经记了） | 通道；可选按 bind（`Metrics.Bind.Enable`） |
| `core.vendor.dr_latency` | Core 匹配到供应商 DR 时 | 匹配时间 − 外发成功时间（外发成功时在消息上记下时间，随 DR 查找记录存下；需要新增一个字段，实现时确认能否复用 `DateIn`） | 通道 |
| `e2e.submit` | Client 发出 submit_sm 时 | 发出时间 − Server 收到的时间（Server 收到时在消息上记下时间；实现时确认现有的 `TimeStamp` 是否就是收到时间） | 无（按 ssid 时有） |
| `e2e.dr` | Server 收到客户的 deliver_sm_resp 时 | 收到时间 − Client 收到供应商 DR 的时间 | 无 |
| `redis.op.{xadd\|lua\|read}` | `StreamQueueManager` 的写、Lua、读 | 调用前后 | 操作 |
| `db.op.{insert\|update\|select}` | `DataManager` 的 SQL 执行 | 调用前后 | 操作；外加瞬时值“异步写库队列长度” |
| `client.defer.wait` | Client 推迟的批次重新处理时 | 重新处理时间 − 推迟时间 | 原因（窗口满 / 限速 / bind 限速） |

按通道的维度数量 = 通道数，在可控范围内；按 bind 默认关（bind 多时键多）。

### 3.4 耗时统计

- 区间改细：`1 / 5 / 10 / 25 / 50 / 100 / 250 / 500 / 1000 / 5000 ms / 更长`。
- 每个窗口多记一个最大值（`AtomicLong` 比较交换，开销可以忽略）。
- 输出时按区间估算 p50 / p95 / p99（区间内按线性插值，精度够用于看趋势）：
  `timer core.consumer.mt.latency count=30120 avg=2.1 p50=1.6 p95=6.8 p99=18 max=240`。
- 消费者耗时的名字带上消费者，不再按消息类型合并：`consumer.mt`、`consumer.mqm`、`consumer.result`、`consumer.inbound_dr`、`consumer.server_dr`、`consumer.http_submit`、`consumer.client_out`。

### 3.5 瞬时值

- 补上各消费者线程池的“活动线程 / 排队任务数”，延迟 DR 和假 DR 超时计时的 ZSET 大小，异步写库队列长度。
- 事件驱动的瞬时值改成汇报时现取（注册取值函数），不再停在最后一次事件的值。

### 3.6 降低开销

- 指标名缓存：同一组（组件、流向、类型、动作）只拼一次字符串，之后查表。
- 计数改用 `LongAdder`。
- 业务日志（每条消息每环节一行）保持现在的内容，生产环境的 log4j2 建议用异步日志（`AsyncLogger` / `AsyncAppender`），日志写盘不阻塞处理线程。
- 改完用 `MemSoakIT`（手工用例）在同样流量下比较改前改后的 CPU 和吞吐。

### 3.7 告警（可选）

在汇报时检查几个阈值，超过就打一行 WARN `[METRICS-ALERT]`，方便现有的日志告警直接接：Stream 排队 p95 超过 `Metrics.Alert.StreamLagMs`、供应商响应 p95 超过 `Metrics.Alert.VendorRttMs`、DB 连接池有等待线程、异步写库队列超过阈值。阈值不配就不检查。

## 6. 已确认（2026-11-11）

1. 默认值改成可见（3.1）。线上 log4j2 需要运维同时加 `metrics.log`。
2. 输出用 **JSON**（`Metrics.Format` 默认 `json`，3.2）。
3. 汇总到 Redis，并提供 `a2pctl metrics`（3.2）。
4. 按 bind 统计供应商响应延迟（3.3），开关 `Metrics.Bind.Enable`；为了控制输出量，只输出本窗口有流量的 bind。
5. 告警：**只在系统里打告警日志**（`[METRICS-ALERT]`），后续由外部监控采集日志再告警；不发邮件。原有的告警邮件功能（`MailSender`）已整体去掉，原来发邮件的地方改为打 `[ALERT]` 日志（管理工具为 `[MGT-ALERT]`）。见第 7 节。

## 7. 告警：系统里做 vs 外部监控

| | 系统里做 | 外部监控 |
|---|---|---|
| 怎么做 | 每个窗口汇报时，Reporter 拿本窗口的数和阈值比，超过就打一行 `WARN [METRICS-ALERT] {...}`（JSON）。阈值在 GmmsConfig（`Metrics.Alert.*`，热加载） | 系统只负责输出：JSON 的 `metrics.log` 由日志采集（Filebeat → ELK / Loki）收走，或者由一个采集脚本读 Redis 的 `metrics:*` 快照推给 Prometheus；告警规则写在 Grafana / Alertmanager / ELK Watcher 里 |
| 看得到的范围 | 单个节点 | 所有节点，可以按通道、按全系统聚合 |
| 规则 | 简单的“超过阈值”，同一个告警按 `LogRateLimiter` 限频 | 任意组合（持续 5 分钟、同比、几个指标一起），静默、升级、值班通知 |
| 历史和图表 | 只有日志 | 有，能看趋势 |
| 依赖 | 无，部署即生效 | 需要日志采集或 Prometheus、Grafana 等基础设施 |
| 适合 | 少数“必须马上知道”的：Stream 排队太久、DB 连接池等待、供应商响应变慢、消费者持续失败 | 趋势、容量、SLA、跨节点的问题 |

**已定：系统里只打日志**：系统里只做 4～5 个关键阈值，超过就打 `[METRICS-ALERT]`，不发邮件；外部监控接上后按关键字 `[METRICS-ALERT]`、`[ALERT]` 告警；完整的看板和告警规则放在外部，用 JSON 日志或 Redis 快照对接。现有的日志告警（如果线上已经按关键字告警）可以直接接 `[METRICS-ALERT]`。

系统里的初始阈值（不配就不检查）：

| 配置 | 含义 |
|---|---|
| `Metrics.Alert.StreamLagMs` | 任一流向的 Stream 排队 p95 超过这个毫秒数 |
| `Metrics.Alert.VendorRttMs` | 任一通道的 submit_sm_resp p95 超过这个毫秒数 |
| `Metrics.Alert.DbPoolWaiting` | DB 连接池等待线程数超过这个值 |
| `Metrics.Alert.ConsumerFailRatio` | 任一消费者本窗口失败数 / 处理数超过这个比例 |

## 8. 性能影响

### 8.1 估算（按单个节点 2000 TPS）

| 改动 | 开销 | 影响 |
|---|---|---|
| 新增延迟指标（3.3，每条消息约 5 次） | 有名字缓存和 `LongAdder` 时每次约 100～200 ns：每秒 1 万次 × 200 ns ≈ 每秒 2 ms CPU | 约占一个 CPU 核的 0.2%，可以忽略 |
| Redis、DB 操作计时 | 每次两次 `System.nanoTime()`，约 50 ns | 可以忽略 |
| 细区间、最大值 | 每次多一次比较、一次比较交换 | 可以忽略 |
| p95 / p99 估算、JSON 拼装、告警检查 | 只在汇报时（每 30 秒一次） | 可以忽略 |
| 按 bind 统计 | 每个 bind 一组计数，约 1 KB；2000 个 bind ≈ 2 MB 内存；输出只含有流量的 bind | 内存可接受；输出量是主要成本（见下） |
| `metrics.log` | 每个模块每 30 秒几行 JSON；开了按 ssid、按 bind 时一个窗口可能几百 KB | 每天几十到几百 MB，单独文件按天滚动，不影响业务日志 |
| Redis 快照 | 每个节点每 30 秒一次写入 | 可以忽略 |
| Stream 积压监控（按 8.2 改过后） | 每个节点每 60 秒：读几个 ZSET + 每个 Stream 3 条命令（pipeline） | 几千个 Stream 时每秒约几百条命令，Redis 可以忽略 |
| DB 连接池统计 | 读内存对象 | 可以忽略 |
| 降开销（3.6） | 名字缓存、`LongAdder`、异步日志 | **是减少**：现在每条消息每环节一行同步 INFO 日志，是现有监控相关开销里最大的一块，改异步日志后处理线程不再等写盘 |

**结论：整体对处理性能的影响在 1% 以内**，前提是同时做名字缓存和 `LongAdder`（第 4 步的优化最好和第 2 步一起做）。真正需要注意的是两点：Stream 积压监控的实现（8.2）和按 ssid / bind 打开后的日志量。

### 8.2 默认打开 Stream 积压监控前要改的

现在的实现（`StreamQueueManager.scanBacklogPattern`）：

- 每个周期每个模式用 SCAN 扫一遍 Redis 的所有 key。Redis 里除了 Stream，还有大量的按消息的 key（外发防重 `core:outbox:*` 等），key 越多扫得越久，虽然不阻塞，但每 30 秒要把整个库过一遍。
- 每个 Stream 4 条命令，其中 `XGROUP CREATE` 每次都发（已经存在时报错返回），没有必要。

改为：Stream 名从已有的活跃流 ZSET（doorbell）取；消费组只在第一次建；XLEN、XPENDING、ZSCORE 用 pipeline；周期 60 秒。改完再默认打开。

已按此实现（第 9 节）：门铃在消费者处理时会被取走，所以另外记住“上次见过、还有数据”的 stream，直到它变空；每 `RedisStreamMonitor.FullScanEveryCycles`（默认 10）个周期 SCAN 一次全库，找有数据但丢了门铃的 stream。消费组不在这里建，没有组的 stream 待确认数记 0。

### 8.3 验证

第 2 步做完后用 `MemSoakIT`（600 TPS，手工用例）分别在指标全关、全开（含按 ssid、按 bind）下跑，比较 CPU、吞吐、GC；预期差别在 1% 以内，超过就看是哪个指标导致的。

## 9. 实现记录（2026-11-11）

| 设计 | 实现 |
|---|---|
| 3.1 默认可见 | `Metrics.LogLevel=INFO`、`Metrics.PrintGauge=true`、`DB.PoolStats.Enable=true`、`RedisStreamMonitor.Enable=true`（60 秒）。`metrics.log` 的 log4j2 配置要运维在线上的 `conf/log4j2.xml` 里加（3.1 的片段）；不加时指标行进主日志 |
| 3.2 输出 | `MetricsReporter`：每个窗口 `[METRICS-TPS]`、`[METRICS-SSID]`、`[METRICS-GAUGE]`、`[METRICS-TIMER]` 各一行，`Metrics.Format=json`（默认）或 `kv`，超过约 4KB 分行（`"part":2`）。每行带 `module`、`node`、`ts`、`window`。Redis 快照 `metrics:{模块}:{NodeID}`（Hash：`tps`、`gauge`、`timer` 为 JSON，TTL 3 个窗口）+ 索引 `metrics:index`（ZSET）；`A2pCtl metrics` 每个模块一行（收、发、DR 每秒数，Stream 积压，排队 / 供应商响应 / 端到端 p95），`A2pCtl metrics 模块` 列出该模块的所有指标，`--json` 输出原始 JSON |
| 3.3 延迟 | `stream.lag.{流向}`（`StreamQueueManager.consumeBatch`，按条目 id 的时间）；`client.vendor.submit_rtt.{rssid}[.{bind}]`（`MultiSmppSession.handleSubmit_SM_Resp`，从 Redis 恢复的待响应项不算）；`core.vendor.dr_latency.{rssid}`（Core 匹配到最终 DR 时）；`e2e.submit`（Client 发出 submit_sm 时）；`e2e.dr`（Server 收到客户的 deliver_sm_resp 时；假 DR 从生成时算）；`redis.op.{xadd\|lua\|read}`；`db.op.{insert\|update\|delete\|select\|batch\|other}`（`DataManager`，含取连接）；`defer.wait.{消费者}.{原因}`（推迟的批次等了多久，原因 `window_full`、`throttled`、`bind_throttled`、`other`） |
| 3.3 补的时间 | 消息新增两段（`SerializableHandler` 第 60、61 段，毫秒，旧版本读到时忽略）：`inTimeMs` 进入网关的时间（MT 在 Server 写 `mt:pending` 时，供应商 DR 在 Client 写 `inbound-dr` 时；Core 把 MT 变成 DR 时换成 DR 的时间）；`outTimeMs` 供应商接收的时间（submit_sm_resp 成功时）。没有用 `TimeStamp`：它是 GMT 换算后的时间，不能直接和本机时钟比 |
| 3.4 耗时 | 区间 1/5/10/25/50/100/250/500/1000/5000 ms 和更长；每个窗口的最大值；输出 count、avg、p50、p95、p99、max（区间内线性插值，不超过最大值）。消费者耗时按消费者命名：`consumer.mt`、`consumer.mqm`、`consumer.result`、`consumer.inbound_dr`、`consumer.server_dr`、`consumer.http_submit`、`consumer.http_dr`、`consumer.client_out`（原来的 `consumer.process.{类型}.latency` 不再输出） |
| 3.5 瞬时值 | `MetricsCollector.registerGauge`（汇报时现取）：各消费者线程池 `consumer.{名}.pool.active/queued`、异步写库队列 `db.async_sql.queued`、SMPP 待响应 `smpp.pending.{submit\|dr}.pending/timeout_queue_size/timeout_worker_count`、假 DR 超时计时中的 MT 数 `fakedr.timeout.timing`（每个分片一次 ZCARD）、Stream 监控的 `redis.stream.{流向}.streams` |
| 3.6 开销 | 计数和耗时改用 `LongAdder`；`MetricsNames.build` 按四段缓存名字，`MetricsNames.metric(base, part)` 按段缓存（各最多 5 万个，超过就现拼）；异步日志属于线上 log4j2 配置，代码没改 |
| 3.7 / 7 告警 | `Metrics.Alert.*`（默认 0 不检查），超过打 WARN `[METRICS-ALERT] {...}`（JSON，主日志，logger `MetricsReporter`），同一告警 `Metrics.Alert.RepeatSeconds`（300）内只打一次，`windows` 是期间超过的次数。不发邮件，原有的告警邮件功能已去掉（原来发邮件的地方改为 `[ALERT]` / `[MGT-ALERT]` 日志） |
| 没做 | HTTP 通道的供应商响应延迟和 DR 延迟（只量了 SMPP）；HTTP 客户的 `e2e.dr`；延迟 DR ZSET 的大小 |
