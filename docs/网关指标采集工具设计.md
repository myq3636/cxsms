# 网关指标采集工具 gw-metrics-agent 设计

> 日期：2026-11-25，设计稿，代码未写。
> - 代码放在网关仓库的 `tools/gw-metrics-agent/`。
> - 它是 Portal《网关性能监控图（设计稿）》（Portal 仓库 `docs/designs/2026-11-25-gateway-metrics-chart-design.md`）的数据来源。那份文档定页面、接口、落库和汇总，本文定部署在每台网关机器上的采集工具。
> - 依赖的日志格式和 log4j2 配置见《性能监控指标说明》6.1、8.3 节。

## Intent Contract

- intent:
  - 在每台网关机器上常驻一个只读进程，跟读各模块的 metrics 日志 `{模块}_metrics.log`，以及主日志 `{模块}.log` 里的 `[METRICS-ALERT]` 行。
  - 把读到的窗口原样批量推送给 Portal，Portal 确认收到后才记下读取位置。
- constraints:
  - 不改网关代码，不连网关的 Redis 和数据库。
  - 对日志文件只读：不写、不截短、不改名、不删除、不加锁，不能影响网关模块写日志和 log4j 滚动（见 Decisions 9）。
  - 用 JDK 17，和网关机器上的 JDK 一致：openjdk 17.0.19，CentOS 7。
- success_criteria:
  - 日志里的每个窗口在 Portal 恰好出现一次。这包括运行中滚动、停机期间滚动、.gz、`kill -9`、Portal 停机、网络中断等情况。前提是日志还在保留期（7 天）内。
  - 正常运行时，从日志写出到 Portal 收到不超过 20 秒。
  - 在 4000 TPS、打开按 ssid 统计的情况下，资源占用：CPU < 单核的 2%，常驻内存 < 200 MB；实时跟读时磁盘读几乎为 0（读的都是页缓存）。
- risk_level: low
  - 最坏情况是 Portal 缺数据，网关不受影响。
  - 唯一需要专门处理的是“开着已删除文件的句柄占住磁盘空间”，见 Decisions 9。

## Scope

**本次包含**：
- 采集工具的进程结构。
- 文件跟读与滚动处理。
- 窗口拼接。
- 推送协议与读取位置的提交。
- 配置。
- 自身监控。
- 运维命令。
- 部署。
- 对网关的影响分析。
- 测试。

**不在本文**：Portal 接收后怎么处理（去重、按 ssid 把每秒次数换算成条数、累加、汇总），见主文档 Decisions 4–5。

**与主文档的分工**：
- 采集工具**只读、拼接、转发，不做任何计算**，也不按指标名过滤。
- 好处是：网关改指标名、Portal 改换算口径或增加曲线，都不用升级采集工具，计算规则只在 Portal 有一份。
- 代价是多传一些 Portal 用不到的指标。不过滤时一个模块一个窗口约 5–20 KB，gzip 后约为原来的 1/5，10 台模块每 10 秒一批，几十 KB。

## Decisions

### 1. 形态与工程

- **位置**：网关仓库 `tools/gw-metrics-agent/`，`.gitignore` 已放行 `tools/`，`tools/*/build/` 不提交。
  - 不放进 `src/`：放进去会被编进网关的 a2p.jar。
  - 采集工具单独部署、单独升级，不随网关发布。
- **语言**：JDK 17（`javac --release 17`），与网关和网关机器上的 JDK 相同（openjdk 17.0.19）。
  - 网关机器只有 Python 2.7，没有 python3。
  - 用 shell 的 `tail -F` 做不到“按记录的位置续读”和读 .gz。
  - Java NIO 能可靠地按 inode 认文件：`Files.getAttribute(p, "unix:ino")`。
- **构建**：沿用网关和 `routetest` 的做法，不用 Maven。`tools/gw-metrics-agent/build.sh` 做三件事：
  1. `javac --release 17 -encoding UTF-8 -cp ../../jar/fastjson-1.2.47.jar -d build/classes $(find src -name '*.java')`；
  2. 把 `fastjson-1.2.47.jar` 解开放进 `build/classes`；
  3. `jar cfe build/gw-metrics-agent.jar com.king.tools.metricsagent.AgentMain -C build/classes .`。
  - 产物是一个可执行 jar，约 1 MB，部署时不依赖网关的 `WEB-INF/lib`。
- **依赖**：
  - JDK 自带的：`java.net.http.HttpClient` 用于 HTTPS，`javax.crypto.Mac` 用于 HMAC，`java.util.zip` 用于 gzip。
  - JSON 用网关仓库 `jar/` 里网关本身就在用的 fastjson 1.2.47，和网关的 `MetricsView` 一样。只用 `JSON.parseObject` 解析本机日志里的对象，不开 autoType，也不反序列化成 Java 类。
- **代码结构**（包 `com.king.tools.metricsagent`）：

| 类 | 职责 |
| --- | --- |
| `AgentMain` | 读配置、取单实例锁、启动各线程、处理命令行（Decisions 8） |
| `AgentConfig` | `agent.properties`，启动时校验 |
| `FileScanner` | 每秒扫描文件、发现滚动（Decisions 3） |
| `Tailer` | 一个文件一个：读完整的行，每行带上它的开始和结束位置 |
| `RolledFileFinder` | 停机后在 `rolled.dir` 里找回滚动出去的文件，按顺序排列 |
| `LineParser` | 识别标签，取出 JSON（Decisions 4） |
| `WindowAssembler` | 按 `(module, node, ts)` 拼窗口（Decisions 4） |
| `Outbox` | 有上限的发送队列，满了让 Tailer 暂停读 |
| `Sender` | 批量 gzip、HMAC、POST，退避重试（Decisions 5） |
| `PositionStore` | 安全位置的计算和原子写入（Decisions 6） |
| `Heartbeat` | 自身状态，随每批数据发送（Decisions 7） |

### 2. 线程

```
FileScanner（1 个，每 1 s）
   │ 新文件 → 建 Tailer；路径的 inode 变了 → 通知 Tailer 读完旧文件再切换
   ▼
Tailer × N（共用一个固定大小 4 的读线程池，每个文件每次最多读 1 MB 就让出）
   │ 完整的行 + 行的位置
   ▼
LineParser → WindowAssembler（1 个线程，单线程处理，不加锁）
   │ 完整的窗口 / 告警事件
   ▼
Outbox（有上限）──► Sender（1 个，每 10 s，或者攒满 batch.max.windows 就立即发）
                       │ 收到 200
                       ▼
                  PositionStore：推进安全位置，原子写入 positions.json
```

### 3. 文件跟读与滚动

**跟踪哪些文件**：
- `log.dir` 下匹配 `metrics.glob`（默认 `*_metrics.log`）的文件。
- 匹配 `alert.glob`（默认 `*.log`）、但不匹配 `alert.exclude`（默认 `*_metrics.log,*_gc.log*,*_smpp_pdu.log,*.out`）的主日志。
- 滚动出去的文件在 `rolled.dir`（默认 `log/previous`），文件名是 `{原文件名}.{yyyy-MM-dd}-{i}.gz`。这个规则用网关 log4j2 的 `filePattern` 推出来，可以配置。

**每个文件记录**：`inode`、文件开头 256 字节的 CRC32（`head`）、读取位置 `offset`、已读到的最后一个窗口的 ts（`lastTs`）。只用 inode 不够：文件删掉后，新文件可能拿到同一个 inode。

**原则**：Portal 按窗口 `(module, node, ts)` 去重，所以重读是安全的；读取位置只是为了少读，判断错了最多重读一遍。唯一会丢数据的情况，是日志在被读到之前就被删了。

| 情况 | 处理 |
| --- | --- |
| 正常追加 | 句柄一直开着，读到文件末尾后等下一次扫描。只交出以 `\n` 结尾的行，半行留到下次再读 |
| 运行中滚动（log4j 把文件改名挪到 `rolled.dir`，再压缩成 .gz 并删除改名后的文件） | FileScanner 发现路径对应的 inode 变了，就让旧 Tailer 读到 EOF；隔 1 秒再读一次，确认没有新内容后关闭句柄，再从头读新文件。log4j 滚动之前已经把缓冲刷出，句柄被关之后不会再有写入。**旧句柄最多保留 `rolled.maxHoldSec`（默认 60 秒）**，超时还没读完就关掉，剩下的部分改为到 `rolled.dir` 里按文件名读 .gz（Decisions 9） |
| 停机期间滚动了一次或多次 | 启动时路径的 inode 或 `head` 和记录的不一致：用 RolledFileFinder 在 `rolled.dir` 里找同一个原文件名、日期不早于 `lastTs` 那一天的文件，按日期和 `-i` 排序。逐个检查，`head` 一致的那个从 `offset` 读，后面的从头读，最后读当前文件 |
| 滚动出去的是 .gz | 用 `GZIPInputStream` 边解压边读，跳过 `offset` 字节。解压后的内容和压缩前一样，所以位置仍然有效 |
| 找不到记录的那个文件（已超过保留期被删除） | 从找得到的最早那个开始读，并把 `lastTs` 到这个文件第一个窗口之间的时间段作为缺口，报给 Portal（Decisions 7） |
| 文件被截短（同一个 inode，大小 < offset） | 从头读，打 WARN。log4j 不会这样做；禁止手动清空文件，也禁止对这些文件用 logrotate 的 `copytruncate` |
| 模块重启 | log4j 以追加方式打开同一个文件，照常续读；启动时如果触发了滚动，按“运行中滚动”处理 |
| 新模块（新文件） | metrics 文件从开头读，主日志从末尾读（`start.alert=end`，不扫历史告警） |
| 第一次启动（没有 positions.json） | metrics 文件从开头读，把当天的数据补上。还可以用 `--replay` 补更早的 |

### 4. 解析与窗口拼接

**行格式**：网关 log4j2 的 pattern 是 `%d{yyMMdd HH:mm:ss,SSS} %m %n`，所以一行是 `日期 时间 [METRICS-xxx] {json} `（末尾有一个空格）。

- 只按 `[METRICS-` 定位标签，然后取 `] ` 后面、去掉首尾空白的部分作为 JSON。
- 不解析日志时间，一律用 JSON 里的 `ts`。这样改日志 pattern 不影响采集，网关和 Portal 的时钟不一致也不影响。

**metrics 文件的四类标签**：

| 标签 | JSON 里的字段 | 转发为 |
| --- | --- | --- |
| `[METRICS-TPS]` | `tps` | `tps` |
| `[METRICS-SSID]` | `tps` | `ssid` |
| `[METRICS-GAUGE]` | `gauge` | `gauge` |
| `[METRICS-TIMER]` | `timer` | `timer` |

- kv 格式的行（标签后面不是 `{`）：跳过，计入 `skippedKvLines`，每 10 分钟打一条 WARN。
- 解析失败的行：跳过，计入 `badLines`，并保留最近 5 行样本，供 `--check` 查看。

**主日志**：
- 每行先用 `indexOf("[METRICS-ALERT]")` 判断，不含就丢弃，不做别的解析，所以几百 MB 的主日志也很便宜。
- 含有的行，取后面的 JSON 作为告警事件。

**窗口拼接**：
- 网关一个窗口的几行是在同一次汇报里连续写出的，同一个模块的不同窗口之间相隔 30 秒。
- 按 `(module, node, ts)` 汇总，同一个标签有多个 `part` 时把对象合并。
- 一个窗口在满足以下任一条件时完成，交给 Outbox：
  - 同一个文件出现了更新的 ts；
  - 已经 5 秒没有这个窗口的新行；
  - 文件切换（滚动）时，拼接缓冲跨文件保留，切换完成后再按前两个条件判断。
- 模块前缀 `{m}.` 在这里去掉，减少传输量；这只是字符串处理，不涉及计算。

### 5. 推送协议

- **请求**：`POST {portal.url}`（主文档的 `/api/v1/gw/metrics/ingest`），请求体是 gzip 后的 JSON。
  - 请求头：`Content-Encoding: gzip`。
  - `X-Agent-Host`：机器名。
  - `X-Batch-Id`：从 1 开始递增的序号，持久化在 state 里，方便两边对照日志排查。
  - `X-Signature`：`HMAC-SHA256(secret, gzip 后的请求体)`，十六进制。
- **请求体**：

```json
{"host":"a2p-gw-1","agentVersion":"1.0.0","batchId":1832,"sentAt":1795600000000,
 "windows":[{"module":"coreengine1","node":"0","ts":1795599990123,"window":30,
             "tps":{"business.core.submit.routing_success":3998.50},
             "ssid":{"ssid.9995.insubmit.received_from_stream":2999.10},
             "gauge":{"redis.stream.server_to_core.xlen":120},
             "timer":{"stream.lag.server_to_core":{"count":119955,"avg":3.10,"p50":2.00,"p95":8.40,"p99":15.20,"max":96.00}}}],
 "alerts":[{"module":"multismppclient1","ts":1795599991000,"alert":"vendor_rtt","metric":"multismppclient1.client.vendor.submit_rtt.81","value":3250.80,"threshold":3000.00,"count":3,"windows":1}],
 "heartbeat":{...见 Decisions 7...}}
```

- **一批多大**：最多 `batch.max.windows`（默认 500）个窗口，或者 gzip 前不超过 `batch.max.mb`（默认 8 MB）。补读时会连续发多批。
- **应答**：

| 应答 | 采集工具怎么做 |
| --- | --- |
| `200 {"accepted":n,"duplicated":m}` | 成功，推进安全位置 |
| `401` | 签名错误。停止发送，每分钟打一条 ERROR，等运维修正密钥后重启 |
| `413` | 请求体太大。把这一批拆成两半重发 |
| `5xx`、`503`、超时、连接失败 | 按 10、20、40…秒退避重试，最长 300 秒；期间不推进位置，也不再继续读 |

- **HTTPS**：
  - 用 JDK 自带的信任库。
  - 如果 Portal 用的是自签证书，可以配 `http.trustStore`。
  - 不提供“跳过证书校验”的开关。

### 6. 读取位置的提交（不丢不重的关键）

**安全位置**：每个文件记一个“安全位置”，等于还没被 Portal 确认的窗口里，最早一行的开始位置。
- WindowAssembler 记下每个窗口包含的行来自哪个文件、在什么位置。
- Sender 收到 200 后，把这一批的窗口标为已确认，PositionStore 据此把各文件的安全位置往前推。
- 不含窗口的行（空行、跳过的 kv 行），在它后面的窗口被确认时一起推过去。

**写入 `state/positions.json`**：
- 每次推进后，最多每秒写一次。
- 写法是先写 `positions.json.tmp`，fsync，再 rename，所以任何时刻断电都只会留下旧的或新的完整文件。

```json
{"version":1,"batchId":1832,"files":{
  "CoreEngine1_metrics.log":{"inode":2883912,"head":"9f1c33a0","offset":18234881,"lastTs":1795599990123},
  "CoreEngine1.log":{"inode":2883907,"head":"04be77d2","offset":402113920,"lastTs":1795599991000}}}
```

**语义**：
- 至少一次。进程在任何时刻被 `kill -9`，重启后都从安全位置重读，重读的窗口由 Portal 去重。
- 告警事件也一样，Portal 按 `(module, ts, metric)` 去重。

**背压**：
- Outbox 达到上限（`outbox.max.windows` 默认 20000，或者 `outbox.max.mb` 默认 50）时，Tailer 暂停读，安全位置停在原地。
- 日志文件本身就是缓冲，只要在 7 天的保留期内恢复都能补齐。

### 7. 自身监控

- **心跳**：随每批数据发送；空闲时每 30 秒单独发一次。内容如下：

```json
{"startedAt":1795590000000,"uptimeSec":3600,
 "files":[{"name":"CoreEngine1_metrics.log","lagBytes":0,"lastTs":1795599990123,"heldDeleted":false}],
 "outboxWindows":3,"retrying":false,"lastError":"",
 "skippedKvLines":0,"badLines":0,
 "gaps":[{"module":"coreengine2","from":1795000000000,"to":1795100000000,"reason":"rolled file gone"}],
 "unreadOldestTs":1795599990123}
```

- Portal 据此显示“采集中断 / 滞后 / 有缺口”：
  - 60 秒没收到心跳，显示“采集中断”。
  - `unreadOldestTs` 早于现在 5 天（`lag.warn.days`），显示“即将超过日志保留期”。
- **自身日志** `log/agent.log`：按 10 MB 滚动，保留 5 个。只记启动和停止、文件切换、补读、发送失败、跳过行，后两类限频。
- **单实例**：`state/agent.lock` 加 `FileChannel.tryLock`，第二个实例启动时直接退出并报错。

### 8. 命令行

```
java -jar gw-metrics-agent.jar [--config agent.properties] <命令>
```

| 命令 | 用途 |
| --- | --- |
| （无） | 常驻运行，由 systemd 调用 |
| `--check` | 校验配置；列出找到的文件、inode、读取位置、滞后字节数；在 `rolled.dir` 里能找到哪些滚动文件；试连 Portal（发一个空心跳）；显示最近的 badLines 样本 |
| `--dry-run [--limit N]` | 从当前位置解析，把将要发送的窗口打印成 JSON，不发送、不改位置。上线前对照网关日志核对 |
| `--replay <文件或通配> [--from 时间] [--to 时间]` | 把指定的旧文件（含 .gz）在指定的时间段内重新发一遍，用来补数据，Portal 会去重。不改常驻进程的位置，可以和常驻进程同时运行 |
| `--reset <文件> --to begin\|end` | 重置某个文件的读取位置。先停常驻进程，命令会检查锁 |

### 9. 对网关的影响

结论：**采集工具不会影响网关模块写日志和 log4j 滚动**。唯一需要专门处理的是“开着已删除文件的句柄会占住磁盘空间”，用最长保留 60 秒的规则解决。逐项说明如下：

| 方面 | 分析 | 措施 |
| --- | --- | --- |
| 文件锁和写入冲突 | Linux 上读文件不加锁，也不阻塞别的进程追加写入。log4j 的 `RollingFile` 不用文件锁，各写各的 | 只用 `StandardOpenOption.READ` 打开，从不写入或截短，也从不调用 `lock` |
| 滚动（改名、压缩、删除） | Linux 允许对已被别的进程打开的文件改名和删除，log4j 的滚动不会因此失败。这和 Windows 不同，Windows 上开着的文件不能改名 | 不需要 |
| **已删除文件占着磁盘空间** | log4j 把文件改名、压缩成 .gz 后，会删除改名后的那个文件。如果采集工具还开着它的句柄，这部分空间要等句柄关闭才释放，最多 1 GB（大小滚动的阈值）。2026-11-25 测试机的日志盘就因为 CDR 写满触发了保护，这里不能再占空间 | 旧句柄读完就关；最多保留 `rolled.maxHoldSec`（默认 60 秒），超时就关掉，剩下的改为读 .gz。心跳里报 `heldDeleted`，`--check` 也显示 |
| 磁盘读 I/O | 实时跟读的是刚写出的内容，都在页缓存里，几乎不产生磁盘读 | 不需要 |
| 补读 I/O | 停机后补读旧的 .gz 时会真正读盘，与网关写日志、写 CDR 抢磁盘 | 补读限速 `read.backfill.mbps`（默认 20 MB/s，按解压前的字节计）；systemd 里设 `IOSchedulingClass=idle`。CentOS 7 的 virtio 盘默认是 deadline 调度器，idle 不一定生效，所以主要靠限速 |
| 页缓存 | 实时跟读不增加页缓存（内容本来就在缓存里）。补读旧文件会把它们读进缓存，可能挤掉别的缓存 | 有补读限速；7 天的量最多几十 GB，按 20 MB/s 读完约半小时。不必为此做 `fadvise` |
| CPU | 解析 metrics 日志每秒只有几十 KB；扫主日志在 4000 TPS 时约每秒 100 KB，只做 `indexOf` 判断。估算在单核的 1% 以内 | systemd：`Nice=10`、`CPUQuota=20%`。CentOS 7 的 systemd 219 支持这两项 |
| 内存 | Outbox 有上限，堆 `-Xmx128m`，加上 JVM 本身，常驻约 150–200 MB | systemd：`MemoryLimit=300M`（219 版本用 `MemoryLimit`，不是 `MemoryMax`） |
| 文件句柄 | 每个模块 2 个（metrics 和主日志），10 个模块约 20 个 | 不需要 |
| 网络 | 每 10 秒一批，gzip 后几十 KB；补读时连续发 | 补读也受 `read.backfill.mbps` 限制 |

网关这边真正的成本是打开 `Metrics.Ssid.Enable` 后自己多写的日志（主文档 Risks），和采集工具无关。

### 10. 部署

```
/usr/local/a2p/metrics-agent/
  gw-metrics-agent.jar
  agent.properties
  agent.secret          # 600，root
  state/positions.json  state/agent.lock
  log/agent.log
```

**`/etc/systemd/system/gw-metrics-agent.service`**：

```ini
[Unit]
Description=Gateway metrics agent (reads metrics logs, posts to Portal)
After=network-online.target

[Service]
ExecStart=/usr/bin/java -Xms64m -Xmx128m -XX:+UseSerialGC -jar /usr/local/a2p/metrics-agent/gw-metrics-agent.jar --config /usr/local/a2p/metrics-agent/agent.properties
WorkingDirectory=/usr/local/a2p/metrics-agent
Restart=always
RestartSec=10
Nice=10
CPUQuota=20%
MemoryLimit=300M
IOSchedulingClass=idle

[Install]
WantedBy=multi-user.target
```

- 用 `-XX:+UseSerialGC`：堆很小，单线程 GC 最省资源，也不会和网关模块抢 GC 线程。
- 以 root 运行，因为日志文件属于 root，权限是 644，只读其实不需要 root。如果运维要求，可以新建一个用户，把它加进能读 `log/` 的组。
- 升级：替换 jar 后 `systemctl restart`，从 state 里的位置继续读。

## 测试

1. **单元套件**，进全量回归（`regression/run.sh`，`unit` 模式）。和网关现有的 `ShardHashCheck` 等检查类一样，`main` 里逐项 `PASS` / `FAIL`，不用 JUnit。都在临时目录里模拟 log4j 的行为：
   - `TailerCheck`：追加、半行、截短、inode 复用（删除后新建文件，用测试钩子模拟同一个 inode）。
   - `RolloverCheck`：运行中 rename 加 gzip 加删除；停机期间多次滚动；.gz 跳过 offset；滚动文件已被删除时报缺口；`rolled.maxHoldSec` 超时后改读 .gz。
   - `AssemblerCheck`：多个 `part` 合并；窗口跨了新旧文件；空闲超时；多个模块交错写。
   - `PositionStoreCheck`：只有确认后才推进；在任意一步 `kill`（用异常模拟）后重读，窗口集合不变。
   - `SenderCheck`：用内置的 `HttpServer` 模拟 200、401、413、500、超时。
   - `AgentEndToEndCheck`：写一个“log4j 模拟器”生成 10 万个窗口，期间随机滚动、压缩、重启采集工具；用模拟的 Portal 按窗口去重后，收到的集合应与写出的集合完全相同。
2. **测试机联调**（主文档 Verification）：
   - 用 `PF007_4000tps_1h` 跑完 `kill -9`、停 Portal、逼出多次滚动这几种场景，核对条数。
   - 用 `lsof +L1` 确认被删除文件的句柄最多保留 60 秒。
   - 对比采集工具开着和关着时网关模块的 CPU，以及 `e2e.submit` 的 p99。

## Risks & Open Questions

- **滚动文件名规则依赖 log4j2 配置**：`rolled.dir` 和 `rolled.pattern` 要与网关的 `filePattern` 一致。网关改了配置而采集工具没改时，停机期间滚动出去的文件会找不到，表现为心跳里报缺口，不会读错数据。`--check` 会列出按规则找到的文件，方便核对。
- **补读会读盘**：长时间停机后补读几十 GB 的 .gz 会有真实的磁盘读。已经用限速控制，生产上可以按磁盘能力调整 `read.backfill.mbps`。
- **以 root 运行**：采集工具只读，但仍然是 root 进程。如果运维有要求，就新建一个只读用户，并让它能读 `/usr/local/a2p/log` 和 `log/previous`。
- **主日志很大时**：trace 级别的主日志可能每小时几 GB，例如测试机的 `com.king` 是 trace。只为告警而扫这些日志，CPU 仍然很小，但会多读页缓存。如果嫌这部分开销不值，可以设 `alert.glob=` 为空，不采集告警，页面就不显示告警事件。
- **网关日志格式**：依赖 `[METRICS-*] {json}` 这个形式。采集工具和 `MetricsReporter` 在同一个仓库里，改动输出格式时一起改。《性能监控指标说明》6.1 节是双方的约定，`AssemblerCheck` 用 `MetricsReporter` 实际输出的行做样本。
