# 消息经过模块路径（modulePath）设计与测试

> 日期：2026-11-10。状态：已实现。用例 `regression/test/it/PathChainIT.java`（`suites.txt`）。

## 1. 目标

一条 MT 或 DR 经过了哪个 Server、哪个 Core、哪个 Client，只看一个模块的一行日志或一条 CDR 就能知道，不用去每台机器上按 msgId 查。

## 2. 为什么不用原来的 `deliveryChannel`

CDR 里原来有一列 `DeliveryChannel`（`GmmsMessage.deliveryChannel`）。旧架构里 Server 交给 Core 时写成 `Server模块:Core队列`，但是：

- **Stream 架构下 MT 不再写这个字段**：Server 直接 `produceSubmitMessage`，写 Stream 时也不带这个字段（`SerializableHandler` 里那一行被注释掉了）。所以 MT 的 CDR 里这一列是 `NULL`。
- **DR 路由在读它**：`StreamQueueManager.buildServerPendingQueue`、`SmppServerDrRouteResolver` 把最后一个 `:` 后面的部分当作 DR 要回的 Server 模块；`processStoredDeliveryReport` 看它是不是 `CommonHttpServer` 开头。往里面写路径会让 DR 走错。

所以新加一个只做追踪的字段 `modulePath`，路由逻辑都不读它；CDR 的 `DeliveryChannel` 这一列改为写这个路径（CDR 里模块之间用 `:` 分隔，和这一列原来的格式一致）。

**消息上的 `deliveryChannel` 不变**：只在写 CDR 时复制出来的 CDR 对象上替换，这个对象只拼成 CDR 文本行，不写回消息，不进 Stream、DB、SDQ。所有按 `:` 解析 `deliveryChannel` 的代码（DR 选 Server 模块、`CommonHttpServer` 判断、DB 存储等）读的都是消息本身，不受影响。

## 3. 方案

**格式：** 模块名用 `>` 连起来，例如 `MultiSmppServer1>CoreEngine1>MultiSmppClient1`。同一个模块连续两次只记一次。超过 255 个字符时保留后面的部分，前面用 `..` 表示（消息反复重试时才会出现）。工具类 `com.king.gmms.util.ModulePath`。

**什么时候加上本模块：**

| 时机 | 说明 |
|---|---|
| 写进 Redis（Stream、DR 查找用的 MT 等，`SerializableHandler.convertGmmsMessage2RedisMessage`） | 序列化时写 `路径>本模块`，所以哪个模块写的 Redis 就有哪个模块 |
| 打日志、写 CDR | 显示 `路径>本模块`，内存里的消息不改 |

**DR 用自己的路径：** Core 收到供应商 DR、找到原来的 MT 后（`InternalCoreEngineSession.mergeInboundDeliveryReport`），DR 的路径换成供应商 DR 自己的路径（从收到它的 Client 开始）。MT 的路径在同一个 msgId 的 MT CDR 里。

**Stream 格式：** 第 57 段（原来最后一段是第 56 段 `rowId`）。

- 新版读旧数据：没有这一段，路径为空。
- 旧版读新数据：多出来的一段不处理，消息照常处理；但旧版会对每条消息打一行 INFO `Unknown parameter in Redis String`（带整条消息）。**升级时各模块尽量一起升**，混跑期间这行日志会变多。
- 写进 DB 或 SDQ 的消息不带路径：DB 兜底、DR 先存起来以后再匹配的情况，路径从那以后重新开始记。

## 4. 日志和 CDR

| 位置 | 内容（实测） |
|---|---|
| Core `[MT-TO-CLIENT]` | `path=MultiSmppServer1>CoreEngine1` |
| Client `[MT-OUT]` | `path=MultiSmppServer1>CoreEngine1>MultiSmppClient1` |
| Core `[DR-TO-SERVER]` / `[DR-TO-HTTP]` | `path=MultiSmppClient1>CoreEngine1` |
| Server `[DR-OUT]` | `path=MultiSmppClient1>CoreEngine1>MultiSmppServer1` |

CDR 的 `DeliveryChannel` 列（第 27 列，`outClientPull` 后面），模块之间用 `:`，最后一段是写这条 CDR 的 Core：

| CDR | 实测 |
|---|---|
| `IN_SUBMIT` | `MultiSmppServer1:CoreEngine1` |
| `OUT_SUBMIT`（结果回到 Core 时写） | `MultiSmppServer1:CoreEngine1:MultiSmppClient1:CoreEngine1` |
| `OUT_DELI_REP`（供应商 DR） | `MultiSmppClient1:CoreEngine1` |
| `IN_DELI_REP`（客户回 deliver_sm_resp 后写） | `MultiSmppClient1:CoreEngine1:MultiSmppServer1:CoreEngine1` |

- 消息没有路径时（升级前就在路上的消息），这一列和原来一样。
- **对下游的影响**：这一列原来在 Stream 架构下 MT 是 `NULL`，DR 是 Core 的模块名或 `Core:Server` 之类；现在是 `:` 分隔的路径，段数不固定。按“最后一段是模块”取值的下游不会报错，但含义变了（最后一段是写 CDR 的 Core）。
- 一条消息被另一个节点接管时（例如分片迁移、超时未确认被其他 Core 认领），路径里会出现两个 Core，例如日志里 `MultiSmppServer1>CoreEngine1>CoreEngine2>MultiSmppClient1`。

HTTP 外发（`HttpSession`）和 HTTP Server 收消息没有加日志，路径照常记在 CDR 里。

## 5. 测试

`PathChainIT`：Server、Core、Client 各起一个进程（共用 Redis），测试进程扮演客户（SMPP bind 到 Server、发 submit_sm、收 deliver_sm）和供应商（FakeSmsc）。14 项全部通过：

- PC-00a/b：Stream 格式写入后读回有路径；去掉第 57 段（旧数据）也能读，路径为空。
- PC-01～04：客户和供应商都 bind 上，MT 到了供应商。
- PC-05～06：Client `[MT-OUT]`、Core `[MT-TO-CLIENT]` 的路径。
- PC-07～09：DR 回到客户；Core `[DR-TO-SERVER]`、Server `[DR-OUT]` 的路径。
- PC-10～12：Core CDR 的 `IN_SUBMIT`、`OUT_SUBMIT`、`OUT_DELI_REP`。
