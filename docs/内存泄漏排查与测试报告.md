# 内存泄漏排查与测试报告

> 日期：2026-11-06。第 1、2 节是读当前 `main` 代码的结果；第 3 节是本机实测；第 4 节是已做的修复。

## 1. 结论

- **主消息链路没有会无限增长的泄漏。** 本机用真实 SMPP Client 进程浸泡测试，停发超过 `BufferTimeout` 后存活对象全部释放，两轮之间存活堆不增长。
- **有一处“延迟释放”，已修复：** SMPP 外发、Server 发 DR 收到 resp 后，消息仍被超时任务引用到 `BufferTimeout`（默认 60 秒）。滞留量约等于 TPS × BufferTimeout，每条约 1.5 KB；单个 Client 4000 TPS 时约 360 MB，并且这些对象会进老年代。
- **低频或默认不启用的路径上有几处真泄漏**（2.2～2.5），还没有修。

## 2. 排查结果

按六类模式逐类检查：静态或单例里只增不删的集合、没有上限的队列和缓存、每次调用都新建的线程和线程池、没关闭或没归还的连接和流、ThreadLocal、重复注册的监听器。

### 2.1 SMPP pending 的超时任务留住消息（已修复，第 4 节）

`SmppPendingSubmitManager` 每发一条 submit_sm，往全局 `DelayQueue` 放一个 `PendingSubmitTimeoutTask`，任务直接引用 entry，entry 里有整条 `GmmsMessage`。收到 resp 后 `remove()` 只把 entry 从 `pendingMap` 删掉，任务还在队列里，要到超时时间点才出队。任务出队时只拿 entry 做同一性比较（`pendingMap.get(sequence) != entry`），并不需要消息。`SmppPendingDrManager`（Server 给客户发 DR、等 resp）结构相同。

可以用已有指标 `smpp.pending.submit.timeout_queue_size` 观察：它就是同时在队列里的任务数。

### 2.2 数据库连接坏掉后线程上的连接列表只增不删（未修）

`DataManager.currentConnection()`（`src/com/king/db/DataManager.java`）：

- 线程上挂着的连接已关闭时，新开一条加进 `allConnectionsForThread`，**旧的不从列表删除**。数据库每断一次，每个用过它的线程多留一个已关闭的连接对象。
- `isClosed()` 抛 `SQLException` 时，旧连接**既不还给 HikariCP，也不从列表删除**，成为池里借不回来的一条。

只在数据库故障时发生。

### 2.3 YunPian 通道的 HTTP 请求（未修）

`HttpSession.post`：每次 `new HttpClient()`，不调 `releaseConnection()`，没有连接、读取超时。socket 要等 GC 才关闭；对端不响应时工作线程一直卡住。只影响 `YunPian` 协议的通道。

### 2.4 RedisMonitor 的 Jedis 连接（未修，默认不运行）

`RedisMonitor` 心跳的 `returnResource` 不在 finally 里，异常时不归还；`switchRedis` 借出的 `sjedis` 在任何分支都不归还。只在 `SystemManager.enable=true` 时运行，默认关闭。

### 2.5 旧代码路径（未修，现在基本不走）

- `ExpiredMessageQueue` 的 `backupMessageQueue` 没有上限：处理器（写库）慢或数据库挂了时一直增长。用在 `DeliveryRouterHandler`、`SenderRentHandler`、PMQ、MQM。
- `InternalCoreEngineSession`、`InternalMQMSession` 每次建 `BufferMonitorWithSafeExit` 都会注册一个停机监听器，从不移除；前者每次重连建一个。这两种内部 TCP 会话的监听器在现在的启动流程里没有启动。

### 2.6 检查过、没有问题的

| 位置 | 结论 |
|---|---|
| 各 stream 消费者（MT、结果、入向 DR、Client 外发、Server DR、HTTP、hold） | `stop()` 关掉了 `start()` 建的所有线程池 |
| SMPP Server 会话 | 结束时一定 `stop()`：BufferMonitor 注销，会话从连接的会话表和 URI 表删除 |
| SMPP Client 会话 | 删除时 `destroy()`，GuavaCache 线程池关闭；重连复用同一个会话对象 |
| `drAwaitingResp` | 跟着会话对象回收；超时路径也会删除 |
| 按 ssid、stream 名作 key 的 Map | 上限是客户数 × 分片数 |
| `LogRateLimiter` | 超过 1 万个 key 整体清空 |
| `DuplicateMessageCheck` | Guava Cache，有上限、有过期 |
| Server 入向、长连接客户共享队列 | 有全局和单客户上限 |
| 客户配置热加载 | 整体替换快照，不保留旧版本 |
| XSD 解析表、`MetricsNames` 缓存 | 只在初始化填充 / 固定小集合 |
| DAO | 都在 finally 里 `closeSession` |
| `DBLockConnection` | 故意长期占一条连接做数据库锁 |

**没查：** Redis 侧的 key 增长、NIO 直接内存、动态加载的协议处理类。

## 3. 本机实测（`MemSoakIT`）

### 3.1 方法

- 一个真实的 SMPP Client 进程（`ClientNode`，`-Xmx512m`），接假供应商 `FakeSmsc`（立即回 submit_sm_resp），`BufferTimeout` 60 秒，1 条连接，窗口 500。
- 预热 2 万条；之后两轮“按固定 TPS 加压 120 秒 → 停发 75 秒”。
- 每 15 秒对 Client 做 `jmap -histo:live`（先 Full GC，只统计存活对象），记录 `GmmsMessage`、超时任务、`PendingSubmitEntry` 的数量和存活堆。
- 最后核对供应商收到的总数和去重数。
- 运行：`SUITE_TIMEOUT=900 SUITE_JAVA_OPTS="-Dsoak.rate=600 -Dsoak.threads=3" regression/run.sh MemSoakIT`。不在全量回归里（`regression/manual-suites.txt`）。每次运行前先停掉 Redis，否则上一次留下的积压会让清库超时。

### 3.2 结果（600 TPS，同样条件跑修复前、修复后各一次）

| | 修复前 | 修复后 |
|---|---|---|
| 加压期间存活的 `GmmsMessage` | 16,000～23,000 | 200 |
| 存活的 `PendingSubmitEntry` | 16,000～23,000 | 2～5 |
| 存活堆 | 31～47 MB | 11～13 MB |
| 停发 75 秒后存活的消息 | 25,877 / 27,467 | 0 / 0 |
| 两轮加压结束时供应商累计收到 | 56,817 / 128,166 | 59,443 / 129,918 |
| 送达 | 164,000 条，每条一次 | 164,000 条，每条一次 |

修复前在 350 TPS 下还单独跑过一次（Client 完全跟得上）：存活消息稳定在约 21,000 条（= 350 × 60），停发后按 60 秒线性降到 0，存活堆从 38 MB 回到 7 MB。由此估算每条滞留消息约 1.5 KB。

### 3.3 注意

- **吞吐：** 这台机器（8 核、6.4 GB）上发送端、Redis、Client 在一起，Client 的上限约每秒 400～450 条，修复前后一样。这个数字不代表线上能力，没有进一步测 Client 的吞吐上限。
- **高 TPS 没有实测：** 4000、10000 TPS 下的堆占用是按每条 1.5 KB 线性推算的。建议预发演练时用 `jmap -histo:live <pid>` 每 10 分钟采样一次，同时看 `timeout_queue_size`，JVM 加 `-XX:+HeapDumpOnOutOfMemoryError`。
- **只测了 Client：** Server 发 DR 的 `SmppPendingDrManager` 改法相同，没有单独做浸泡测试。

## 4. 修复

`SmppPendingSubmitManager.PendingSubmitTimeoutTask`、`SmppPendingDrManager.PendingDrTimeoutTask` 改为用 `WeakReference` 持有 entry：

- 还在 `pendingMap` 里的 entry 有强引用，不会被回收，超时照常触发；
- 已经删掉的 entry 可以被回收，任务到期时 `getEntry()` 返回 null，直接跳过（`processTimeoutTask` 先判断 null，再做原来的同一性比较）。

每个任务仍在队列里待到超时，但只剩任务本身和一个弱引用对象（几十字节）。
