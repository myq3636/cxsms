# MT 路由重构设计

> 日期：2026-11-11。状态：**设计稿，没有改代码**。2026-11-11 修订：优先级只在同一个号码前缀（国家）里比较，先按最长前缀定国家；二次路由、号码路由、运营商路由单独成层，排在普通路由前面；规则命中后通道不可用直接路由失败（第 2 节）。第 9 节的问题需要确认。第 1 节来自读当前 `main` 的代码（`IOSMSDispatcher`、`IOSMSChannelRouter`、`IOSMSBackupChannelRouter`、`SMSOPChannelRouter`、`SMSNumberChannelRouter`、`A2PSecondChannelRouter`、`IOSMSRerouteDispatcher`、`A2PCustomerManager` 的路由加载和匹配）。

## 1. 现在的路由

### 1.1 配置

路由写在 `conf/routing/{客户}_routingInfo.cfg`，每个客户一个文件（`CCBSSID` 小于等于 0 的块是所有客户共用的默认路由）。按“路由类型 × 匹配条件 × 主/备”组合出很多个配置名：

| 类型 | 主 | 备（`Backup`、`Backup1`…`Backup19`） | 匹配条件 |
|---|---|---|---|
| 号码 | `A2PNumberRoutingRelay` | 无 | `Number`（完整号码） |
| 运营商 | `A2POPSenderRoutingRelay`、`A2POPContentKeywordRoutingRelay`、`A2POPRoutingRelay` | 各自的 `...Backup...` | `Opid`（MNP 查到的运营商），加发送方 / 内容关键字 |
| 国家（号码前缀） | `A2PSenderRoutingRelay`、`A2PContentKeywordRoutingRelay`、`A2PRoutingRelay` | 各自的 `...Backup...` | `PhonePrefix`，加 `Sender` / `KeywordId` |
| 二次路由 | `A2PSecSenderRoutingRelay`、`A2PSecContentKeywordRoutingRelay`、`A2PSecRoutingRelay` | 各自的 `...Backup...` | 同国家路由，只对最近发过的号码（客户开了 `SMSOptionNeedSupportSecondRouting`） |

`Relay` 的写法：`V1` 单个通道；`V1:70,V2:30` 按权重随机；`V1,V2` 轮询。`V1;V2` 里 `;` 后面的部分被忽略（不是故障切换，`CoreDrBizIT` RT-05 验证过）。

### 1.2 选路顺序（写死在代码里）

```text
二次路由（命中号码缓存时）
 └ 没选出 ─> 号码路由
             └ 没选出 ─> 有运营商（MNP 查到）时：运营商 发送方 → 关键字 → 前缀；再运营商备份
                         └ 没选出 ─> 国家 发送方 → 关键字 → 前缀
                                     └ 没选出 ─> 国家备份（Backup、Backup1…）
                                                 └ 没选出 ─> 路由失败
```

- 每一类内部：号码前缀按**最长前缀**优先；都不匹配时用 `all`；客户自己的路由都没有时用默认路由。
- 选出的通道不存在、或者通道的内容长度限制不允许时，这一类算“没选出”，掉到下一类。
- 选出的通道处于 ROP 失败模式时，消息进 SMQ 等待，不继续选。
- 之后还有一次“系统路由替换”（`vendorRoutingReplacement.cfg`），把选出的通道换成另一个。

### 1.3 外发失败后的改道

- **submit 失败**：Core 处理外发结果时（`handleOutSubmitRes(msg, true)` → `IOSMSRerouteDispatcher`），**除了成功、SUBMIT_RESP_ERROR、SUBMIT_NOTPAID、DELIVERED 之外的所有失败都改道**，没有错误码列表可以配。改道只看国家备份路由，跳过已经走过的通道（`routingSsIDs`）。
- **DR 失败**：通道配了 `NeedDRReroute` 和 `SMSOptionDRRerouteCode` 时，DR 状态在列表里、且在 `RerouteDRDelayTimeInSec` 时间内的，改道到备份路由。

### 1.4 现在的问题

| 问题 | 说明 |
|---|---|
| 顺序写死 | 发送方 > 关键字 > 前缀、号码 > 运营商 > 国家，没法让一条宽泛的规则排在一条具体的规则前面 |
| 配置名太多 | 4 类 × 3 种条件 × 主备，再乘 20 个备份级别，约 18 组配置名，同一个意思写好几遍 |
| `Priority` 名不副实 | 运营商、号码路由有 `Priority` 属性，但只取最小的那一个，后面的永远用不上 |
| 备份级别对不上 | 加载 `Backup`…`Backup19` 共 20 级，取的时候只看前 10 级，`Backup10`～`Backup19` 配了也不生效 |
| 改道不看错误码 | submit 几乎任何失败都改道，对方偶发的临时错误也会让消息换通道 |
| 有配置不生效 | `A2PServiceTypeIDRoutingRelay`、`A2PContentRoutingRelay`、`A2PSenderAddrRoutingRelay`、`A2PContentRouting` 会被读取，但选路时没有任何地方用到 |

## 2. 新设计

### 2.1 分层

路由分成四层，**从上往下看，某一层有规则命中就用这一层，不再看下面的层**：

| 层 | 配置（主 / 备） | 什么时候看 | 层内怎么选 |
|---|---|---|---|
| 1 二次路由 | `A2PSecRouting` / `A2PSecBackupRouting` | 客户开了 `SMSOptionNeedSupportSecondRouting`，号码在“最近发过”的缓存里（同现在） | 同第 4 层 |
| 2 号码路由 | `A2PNumberRouting` / 无（第 9 节问题 5） | 总是 | 号码完全相等；同一号码多条规则按 `Priority` |
| 3 运营商路由 | `A2POPRouting` / `A2POPBackupRouting` | MNP / ENUM 查到了运营商（`rOperator > 0`，同现在） | 运营商 id 完全相等 → 国家级（`国家码*10000`）→ 默认（`Opid=-2`），每一级里按 `Priority` |
| 4 普通路由 | `A2PMainRouting` / `A2PBackupRouting` | 总是 | 号码最长前缀 → 更短前缀 → `all`，每个前缀里按 `Priority`（2.3） |

客户自己的四层都没有规则命中时，再按同样的顺序看默认路由（`CCBSSID ≤ 0` 的块）；还没有就路由失败（和现在一样：DB 兜底、回失败 DR）。

**为什么这三种单独成层、排在普通路由前面：**

- **号码路由**：完整号码是最具体的条件，必然要先于任何前缀。
- **运营商路由**：MNP 查到的是号码实际所属的运营商（携号转网后和号段不一致），比号码前缀准，所以应该先于按前缀的普通路由。查不到运营商时自然落到普通路由。
- **二次路由**：针对“最近发过的号码”换一套路由（例如验证码重发换通道），是对正常选路的覆盖，必须最先看。
- 这和现在代码里的顺序一致（第 1.2 节），迁移时这几类不会出现顺序变化。

**要注意的一点**：分层以后，运营商层的规则总是压过普通层的规则，哪怕普通层的规则更具体（例如普通层有 `PhonePrefix=8613,Sender=BANK`，运营商层有中国移动的规则，BANK 发往中国移动号码会走运营商层）。需要“某个发送方不管运营商都走某通道”时，要在运营商层也写一条带 `Sender` 的规则。

### 2.2 一条规则

```text
A2PMainRouting:   (Priority=10,PhonePrefix=86;852,Sender=BANK;OTP,Relay=V1:70,V2:30);(Priority=50,PhonePrefix=86,Relay=V3);(Priority=100,PhonePrefix=all,Relay=V9)
A2PBackupRouting: (Priority=10,PhonePrefix=86,Relay=V4);(Priority=20,PhonePrefix=all,Relay=V5)
A2POPRouting:     (Priority=10,Opid=860001,Relay=V6);(Priority=10,Opid=860000,Relay=V7)
A2PNumberRouting: (Priority=10,Number=8613800000000;8613900000000,Relay=V8)
```

| 属性 | 用在哪层 | 说明 |
|---|---|---|
| `Priority` | 全部，必填 | 1～100，越小越先匹配；只在同一个号码 / 运营商 / 前缀里比较 |
| `Relay` | 全部，必填 | 同现在：`V1`、`V1:70,V2:30`（权重）、`V1,V2`（轮询） |
| `PhonePrefix` | 1、4 | 接收号码前缀，`;` 分隔；`all` 或不写 = 所有号码 |
| `Number` | 2，必填 | 完整接收号码，`;` 分隔 |
| `Opid` | 3，必填 | 运营商 id，`;` 分隔；国家级写 `国家码*10000`；`-2` = 所有运营商 |
| `Sender` | 全部，可选 | 发送方，`;` 分隔，完全相等 |
| `KeywordId` | 全部，可选 | 内容关键字（内容模板里的关键字 id） |
| `ReplaceContentByTemplate` | 全部，可选 | 命中这条规则时按模板替换内容，同现在 |

**条件之间是“并且”**：写了的条件都满足才算命中，没写的不限制。

### 2.3 层内选路（以普通路由为例）

**优先级只在同一个号码前缀里比较**：号码前缀决定目的地（国家或号段），不同目的地的规则之间比优先级没有意义。

```text
接收号码 77012345678，普通路由规则：
  (Priority=1, PhonePrefix=7,  Relay=V1)
  (Priority=2, PhonePrefix=77, Sender=BANK, Relay=V2)
  (Priority=5, PhonePrefix=77, Relay=V3)
  (Priority=9, PhonePrefix=all, Relay=V9)

前缀从长到短：77 → 7 → all
  先看 77：按优先级 2（BANK 才命中）→ 5
     发送方 BANK：V2；其他发送方：V3
  77 下没有规则命中（条件都不满足）时才看 7 → V1；再看 all → V9
```

**命中即定（已确认）**：一条规则的条件满足就算命中，用它选通道；**选出的通道不可用**（通道不存在、内容长度不允许）时**直接路由失败**，不再看同一前缀的下一条、不再退到更短的前缀、不再看下面的层，也不在选路时进备份路由。日志写明是哪条规则、为什么不可用。

```text
for 层 in 二次 → 号码 → 运营商 → 普通（→ 默认路由的同样几层）:
   for 分组 in 这一层的分组（号码 / 运营商 id 由具体到宽泛 / 前缀由长到短）:
      for 规则 in 分组里的规则，按 Priority 从小到大:
         条件（Sender、KeywordId）不满足 ──> 下一条
         命中：按 Relay 选出通道（权重 / 轮询）
            通道不存在、内容长度不允许 ──> 路由失败
            ROP 失败模式 ──────────────> 第 9 节问题 4
            否则：用这个通道，结束
都没有命中 ─> 路由失败
```

**普通层的规则归到哪个前缀**：`PhonePrefix=86;852` 在 86、852 下各一份（优先级相同）；没写 `PhonePrefix` 或 `PhonePrefix=all` 的归 `all`。

- 日志：`[MT-ROUTE] ossid=... rssid=... by main prefix=77 priority=5`、`by op opid=860001 priority=10`、`by number priority=10`、`by second ...`。选中的规则写进消息（`routingRule`，见 2.6）。
- 系统路由替换（`vendorRoutingReplacement.cfg`）不变，在选出通道之后做。

### 2.4 失败后进备份路由

**什么时候进备份：**

| 失败 | 条件 |
|---|---|
| submit 失败（submit_sm_resp 错误、超时等） | 失败码在**这次发送的通道**的 `SMSOptionSubmitRerouteCode` 里（新增，cm.cfg 通道配置，逗号分隔）。没配就不改道，按现在的重试策略处理 |
| DR 失败 | 不变：通道 `NeedDRReroute=true`，DR 状态在 `SMSOptionDRRerouteCode` 里，且在 `RerouteDRDelayTimeInSec` 内 |

**用哪一层的备份**：选出这个通道的那一层的备份规则（二次 → `A2PSecBackupRouting`，运营商 → `A2POPBackupRouting`，普通 → `A2PBackupRouting`；号码层见第 9 节问题 5）。层内选法和主路由一样，并跳过这条消息已经走过的所有通道（`routingSsIDs`）。这一层的备份没有规则命中时，再看普通层的备份（第 9 节问题 6）。

- 备份规则命中但通道不可用：和主路由一样，不再找，按这次失败的状态处理。
- 备份通道又失败、失败码在**备份通道**的改道码里：继续在备份规则里找（跳过走过的通道），直到没有命中的规则，或达到改道次数上限（`SMSOptionMaxReroute`，新增，客户配置，默认 3）。
- 没有可用的备份：按这次失败的状态走现在的流程（重试策略或失败 DR）。
- 改道后的发送和现在一样：同一个 Core 重新写进新通道的 `stream:mt:routed:*`，`OUT_SUBMIT` CDR 每次发送各一条。长短信只看第 1 段的结果决定是否改道。

### 2.5 同一个优先级有多条规则

冲突只在同一个分组里才有（同一层、同一个号码 / 运营商 id / 前缀）：`PhonePrefix=7` 和 `PhonePrefix=77` 都用 1 不冲突。建议：**加载时不允许**同一分组里两条规则用同一个优先级，有就拒绝这次 reload（`RELOAD_ROUTING` 的原有处理：报错、保持旧配置）。另一种做法见第 9 节问题 1。

### 2.6 加载和性能

- 加载时每个客户、每一层各建索引：普通层、二次层是前缀树（每个前缀节点挂着按优先级排好的规则列表）；号码层是“号码 → 规则列表”的哈希表；运营商层是“运营商 id → 规则列表”的哈希表。发送方、关键字建成集合。
- 选路：每层一次哈希查找或沿号码走一遍前缀树，再看分组里的几条规则。开销和现在每类依次查几张表同一个量级，比现在的正则逐个匹配更快。
- `RELOAD_ROUTING` 照旧：整套路由表构建好后一次替换，正在选路的消息用旧表走完。
- 选中的规则（层、主/备、分组、优先级）记到消息的新字段 `routingRule`，写进 Stream（和 `modulePath` 一样追加在最后），方便查“为什么走这个通道”（是否写 CDR 见第 9 节问题 7）。

## 3. 和现在相比

| 方面 | 现在 | 新设计 |
|---|---|---|
| 层的顺序 | 二次 → 号码 → 运营商 → 国家（代码写死） | 不变，四层 |
| 层内顺序 | 发送方 → 关键字 → 前缀（写死），前缀取最长 | 号码 / 运营商 / 前缀分组，组内按 `Priority` |
| 条件组合 | 每种组合一个配置名 | 一条规则里组合 `Sender`、`KeywordId` |
| 规则命中但通道不可用 | 掉到下一类，或直接进备份 | 路由失败 |
| 备份级别 | `Backup`…`Backup19`（实际只用前 10 级） | 备份规则按优先级，不限级数 |
| 何时改道 | submit 几乎所有失败 | 只在通道配的 `SMSOptionSubmitRerouteCode` 里的失败码 |
| 改道次数 | 直到备份用完 | `SMSOptionMaxReroute`，默认 3 |
| 改道用哪套备份 | 只用国家备份 | 选出通道那一层的备份，再普通层备份 |

## 4. 去掉的配置和代码

按之前的约定：旧逻辑去掉，全部改成新配置。

- 路由文件里所有 `A2P*RoutingRelay*` 配置名（第 1.1 节表里全部，以及不生效的 `A2PServiceTypeIDRoutingRelay`、`A2PContentRoutingRelay`、`A2PSenderAddrRoutingRelay`、`A2PContentRouting`）。读到时打 WARN，不生效。
- 代码：`IOSMSChannelRouter`、`IOSMSBackupChannelRouter`、`SMSOPChannelRouter`、`SMSOPBackupChannelRouter`、`SMSNumberChannelRouter`、`A2PSecondChannelRouter` 合并成一个按层、按规则选路的 `RuleRouter`；`A2PCustomerManager` 里对应的十几张路由表和加载、匹配方法删掉，换成每层的索引。`IOSMSDispatcher.dispatch` 里写死的嵌套 if 改为按层循环。
- `IOSMSRerouteDispatcher.reroute` 的“除了几种状态都改道”改为按改道码判断。

## 5. 迁移

旧配置不再读取，升级前要把路由文件转换成新格式。提供一个转换工具（a2pctl 子命令，读旧的 routingInfo 文件，输出新的）。

| 旧配置 | 新配置 | 优先级 |
|---|---|---|
| `A2PNumberRoutingRelay` | `A2PNumberRouting` | 原来的 `Priority` |
| `A2POPSenderRoutingRelay` | `A2POPRouting`，带 `Sender` | 10 |
| `A2POPContentKeywordRoutingRelay` | `A2POPRouting`，带 `KeywordId` | 20 |
| `A2POPRoutingRelay` | `A2POPRouting` | 30 + 原来的 `Priority` 顺序 |
| `A2PSenderRoutingRelay` | `A2PMainRouting`，带 `Sender` | 10 |
| `A2PContentKeywordRoutingRelay` | `A2PMainRouting`，带 `KeywordId` | 20 |
| `A2PRoutingRelay` | `A2PMainRouting` | 30 |
| `A2PSec*` | `A2PSecRouting` / `A2PSecBackupRouting`，同普通层 | 同普通层 |
| 各种 `...Backup...` 第 N 级 | 对应层的备份规则 | 同上，再按级别 +N |

**层之间的顺序和现在一样，不会变。普通层内部跨前缀时新旧结果可能不同**，因为现在是“先发送方、再关键字、再前缀，各自取最长前缀”，新设计是“先最长前缀、前缀内再按优先级”：

```text
旧：A2PSenderRoutingRelay: (PhonePrefix=7,Sender=BANK,Relay=V1)
    A2PRoutingRelay:       (PhonePrefix=77,Relay=V2)
发送方 BANK、号码 77...：现在走 V1；直接按新规则走 V2（77 更长）
```

工具会把这种情况转换成等价写法：把短前缀的发送方 / 关键字规则复制一份到更长的前缀下（例子里多一条 `(Priority=10,PhonePrefix=77,Sender=BANK,Relay=V1)`），保证转换后结果和现在一样，并在报告里列出每一条复制出来的规则，方便人工确认是否真的需要保留旧行为。

- “规则命中但通道不可用”现在会掉到下一类或备份，新设计直接路由失败。工具的报告里列出指向不存在通道的规则、配了内容长度限制的通道，上线前确认。
- 转换后先用工具的“试算”模式：对一批真实号码、发送方分别用旧规则和新规则选路，列出结果不同的组合，确认后再上线。
- 改道行为变了（只按改道码），上线前要给各通道配好 `SMSOptionSubmitRerouteCode`；想保持现在“几乎都改道”的，可以把常见失败码都配上。

## 6. 日志、指标、测试

**日志：** `[MT-ROUTE] ... by {second|number|op|main} ... priority=N`、`by ...backup...`；规则命中但通道不可用时 INFO 写明规则和原因；`[MT-REROUTE] from=V1 to=V4 code=2500 attempt=1`。

**指标：** 按层、主/备、优先级统计命中数；改道次数；路由失败数（按原因：没有规则 / 通道不可用）。

**测试**（真实 Core，`CoreRouteIT` / `CoreRetryIT` 的做法）：

| 编号 | 场景 | 预期 |
|---|---|---|
| RR-01 | `(1, PhonePrefix=7, V1)`、`(2, PhonePrefix=77, Sender=BANK, V2)`、`(5, PhonePrefix=77, V3)`，号码 77... | BANK 走 V2，其他走 V3；7 开头（非 77）的号码走 V1 |
| RR-01b | 同一前缀：宽泛规则 Priority=10、`Sender=BANK` 的规则 Priority=20 | 都走 10；把 BANK 规则改成 5 后 BANK 走它 |
| RR-01c | 77 下只有 `Sender=BANK` 的规则，发送方不是 BANK | 退到 7 |
| RR-01d | 77 的规则命中，通道不存在 / 内容长度不允许 | 路由失败，不退到 7 |
| RR-02 | 号码层、运营商层、普通层都有规则 | 号码层先；号码不匹配看运营商层；没查到运营商看普通层 |
| RR-03 | 运营商层：id 完全相等、国家级、`-2` | 由具体到宽泛 |
| RR-04 | 二次路由：号码在缓存 / 不在缓存 | 在缓存走二次层 |
| RR-05 | 客户规则都不命中 | 默认路由；默认也没有时路由失败（DB 兜底、失败 DR） |
| RR-06 | 权重、轮询 | 比例和现在一样 |
| RR-07 | submit 失败，码在通道的改道码里 | 改到对应层备份规则的通道；那一层没有时用普通层备份 |
| RR-08 | 失败码不在改道码里 | 不改道，按重试策略 |
| RR-09 | 备份也失败 | 继续下一条备份，跳过走过的通道；到 `SMSOptionMaxReroute` 停 |
| RR-10 | DR 失败改道 | 和现在一样，只是备份按新规则选 |
| RR-11 | 同一分组同一优先级两条规则 | reload 被拒绝，保持旧配置 |
| RR-12 | 旧配置名 | 不生效，打 WARN |
| RR-13 | 转换工具 | 对现有回归用例里的所有路由文件转换后，选路结果和转换前一致（通道不可用的情况除外） |
| RR-14 | 长短信、系统路由替换 | 和现在一样 |

## 8. 不在这次范围

- 选路之前的步骤（黑白名单、内容检查、MNP / ENUM 查询、二次路由的号码缓存）和之后的步骤（系统路由替换、拆分、限速）不变。
- 通道内部的连接选择（`SubmitPolicy_Conn`）、bind 级限速不变。
- DR、MO 的路由不变（它们回客户，不走这套规则）。

## 9. 需要确认的问题

已确认：规则命中但通道不可用时直接路由失败（2.3）。

1. **同一分组、同一优先级多条规则**：建议加载时拒绝（2.5）。另一种做法：允许，再按“条件多的先、文件里靠前的先”排。
2. **改道码配在哪**：建议配在通道上（`SMSOptionSubmitRerouteCode`），因为失败码是通道（供应商）给的。也可以配在规则上（`RerouteCode=...`），或者两处都能配、规则上的优先。
3. **改道次数上限**：建议客户配置 `SMSOptionMaxReroute`，默认 3。也可以不设上限（备份规则用完为止，和现在一样）。
4. **选出的通道处于 ROP 失败模式**：现在是进 SMQ 等通道恢复。建议保持，避免通道短暂断开时把流量都切走；也可以和“通道不可用”一样算路由失败。
5. **号码路由要不要备份**：现在没有号码备份。建议不加，号码层的通道失败时直接用普通层的备份；需要时再加 `A2PNumberBackupRouting`。
6. **对应层的备份没有命中时要不要再看普通层备份**：建议看（2.4）。也可以只看本层的备份。
7. **`routingRule` 写不写 CDR**：写进 CDR 会改 CDR 格式（下游解析受影响）；建议先只写日志和 Stream。
8. **默认路由**（`CCBSSID ≤ 0` 的块）：建议保留，四层都用同样的规则格式，在客户的四层之后看。
