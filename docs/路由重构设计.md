## 1. 现在的路由

### 1.1 配置

路由写在 `conf/routing/{客户}_routingInfo.cfg`，每个客户一个文件（`CCBSSID` 小于等于 0 的块是所有客户共用的默认路由）。按“路由类型 × 匹配条件 × 主/备”组合出很多个配置名：

| 类型 | 主 | 备（`Backup`、`Backup1`…`Backup19`） | 匹配条件 |
|---|---|---|---|
| 号码 | `A2PNumberRoutingRelay` | 无 | `Number`（完整号码） |
| 运营商 | `A2POPSenderRoutingRelay`、`A2POPContentKeywordRoutingRelay`、`A2POPRoutingRelay` | 各自的 `...Backup...` | `Opid`（MNP 查到的运营商），加发送方 / 内容关键字 |
| 国家（号码前缀） | `A2PSenderRoutingRelay`、`A2PContentKeywordRoutingRelay`、`A2PRoutingRelay` | 各自的 `...Backup...` | `PhonePrefix`，加 `Sender` / `KeywordId` |
| 二次路由 | `A2PSecSenderRoutingRelay`、`A2PSecContentKeywordRoutingRelay`、`A2PSecRoutingRelay` | 各自的 `...Backup...` | 同国家路由，只对最近发过的号码（客户开了 `SMSOptionNeedSupportSecondRouting`） |

`Relay` 的写法：`V1` 单个通道；`V1:70,V2:30` 按权重随机；`V1,V2` 轮询。`V1;V2` 里 `;` 后面的部分被忽略（不是故障切换，`CoreDrBizIT` RT-05 验证过）。

### 1.2 选路顺序（写死在代码里）

```text
二次路由（命中号码缓存时）
 └ 没选出 ─> 号码路由
             └ 没选出 ─> 有运营商（MNP 查到）时：运营商 发送方 → 关键字 → 前缀；再运营商备份
                         └ 没选出 ─> 国家 发送方 → 关键字 → 前缀
                                     └ 没选出 ─> 国家备份（Backup、Backup1…）
                                                 └ 没选出 ─> 路由失败
```

- 每一类内部：号码前缀按**最长前缀**优先；都不匹配时用 `all`；客户自己的路由都没有时用默认路由。
- 选出的通道不存在、或者通道的内容长度限制不允许时，这一类算“没选出”，掉到下一类。
- 选出的通道处于 ROP 失败模式时，消息进 SMQ 等待，不继续选。
- 之后还有一次“系统路由替换”（`vendorRoutingReplacement.cfg`），把选出的通道换成另一个。

### 1.3 外发失败后的改道

- **submit 失败**：Core 处理外发结果时（`MessageStoreManager.handleOutSubmitRes(msg, true)` → `IOSMSRerouteDispatcher`），**除了成功、SUBMIT_RESP_ERROR、SUBMIT_NOTPAID、DELIVERED 之外的所有失败都改道**，改道不看错误码。改道只看国家备份路由，跳过已经走过的通道（`routingSsIDs`）。
- **改道不成功（没有可用的备份）时**：看这次发送的通道的 `SMSOptionSubmitRetryCode`（cm.cfg 通道配置，逗号分隔的内部状态码，例如 `SMSOptionSubmitRetryCode: 10200,10203`；`MessageStoreManager.needRetryForOutSubmitRes`）：失败码在里面 → 按重试策略重试（到时间后重新选路，回到主路由）；不在里面（或没配）→ 直接回失败 DR。
- **DR 失败**：通道配了 `NeedDRReroute` 和 `SMSOptionDRRerouteCode` 时，DR 状态在列表里、且在 `RerouteDRDelayTimeInSec` 时间内的，改道到备份路由。

### 1.4 现在的问题

| 问题 | 说明 |
|---|---|
| 顺序写死 | 发送方 > 关键字 > 前缀、号码 > 运营商 > 国家，没法让一条宽泛的规则排在一条具体的规则前面 |
| 配置名太多 | 4 类 × 3 种条件 × 主备，再乘 20 个备份级别，约 18 组配置名，同一个意思写好几遍 |
| `Priority` 名不副实 | 运营商、号码路由有 `Priority` 属性，但只取最小的那一个，后面的永远用不上 |
| 备份级别对不上 | 加载 `Backup`…`Backup19` 共 20 级，取的时候只看前 10 级，`Backup10`～`Backup19` 配了也不生效 |
| 改道不看错误码 | submit 几乎任何失败都改道，对方偶发的临时错误也会让消息换通道 |
| 有配置不生效 | `A2PServiceTypeIDRoutingRelay`、`A2PContentRoutingRelay`、`A2PSenderAddrRoutingRelay`、`A2PContentRouting` 会被读取，但选路时没有任何地方用到 |

## 2. 新设计

### 2.1 分层

路由分成四层，**从上往下看，某一层有规则命中就用这一层，不再看下面的层**：

| 层 | 配置（主 / 备） | 什么时候看 | 层内怎么选 |
|---|---|---|---|
| 1 二次路由 | `A2PSecRouting` / `A2PSecBackupRouting`、`A2PSecBackup2Routing`… | 客户开了 `SMSOptionNeedSupportSecondRouting`，号码在“最近发过”的缓存里（同现在） | 同第 4 层 |
| 2 号码路由 | `A2PNumberRouting` / 无（第 9 节问题 5） | 总是 | 号码完全相等；同一号码多条规则按 `Priority` |
| 3 运营商路由 | `A2POPRouting` / `A2POPBackupRouting`、`A2POPBackup2Routing`… | MNP / ENUM 查到了运营商（`rOperator > 0`，同现在） | 运营商 id 完全相等 → 国家级（`国家码*10000`）→ 默认（`Opid=-2`），每一级里按 `Priority` |
| 4 普通路由 | `A2PMainRouting` / `A2PBackupRouting`、`A2PBackup2Routing`、`A2PBackup3Routing`… | 总是 | 号码最长前缀 → 更短前缀 → `all`，每个前缀里按 `Priority`（2.3） |

客户自己的四层都没有规则命中时，再按同样的顺序看默认路由（`CCBSSID ≤ 0` 的块）；还没有就路由失败（和现在一样：DB 兜底、回失败 DR）。

**为什么这三种单独成层、排在普通路由前面：**

- **号码路由**：完整号码是最具体的条件，必然要先于任何前缀。
- **运营商路由**：MNP 查到的是号码实际所属的运营商（携号转网后和号段不一致），比号码前缀准，所以应该先于按前缀的普通路由。查不到运营商时自然落到普通路由。
- **二次路由**：针对“最近发过的号码”换一套路由（例如验证码重发换通道），是对正常选路的覆盖，必须最先看。
- 这和现在代码里的顺序一致（第 1.2 节），迁移时这几类不会出现顺序变化。

**要注意的一点**：分层以后，运营商层的规则总是压过普通层的规则，哪怕普通层的规则更具体（例如普通层有 `PhonePrefix=8613,Sender=BANK`，运营商层有中国移动的规则，BANK 发往中国移动号码会走运营商层）。需要“某个发送方不管运营商都走某通道”时，要在运营商层也写一条带 `Sender` 的规则。

### 2.2 一条规则

```text
A2PMainRouting:   (Priority=10,PhonePrefix=86;852,Sender=BANK;OTP,Relay=V1:70,V2:30);(Priority=50,PhonePrefix=86,Relay=V3);(Priority=100,PhonePrefix=all,Relay=V9)
A2PBackupRouting: (Priority=10,PhonePrefix=86,Relay=V4);(Priority=20,PhonePrefix=all,Relay=V5)
A2PBackup2Routing:(Priority=10,PhonePrefix=86,Relay=V10,V11);(Priority=20,PhonePrefix=all,Relay=V12)
A2PBackup3Routing:(Priority=10,PhonePrefix=all,Relay=V13)
A2POPRouting:     (Priority=10,Opid=860001,Relay=V6);(Priority=10,Opid=860000,Relay=V7)
A2PNumberRouting: (Priority=10,Number=8613800000000;8613900000000,Relay=V8)
```

| 属性 | 用在哪层 | 说明 |
|---|---|---|
| `Priority` | 全部，必填 | 1～100，越小越先匹配；只在同一个号码 / 运营商 / 前缀里比较 |
| `Relay` | 全部，必填 | 同现在：`V1`、`V1:70,V2:30`（权重）、`V1,V2`（轮询） |
| `PhonePrefix` | 1、4 | 接收号码前缀，`;` 分隔；`all` 或不写 = 所有号码 |
| `Number` | 2，必填 | 完整接收号码，`;` 分隔 |
| `Opid` | 3，必填 | 运营商 id，`;` 分隔；国家级写 `国家码*10000`；`-2` = 所有运营商 |
| `Sender` | 全部，可选 | 发送方，`;` 分隔，完全相等 |
| `ExcludeSender` | 全部，可选 | 排除的发送方，`;` 分隔：消息的发送方在里面时这条规则**不命中**（2.7） |
| `KeywordId` | 全部，可选 | 内容关键字（内容模板里的关键字 id） |
| `ExcludeKeywordId` | 全部，可选 | 排除的关键字：内容命中其中任何一个时不命中 |
| `ExcludePhonePrefix` | 1、3、4，可选 | 排除的号码前缀：接收号码以其中任何一个开头时不命中（例如 `PhonePrefix=86,ExcludePhonePrefix=86170;86171`） |
| `ReplaceContentByTemplate` | 全部，可选 | 命中这条规则时按模板替换内容，同现在 |

**条件之间是“并且”**：写了的条件都满足、写了的排除条件都不满足，才算命中；没写的不限制。备份各级的规则和主路由的写法完全一样。

### 2.3 层内选路（以普通路由为例）

**优先级只在同一个号码前缀里比较**：号码前缀决定目的地（国家或号段），不同目的地的规则之间比优先级没有意义。

```text
接收号码 77012345678，普通路由规则：
  (Priority=1, PhonePrefix=7,  Relay=V1)
  (Priority=2, PhonePrefix=77, Sender=BANK, Relay=V2)
  (Priority=5, PhonePrefix=77, Relay=V3)
  (Priority=9, PhonePrefix=all, Relay=V9)

前缀从长到短：77 → 7 → all
  先看 77：按优先级 2（BANK 才命中）→ 5
     发送方 BANK：V2；其他发送方：V3
  77 下没有规则命中（条件都不满足）时才看 7 → V1；再看 all → V9
```

**命中即定（已确认）**：一条规则的条件满足就算命中，用它选通道；**选出的通道不可用**（通道不存在、内容长度不允许）时**直接路由失败**，不再看同一前缀的下一条、不再退到更短的前缀、不再看下面的层，也不在选路时进备份路由。日志写明是哪条规则、为什么不可用。

```text
for 层 in 二次 → 号码 → 运营商 → 普通（→ 默认路由的同样几层）:
   for 分组 in 这一层的分组（号码 / 运营商 id 由具体到宽泛 / 前缀由长到短）:
      for 规则 in 分组里的规则，按 Priority 从小到大:
         条件（Sender、KeywordId）不满足 ──> 下一条
         命中：按 Relay 选出通道（权重 / 轮询）
            通道不存在、内容长度不允许 ──> 路由失败
            ROP 失败模式 ──────────────> 第 9 节问题 4
            否则：用这个通道，结束
都没有命中 ─> 路由失败
```

**普通层的规则归到哪个前缀**：`PhonePrefix=86;852` 在 86、852 下各一份（优先级相同）；没写 `PhonePrefix` 或 `PhonePrefix=all` 的归 `all`。

- 日志：`[MT-ROUTE] ossid=... rssid=... by main prefix=77 priority=5`、`by op opid=860001 priority=10`、`by number priority=10`、`by second ...`。选中的规则写进消息（`routingRule`，见 2.6）。
- 系统路由替换（`vendorRoutingReplacement.cfg`）不变，在选出通道之后做。

### 2.4 失败后逐级进备份路由

**备份分级**：每一层（二次、运营商、普通）的备份路由分成第 1 级、第 2 级、第 3 级……，每一级是一组独立的规则，写法和主路由一样（前缀分组、组内按 `Priority`、条件和排除条件）：

| 级别 | 普通层 | 运营商层 | 二次层 |
|---|---|---|---|
| 主 | `A2PMainRouting` | `A2POPRouting` | `A2PSecRouting` |
| 备份 1 | `A2PBackupRouting` | `A2POPBackupRouting` | `A2PSecBackupRouting` |
| 备份 2 | `A2PBackup2Routing` | `A2POPBackup2Routing` | `A2PSecBackup2Routing` |
| 备份 3 | `A2PBackup3Routing` | `A2POPBackup3Routing` | `A2PSecBackup3Routing` |
| … | 最多到 `A2PBackup10Routing`（10 级，和现在实际生效的级数一样） | 同左 | 同左 |

级别可以不连续（只配了 1 和 3，就是 1 → 3）。

**什么时候进下一级：**

| 失败 | 条件 |
|---|---|
| submit 失败（submit_sm_resp 错误、超时等） | 失败码在**这次发送的通道**的 `SMSOptionSubmitRetryCode` 里（**沿用现有配置**，cm.cfg 通道配置，逗号分隔的内部状态码；现在用来判断要不要重试，新设计同时用来判断要不要进下一级）。**不在里面：不改道、不重试，直接回失败 DR**（已确认，2.9） |
| DR 失败 | 不变：这次发送的通道开了 `NeedDRReroute=true`，DR 不是 DELIVERED，在 `RerouteDRDelayTimeInSec` 内，且状态在 `SMSOptionDRRerouteCode` 里（列表没配时任何失败都算，同现在）。**没开 `NeedDRReroute` 不改道**（2.9） |

**逐级的流程**：

```text
主路由（第 0 级）选出 V1 发送
  V1 失败，码在 V1 的改道码里 ──> 第 1 级
第 1 级：在“选出 V1 的那一层”的备份 1 里按前缀、优先级选（同主路由的选法）
  命中，选出 V4（跳过这条消息已经走过的通道）发送
  V4 失败，码在 V4 的改道码里 ──> 第 2 级
第 2 级：备份 2 里选 ... 第 3 级 ...
直到：某一级发送成功；或失败码不在改道码里（直接回失败 DR）；或级别用完 / 达到 SMSOptionMaxReroute（2.9）
```

- **每一级只用一次**（已确认）：一级选出的通道失败后进下一级，不在同一级里换下一条规则。和主路由一样，一级里的优先级是“哪条规则命中”，不是“失败了换哪条”。
- **一级里的规则命中，Relay 有多个通道**（`V10,V11` 轮询或 `V10:50,V11:50` 权重）时，只在**没走过的**通道里选；都走过了，这一级算没有命中。
- **某一级没有规则命中**（没配这一级、条件不满足、通道都走过了）：直接看下一级，不算一次改道。
- **某一级的规则命中但通道不可用**（通道不存在、内容长度不允许）：跳到下一级（已确认）。主路由命中但不可用时仍然是直接路由失败（2.3）。
- **用哪一层的备份**：第 N 级先看选出主路由通道的那一层的第 N 级；那一层的第 N 级没有命中时，看普通层的第 N 级（第 9 节问题 6）；都没有再看第 N+1 级。客户自己的第 N 级都没有命中时，看默认路由（`CCBSSID ≤ 0`）的第 N 级。
- **记住到了第几级**（不加轮次，已确认）：消息新增字段 `routingLevel`（0 = 主路由，1、2、3… = 备份级别），和 `routingSsIDs`（走过的通道）一起写进 Stream 和 DB 的重试记录。改道时从 `routingLevel + 1` 级开始找，改道后更新。现在的代码每次都从第 1 级找起、靠跳过用过的通道“推进”，权重路由时会在同一级里换通道，新设计不会。
- **改道次数上限**：`SMSOptionMaxReroute`（新增，客户配置，默认 10，即不比级数更严）。达到上限后按这次失败处理。
- 没有可用的下一级：见 2.9（submit 重试主路由，DR 回失败 DR）。
- 改道后的发送和现在一样：同一个 Core 重新写进新通道的 `stream:mt:routed:*`，`OUT_SUBMIT` CDR 每次发送各一条。长短信只看第 1 段的结果决定是否改道，后面的段跟着第 1 段的通道和级别。

**例子：**

```text
A2PMainRouting:    (Priority=10,PhonePrefix=86,Relay=V1)
A2PBackupRouting:  (Priority=10,PhonePrefix=86,Sender=BANK,Relay=V2);(Priority=20,PhonePrefix=86,Relay=V3)
A2PBackup2Routing: (Priority=10,PhonePrefix=86,Relay=V4:50,V5:50)
A2PBackup3Routing: (Priority=10,PhonePrefix=all,Relay=V6)

发送方 BANK、号码 86...：V1 失败 → 第 1 级 V2 → 失败 → 第 2 级 V4 或 V5 → 失败 → 第 3 级 V6
发送方 OTP： V1 失败 → 第 1 级 V3（BANK 的规则不命中，同一级的下一条优先级）→ 失败 → 第 2 级 ...
第 2 级选了 V4 失败：进第 3 级 V6，不会再试 V5
```

### 2.5 同一个优先级有多条规则

冲突只在同一个分组里才有（同一层、同一个号码 / 运营商 id / 前缀）：`PhonePrefix=7` 和 `PhonePrefix=77` 都用 1 不冲突。建议：**加载时不允许**同一分组里两条规则用同一个优先级，有就拒绝这次 reload（`RELOAD_ROUTING` 的原有处理：报错、保持旧配置）。另一种做法见第 9 节问题 1。

### 2.6 加载和性能

- 加载时每个客户、每一层各建索引：普通层、二次层是前缀树（每个前缀节点挂着按优先级排好的规则列表）；号码层是“号码 → 规则列表”的哈希表；运营商层是“运营商 id → 规则列表”的哈希表。发送方、关键字建成集合。
- 选路：每层一次哈希查找或沿号码走一遍前缀树，再看分组里的几条规则。开销和现在每类依次查几张表同一个量级，比现在的正则逐个匹配更快。
- `RELOAD_ROUTING` 照旧：整套路由表构建好后一次替换，正在选路的消息用旧表走完。
- 选中的规则（层、主/备、分组、优先级）记到消息的新字段 `routingRule`，写进 Stream（和 `modulePath` 一样追加在最后），方便查“为什么走这个通道”（是否写 CDR 见第 9 节问题 7）。

### 2.7 排除条件：“除了某个发送方，其他都走通道 C”

**写法**：在规则里写 `ExcludeSender`：

```text
A2PMainRouting: (Priority=10,PhonePrefix=86,ExcludeSender=BANK;OTP,Relay=C);(Priority=20,PhonePrefix=86,Relay=V1)
```

- 发送方不是 BANK、OTP：命中优先级 10，走 C。
- 发送方是 BANK 或 OTP：优先级 10 不命中，看同一前缀的下一条（优先级 20）→ V1。
- 同一前缀里没有下一条：和其他不命中一样，退到更短的前缀、再到 `all`、再到下面的层（2.3）。

**用优先级也能表达**（不用排除条件）：

```text
A2PMainRouting: (Priority=10,PhonePrefix=86,Sender=BANK;OTP,Relay=V1);(Priority=20,PhonePrefix=86,Relay=C)
```

两种写法在 BANK、OTP 有明确去处（V1）时结果一样。**排除条件真正需要的情况**是：被排除的发送方**不在这个前缀里另指通道**，而是要“当这条规则不存在”，继续按原来的规则走（更短的前缀、`all`、默认路由，或者下面的层）。例如：

```text
A2PMainRouting: (Priority=10,PhonePrefix=8613,ExcludeSender=BANK,Relay=C);(Priority=10,PhonePrefix=86,Relay=V1);(Priority=10,PhonePrefix=all,Relay=V9)
号码 8613...：BANK 以外走 C；BANK 退到 86 → V1
```

不用排除条件就要在 8613 下给 BANK 再写一条 `Relay=V1`，以后 86 的通道改了还得记得改两处。

**其他排除条件**，同样的规则：

| 需求 | 写法 |
|---|---|
| 除了某几个关键字（例如营销内容），其他都走 C | `(Priority=10,PhonePrefix=86,ExcludeKeywordId=5;6,Relay=C)` |
| 中国除了 170、171 号段，都走 C | `(Priority=10,PhonePrefix=86,ExcludePhonePrefix=86170;86171,Relay=C)` |
| 只有 BANK 走 C，但 BANK 的验证码（关键字 3）不走 C | `(Priority=10,PhonePrefix=86,Sender=BANK,ExcludeKeywordId=3,Relay=C)` |
| 备份路由里也排除 | 备份各级的规则一样可以写，例如 `A2PBackupRouting: (Priority=10,PhonePrefix=86,ExcludeSender=BANK,Relay=C2)` |

**加载时检查**：同一条规则里 `Sender` 和 `ExcludeSender` 有相同的值、`ExcludePhonePrefix` 不是 `PhonePrefix` 的下级号段（排除了一个本来就不会命中的前缀）时，拒绝这次 reload（同 2.5 的处理），避免写错的规则悄悄不生效。

**日志**：被排除条件挡掉、退到下一条规则时，DEBUG 写明是哪条规则的哪个排除条件；`[MT-ROUTE]` 里照常写最终命中的规则。

### 2.8 系统路由替换（`vendorRoutingReplacement.cfg`）和改道

**现在的替换**：运维在通道出问题时用这个文件（或管理命令）把某个通道临时换成另一个，每行 `前缀|ossid|原通道|替换通道`（ossid `-1` = 所有客户，前缀 `all` = 所有号码）。选路选出原通道后再换成替换通道；改道（`IOSMSRerouteDispatcher`）选出备份通道后也会换。

**现在的问题：**

| 问题 | 说明 |
|---|---|
| 记录的通道不一致 | 主路由把**替换前**的通道记进 `routingSsIDs`，改道时记的是**替换后**的通道。主路由 V1 被换成 V2 发出，V2 失败后，备份规则如果选到 V2（或选到 V1、又被换成 V2），不会被认为“走过了”，又发给同一个失败的通道 |
| 替换目标不检查 | 替换通道不存在、或在 ROP 失败模式时没有单独处理 |
| 日志看不出来 | `[MT-ROUTE]` 只有最终通道，查不出是规则选的还是替换来的 |

**新设计：替换在“选通道”这一步里做，每一级都一样**

```text
规则命中，按 Relay 选出候选通道 V1
  └ 查替换表（前缀、客户、V1）：有替换 → 实际通道 V2；没有 → 实际通道 V1
  └ “走过了”按实际通道判断：V2 已经在 routingSsIDs 里 → 这个候选算走过了，在 Relay 的其他通道里选；都走过了 → 这一级没有命中
  └ 实际通道不可用（不存在、内容长度不允许）→ 同 2.3 / 2.4：主路由直接路由失败，备份跳到下一级
记录：routingSsIDs 记实际通道；日志、routingRule 里同时写规则选的通道和替换后的通道
```

- **改道码看实际通道**：V2 发送失败，看 V2 的 `SMSOptionSubmitRetryCode`（失败码是 V2 的供应商给的）。
- **替换只做一次**：V1 换成 V2 后不再查 V2 的替换（和现在一样，避免 V1→V2→V1 循环）。替换表里出现链条（V1→V2、V2→V3）时，加载时打 WARN。
- **备份规则直接选到被替换的通道**：同样替换（例如备份 1 选到 V1，V1 正被替换成 V2，而 V2 刚失败过 → 算走过了 → 这一级换别的通道或跳到下一级）。这样替换和备份不会把消息反复送到同一个失败的通道。
- **日志**：`[MT-ROUTE] ... by main prefix=86 priority=10 rule=V1 replaced=V2`；改道 `[MT-REROUTE] level=2 rule=V4 replaced=V5 code=...`。

### 2.9 失败之后的处理（已确认）

**两个概念先分清：**

- **改道码**：通道的 `SMSOptionSubmitRetryCode`（submit 失败）/ `SMSOptionDRRerouteCode`（DR 失败），列出“这个通道返回这些失败时，换下一级的通道再发”。
- **失败码不在改道码里**：例如消息发给通道 C，C 返回 submit 失败，失败码不在 C 的 `SMSOptionSubmitRetryCode` 里：说明这个失败换通道也没用（号码错误、内容被拒等），**不再选下一级，直接回失败 DR**。

| 情况 | 处理 |
|---|---|
| submit 失败，码在这个通道的改道码里，还有下一级 | 立刻进下一级（不等，不算重试次数） |
| submit 失败，码**不在**这个通道的改道码里（主路由或任何一级备份） | 不改道、不重试，**直接回失败 DR** |
| submit 失败，码在改道码里，但**级别用完**（或达到 `SMSOptionMaxReroute`、后面的级别都没有命中） | 按重试策略（`RetryPolicy`）等间隔，**只重试主路由**；重试次数用完或消息过期后回失败 DR |
| DR 失败，满足 DR 改道条件（上表），还有下一级 | 进下一级 |
| DR 失败，不满足 DR 改道条件（**没开 `NeedDRReroute`**、超时、状态不在列表），或级别用完 | 不改道、不重试，按下面“DR 不改道时”处理 |

**DR 失败的处理顺序**（和现在 `MessageStoreManager` 处理供应商 DR 的顺序一致）：

```text
供应商 DR 匹配到原 MT
  └ 先写 OUT_DELI_REP CDR（每个供应商 DR 都写，改不改道都写）
  └ 这次发送的通道开了 NeedDRReroute，且 DR 不是 DELIVERED、在 RerouteDRDelayTimeInSec 内、状态在 SMSOptionDRRerouteCode 里（列表没配 = 任何失败）？
       是，并且还有下一级 ──> 改道到下一级发送；这时不给客户回 IN DR
       否（包括没开 NeedDRReroute），或没有下一级 ──> DR 不改道时：
           ├ 假 DR 方式 3：客户配了 SMSOptionDRSuccessRatio 且号码在 SMSOptionDRSuccessRatioPrefix 里，按比例把失败改成 DELIVERED
           ├ 客户已经收到过假 DR（FakeDr.given：方式 1、2、4 已经给了）──> 不再回 IN DR，只记录
           └ 否则回 IN DR（客户走 DR 查询的：写进查询表，同现在）
```

- 改道后新通道的结果和 DR 照常处理；客户已经收到假 DR 的消息改道后也不会再收到第二个 DR（`FakeDr.given` 跟着消息走）。

**现在代码里 DR 改道的准确条件**（`MessageStoreManager.handleOutDeliveryReportResForInnerAck`，Redis Stream 流程里供应商 DR 匹配到原 MT 后走这里；新设计保留，只是“改到哪”换成逐级备份）：

| 条件 | 说明 |
|---|---|
| 这次发送的通道 `NeedDRReroute=true` | 默认 `false` |
| DR 状态不是 DELIVERED | |
| 在 `RerouteDRDelayTimeInSec` 内 | 默认 1800 秒，从消息的 `TimeStamp` 算 |
| `SMSOptionDRRerouteCode` | **配了：只有状态码在列表里才改道**；没配：任何非 DELIVERED 的状态都改道（保留，已确认） |

- 比较的是**内部状态码**（如 `10400`、`10405`），是 Core 按 DR 错误码对照表（`DrErrorConfig.applyVendorDr`）细分之后的状态，所以 `SMSOptionDRRerouteCode` 要按细分后的码配；`SMSOptionDRNotPaidCode` 命中的 DR 已经变成 `REJECTED_BYNC`，按这个码判断。
- 不改道的 DR 类型：`ACCEPT`（中间状态）只写 CDR；`FAIL_SENDOUT_DELIVERYREPORT` 只写 CDR；`EXPIRED` 但原 MT 还没过期时进 WDQ 等到期，不改道。
- DR 查询客户（`InClientPull=2`）：原 MT 和通道在同一个 A2P（`OA2P==RA2P`，或 `OA2P==CurrentA2P`）时**不改道**，直接写查询表；不在同一个 A2P 时按上面的条件改道。新设计保持。
- 其他入口（`handleOutDeliveryReportRes`：MQM 重投的 DR、DB 兜底、旧的 TCP 路径等）里的 DR 改道代码是注释掉的，**这些入口不改道**。新设计保持，只在 Stream 流程的这个入口改道。
- 现有问题（这次不改，记下来）：时间窗口的计算里写死了减 8 小时（`TimeStamp` 是 GMT 换算后的时间，假设服务器在 UTC+8），服务器不在 UTC+8 时窗口会偏。
- 级别用完时，DR 的最后一次失败按“DR 不改道时”处理，不重试主路由（submit 才重试主路由）。

**只重试主路由**（submit，级别用完后）：

```text
主 V1 ✗ → 备份1 V4 ✗ → 备份2 V6 ✗ → 备份3 V8 ✗   （每次失败码都在各自通道的改道码里）
   └ 级别用完 → 重试策略：等第 1 个间隔 → 按主路由重新选（V1）发送
        V1 成功：结束
        V1 失败，码在改道码里：routingLevel 已经是最后一级，没有下一级 → 再等下一个间隔，重试主路由
        V1 失败，码不在改道码里：回失败 DR
   └ 重试次数用完 / 过期：回失败 DR
```

- 不加轮次字段（已确认）。靠 `routingLevel` 判断：重试主路由时 `routingLevel` 不清零，主路由再失败时下一级不存在，就直接进重试策略，不会再走一遍备份。和现在的效果一样（现在靠 `routingSsIDs` 里记着走过的备份通道做到）。
- 重试主路由时重新选路：主路由的权重、轮询会重新抽；系统路由替换按当时的替换表（运维可能已经换了通道）。
- 重试间隔按现在的重试策略查找方式（发送通道的策略，没有再按客户），不变。

**和现在的区别（上线前要注意）**：改道码沿用 `SMSOptionSubmitRetryCode`，不在里面的失败现在就是直接回失败 DR，这一点不变。变化只有一个：**现在不管什么失败都会先尝试改道**，新设计只有失败码在 `SMSOptionSubmitRetryCode` 里才改道。所以：

- 没配 `SMSOptionSubmitRetryCode` 的通道，以后失败了不会再改道到备份（现在会）。
- 迁移工具的报告列出“客户的路由里有备份规则、但主路由通道没配 `SMSOptionSubmitRetryCode`”的通道，上线前补配；想保持“几乎都改道”的，把常见的失败码都配上。

### 2.10 改道后的 CDR MsgID（和现在一致）

**现在的做法**（`CDRManager` 写 CDR 文件和写 Redis 监控 CDR 的三处，规则相同）：CDR 的 MsgID 列看消息的 `routingSsIDs`（走过的通道，格式 `,80,` / `,80,,81,` …）：

| 情况 | MsgID 列 |
|---|---|
| `routingSsIDs` 为空，或只有一个通道（没改过道） | `msgId` |
| 有两个以上通道（改过道） | `msgId-{routingSsIDs 里最后一个通道}`，例如 `A1B2C3-81` |
| `IN_DELI_REP`（收到供应商 DR） | 总是 `msgId` |

**一条消息改道时各条 CDR 的 MsgID**（主路由 V1=80，备份 V4=81）：

| CDR | 什么时候写 | `routingSsIDs` | MsgID 列 |
|---|---|---|---|
| `IN_SUBMIT` | Server 收到 | 空 | `msgId` |
| V1 的 `OUT_SUBMIT`（失败） | Core 处理 V1 的结果，**改道之前**复制一份消息写（`handleOutSubmitRes` 里的 `cdr`） | `,80,` | `msgId` |
| V4 的 `OUT_SUBMIT` | V4 的结果回来 | `,80,,81,` | `msgId-81` |
| 之后的 DR 类 CDR（`OUT_DELI_REP` 等） | DR 回来 | `,80,,81,` | `msgId-81` |

**新设计保持这个规则不变**：

- `routingSsIDs` 的格式、追加的方式不变（每进一级追加一个通道）；MsgID 列的规则不变。所以：主路由的 CDR 是 `msgId`；进了备份 1、2、3 后，每一条 CDR 都是 `msgId-{当前这一级的通道}`，例如 `msgId-81`、`msgId-82`、`msgId-83`；`IN_DELI_REP` 仍然是 `msgId`。
- 失败的那一次发送，CDR 仍然在改道**之前**写（用改道前的消息复制），所以每个通道自己的 `OUT_SUBMIT` 带的是它自己的后缀：主路由 `msgId`，备份 1 的 `msgId-81`，备份 2 的 `msgId-82`……
- 系统路由替换（2.8）：`routingSsIDs` 记替换后的实际通道，后缀也就是实际通道。现在改道时记的就是替换后的通道，这一点一致；主路由只有一个通道、没有后缀，替换前后都是 `msgId`，也一致。
- **级别用完后重试主路由（2.9）：CDR 用原来的 `msgId`**（已确认），和主路由第一次的 `OUT_SUBMIT` 一致，之后这次发送的 DR 类 CDR 也是 `msgId`。现在的代码在这种情况下会写成 `msgId-{最后一级备份的通道}`（主路由通道已经在 `routingSsIDs` 里，不再追加，最后一个仍是备份通道），要改。

  **改法**：MsgID 列从“看 `routingSsIDs` 的最后一个通道”改成“看这条 CDR 的通道（`rssid`）”：

  | 这条 CDR 的通道 | MsgID 列 |
  |---|---|
  | `routingSsIDs` 为空或只有一个通道 | `msgId`（同现在） |
  | 是 `routingSsIDs` 的**第一个**通道（主路由） | `msgId`（新：主路由的重试） |
  | 是后面的通道（备份） | `msgId-{这个通道}` |
  | 不在 `routingSsIDs` 里（不应出现） | 按现在的规则（最后一个通道） |
  | `IN_DELI_REP` | `msgId`（同现在） |

  正常改道时，这条 CDR 的通道就是 `routingSsIDs` 的最后一个，结果和现在完全一样；只有“回到主路由重试”这一种情况由 `msgId-83` 变成 `msgId`。`routingSsIDs` 本身不变（主路由通道不重复追加），所以主路由重试再失败时也不会被当成新的通道再进备份。

  例子（主 80、备份 81、82、83 都失败，之后重试主路由）：

  | CDR | MsgID 列 |
  |---|---|
  | 80 第一次 `OUT_SUBMIT` | `msgId` |
  | 81 / 82 / 83 的 `OUT_SUBMIT` | `msgId-81` / `msgId-82` / `msgId-83` |
  | 重试 80 的 `OUT_SUBMIT`（每次重试一条） | `msgId` |
  | 重试 80 成功后的 DR 类 CDR | `msgId` |
- 长短信：改道时现在会把 `splitStatus` 设成 0、按新通道重新拆分，CDR 的分段字段跟着新通道的拆分；不变。

### 2.11 `RoutingLevel` 的 DB 列

消息从 DB 重试（RMQ、SMQ 等）时要知道到了第几级，所以存消息的表加一列 `RoutingLevel`（`tinyint`，可空）。走过的通道已经存在 `RoutingSsIDs` 列里，不变。SQL：`docs/sql/2026-11-13_routing_level.sql`（表和 DR 错误码那次一样：`messagestore`、`PMQ` 和每天的 `PMQ_*`、`RMQ`、`SMQ`、`WDQ`、`QDQ`、`RDQ`、`SDQ`、`IQDQ`、`CSMQ`）。

- **新配置 `DB.RoutingLevelColumn`**（GmmsConfig，`auto|true|false`，默认 `auto`，热加载）：`auto` 时按 `DB.DrErrorCodeColumns` 的方式探测，所有表都有这一列才写；`RELOAD_ROUTING` 时重新探测。
- **没有这一列，或读到 NULL**（升级前写进 DB 的消息）：级别未知，改道时从第 1 级找起、跳过 `RoutingSsIDs` 里的通道（即现在的做法），不会重复发到同一个通道，只是可能多看几级。
- 上线顺序：先执行 SQL（加列不影响旧版本，旧版本不写这一列），再升级；或者先升级、后执行 SQL，执行后 `RELOAD_ROUTING`。

## 3. 和现在相比

| 方面 | 现在 | 新设计 |
|---|---|---|
| 层的顺序 | 二次 → 号码 → 运营商 → 国家（代码写死） | 不变，四层 |
| 层内顺序 | 发送方 → 关键字 → 前缀（写死），前缀取最长 | 号码 / 运营商 / 前缀分组，组内按 `Priority` |
| 条件组合 | 每种组合一个配置名 | 一条规则里组合 `Sender`、`KeywordId` |
| 规则命中但通道不可用 | 掉到下一类，或直接进备份 | 路由失败 |
| 备份级别 | `Backup`、`Backup1`…`Backup19`（实际只用前 10 级）；每次改道从第 1 级找起，跳过走过的通道 | `A2PBackupRouting`、`A2PBackup2Routing`…`A2PBackup10Routing`，逐级进，消息记住当前级别（`routingLevel`）；每一级里同样按前缀、优先级选 |
| 排除条件 | 没有，只能为被排除的发送方另写规则 | `ExcludeSender`、`ExcludeKeywordId`、`ExcludePhonePrefix` |
| 何时改道 | submit 几乎所有失败 | 只在通道配的 `SMSOptionSubmitRetryCode` 里的失败码 |
| 改道次数 | 直到备份用完 | 级数用完，或 `SMSOptionMaxReroute`（默认 10） |
| 系统路由替换 | 选路后替换；主路由记替换前的通道 | 选通道时替换，“走过了”和改道码都按替换后的实际通道（2.8） |
| 备份都失败后 | 重试回主路由，备份不会再试 | submit：同现在，按重试策略只重试主路由；DR：直接回失败 DR（2.9） |
| 改道看什么 | 不看失败码，几乎都改道 | 失败码在通道的 `SMSOptionSubmitRetryCode` 里才改道（沿用现有配置） |
| 失败码不在 `SMSOptionSubmitRetryCode` 里 | 先试改道，改不了就回失败 DR | 直接回失败 DR，不改道 |
| 改道后 CDR 的 MsgID | `msgId-最后一个通道` | 正常改道不变；级别用完后重试主路由用原来的 `msgId`（2.10） |
| 改道用哪套备份 | 只用国家备份 | 第 N 级：选出主路由通道那一层的第 N 级，再普通层的第 N 级 |

## 4. 去掉的配置和代码

按之前的约定：旧逻辑去掉，全部改成新配置。

- 路由文件里所有 `A2P*RoutingRelay*` 配置名（第 1.1 节表里全部，以及不生效的 `A2PServiceTypeIDRoutingRelay`、`A2PContentRoutingRelay`、`A2PSenderAddrRoutingRelay`、`A2PContentRouting`）。读到时打 WARN，不生效。
- 代码：`IOSMSChannelRouter`、`IOSMSBackupChannelRouter`、`SMSOPChannelRouter`、`SMSOPBackupChannelRouter`、`SMSNumberChannelRouter`、`A2PSecondChannelRouter` 合并成一个按层、按规则选路的 `RuleRouter`；`A2PCustomerManager` 里对应的十几张路由表和加载、匹配方法删掉，换成每层的索引。`IOSMSDispatcher.dispatch` 里写死的嵌套 if 改为按层循环。
- `IOSMSRerouteDispatcher.reroute` 的“除了几种状态都改道”改为按改道码判断。

## 5. 迁移

旧配置不再读取，升级前要把路由文件转换成新格式。提供一个转换工具（a2pctl 子命令，读旧的 routingInfo 文件，输出新的）。

| 旧配置 | 新配置 | 优先级 |
|---|---|---|
| `A2PNumberRoutingRelay` | `A2PNumberRouting` | 原来的 `Priority` |
| `A2POPSenderRoutingRelay` | `A2POPRouting`，带 `Sender` | 10 |
| `A2POPContentKeywordRoutingRelay` | `A2POPRouting`，带 `KeywordId` | 20 |
| `A2POPRoutingRelay` | `A2POPRouting` | 30 + 原来的 `Priority` 顺序 |
| `A2PSenderRoutingRelay` | `A2PMainRouting`，带 `Sender` | 10 |
| `A2PContentKeywordRoutingRelay` | `A2PMainRouting`，带 `KeywordId` | 20 |
| `A2PRoutingRelay` | `A2PMainRouting` | 30 |
| `A2PSec*` | `A2PSecRouting` / `A2PSecBackupRouting`，同普通层 | 同普通层 |
| 各种 `...Backup...`（无数字） | 对应层的备份 1 级（`A2PBackupRouting` 等） | 同上 |
| 各种 `...Backup1...`～`...Backup9...` | 对应层的备份 2～10 级（`A2PBackup2Routing`～`A2PBackup10Routing`） | 同上 |
| `...Backup10...`～`...Backup19...` | 不转换（现在就不生效），报告里列出 | |

**层之间的顺序和现在一样，不会变。普通层内部跨前缀时新旧结果可能不同**，因为现在是“先发送方、再关键字、再前缀，各自取最长前缀”，新设计是“先最长前缀、前缀内再按优先级”：

```text
旧：A2PSenderRoutingRelay: (PhonePrefix=7,Sender=BANK,Relay=V1)
    A2PRoutingRelay:       (PhonePrefix=77,Relay=V2)
发送方 BANK、号码 77...：现在走 V1；直接按新规则走 V2（77 更长）
```

工具会把这种情况转换成等价写法：把短前缀的发送方 / 关键字规则复制一份到更长的前缀下（例子里多一条 `(Priority=10,PhonePrefix=77,Sender=BANK,Relay=V1)`），保证转换后结果和现在一样，并在报告里列出每一条复制出来的规则，方便人工确认是否真的需要保留旧行为。

- 备份的推进方式变了：现在每次从第 1 级找起，权重 / 轮询的备份会在同一级里换到没走过的通道；新设计每级只用一次。报告里列出 Relay 有多个通道的备份规则，需要“同一级换通道”的，把通道拆到下一级。
- “规则命中但通道不可用”现在会掉到下一类或备份，新设计直接路由失败。工具的报告里列出指向不存在通道的规则、配了内容长度限制的通道，上线前确认。
- 转换后先用工具的“试算”模式：对一批真实号码、发送方分别用旧规则和新规则选路，列出结果不同的组合，确认后再上线。
- 改道行为变了（只按改道码），上线前要给各通道配好 `SMSOptionSubmitRetryCode`；想保持现在“几乎都改道”的，可以把常见失败码都配上。

## 9. 需要确认的问题

已确认：规则命中但通道不可用时直接路由失败（2.3）。2026-11-13 已确认 1～8：都按建议。2026-11-13 已确认 9～13：备份某一级通道不可用跳到下一级；最多 10 级；一级的通道失败直接进下一级；排除条件用 `ExcludeSender` 等单独属性；发送方不区分大小写。

1. ~~**同一分组、同一优先级多条规则**~~ 已确认：按建议。原文：建议加载时拒绝（2.5）。另一种做法：允许，再按“条件多的先、文件里靠前的先”排。
2. ~~**改道码配在哪**~~ 已确认：沿用通道上现有的 `SMSOptionSubmitRetryCode`，不新增配置（2.4、2.9）。原文：建议配在通道上（`SMSOptionSubmitRetryCode`），因为失败码是通道（供应商）给的。也可以配在规则上（`RerouteCode=...`），或者两处都能配、规则上的优先。
3. ~~**改道次数上限**~~ 已确认：按建议。原文：建议客户配置 `SMSOptionMaxReroute`，默认 10（等于最多的级数，相当于不额外限制）。也可以默认更小，例如 3。
4. ~~**选出的通道处于 ROP 失败模式**~~ 已确认：按建议。原文：现在是进 SMQ 等通道恢复。建议保持，避免通道短暂断开时把流量都切走；也可以和“通道不可用”一样算路由失败。
5. ~~**号码路由要不要备份**~~ 已确认：按建议。原文：现在没有号码备份。建议不加，号码层的通道失败时直接用普通层的备份；需要时再加 `A2PNumberBackupRouting`。
6. ~~**对应层的备份没有命中时要不要再看普通层备份**~~ 已确认：按建议。原文：建议看（2.4）。也可以只看本层的备份。
7. ~~**`routingRule` 写不写 CDR**~~ 已确认：按建议。原文：写进 CDR 会改 CDR 格式（下游解析受影响）；建议先只写日志和 Stream。
8. ~~**默认路由**~~ 已确认：按建议。原文：（`CCBSSID ≤ 0` 的块）：建议保留，四层都用同样的规则格式，在客户的四层之后看。
9. ~~**备份某一级的规则命中但通道不可用**~~ 已确认：跳到下一级。原文：（通道不存在、内容长度不允许）：建议跳到下一级（已经在失败处理中，目的是尽量送达）。也可以和主路由一样直接按这次失败处理。
10. ~~**备份最多几级**~~ 已确认：10 级。原文：建议 10 级（`A2PBackupRouting` + `A2PBackup2Routing`～`A2PBackup10Routing`），和现在实际生效的级数一样。
11. ~~**一级里 Relay 有多个通道时**~~ 已确认：一级的通道失败直接进下一级。原文：建议只发一个（每级只用一次，2.4）。另一种做法：同一级里没走过的通道都试完再进下一级（和现在的行为接近）。
12. ~~**排除条件的写法**~~ 已确认：`ExcludeSender` 等单独属性。原文：建议单独的属性（`ExcludeSender` 等）。另一种是在原属性里用 `!` 前缀（`Sender=!BANK`），更短但容易看漏，而且 `Sender=A;!B` 这种混写的含义不清楚。
13. ~~**发送方的比较**~~ 已确认：不区分大小写（通配先不支持）。原文：现在是完全相等、区分大小写。字母发送方要不要不区分大小写（`BANK` 和 `Bank` 算同一个）？要不要支持通配（`Sender=BANK*`）？建议先不区分大小写、不支持通配。
14. ~~**一轮全部失败后要不要开新一轮**~~ 已确认：不开新一轮；submit 级别用完后按重试策略只重试主路由，DR 直接回失败 DR（2.9）。
15. ~~**新一轮的重试间隔按谁的重试策略**~~ 已确认：不加轮次，重试策略的查找不变。
16. ~~**不改道的失败**~~ 已确认：失败码不在这个通道的改道码里，不进下一级、不重试，直接回失败 DR（2.9）。
17. ~~**级别用完后重试主路由的 CDR MsgID**~~ 已确认：用原来的 `msgId`，和主路由第一次的 `OUT_SUBMIT` 一致（2.10）。
18. ~~**通道没配 `SMSOptionSubmitRetryCode`**~~ 已确认：失败不改道、不重试，直接回失败 DR（2.9）。DR 失败同理：通道没开 `NeedDRReroute` 不改道，写 `OUT_DELI_REP` 后按假 DR 的配置决定是否回 IN DR。
