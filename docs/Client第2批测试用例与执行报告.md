# Client 第 2 批：测试用例与执行报告（HTTP 通道限速、按通道配置超时）

> 设计见《Client第2批优化设计》。同时对 Core 前 7 批、通道限速和 Client 第 1 批做了全量回归。

## 1. 测试环境

与之前的报告相同：本地 Redis 7.2.5，JDK 17，真实的初始化流程，没有数据库。新增测试套件 `ClientBatch2IT`。

测试通道（cm.cfg）：

| 通道 | 配置 | 用途 |
|---|---|---|
| HTTP14 | `ChlQueue: CommonHttpClient`、`ChlInit: true`、`ChlURL` 指向本机的测试 HTTP 服务（固定 4 秒后才响应）、`SMSOptionHttpReadTimeout: 1` | 超时测试 |
| HTTP15 | `SMSOptionOutgoingThrottlingNum: 2`，未初始化（没有 HTTP 会话） | 限速测试 |
| HTTP16 | 不限速，未初始化 | 对照 |

**为什么限速测试用没有会话的通道：** 本地没有 HTTP 供应商，也没有对应的协议模板。HTTP15 和 HTTP16 没有会话，每条消息被处理时恰好产生 1 条失败结果。按 msgId 统计这些结果，既能看出处理速率，也能看出每条消息是否只被处理了一次。限速发生在取会话之前，所以测的就是真实的限速和延后路径。

**超时测试** 直接调用会话真正发请求的方法 `HttpSession.doPost`，因为超时就是在这里设置的。完整的 `submit` 需要协议模板（如 `HTTP.xml`），本地没有。

**自动重投** 和 Client 第 1 批一样调得很激进：空闲 1.5 秒就领走，每 0.5 秒扫描一次。HTTP 外发的 worker 数设为 2。

## 2. 用例

### 2.1 按通道配置超时

| ID | 场景 | 预期 | 级别 |
|---|---|---|---|
| H-T0/T1 | HTTP14 配置了 `SMSOptionHttpReadTimeout: 1`，没有配置连接超时 | 读超时 1000 毫秒；连接超时使用模块的 30000 毫秒 | P0 |
| H-T2 | 供应商 4 秒后才响应 | 请求确实发到了供应商，约 1 秒后放弃（不再等模块的 60 秒） | P0 |
| H-T3 | 热加载 cm.cfg，把读超时改为 6 秒 | 同一个会话的下一个请求就使用 6000 毫秒，不需要重建会话 | P0 |
| H-T4 | 读超时 6 秒，供应商 4 秒响应 | 正常收到响应 | P1 |

### 2.2 HTTP 外发限速（真实运行 `HttpClientStreamConsumer`）

| ID | 场景 | 预期 | 级别 |
|---|---|---|---|
| H-R1 | 2 TPS 的 HTTP 通道积压 20 条 | 全部处理完；每条恰好处理 1 次（虽然排队时间远超 1.5 秒的自动重投阈值）；速率不超过限制 | P0 |
| H-R2 | 延后的消息被反复领回 | 不增加投递次数，没有消息进入死信队列 | P0 |
| H-R3 | 只有 2 个 worker，2 TPS 通道在积压，这时给不限速的 HTTP 通道发 20 条 | 不限速通道很快处理完，此时限速通道仍有积压 | P0 |
| H-R4 | 同上 | 没有任何线程在 `RateLimiter.acquire` 中等待 | P0 |
| 回归 | SMPP 外发改用公共的 `StreamDeferrals` | Client 第 1 批的 19 项全部通过 | P0 |

## 3. 不在本地范围的项

| ID | 项 | 建议做法 |
|---|---|---|
| X-C21 | 真实 HTTP 供应商的完整外发（使用协议模板） | 测试环境给一个 HTTP 通道配置 `SMSOptionOutgoingThrottlingNum` 和较短的 `SMSOptionHttpReadTimeout`，压测时确认供应商侧的速率不超过 TPS × Client 节点数；在供应商响应变慢时，确认超时按通道配置生效 |
| X-C22 | 连接超时 | 本地无法模拟"连不上"（本机端口会立即拒绝连接）。测试环境把 `ChlURL` 指向一个不响应的地址，确认按 `SMSOptionHttpConnectTimeout` 放弃 |

### 4.2 执行过程中的调整（都是测试代码的问题）

| 问题 | 原因 | 处理 |
|---|---|---|
| H-T2 第一版 2 毫秒就失败了 | 测试通道没有协议模板（`HTTP.xml`），`submit` 在发请求之前就返回了 | 改为直接调用真正发请求的 `doPost` |
| H-T4 第一版用了 6 秒才失败 | JDK 自带的测试 HTTP 服务默认只有一个线程，第二个请求排在第一个请求的 4 秒等待后面 | 给测试服务配置线程池 |
